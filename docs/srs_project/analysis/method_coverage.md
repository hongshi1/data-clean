## 1. 逐方法分析

### 1.1 Check 1: `check_same_value_consistency` — 同值一致性

**代码位置**: `srs_consistency_checker_v2.py:124-227`

#### 1.1.1 方法名称与输入输出

| 项目 | 内容 |
|------|------|
| 方法名 | `check_same_value_consistency` |
| 输入 | `constraints: list` — 约束列表, 每条含 `param`, `value`, `unit`, `section`, `original` |
| 输出 | `issues: list` — check_type=`same_param_diff_value`, severity=HIGH |
| 核心逻辑 | 按 param 分组 → 单位归一化 (时间→ms, 频率→MHz, 存储→MB) → 比较归一化值 → 排除兄弟章节同名参数 |

#### 1.1.2 能检测的矛盾类型

| 矛盾类型 | 说明 | 示例 |
|----------|------|------|
| 同参数不同值 | 同一参数名在不同章节出现, 归一化后数值不同 | "计算时间"在3.2.1为5ms, 在3.11为10ms |
| 单位不一致的同值 | 同参数同数值但单位不同, 归一化后值不同 | "超时=5s" vs "超时=5000ms" (理论上应一致但数值不同) |

#### 1.1.3 不能检测的矛盾类型

| 矛盾类型 | 原因 |
|----------|------|
| 同值不同义 | 25ms超时阈值 vs 25ms调度周期 — 值相同不报 (正确行为, 但依赖精确的参数名匹配) |
| 非数值参数矛盾 | 文本型参数 (如"单一状态" vs "多种状态") 无法提取数值 |
| 参数名变体 | "计算时间" vs "分析时间" vs "执行时间" — 精确字符串匹配, 无法识别同义参数名 |
| 跨文档值矛盾 | 仅在单文档约束列表内分组, 不跨文档 |
| 隐式数值关系 | 如 3×5s=15s > 10s — 值本身一致(各5s), 矛盾在于之和超限 (由Check 3覆盖) |

#### 1.1.4 评测指标 (TP/FP/FN)

| 指标 | 值 | 说明 |
|------|-----|------|
| TP | 0 | GT中无 same_param_diff_value 类型真矛盾 |
| FP | 0 | 未产生误报 |
| FN | 0 | 无遗漏 (GT中无此类型矛盾) |
| TN贡献 | 11 | 10个 same_param_same_value + 1个 same_value_diff_semantics 正确未报 |

> **评价**: 该方法在当前GT上无检出也无遗漏, 主要贡献是正确识别一致性 (TN)。假阳性已在v2中通过兄弟章节排除逻辑修复。

#### 1.1.5 主要难点

1. **参数名匹配**: 使用精确字符串匹配, 无法处理 "计算时间" vs "执行时间" 等同义变体
2. **兄弟章节排除**: 通过章节号父级分组排除 (3.2.2/3.2.3/3.2.4为不同模块), 但依赖章节号格式, 无章节号的约束无法排除
3. **单位归一化**: 仅覆盖时间/频率/存储三类, 电压(V)、电流(A)、温度(°C)等归入 `other` 维度只比较数值
4. **数值提取**: `re.findall(r"\d+(?:\.\d+)?")` 取第一个数字, 多值约束 (如"范围[0, 1]")可能提取错误

#### 1.1.6 改进方向

- 引入参数名语义相似度匹配 (embedding/同义词表)
- 扩展单位归一化维度 (电压/电流/温度/角度)
- 支持范围型约束的比较 (区间交集而非点值)
- 增加跨文档参数对比能力

### 1.2 Check 2: `check_text_table_consistency` — 文本-表格一致性

**代码位置**: `srs_consistency_checker_v2.py:232-408`

#### 1.2.1 方法名称与输入输出

| 项目 | 内容 |
|------|------|
| 方法名 | `check_text_table_consistency` |
| 输入 | `constraints: list` + `tables: list` (含 `table_type`, `rows`, `headers`, `requirements`, `mappings`) |
| 输出 | `issues: list` — check_type=`traceability_value_mismatch`(LOW) / `empty_table_placeholder`(HIGH) |
| 核心逻辑 | (1) 合格性表/追踪表占位符检测 (2) 追踪表数值与正文约束的匹配 (排除章节号) |

#### 1.2.2 能检测的矛盾类型

| 矛盾类型 | 说明 | 示例 |
|----------|------|------|
| 空表/占位符表 | 合格性规定表或追踪表全部为模板占位符, 未填写实际内容 | compiler GT-004: 合格性表全填"合规性方法" |
| 追踪表值不在正文中 | 追踪表中的数值 (带单位) 在正文约束中找不到对应 | 追踪表写"50ms"但正文无此约束 |

#### 1.2.3 不能检测的矛盾类型

| 矛盾类型 | 原因 |
|----------|------|
| OCR表格结构断裂 | 单元格被OCR拆分为多行, 表格行列结构破坏 → battery GT-007 (FN) |
| 表格内容语义矛盾 | 合格性方法填了"演示"但实际应为"测试" — 仅检测占位符, 不验证内容正确性 |
| 跨表值矛盾 | 同一参数在合格性表和追踪表中值不同 — 无跨表比较逻辑 |
| 正文-表格数值矛盾 | 正文写"5秒"但表格写"10秒" — 追踪表匹配仅检查值是否存在, 不检查矛盾 |
| 表格结构合规性 | 表格列数/行数不符合GJB模板要求 — 无结构验证 |

#### 1.2.4 评测指标 (TP/FP/FN)

| 指标 | 值 | 说明 |
|------|-----|------|
| TP | 2 | compiler GT-004 (合格性表占位符) + GT-005 (追踪表占位符) |
| FP | 0 | 无误报 |
| FN | 1 | battery GT-007 (OCR将"单元测试+对比验证"拆为两行, 表格结构断裂) |
| P / R / F1 | 1.0 / 0.667 / 0.80 | 精确率满分但召回率受OCR质量限制 |

#### 1.2.5 主要难点

1. **OCR质量依赖**: 表格经MinerU OCR后可能出现单元格拆分/合并/错行, 直接影响占位符检测和值提取
2. **章节号排除**: `re.match(r"^\d+\.\d+$")` 排除章节号, 但复杂章节号 (如"3.10.2") 或带文字的引用可能漏排
3. **占位符集合有限**: `PLACEHOLDER_CELLS` 是固定集合, 新模板的占位符文本可能遗漏
4. **追踪表值匹配**: 使用 `num_str in c_val` 子串匹配, 可能误匹配 (如"5" in "15") 或漏匹配 (格式差异)

#### 1.2.6 改进方向

- 增加OCR后处理: 表格单元格修复 (合并被拆分的行, 检测异常行数)
- 占位符检测改为语义判断 (LLM判断单元格是否为有效内容) 而非固定集合
- 增加正文-表格数值矛盾检测: 提取表格中的约束值, 与正文约束做同值比较
- 增加表格结构合规性检查 (列数/行数 vs GJB模板定义)

### 1.3 Check 3: `check_logic_consistency_z3` — 逻辑一致性 (Z3求解)

**代码位置**: `srs_consistency_checker_v2.py:486-689`

#### 1.3.1 方法名称与输入输出

| 项目 | 内容 |
|------|------|
| 方法名 | `check_logic_consistency_z3` |
| 输入 | `constraints: list` — 类型为 numerical/tolerance/cumulative/default/conditional 的约束, 最多25条 |
| 输出 | `issues: list` — check_type=`logic_unsatisfiable`(HIGH) / `logic_analysis`(INFO) |
| 核心逻辑 | LLM将约束转为Z3 Python代码 → `exec()`执行Z3 → 读取 `conflict_found` / `s.check()` 结果 |

#### 1.3.2 能检测的矛盾类型

| 矛盾类型 | 说明 | 示例 |
|----------|------|------|
| 串行时间之和超限 | 多阶段各有时间上限, 串行总和超过总时间约束 | compiler GT-003: 3×5s=15s > 10s总编译时间 |
| 显式数值约束不可满足 | 多个数值约束互相矛盾, Z3求解UNSAT | A≤5 且 A≥10 |
| 隐含关系违反 | 子模块时间之和 > 总执行时间 | 0.1+0.1+0.05=0.25ms ≤ 1ms (正确识别为可满足) |

#### 1.3.3 不能检测的矛盾类型

| 矛盾类型 | 原因 |
|----------|------|
| 非数值逻辑矛盾 | "单一状态" vs "三种状态" — 无数值, Z3无法表达 (由Check 4覆盖) |
| 跨文档逻辑冲突 | battery CPU 5% vs scheduler CPU 10% — 仅单文档约束输入 |
| 条件逻辑矛盾 | 复杂条件分支 (if A then B, if B then not A) — LLM可能无法正确转Z3 |
| 时序/调度约束 | 事件先后顺序、周期/截止时间关系 — Z3代码模板仅覆盖时间相加 |
| 大规模约束集 | >25条约束时截断, battery 57条相关约束导致Z3代码生成失败 |
| Z3代码生成失败 | LLM无法生成有效Z3代码 → 退化为INFO, 不产生检测结果 |

#### 1.3.4 评测指标 (TP/FP/FN)

| 指标 | 值 | 说明 |
|------|-----|------|
| TP | 1 | compiler GT-003 (3×5s=15s > 10s, Z3精确检出) |
| FP | 0 | 无误报 (Z3求解确定性, 不产生假阳性) |
| FN | 0 | 无遗漏 (GT中数值逻辑矛盾仅此1例) |
| 失败案例 | 1 | battery: "LLM分析57条约束, 但无法生成Z3代码" — 退化为INFO, 未造成FN (battery逻辑GT均为正值) |
| TN贡献 | 3 | scheduler GT-003 (5ms < 25ms), GT-004 (1.02ms ≤ 5ms), battery GT-004 (0.25ms ≤ 1ms) — Z3正确识别为可满足 |

> **评价**: Z3方法精确率最高 (P=1.0), 是唯一产生确定性检测结果的方法。但覆盖面窄, 依赖LLM生成正确的Z3代码。

#### 1.3.5 主要难点

1. **Z3代码生成可靠性**: LLM生成的Z3代码可能语法错误/逻辑错误/变量命名混乱 → battery案例完全失败
2. **约束数量限制**: 最多25条约束, battery有57条relevant约束被截断, 导致Z3代码生成失败
3. **`exec()` 安全风险**: 直接执行LLM生成的Python代码, 无沙箱隔离
4. **隐含关系识别**: 完全依赖LLM在prompt中识别"串行时间相加"等隐含关系, 无结构化保障
5. **单位统一**: LLM需在Z3代码中统一单位 (全转秒或毫秒), 可能出错
6. **Z3结果解读**: LLM生成的代码设置 `conflict_found` 变量, 但变量名/逻辑可能不一致, 需fallback到 `s.check()` 结果

#### 1.3.6 改进方向

- **分批Z3求解**: 将约束按参数/章节分组, 每组≤10条分别生成Z3代码, 合并结果
- **预构建Z3模板**: 为常见模式 (串行时间相加/子模块之和/执行时间<周期) 预置Z3模板, 减少LLM生成负担
- **约束类型自动分类**: 在提取阶段区分时间约束/资源约束/功能计数, 按类型分别验证
- **Z3代码验证层**: 执行前静态检查Z3代码 (变量定义/约束完整性), 失败则重试或降级
- **扩展隐含关系库**: 除时间相加外, 增加 CPU占用率=执行时间/周期、内存占用=各模块之和等关系模板

### 1.4 Check 4: `check_cross_section_consistency` — 跨章节语义矛盾 (LLM)

**代码位置**: `srs_consistency_checker_v2.py:413-481`

#### 1.4.1 方法名称与输入输出

| 项目 | 内容 |
|------|------|
| 方法名 | `check_cross_section_consistency` |
| 输入 | `doc_name: str` + `constraints: list` (最多80条) + `sections: list` (最多40个, 每个200字预览) |
| 输出 | `issues: list` — check_type=`cross_section_{declaration_contradiction/promise_implementation_mismatch/policy_contradiction/value_contradiction}` |
| 核心逻辑 | 构造章节摘要+约束摘要 → 单次LLM调用 → 解析JSON输出矛盾列表 |

#### 1.4.2 能检测的矛盾类型

| 矛盾类型 | 说明 | 检出示例 |
|----------|------|----------|
| 声明矛盾 | 某处声明X但另一处定义非X | compiler GT-001: "单一状态" vs 3.1.1/3.1.2/3.1.3三种状态 ✓TP |
| 承诺-实现不一致 | 概述承诺N项但详述仅M项 (M<N) | compiler GT-002: 概述6项功能 vs 3.2仅定义3项 ✓TP |
| 策略矛盾 | 某处允许X但另一处禁止X | scheduler GT-002: 3.4.1允许忙等待 vs 3.12禁止忙等待 ✓TP |
| 值矛盾 | 同一参数在不同章节有不同值 | (无TP, 2个FP) |

#### 1.4.3 不能检测的矛盾类型

| 矛盾类型 | 原因 |
|----------|------|
| 跨文档矛盾 | 仅输入单文档的章节和约束 |
| 数值逻辑矛盾 | LLM不擅长精确数值推理 (由Check 3 Z3覆盖) |
| 章节窗口外矛盾 | 仅检查前40个章节, 长文档尾部遗漏 |
| 约束窗口外矛盾 | 仅检查前80条约束, 约束密集文档遗漏 |
| 细粒度语义矛盾 | 需要领域知识的矛盾 (如接口参数类型不匹配) — LLM可能误判 |

#### 1.4.4 评测指标 (TP/FP/FN)

| 指标 | 值 | 说明 |
|------|-----|------|
| TP | 3 | compiler GT-001 (声明矛盾) + GT-002 (承诺-实现) + scheduler GT-002 (策略矛盾) |
| FP | 7 | **全部FP来自此方法** — battery 3个 + compiler 2个 + scheduler 2个 |
| FN | 0 | 单文档范围内的矛盾无遗漏 |
| P / R / F1 | 0.30 / 1.0 / 0.46 | **精确率极低 (0.30), 是系统最大短板** |

**7个假阳性详细分析:**

| 文档 | FP类型 | LLM判断的"矛盾" | 为何是FP |
|------|--------|-----------------|----------|
| battery | declaration_contradiction | battery_step接口参数: 3.4.2两个参数 vs 3.3.1一个参数 | 设计文档不同层级的描述详略不同, 非矛盾 |
| battery | policy_contradiction | "固定步长25ms" vs "dt参数可配置" | 接口提供参数不代表步长可变, 是防御性设计 |
| battery | declaration_contradiction | 3.2.5输入仅I_out vs 3.4.2需I_out+dt | 功能描述省略实现细节参数, 非矛盾 |
| compiler | policy_contradiction | "无特殊约束" vs "必须用C/C++" | "无特殊约束"指无额外限制, C/C++是常规约束 |
| compiler | value_contradiction | 最低内存512MB vs 占用500MB | 最低配置≠实际占用, 500<512合理 |
| scheduler | value_contradiction | CPU 20% (5ms/25ms) vs 10%上限 | 5ms是上限非均值, 实际CPU占用可远低于20% |
| scheduler | value_contradiction | 输出格式3.2.4含SOC vs 3.2.5不含SOC | 降采样输出可省略部分字段, 非矛盾 |

> **FP根因**: LLM倾向于将"描述详略不同""设计余量""防御性参数"等合理设计差异误判为矛盾, 缺乏对工程语境的理解。

#### 1.4.5 主要难点

1. **假阳性率极高 (70%)**: 7/10检出为误报, 是系统Precision的最大拖累
2. **LLM幻觉矛盾**: 将合理的设计差异 (参数省略/防御性接口/描述粒度差异) 误判为矛盾
3. **上下文窗口限制**: 40章节×200字 + 80约束, 大文档覆盖不全
4. **无grounding验证**: LLM输出直接采信, 不回溯原文验证矛盾是否成立
5. **单次调用**: 一次LLM调用检测所有矛盾类型, 无分阶段/分类型检测
6. **LLM一致性**: 同一文档多次运行可能产生不同结果 (temperature=0.1仍有波动)

#### 1.4.6 改进方向

- **两阶段LLM**: 第一阶段检测候选矛盾 → 第二阶段对每个候选矛盾回溯原文验证 (grounding)
- **分类型检测**: 声明矛盾/承诺-实现/策略矛盾分别用不同prompt, 提高针对性
- **FP过滤规则**: 增加"描述详略差异""防御性参数""设计余量"等非矛盾模式的识别规则
- **滑动窗口**: 对长文档按章节分批检测, 合并结果, 避免截断遗漏
- **置信度校准**: 当前固定confidence=0.8, 应根据LLM输出确定性动态调整
- **增加"非矛盾"示例**: 在prompt中加入FP示例 (如"接口参数数量不同≠矛盾"), 引导LLM更保守

### 2.2 各方法覆盖的矛盾类型矩阵

| 矛盾类型 | Check 1 | Check 2 | Check 3 | Check 4 | GT中有? | 覆盖状态 |
|----------|---------|---------|---------|---------|---------|----------|
| 同参数不同值 | ✓ | | | | 无 | 覆盖 (无GT验证) |

| 空表/占位符表 | | ✓ | | | compiler GT-004/005 | ✓覆盖 |
| OCR表格断裂 | | ✗ | | | battery GT-007 | ✗ **未覆盖 (FN)** |

## 3. 综合分析

### 3.1 当前完全没有方法覆盖的矛盾类型

#### 3.1.1 跨文档矛盾 (cross_document_conflict) — **有GT, 产生FN**

- **GT示例**: battery GT-008 — battery_srs声明电池模型CPU≤5%, scheduler_srs声明CPU≤10%(含电池模型), 两文档对同一组件测量基准不一致
- **现状**: 所有4个方法均以单文档为输入, 无任何跨文档比较逻辑
- **影响**: 这是2个FN之一, 直接影响Recall
- **难度**: 需要建立文档间的实体对齐 (哪些约束描述同一组件/参数), 且数值兼容性≠语义一致 (5%<10%数值兼容但基准不同)

#### 3.2.2 OCR结构损伤 (OCR-induced structural issue) — **有GT, 产生FN**

- **GT示例**: battery GT-007 — 合格性表"单元测试+对比验证"被OCR拆为两行, 表格结构断裂
- **现状**: Check 2依赖表格解析结果, 无OCR后处理/表格修复能力
- **影响**: 这是2个FN之一
- **难度**: OCR表格修复是独立研究问题, 需要基于表格结构先验重建行列关系

#### 3.1.3 文本-图片矛盾 (text_image_conflict) — **无GT, 但工具已存在**

- **现状**: `srs_image_text_matcher.py` 已实现图片引用提取+VLM描述, 但**未集成到一致性检测器**中
- **潜在矛盾**: 图片中的数值/流程与正文描述不一致, 图片caption与引用上下文不匹配
- **影响**: 当前检测器完全不处理图片信息

#### 3.1.4 时序/调度约束矛盾 (temporal_constraint_conflict) — **无GT**

- **现状**: Check 3的Z3模板仅覆盖"串行时间相加", 不覆盖事件先后顺序、周期/截止时间、优先级调度等时序约束
- **潜在矛盾**: "A必须在B之前完成" vs "B依赖A的输出" (循环依赖); "周期10ms" vs "截止时间5ms" (不合理)

#### 3.1.5 语法/格式合规矛盾 (syntax_compliance_conflict) — **无GT, 整层空白**

- **现状**: 语法层 TP=0/FP=0/FN=0/TN=0, 完全空白
- **应有检测**: GJB 438C规定的必须章节是否齐全, 章节编号是否连续, 表格列数是否符合模板, 术语是否一致
- **工具存在但未集成**: `srs_gjb_compliance_scan.py` 已实现GJB规则扫描, 但未接入检测器

### 3.2 最需要新增的方法 (按优先级排序)

#### 优先级 1: 跨文档一致性检测器 (`check_cross_document_consistency`)

| 维度 | 说明 |
|------|------|
| **理由** | 唯一有GT验证的完全未覆盖类型 (battery GT-008 FN), 直接影响Recall |
| **输入** | 多文档的约束集合 + 文档间实体对齐关系 |
| **输出** | cross_document_conflict (HIGH/MEDIUM) |
| **核心逻辑** | (1) 提取各文档中的共享实体 (组件名/参数名/接口名) (2) 对齐跨文档约束 (3) 比较数值兼容性+语义基准一致性 |
| **难点** | 实体对齐 (不同文档对同一组件的命名可能不同), 数值兼容≠语义一致 |
| **预期收益** | 消除1个FN, Recall从0.75提升至0.875 |

#### 优先级 2: 跨章节LLM假阳性抑制 (Check 4改进)

| 维度 | 说明 |
|------|------|
| **理由** | 7个FP全部来自Check 4, 占总FP的100%, 是Precision=0.46的主因 |
| **方案** | 两阶段LLM: 检测→验证 (grounding), 或增加FP过滤规则 |
| **预期收益** | 若FP从7降至2, Precision从0.46提升至0.75, F1从0.57提升至0.81 |

#### 优先级 3: 语法层检测器集成 (`check_syntax_compliance`)

| 维度 | 说明 |
|------|------|
| **理由** | 语法层完全空白, `srs_gjb_compliance_scan.py` 已实现但未接入 |
| **方案** | 集成GJB规则扫描结果, 检测缺失章节/表格/编号不连续等格式问题 |
| **预期收益** | 补全三层架构的语法层, 扩大矛盾类型覆盖 |

#### 优先级 4: 图片-文本一致性检测集成

| 维度 | 说明 |
|------|------|
| **理由** | `srs_image_text_matcher.py` 已实现但未接入检测器, 图片信息完全未利用 |
| **方案** | 将图片匹配结果接入一致性检测流程, 检测图片caption与引用上下文的矛盾 |

#### 优先级 5: OCR表格修复

| 维度 | 说明 |
|------|------|
| **理由** | battery GT-007 FN, OCR质量是表格检测的前置依赖 |
| **方案** | 表格后处理: 检测异常行数/单元格拆分, 基于表格结构先验修复 |

### 3.3 现有方法组合后的覆盖盲区

#### 盲区 1: 文档间信息孤岛

```
battery_srs ──┐
              ├── 无跨文档比较 → GT-008 FN
scheduler_srs ┘
```

4个方法均以单文档为边界, 无法检测文档集合内跨文档的约束矛盾。电池模型(battery)和调度器(scheduler)描述同一系统的不同组件, CPU占用率/执行时间等约束存在隐式关联, 当前无任何方法处理。

#### 盲区 2: 大约束集的Z3失效

```
battery_srs (102 constraints, 57 relevant)
    └── Check 3 截断至25条 → LLM无法生成Z3代码 → 退化为INFO
        └── 逻辑层对battery_srs完全失效 (仅靠Check 4 LLM兜底)
```

battery_srs有102条约束, 其中57条为数值/条件型, 远超25条限制。Z3方法对battery完全失效, 仅靠Check 4的LLM检测逻辑矛盾 (而Check 4在battery上产生3个FP, 0个TP)。

#### 盲区 3: Check 4高假阳性无过滤

```
Check 4 LLM输出 → 直接采信 (无grounding验证)
    └── 7个FP: "描述详略不同""防御性参数""设计余量" 被误判为矛盾
        └── Precision = 0.30
```

Check 4是唯一的"软"检测方法 (LLM判断), 输出无任何验证层, 假阳性率70%。所有FP的共同特征是LLM缺乏工程语境理解, 将合理的设计差异误判为矛盾。

#### 盲区 4: 图片/图表信息未利用

```
MinerU解析 → Markdown文本 + 图片文件
    └── 检测器仅处理文本和表格
        └── 图片中的数值/流程/结构信息完全未参与一致性检测
```

MinerU已提取图片, `srs_image_text_matcher.py`已实现图片-caption匹配, 但检测器不读取图片匹配结果, 不检测图片内容与正文描述的一致性。

#### 盲区 5: 语法层空壳

```
三层架构: 语法 → 语义 → 逻辑
           ↑
         完全空白 (0/0/0/0)
```

`srs_gjb_compliance_scan.py`和`knowledge/gjb_438c_rules.json`已存在, 但检测器不调用语法层检查。GJB 438C规定的必须章节/表格/编号规则均未检测。

#### 盲区 6: 非数值语义矛盾的检测精度低

```
声明矛盾 / 策略矛盾 / 承诺-实现不一致
    └── 仅Check 4 (LLM) 可检测
        └── 无结构化/规则化方法, 完全依赖LLM判断
            └── 假阳性高, 且无法对LLM输出做形式化验证
```

非数值的语义矛盾 (如"单一状态"vs"三种状态") 只能靠LLM检测, 无Z3等确定性方法辅助。LLM的不确定性导致这类矛盾的检测精度不可控。
