## 一、核心结论（先说结果）

### 1.1 三个确凿的学术空白

| 空白 | 证据 | 强度 |
|------|------|------|
| **文档级需求理解不存在** | arXiv全库检索"document-level requirement"返回0条；Zhao 2020(404篇)和Zadenoori 2025(74篇)两个权威综述的task taxonomy中均无文档级任务 | **铁证** |
| **SRS文档内条目聚合无人做** | 5个直接竞品全部停在句对级；DeepSpecs(5G标准)做跨引用但做QA不做聚合；AORE识别"散落"但用词法方法；通用NLP的document-level coreference从未迁移到RE | **铁证** |
| **中文/军事/GJB SRS零覆盖** | arXiv检索"GJB"返回0条；"Chinese requirement NLP"返回0条有效结果；"military software requirement"返回0条NLP相关工作 | **铁证** |

### 1.2 我们的竞品只有1个

在2025-2026年最新工作中，**唯一做"需求冲突检测"的是TSRCDF-SS**(arXiv:2511.23007)，它的局限：
- **句对级**：输入两条需求句，输出冲突/不冲突——不解决"同一参数散布在3.2.1节正文+接口图+合格性表+追溯表"的聚合问题
- **纯文本**：不处理表格、图片
- **无形式化**：不做Z3/SAT逻辑层检测
- **合成数据**：未在真实SRS文档上验证

### 1.3 LLM在领域需求上表现崩溃

S3CDA(arXiv:2206.13690)在5个数据集上对比GPT-4o与NLP方法：

| 数据集 | 领域 | GPT-4o F1 | NLP方法F1 | 差距 |
|--------|------|-----------|-----------|------|
| WorldVista | 医疗(通用英文) | **0.936** | 0.871 | +0.065 (LLM赢) |
| OpenCoss | 交通(铁路) | **0.670** | 0.570 | +0.100 (LLM赢) |
| IBM-UAV | 硬件(专有) | 0.634 | **0.711** | -0.077 |
| PURE | 热力学 | 0.594 | **0.896** | **-0.302** |
| UAV | 航空航天(EARS模板) | 0.462 | **0.923** | **-0.461** |

**GPT-4o从通用领域0.936暴跌到领域专用0.462**——退化幅度0.474。

暴跌原因分析：
1. **EARS模板的高词面相似性**：冲突与非冲突需求词面几乎相同（"shall support" vs "shall support up to three"），零样本LLM无法区分
2. **Metric冲突需要定量推理**：数值矛盾(50% vs 100%充电目标)需要精确数值推理，LLM在此类"语义近但数值矛盾"上表现差
3. **领域术语缺失**：UAV含InternalSimulator、VehicleCore等专有术语，LLM训练语料稀疏
4. **数据集偏斜放大**：小样本+类别偏斜下零样本LLM决策边界不稳定

**对GJB的启示**：GJB军事SRS比UAV更极端领域化（军事术语、GJB 438C格式约束、武器装备参数），纯LLM的F1预期落在**0.40-0.55区间**。必须走混合路线。

**LLM失败案例完整图谱**（6个独立研究从不同角度证明LLM在矛盾检测上不可靠）：

| 论文 | 失败模式 | 数据 | 领域 |
|------|----------|------|------|
| **S3CDA**(2206.13690) | 领域专有需求F1暴跌 | 0.936→0.462 | 航空需求 |
| **ContraDoc**(2311.09182) | 长文档自矛盾"不可靠" | GPT-4 + 人工标注者也漏检大量矛盾 | 通用文档 |
| **LegalWiz**(2510.03418) | 法律矛盾"接近随机" | GPT-4/LLaMA仅略好于随机；人工仅检测43% | 法律合同 |
| **Statutory**(2511.11954) | 法规不一致"仅33%" | GPT-4o三种策略仅一种成功 | 法律法规 |
| **ECon**(2410.04068) | "无理由偏向一方" | LLM在证据冲突中偏向有先验信念的一方 | 证据冲突 |
| **Korn 2026**(2606.25550) | 合成smell数据不可靠 | LLM无法可靠生成/注入/检测smell | 需求smell |

**NLI粒度演进时间线**——RE领域的"4年滞后"：

```
NLP领域                              RE领域
─────────────────────────────────────────────────────
2015  SNLI数据集(句对)
2018  BERT(句对分类设计)

2021  DocNLI: "句对级限制了NLI应用" [转折点]

```

NLP界在2021年(DocNLI/SummaC)就已诊断并开始解决粒度问题，但**RE领域晚了4年**。这个"4年滞后"是强有力的论证：RE领域继承了NLI框架但没跟上NLI的粒度演进。

## 二、NLP4RE → LLM4RE的范式转移

### 2.1 两个权威综述定义的任务版图

**Zhao et al. 2020**（arXiv:2004.01099，REJ，404篇primary studies）是NLP4RE最权威的systematic mapping study。核心结论：

> "most studies have focused on the **analysis phase**, with **detection** as their central linguistic analysis task and **requirements specification** as their commonly processed document type"

即NLP4RE的主流范式 = **对SRS做检测任务，粒度=句子/条目级**。

**Zadenoori et al. 2025**（arXiv:2509.11446，74篇primary studies）是LLM4RE首个系统性SLR。核心发现：

| 维度 | NLP4RE (404篇, 1983-2019) | LLM4RE (74篇, 2023-2024) | 信号 |
|------|---------------------------|---------------------------|------|
| 主流任务 | **缺陷检测#1**、分类#2 | 需求获取#1、验证#2、**缺陷检测跌至#8(仅5%)** | **检测被忽视了** |
| 粒度 | 句子/条目级 | 句子/条目级（**仍无文档级**） | **文档级仍是空白** |
| 输入 | SRS(60%) | SRS(38%)，多元化 | — |
| 输出 | 标签/分类 | **生成性输出**(SRS/报告/模型) | LLM能力转向生成 |
| RAG | — | 仅6% | **检索增强严重不足** |
| 公开数据集 | — | 仅16% | **可复现性是领域问题** |
| 模型 | — | 90%依赖GPT闭源API | 军事领域无法使用 |

**范式转移的核心信号**：LLM4RE的研究者转向了生成型任务（获取/验证/建模），**一致性检测在LLM时代被忽视了**——这是我们的蓝海。SLR明确列出"underexplored tasks"：术语提取、关系抽取、变更影响分析——**这三个正是方向A的任务**。

### 2.2 "文档级需求理解"在学术界不存在

对arXiv全库精确检索 `"document-level requirement"` 返回 **0条结果**。这意味着：

- "document-level requirement understanding"作为一个**被命名的、有明确任务定义的研究对象**，在学术界**并不存在**
- 对比：通用NLP中 `document-level coreference`(40条)、`document-level relation extraction`、`document-level event extraction`都是成熟任务（有专属数据集DocRED、WikiEvents、RAMS）
- Zhao综述的task taxonomy中**没有任何一个category是"文档级聚合"或"跨章节实体链接"**

**这是结构性盲区，也是方向A的研究机会。**

### 2.3 NLP4RE的8个子任务

| 子任务 | 定义 | 粒度 | LLM化程度 | 代表工作 |
|--------|------|------|-----------|----------|
| 需求抽取 | 从文本识别需求条目 | 句子级 | 中 | ReXCL, Tregex/Semgrex |
| 需求分类 | FR/NFR分类 | 句子级 | 高 | BERT, LLM few-shot |
| 实体关系识别 | 抽取领域模型要素 | 句子级 | 低 | 依存解析+Semgrex |
| 质量检测(smell) | 检测需求缺陷 | 句子级 | 中 | Smella, DL分类器 |
| 需求问答 | 基于SRS回答问题 | 文档级(RAG) | 高 | LLM+RAG |
| 追溯链接(TLR) | 需求↔代码/测试链接 | **跨制品** | 高 | SimCSE, TraceLLM |
| 形式化转换 | NL→形式规约 | 句子级 | **低** | LLM辅助 |
| 一致性检测 | 检测需求矛盾 | 条目级 | **低** | NLI, SAT, LLM |

**关键观察**：8个子任务中，6个是句子/条目级，1个是跨制品级(TLR)，1个是文档级(QA但用RAG)。**"文档内跨章节实体聚合"完全缺失**。

**核心结论**：11个竞品中**无一做"文档级多模态条目聚合+三层一致性"**。

### 3.2 关键竞品分析

**TSRCDF-SS(arXiv:2511.23007) — 唯一直接竞品**
- 方法：SBERT+SimCSE双编码器→六元拼接→FFNN分类
- 结果：in-domain macro-F1 +10.4%，cross-domain +11.4%
- 局限：句对级、纯文本、无形式化、合成数据
- 我们的区别：文档级条目(非句对) + 多模态(非纯文本) + 三层(非仅语义) + 真实GJB(非合成)

**DeepSpecs(arXiv:2511.01305) — 方向A最近参照**
- 方法：SpecDB(clause-aligned) + 跨引用递归解析 + RAG
- 消融：跨引用解析使F1从0.10→0.28(2.75x)，Recall从23%→71%
- 5G vs SRS差异：5G是显式引用(正则可提)，SRS是隐式关联(需推断)
- 我们的区别：隐式关联推断(非正则) + 多模态聚合(非纯文本) + 一致性检测(非QA)

**ContractCheck(arXiv:2504.18422) — 逻辑层方法直接可迁移**
- 方法：本体→blocks→FOL→SMT求解
- 我们的区别：GJB规则库(非合同本体) + 多层(非仅逻辑) + LLM辅助(非纯形式化)

**ContractNLI(arXiv:2110.01799) — 语义层方法直接可迁移**
- 方法：文档级NLI + 证据span，607份合同
- 我们的区别：SRS条目对(非合同条款) + 领域NER(非法律实体) + Z3逻辑层(非仅NLI)

**S3CDA(arXiv:2206.13690) — NLI方法基线**
- 方法：Phase I(余弦相似度筛选) + Phase II(S-NER实体重叠验证)
- 结果：领域数据集F1=0.71-0.92，GPT-4o在UAV上仅0.462
- 局限：句对级、合成冲突、实体重叠太浅、无文档结构

## 四、方向A（上下文关联）的学术定位

### 4.1 这是一个新子任务

方向A的本质是**intra-document requirement context aggregation**（文档内需求上下文聚合）。

- **不是TLR**：TLR是跨制品(req↔code/test)，方向A是文档内(同实体多位置)
- **不是requirement smell检测**：后者假设条目独立
- **不是DeepSpecs的跨引用解析**：5G规范是显式引用(正则可提)，SRS是隐式关联(需推断)
- **最接近**：通用NLP的文档级共指 + DeepSpecs的跨引用解析 + 文档AI的证据聚合

### 4.2 最接近的工作：DeepSpecs详细分析

DeepSpecs（arXiv:2511.01305）是5G规范领域的QA系统，其跨引用递归解析是方向A最重要的参照。

**方法论（四步）**：
1. **SpecDB构建**：clause-aligned切块（按原子条款，带spec_id/clause_id/版本号metadata）
2. **初始检索**：HyDE生成假设文档→稠密检索top-k
3. **跨引用提取**：正则提取"See clause X.Y.Z of TS A.B.C"
4. **递归解析**：metadata lookup精确定位被引条款，递归展开引用链→re-rank裁剪

**消融实验**：跨引用解析使F1从0.10提升到0.28（2.75x），Recall从23%提升到71%。

**5G规范 vs GJB SRS结构对比**：

| 维度 | 3GPP 5G规范 | GJB 438C SRS | 迁移难度 |
|------|-------------|--------------|----------|
| 章节编号 | spec_id(TS X.Y.Z)+clause_id(数字层级) | 章节号(3.2.1)+需求ID(ZZSJHQZHFW-GN-...) | 中 |
| 跨引用方式 | **显式**("See clause X") | **隐式**(位置邻接/序号对应/ID传播) | 高 |
| 引用提取 | 正则即可 | 需推断(序号对齐+ID传播+语义) | 高 |
| 展开方式 | 链式递归 | **扇形汇聚**(多模态聚合) | 中 |
| 多模态 | 纯文本+表格 | **文字+图+表格** | 高 |
| 版本演化 | 核心特性(多release) | 无(终稿) | 裁剪 |
| 文档规模 | 单release数千页,2137份 | 单份SRS数十页,16份 | — |

**迁移方案**：把DeepSpecs的"正则提引用"替换为"**多信号融合的隐式关联推断**"（序号对齐+ID传播+语义相似+位置邻接），这是方向A的原创贡献。

### 4.3 方向A的空白确认

| 问题 | 学术界现状 | 空白程度 |
|------|------------|----------|
| "文档级需求理解"作为被命名任务 | arXiv全库0条 | **完全空白** |
| SRS内跨引用自动解析 | 无专门工作(DeepSpecs在5G标准上最近) | **高，可迁移** |
| 文档内需求实体聚合 | 无端到端工作(AORE最接近但用词法方法) | **完全空白** |
| SRS多模态coreference(文+图+表) | 无工作 | **完全空白** |
| 利用GJB章节结构的自动化检测 | 国际学术界零覆盖 | **完全空白** |
| 表格行↔正文段落的行级关联 | VRDU多做page/block级,RE做req↔code trace | **完全空白** |

## 五、方向B（一致性检测）的学术定位

### 5.1 三层一致性的方法选择

| 层次 | 检测内容 | 推荐方法 | 理由 | 可迁移工作 |
|------|----------|----------|------|------------|
| **语法层** | 章节完整性/编号连续/ID格式/ghost引用 | 规则/启发式 | GJB 120条规则可直接编码，精确可解释 | FSARC, Smella, NALABS |
| **语义层** | 同参数不同值/正文与表格矛盾/版本冲突 | NLI+领域NER+LLM辅助 | S3CDA证明NLI在领域需求上优于纯LLM(F1: 0.92 vs 0.46) | **ContractNLI**(文档级NLI+证据span) |
| **逻辑层** | 约束可满足性(子模块时间之和≤总预算) | Z3/SAT形式化 | 严格正确，LLM无法替代数值推理 | **ContractCheck**(本体+FOL+SMT), **VeriTrans**(LLM+CNF) |

### 5.2 五类方法对比

| 方法类型 | 优点 | 缺点 | 代表工作 | 适用层次 |
|----------|------|------|----------|----------|
| 规则/启发式 | 可解释、精确 | 迁移差、覆盖低 | FSARC, Smella, NALABS | 语法层 |
| NLI/语义相似度 | 需标注数据、领域专有需求上优于LLM | 实体重叠太浅 | **S3CDA**(F1=0.92) | 语义层 |
| SAT/SMT形式化 | 严格正确 | 需人工形式化 | Bendík 2017, rt-Inconsistency, **ContractCheck** | 逻辑层 |
| LLM-based | 通用文本强 | **领域专有需求暴跌**、幻觉、隐私 | GPT-4法规合规 | 语义层 |
| **混合(LLM+NLP/形式化)** | 2025新兴趋势、幻觉减少59% | 仍在探索 | **FormalJudge, VeriTrans, SAFER, Model-Driven** | 全层 |

### 5.3 混合方法的前沿实例

| 工作 | 混合类型 | 关键机制 | 效果 |
|------|----------|----------|------|
| Model-Driven(2607.26220) | LLM+符号验证 | LLM提议→确定性符号校验→错误回溯 | 94.6%消除结构不一致 |
| LLM+ASP(2607.19365) | LLM+Answer Set Programming | LLM生成候选→ASP推理验证 | 等价baseline但更少LLM调用 |
| LLM+Dafny(2604.22601) | LLM+形式化验证 | NL→Verified Code，迭代反馈 | 0%→81.82% |
| LLM+Lean(2607.09072) | LLM+定理证明 | Property Templates+Lean 4 | 成功率提升2.6x，**幻觉减少59%** |
| SAFER(2601.06335) | GenAI+MBSE | LLM生成→形式化模型验证矛盾 | 安全关键系统矛盾检测 |
| ContractCheck(2504.18422) | 本体+blocks+FOL+SMT | 合同条款→形式化→SMT求解 | 合同矛盾检测 |
| VeriTrans(2604.10341) | LLM翻译+CNF编译+往返校验 | NL→PL→CNF→SAT | SAT正确率94.46% |

**趋势**：Neuro-symbolic成为2025-2026主流，形式化验证器作为LLM的"护栏"。

### 5.4 方向B的独特性

方向B与现有工作的差异：
1. **文档级而非句对级**：现有竞品全部停在句对级(TSRCDF-SS/LEREDD/S3CDA)
2. **三层联合检测**：现有方法多只做单层(语法或语义)
3. **依赖方向A产出**：先聚合条目再检测——"聚合前置"有理论支撑
4. **对自然语言SRS做逻辑层检测**：现有形式化方法只处理已形式化的输入

### 5.4 "合理差异vs真实矛盾"的文献定位

**学术界现状：未被显式讨论**。检索"requirement conflict false positive"、"legitimate variation"等关键词，没有找到任何论文显式讨论这个问题。

**最接近的三个线索**：

| 线索 | 来源 | 关系 |
|------|------|------|
| LegalWiz的"Specificity"矛盾类型 | arXiv:2510.03418 | "更宽泛vs更窄"（如"全球适用" vs "仅APAC"）——这是合理差异vs矛盾的边界案例，但被归为矛盾 |
| ECon的"无理由偏向" | arXiv:2410.04068 | LLM无法区分合理差异和矛盾，"favor one piece without justification" |
| 我们的真实数据 | doc10名录节点≥3000/≤3000 | 系统能力下限(≥3000) vs 单次导入上限(≤3000)——形式矛盾但语义合理 |

**这是研究机会**：首次形式化"合理差异vs真实矛盾"区分准则本身就是一个贡献。

区分准则草案：
- **合理差异**：不同设备形态的配置梯度（存储≥128/256/500/512GB对应台式/便携/手持）
- **合理差异**：不同操作场景的差异化要求（系统能力下限 vs 单次操作上限）
- **真实矛盾**：同参数同条件不同值（网络适配器≥4个 vs ≥40个，同一硬件规格）
- **真实矛盾**：同软件不同版本（达梦V7.6 vs V8，同一PZXQ项目内）

### 5.5 A→B流水线的理论支撑

TraceXplainer（arXiv:2412.04704）的信息论分析证明：**无监督TLR在文档质量差时有内在上限**。同理，不做聚合直接做检测会因"证据分散"而漏检。方向A提升文档内部一致性可见度，方向B在此基础上检测——这个"聚合前置"的论证既有工程必要性也有理论依据。

## 六、需求关系类型与矛盾分类法

### 6.1 需求关系类型（Carlshamre 6类 + 扩展）

| 关系类型 | 定义 | 方向A/B关联 |
|----------|------|-------------|
| **Requires** | A依赖B | 方向A：依赖链聚合 |
| **Conflicts** | A与B矛盾 | 方向B：矛盾检测 |
| **Duplicates** | A与B重复 | 方向B：去重 |
| **Details** | A细化B | 方向A：层级聚合 |
| **Composition** | A由B组成 | 方向A：组合聚合 |
| **Is similar** | A与B相似 | 方向A：相似聚合 |

### 6.2 矛盾子类型（FSARC 7类 → 三层映射）

| 矛盾类型 | FSARC定义 | 我们的层次 | 检测方法 |
|----------|-----------|------------|----------|
| 数值矛盾 | 同参数不同值 | 语义层 | NLI+NER+值比对 |
| 单位矛盾 | 同参数不同单位 | 语义层 | 词典(单位族) |
| 允许/禁止矛盾 | A允许B禁止 | 语义层 | NLI+模态词检测 |
| 时序矛盾 | A先于B vs B先于A | 逻辑层 | LTL/Z3 |
| 结构矛盾 | 编号断裂/缺失 | 语法层 | 规则 |
| 格式矛盾 | ID格式不一致 | 语法层 | 正则 |
| 资源矛盾 | 子模块之和>总预算 | 逻辑层 | Z3/SAT |

### 8.2 数据集空白确认

- **中文需求文档NLP**：arXiv检索"Chinese requirement NLP"返回0条有效结果
- **军事/国防SRS自动化**：arXiv检索"military software requirement"返回0条NLP相关工作
- **GJB标准学术研究**：arXiv检索"GJB"返回0条
- **真实SRS矛盾标注**：现有矛盾检测数据集全是合成或半合成

### 8.3 合成数据的不可靠性

Korn et al. 2026(arXiv:2606.25550)发现：
> "LLM无法可靠地(i)生成高质量需求(ii)合成注入requirement smells(iii)单靠LLM或单人都无法可靠检测smells"

**结论**：合成Gold Standard不可靠，必须基于真实SRS+人工标注。我们的16份真实GJB SRS（含真实矛盾：网络适配器4vs40、版本冲突V7.6vsV8等）是稀缺资源。

### 8.4 Gold Standard构建方案

| 构建方式 | 内容 | 标注量 | 可信度 |
|----------|------|--------|--------|
| **真实矛盾(人工确认)** | doc01网络适配器4vs40、doc09 ID拼写错误、ghost引用 | ~20条 | 高 |
| **正负样本对** | doc01(真矛盾) vs doc10名录节点≥3000/≤3000(伪矛盾) | ~5对 | 高 |
| **合成矛盾(LLM辅助+人工审核)** | 在真实SRS中注入数值/单位/时序矛盾 | ~50条 | 中(需人工审核) |
| **跨文档标注** | 10个共享PZXQ ID的接口描述一致性 | ~10对 | 中 |

### 8.5 评测框架

借鉴DocScope(arXiv:2605.08888)四阶段轨迹：
```
检测结论 = 定位章节 → 定位表格/图 → 提取事实 → 判定一致/矛盾
          (Page Loc)  (Region Ground) (Fact Extract) (Verify)
```

每个检测结果必须附带证据链（借鉴ContractNLI的证据span），解决"检测结论不可追溯"的问题。

## 十、任务拆解建议

### 10.1 "粒度×任务×层次"三维矩阵

```
              抽取(Extract)    关联(Associate)    检测(Detect)
句子级         参数/约束抽取      —              需求smell(语法层) [已有大量工作]
条目级         条目结构化       条目内多模态对齐   单条质量/可测试性 [已有]
文档级         章节结构解析     ★方向A:跨章节聚合  ★方向B:语义层(跨条目值矛盾)
跨文档级       —              跨SRS追溯[TLR已有]  全局逻辑可满足性(逻辑层)
```

### 10.2 方向A任务分解

```
方向A: Intra-document Requirement Context Aggregation
├─ A1: 需求ID多位置追踪
│   └─ 章节标题(3.2.x) ↔ 合格性表(第4章) ↔ 追踪表(第5章) ↔ 优先级表(3.18)
│   └─ 技术: DeepSpecs式metadata lookup + ID传播
├─ A2: 跨章节实体链接
│   └─ 同参数/同功能在不同节的隐式指称绑定
│   └─ 技术: 序号对齐 + 语义相似 + 位置邻接 (非正则,需推断)
├─ A3: 图文表三位一体
│   └─ 功能需求表 + 用例图 + 流程图的分组关联
│   └─ 技术: DMAP式文档图 + LFRAG式block检索
└─ A4: 跨文档接口关联
    └─ 10个共享PZXQ ID的双向描述对齐
    └─ 技术: ID精确匹配 + 服务后缀语义匹配
```

### 10.3 方向B任务分解

```
方向B: Document-level Multi-layer Consistency Checking
├─ B1-语法层: GJB规则合规
│   └─ 章节完整性 / 编号连续 / ID格式 / ghost引用
│   └─ 技术: 规则引擎(GJB 120条规则)
├─ B2-语义层: 跨条目值矛盾
│   ├─ 同参数多值: NLI+领域NER+值比对 (借鉴S3CDA+ContractNLI)
│   ├─ 正文与表格矛盾: 文档级NLI+证据span (借鉴ContractNLI)
│   ├─ 版本冲突: 跨文档版本一致性
│   └─ 核心挑战: 区分"合理差异"(设备配置梯度) vs "真实矛盾"
├─ B3-逻辑层: 约束可满足性
│   ├─ NL→形式化: LLM辅助提取约束 (借鉴VeriTrans)
│   └─ Z3求解: 子模块时间之和≤总预算等 (借鉴ContractCheck)
└─ B4-跨文档层: 共享ID接口规格一致性
```

### 10.4 技术路线

**方向A**（借鉴DeepSpecs但改造为隐式聚合）：
1. ReqDB构建：按需求项切块，metadata={doc_id, section, req_id, type}
2. 多信号关联推断：序号对齐 + ID传播 + 语义相似 + 位置邻接
3. 扇形汇聚：把同一实体的文字+图+表行聚合成一个条目

**方向B**（混合方法）：
- 语法层：规则引擎（GJB 120条规则）
- 语义层：LLM粗筛候选矛盾对 → NLI+领域NER精确判定 → LLM生成解释
- 逻辑层：LLM提取约束 → Z3求解 → 不可满足则定位矛盾
