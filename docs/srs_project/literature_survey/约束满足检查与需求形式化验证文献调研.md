## 二、分主题详细分析

### 主题 A：SAT/SMT 求解器用于需求一致性检查（核心主题）

这是与本项目「逻辑层不一致检测」最直接相关的方向——用可满足性求解器自动判定需求集合是否存在矛盾。

#### A1. Vuotto et al. (2018) — Consistency Checking of Functional Requirements ✅ arXiv:1804.10486

- **问题**：需求通常以自然语言/半形式语言表达，人工检查一致性易出错、不可扩展。随着 CPS 复杂度增长，需自动化一致性检查。
- **方法**：将功能需求翻译为形式化约束，用 SMT 求解器（Z3）自动检查需求集合的可满足性。若 UNSAT，则存在矛盾；若 SAT，给出满足模型。
- **工具**：**ReqV** —— 自研工具，支持需求形式化 + SMT 一致性检查 + 反例生成。
- **结果**：在工业级嵌入式系统需求集上验证有效，能自动检测出人工 review 遗漏的矛盾需求。
- **与本项目相关性 ★★★★★**：直接对标。本项目「参数化需求条目库」中的 `{参数名, 运算符, 数值}` 可直接编码为 SMT 约束（如 `(X <= 50) ∧ (X >= 100)` → UNSAT），ReqV 的「翻译→SMT 检查→反例」管线是本项目的直接技术基线。

#### A2. Filipovikj et al. (2017) — Model-Checking vs. SMT-based Consistency Analysis ✅ DOI:10.14279/tuj.eceasst.75.1054

- **问题**：工业嵌入式系统需求一致性分析缺乏两种主流形式方法（model-checking vs. SMT）的系统对比。
- **方法**：对同一组工业需求，分别用 UPPAAL（模型检测，基于时间自动机）和 Z3（SMT 求解）做一致性分析，对比可扩展性、精度、效率。
- **工具**：UPPAAL（model-checking）vs. Z3（SMT）。
- **结果**：SMT 方法在纯逻辑/数值约束检查上更快且更易扩展；model-checking 在时序行为验证上更强。两者互补。
- **与本项目相关性 ★★★★★**：为本项目技术选型提供直接依据——数值/逻辑矛盾检测应优先用 SMT（本项目场景），时序依赖检测可用 model-checking 补充。

#### A3. Mahmud et al. (2016) — ReSA Tool: SAT-based Consistency-checking ✅ DOI:10.15439/2016F404

- **问题**：需求规约通常是结构化文本但缺乏形式语义，无法自动检查一致性。
- **方法**：ReSA 工具提供结构化需求规约模板，将需求自动编码为 SAT 实例，用 SAT 求解器检查全局一致性。
- **工具**：**ReSA**（自研）+ SAT 求解器。
- **结果**：在嵌入式系统需求上能自动检测矛盾需求，结构化模板降低了形式化门槛。
- **与本项目相关性 ★★★★★**：ReSA 的「结构化模板→SAT 编码」思路与本项目「参数化条目→SMT 约束」高度同构。

#### A4. Bendík (2017) — Consistency Checking in Requirements Analysis ✅ DOI:10.1145/3092703.3098239

- **问题**：SAT-based 需求一致性检查在大规模需求集上面临可扩展性瓶颈。
- **方法**：提出优化算法，利用需求间的依赖关系缩减 SAT 求解的搜索空间，增量式检查（仅重新检查受变更影响的需求子集）。
- **工具**：SAT 求解器。
- **结果**：在 1000+ 需求的工业数据集上，增量检查比全量检查快 10x+。
- **与本项目相关性 ★★★★☆**：增量一致性检查思路适配本项目「SRS 条目库动态更新」场景——每次新增/修改条目只需增量检查，而非全量重算。

#### A5. Kühn et al. (2015) — Safety Conflict Analysis in Medical CPS Using an SMT-Solver ✅ (S2)

- **问题**：医疗 CPS 中不同子系统的安全需求可能存在隐性冲突（如两个安全机制互斥）。
- **方法**：用 SMT 求解器对安全需求建模，检测系统级安全冲突，将冲突纳入故障树分析（FTA）的语义扩展。
- **工具**：Z3 / SMT + FTA。
- **结果**：成功检测出医疗网络系统中人工分析遗漏的安全机制冲突。
- **与本项目相关性 ★★★★☆**：安全冲突检测方法可迁移到军工 SRS 的安全/性能需求矛盾检测。

#### A6. Palma et al. (2011) — Using an SMT Solver for Interactive Requirements Prioritization ✅ DOI:10.1145/2025113.2025124

- **问题**：需求优先级排序中，决策者的偏好可能存在逻辑矛盾（如 A>B 且 B>A）。
- **方法**：将优先级偏好编码为 SMT 约束，用 SMT 求解器检测不一致偏好并交互式修复。
- **工具**：Z3（SMT-LIB）。
- **结果**：在有效性、效率、对决策者错误的鲁棒性上优于 state-of-the-art 交互式优先级方法。
- **与本项目相关性 ★★★☆☆**：SMT 用于偏好/约束一致性检查的思路可迁移，但应用场景（优先级排序）与本项目（数值矛盾检测）有所不同。

### 主题 B：LLM + 形式方法用于需求验证（NL → 形式规约 → 验证）

这是 2024–2025 年的前沿方向——用 LLM 弥合自然语言需求与形式规约之间的鸿沟，再用 SMT/model-checker 验证。

#### B1. Chen et al. (2025) — LLM-based Satisfiability Checking of String Requirements ✅ arXiv:2506.16639

- **问题**：字符串需求（NL 表达）的可满足性验证困难——形式方法（SMT）效率有理论限制，且 NL→形式约束翻译需大量人工。
- **方法**：用 LLM 自动将 NL 字符串需求翻译为形式约束，同时生成测试数据（consistent data）和检查器（checker），通过「数据生成 + 检查器执行」验证可满足性。结合 SMT 求解器做形式验证。
- **工具**：LLM + Z3/SMT + 自动生成的 checker。
- **结果**：在字符串需求基准上，LLM+SMT 混合方法比纯 SMT 或纯 LLM 都更有效。
- **与本项目相关性 ★★★★★**：**最高相关性**。本项目核心任务即「NL 需求条目→形式约束→可满足性检查」。该论文的「LLM 翻译 + SMT 验证 + 数据生成」三步管线可直接迁移到本项目参数化条目的矛盾检测。

#### B2. Beg et al. (2025) — Leveraging LLMs for Formal Software Requirements ✅ arXiv:2507.14330

- **问题**：安全关键系统（航空航天、医疗、自动驾驶）强制要求形式验证，但从非形式 NL 需求生成形式规约是关键瓶颈。
- **方法**：系统分析 LLM 在形式需求规约生成中的角色——LLM 辅助从 NL 提取形式规约、辅助模型检测/定理证明。讨论挑战（幻觉、形式语义不保真）与前景。
- **工具**：模型检测器 + 定理证明器 + LLM。
- **结果**：position/roadmap 论文，指明 LLM+形式方法在需求工程中的研究路线。
- **与本项目相关性 ★★★★☆**：为本项目「LLM 辅助形式化」提供方法论框架与挑战清单（幻觉控制、语义保真验证）。

#### B3. Zrelli et al. (2024) — Fine-Tuning LLMs for Translating NL Requirements to CTL ✅ DOI:10.1109/RSP64122.2024.10870993

- **问题**：将 NL 需求翻译为 CTL 时序逻辑公式需要形式方法专家，门槛高。
- **方法**：微调 LLM（fine-tuning）使其能将自然语言需求自动翻译为 CTL 规约，用于后续 model-checking。
- **工具**：微调 LLM + CTL model checker。
- **结果**：微调后的 LLM 在 CTL 翻译准确率上显著优于零样本/少样本提示。
- **与本项目相关性 ★★★★☆**：LLM 微调做 NL→形式逻辑翻译的范式可直接迁移到「NL 需求→SMT 约束」的自动翻译。

#### B4. Lim et al. (2026) — Shift-Left Requirements Verification: Integrating LLMs and Formal Methods ✅ DOI:10.1007/978-3-032-26220-2_31

- **问题**：汽车系统需求验证通常在开发后期进行，错误修复成本高。
- **方法**：将 LLM 与形式方法集成，实现「左移」需求验证——在需求阶段就用 LLM+形式方法检测矛盾。
- **工具**：LLM + 形式方法工具链。
- **结果**：在汽车系统案例上验证了早期需求矛盾检测的可行性。
- **与本项目相关性 ★★★★☆**：「左移」理念与本项目「在 SRS 文档阶段就检测矛盾」完全一致。

#### B5. Lahiri (2024) — Evaluating LLM-driven User-Intent Formalization ✅ arXiv:2406.09757

- **问题**：验证感知语言（Dafny/F*）可机械检查实现与规约的一致性，但无法保证「用户意图的形式化」本身正确——意图是 NL 表达的，规约是形式化的。
- **方法**：评估 LLM 将非形式意图（NL）形式化为 Dafny/F* 规约的能力，分析形式化正确性。
- **工具**：Dafny, F*。
- **结果**：LLM 在简单规约形式化上表现良好，但在复杂意图上存在语义偏差。
- **与本项目相关性 ★★★★☆**：「意图形式化正确性」问题直接对应本项目「NL 需求条目→SMT 约束翻译是否保真」的挑战。

#### B6. Hsia et al. (2025) — Neuro-Symbolic Compliance: Integrating LLMs and SMT Solvers ✅ arXiv:2601.06181

- **问题**：金融法规合规自动化困难——法规逻辑一致性维护需要最少人工干预。
- **方法**：Neuro-Symbolic 框架——LLM 解析法规文本提取逻辑约束，SMT 求解器验证合规一致性并提供优化修正建议。
- **工具**：LLM + Z3/SMT。
- **结果**：在金融法规上实现了形式可验证的合规检查 + 自动修正。
- **与本项目相关性 ★★★★☆**：「LLM 提取约束 + SMT 验证一致性 + 修正建议」管线与本项目的「参数化条目抽取→矛盾检测→修正建议」架构高度同构。

#### B7. Bertram et al. (2023) — Leveraging NLP for a Consistency Checking Toolchain of Automotive Requirements ✅ DOI:10.1109/RE57278.2023.00029

- **问题**：汽车行业需求量大、语言非形式、歧义多，一致性检查困难。
- **方法**：用 Structured English 消除歧义 + NLP + LLM 构建一致性检查工具链。NL 需求→结构化表示→自动一致性检查。
- **工具**：自研工具链（Structured English + NLP + LLM）。
- **结果**：在汽车需求上有效检测一致性问题，Structured English 保持了可读性同时支持自动处理。
- **与本项目相关性 ★★★★★**：直接对标——本项目可用「受控中文（GJB 术语规范）+ NLP 抽取 + 一致性检查」构建类似工具链。

### 主题 C：形式规约语言与时序逻辑用于需求验证

#### C1. Mashkoor et al. (2021) — Validation Obligations: Check Compliance between Requirements and Formal Specification ✅ arXiv:2102.06037

- **问题**：形式方法主要用于 verification（构造正确），但 validation（构造对的东西）被忽视——需求本身或其形式化解释的错误在后期才被发现。
- **方法**：提出「验证义务（Validation Obligations）」概念——在 Event-B 精化过程中，每个精化步骤需生成验证义务，确保形式模型与原始需求一致。
- **工具**：Event-B / Rodin 平台。
- **结果**：在案例研究中，验证义务能早期发现需求解释错误。
- **与本项目相关性 ★★★★☆**：「验证义务」概念可迁移——本项目参数化条目库可生成「一致性验证义务」（如检查同一参数的所有约束是否可满足）。

#### C2. Klimek (2014) — Generating Logical Specifications from Requirements Models for Deduction-based Formal Verification ✅ arXiv:1402.1985

- **问题**：时序逻辑公式难以为非专家手动编写，阻碍了演绎验证在需求工程中的应用。
- **方法**：从需求模型自动生成时序逻辑规约（temporal logic formulas），用于演绎推理验证模型行为正确性。
- **工具**：时序逻辑 + 演绎推理引擎。
- **结果**：自动生成逻辑规约降低了形式验证门槛。
- **与本项目相关性 ★★★★☆**：「从需求模型自动生成逻辑规约」对应本项目的「从参数化条目自动生成 SMT 约束」。

#### C3. Li, Hayes & Truszczynski (2012) — Temporal Action Language (TAL) ✅ DOI:10.1007/978-3-642-28891-3_16

- **问题**：自然语言时序需求的一致性检查缺乏可控的 NL→形式逻辑翻译手段。
- **方法**：设计受控自然语言 TAL（Temporal Action Language），将 NL 时序需求翻译为形式化表示，再用 SAT/SMT 检查一致性。
- **工具**：TAL + SAT solver。
- **结果**：在初步实验中有效检测了时序需求矛盾。

## 五、研究空白与机会（Gap Analysis）

1. **中文 SRS 的形式化验证空白**：现有工作几乎全部针对英文需求。GJB 438C 中文 SRS 的形式化约束提取 + SMT 验证尚无公开工作。→ 本项目可填补。

2. **参数级数值矛盾的自动化检测**：现有 SMT-based 方法主要针对功能行为/时序需求，对「同一参数在不同条目中的数值约束矛盾」（如 X≤50 vs X≥100）的专项检测缺乏系统性工作。→ 本项目参数化条目库天然适配此场景。

3. **LLM + SMT 在需求一致性上的结合尚处早期**：Chen 2025 (字符串需求) 和 Hsia 2025 (金融法规) 是先驱，但针对工程需求（特别是军工 SRS）的 LLM+SMT 一致性检查尚无工作。→ 本项目可贡献。

4. **增量一致性检查与 SRS 版本管理的结合**：Bendík 2017 的增量 SAT 检查思路尚未与 SRS 配置管理（GJB 5000B）结合。→ 本项目可探索。

5. **混合矛盾检测**：数值矛盾（SMT）+ 时序矛盾（model-checking）+ 语义矛盾（LLM）的统一检测框架尚不存在。Filipovikj 2017 指出了 SMT 与 model-checking 的互补性，但未与 LLM 语义检测结合。→ 本项目可提出三层混合架构。
