# SRS数据集增强与检测方法升级：综合调研报告

> 调研日期：2026-08-23
> 方法：arXiv API多关键词检索（requirement inconsistency / requirements engineering + LLM / multimodal document understanding / requirement smells / active learning annotation / flowchart understanding / cross-modal consistency）+ Semantic Scholar检索 + 本地已有9份调研的增量整合
> 定位：在2026-08-05全景调研与2026-08-10无标注评测调研基础上，回答"如何增强数据集、如何构建Gold Standard、如何升级检测方法"三个工程-科研问题
> 输入状态：16份GJB SRS（1444章节/1207表格/381图片/763约束/407版本号）、pair_dataset 366对（7场景）、Visio源提取171个、75条人工标注

## 0. 执行摘要（先说结论）

| # | 问题 | 结论 |
|---|------|------|
| 1 | 合成注入可行吗？ | **规则引导的确定性mutation可行，LLM自由生成不可行**。Korn et al. (AIRE'26)实证LLM无法可靠注入requirement smells；但CodeFuse-CommitEval用rule-guided mutation构建基准成功。我们手握Visio结构化源+表格CSV，具备做确定性注入的独特条件 |
| 2 | 主动学习能省标注吗？ | **当前证据不支持**。两篇2026新工作（arXiv:2604.13899, 2604.08977）表明：LLM标注时代AL不优于随机采样；100-500样本量级下AL策略普遍失效。替代方案：**双模型分歧采样**（disagreement sampling） |
| 3 | Erlangshen-110M可行吗？ | **作为廉价预筛可行，作为主检测器不可行**。中文通用NLI模型在军事术语上会显著退化；建议三级架构：API-LLM zero-shot NLI（上界baseline）→ 本地中型NLI模型（Erlangshen-330M/DeBERTa-Chinese，预筛）→ 规则+值比较（精确层） |
| 4 | 多模态检测用什么？ | **结构化解析路线优于纯VLM端到端**。FlowExtract（YOLO+OCR pipeline）在流程图边抽取上超过VLM baselines；Arrow-Guided VLM显式编码箭头方向+9pp；FloCA用确定性图执行器保证忠实推理。我们的Visio源提取正是这条路线的极端形式（直接拿到结构，跳过感知） |
| 5 | VLM选型？ | **Qwen3-VL系列**。CHaystack（中文文档VQA基准）实测Qwen3-VL Recall@1=71.91，最强非Qwen模型仅14.40——中文密集文本文档上Qwen家族断层领先 |
| 6 | 与SOTA的差距？ | 直接竞品仍只有TSRCDF-SS（句对级纯文本）。**文档级聚合+多模态+中文GJB三个空白仍在**。2026年新出现的SAFER、QRS'25 Hybrid框架都未做条目聚合。我们的差距在数据规模（366 vs ARTA 4752）和评测严谨性，不在选题 |

## 一、数据集增强的三种策略

### 1.1 策略A：自动提取扩展（把现有pipeline跑到极限）

**现状**：366对仅覆盖7场景，Visio映射只做了sc2（89/90，平均匹配度81.6%）。16份文档中还有大量未配对的图-表-文组合。

**扩展路径（按投入产出排序）**：

1. **Visio映射扩展到其余场景**：171个Visio嵌入已提取节点+边结构，但只有sc2用了。sc1（用例图+能力表）、sc3（接口图+接口表）、sc4/sc5的图同样可能是Visio嵌入。脚本已存在（`sc2_visio_extract.py`/`sc2_visio_map.py`），改场景参数即可复用。
2. **ID锚定的跨章节配对**：407个版本号 + 需求ID（SRS中"3.2.1.2"式编号+需求标识符）是最可靠的配对锚。同一ID出现在{3.x正文, 接口表行, 合格性表行, 追溯表行}的组合尚未系统挖掘——这是方向A（条目聚合）的天然训练数据。
3. **负样本免费获取**：同文档不同功能模块的图-表交叉配对 = 近似确定的负对（"结构化数据归集"的用例图 vs "流式数据归集"的能力表）。负样本不足是多标签检测的常见瓶颈，交叉重组可免费扩充。
4. **3份格式异常文档的结构修复**：1444章节中13份结构完整，3份异常——修复后可新增约20%的章节级配对。

**参考基准的构建方法对比**：

| 数据集 | 规模 | 构建方式 | 对我们的启示 |
|--------|------|----------|--------------|
| PURE (79份) | 79文档 | 人工整理公开需求文档 | 文档级语料的下限；我们16份真实文档比合成更有价值 |
| ARTA (4752条) | 4752条标注 | 人工标注requirement smells | 规模靠"条目级"而非"文档级"计数；我们应以"对"为单位报告规模 |
| Enginuity (2026新) | 美军维修手册 | 人工标注工程图+零件表 | 军事域图-表交叉引用benchmark：Task1结构化表格抽取 Recall@all 0.61-0.87但Token F1仅0.03-0.18——**军事工程图对VLM极难，侧面验证我们"结构化源优先"路线** |
| JSynFlow (2026新) | 合成日文流程图VQA | LLM生成DSL→渲染器生成图→程序生成QA | **合成图数据的最优范式：结构从DSL来，不走像素感知** |

**预期规模**：366对 → 自动提取后800-1200对（Visio映射扩展+跨章节配对+交叉负采样）。

### 1.2 策略B：合成注入（synthetic inconsistency injection）

**必须先吸收的负面证据**：

> **Korn et al. 2026 (arXiv:2606.25550, AIRE'26)**：尝试用LLM合成"带requirement smells的需求"和"未实现需求"构建数据集。结论：LLM (i)无法可靠生成高质量需求 (ii)无法可靠注入合成smells (iii)单个人工审核也不足以检测smells。**"Generation of code-to-requirements datasets using LLMs is not yet viable and requires human supervision."**

但反面证据要正确解读——Korn失败的是**LLM自由生成**；成功的先例是**规则引导的确定性mutation**：

> **CodeFuse-CommitEval (arXiv:2511.19875)**：在真实一致样本上做7类规则化mutation（改组件名/改文件路径/改操作类型/改意图），再双重验证正负样本——成功构建了message-diff不一致检测基准，评测6个开源LLM。

**推荐方案：确定性Mutation引擎（三层防线）**

```
输入: 真实pair (Visio结构源, 表格CSV行, 文本片段)
  ↓
Mutation算子库（每类不一致性对应确定性算子）:
  - ID不一致(32%): 需求ID数字替换/章节号偏移 —— 字符串规则
  - 名称不一致(16%): 同义词替换表/删除前后缀 —— 词典规则
  - 值矛盾(7%): 数值±偏移/单位族内换算错误(kb→MB) —— 单位换算表(已有srs_kb.json 10单位族)
  - 章节错位(24%): 表格行与错误章节的图配对 —— 重组规则
  - 异常流缺失(8%): 从用例表删除"异常流"行 / 从Visio边删除异常分支 —— 结构规则
  - caption错误(5%): 图号/表号偏移 —— 字符串规则
  ↓
渲染层: Visio源改节点→重新渲染图 / CSV改单元格→重制表 / 文本改写
  ↓
验证层(对抗Korn的失败模式):
  1. 程序验证: mutation后的图结构可被解析器重新读出且diff符合预期
  2. 双LLM交叉验证: 两个异族模型都应能检测出注入的不一致(注入样本=已知答案的检查器测试)
  3. 对照组: 同比例做"语义保持改写"(合理差异),确保检测器区分"变化"与"矛盾"
```

**关键优势**：我们有Visio源（171个图的节点+边结构化表示），mutation可以**直接改结构化源再渲染**，而非在像素上操作——这比所有同行（只有渲染后的PNG）都多一个自由度。这正是JSynFlow范式（DSL→渲染）在数据增强方向的应用。

**规模预期**：366真实对 × 7类mutation × 保真验证 ≈ 2000+注入对，正负可控。

### 1.3 策略C：数据扩增（对现有366对的增强）

1. **交叉负采样**（见1.1第3条）：零成本负对，预估可产500+。
2. **图重渲染扩增**：同一Visio源改变布局/配色/节点位置但保持语义 → 检测器应对布局不变的语义等价（防止检测器学到布局捷径）。参考Structure-aware Contrastive Learning（arXiv:2509.01959）的hard negative思想。
3. **层次化任务分解**（参考ReceiptBench, arXiv:2605.22413的四层任务）：每个pair可拆出 (1)基础感知（图中节点文本是什么）(2)格式归一（表格结构解析）(3)语义推理（图节点集vs表行的对应）(4)结构解析（流程图分支逻辑vs用例表异常流）——同一数据支撑4个粒度的评测，等于规模×4。
4. **文本侧回译/同义改写**：对text.txt做语义保持改写，测试检测器对表述变化的鲁棒性。

### 1.4 三策略组合的定位

| 策略 | 用途 | 数据角色 |
|------|------|----------|
| A 自动提取 | 真实分布 | 评测集主体（真实对） |
| B 合成注入 | 已知答案 | 训练集 + 检测器单元测试 + 上界测量 |
| C 数据扩增 | 鲁棒性 | 消融实验（防捷径学习） |

**原则：合成的只用于训练/开发，评测报告必须以真实对为主**（论文可信度的生命线，详见第五节）。

## 二、Gold Standard构建方案（零/低标注场景）

### 2.1 现状诊断

- 75条人工标注（2份文档）：类型分布严重不均（ID不一致32% vs 逻辑矛盾3%），无法支撑per-type F1
- 已有机器标注基础：`multi_llm_annotations.json`、双源解析锚点（31/31）、OCR验证（10/10）、223条合成Gold Standard（无人工锚点）

### 2.2 分层Gold Standard架构（推荐）

```
L0 确定性锚点层（零人工，可执行检查器即真值）
   ├─ 语法层: 7项GJB标准检测(167条违规) — 规则输出即gold
   ├─ 注入样本: mutation引擎产物 — 注入位置即gold
   └─ 双源解析: 31/31锚点(已有) — 扩展到全部407版本号
L1 Silver层（机器标注+交叉验证，零人工）
   ├─ 双异族LLM交叉标注(已有基础) + 分歧仲裁(第三模型)
   ├─ 强制报告: Cohen's kappa(扣随机一致), 逐类一致率
   └─ 自一致性: 同模型多次采样分歧度(SelfCheckGPT思路)
L2 Gold层（人工，目标150-200条）
   ├─ 现有75条 + 分歧采样扩展(见2.3)
   └─ 用途: 锚定L1的效度(Alternative Annotator Test) + 最终评测
```

这个架构的直接依据是2026-08-10调研的核心结论（ACL 2025 Alternative Annotator Test：需50-100条人工子集做统计检验证明LLM可替代人类），本次调研没有推翻它，只是把L0层的"注入样本"从假设变成了可执行方案。

### 2.3 主动学习的最新裁决与替代方案

**新证据（2026，对传统AL不利）**：

1. **arXiv:2604.13899**（277,902条德语TikTok评论，GPT-5.2 vs Prolific人工）：LLM大规模标注以1/10成本（$28 vs $316）超过人工监督分类器；**AL在LLM标注下不优于随机采样**。关键发现：LLM标注的优势来自"两问题分解"式任务设计而非采样策略。
2. **arXiv:2604.08977**（翻译任务，100-500样本）：AL策略优化的informativeness/diversity与测试性能**不相关**；样本顺序和与预训练数据的交互影响更大。

**裁决**：在75→200条的量级，不要投入传统AL框架（不确定性采样/聚类采样）。

**替代方案：双模型分歧采样（disagreement-based prioritization）**

```
对未标注池(1000+候选对):
  模型X(GLM) + 模型Y(异族,如Qwen/DeepSeek) 独立标注
  ├─ 一致(高置信) → 直接进L1 silver, 不耗费人工
  ├─ 分歧(中置信) → 优先人工仲裁 ← 人工预算全部花这里
  └─ 双双低置信  → 按类型配额补采(保证每类≥20条)
```

理由：(a) 分歧样本是信息密度最高的（无论是模型错还是边界case）；(b) 类型配额直接解决75条标注的类型不均衡（逻辑矛盾3%→必须补采到≥20条才能算per-type F1）；(c) 实现成本低于AL（无训练循环）。

### 2.4 LLM-as-Judge可靠性验证清单（操作化）

已有调研结论（judge与被评不能同族、位置偏差交换测、92%一致≠正确）之外，新增操作项：

1. **异族强制**：GLM-5做检测器时，judge用Qwen/DeepSeek系（CHaystack证据同时支持Qwen做中文文档判读）。
2. **rubric锚定**：judge prompt必须引用GJB规则库条号（120条规则可追溯），禁止自由心证——把judge从"语义判断"降维到"规则匹配"，可靠性可控。
3. **上界标定**：注入样本（已知答案）跑judge全流程，测出judge自身的P/R——judge的误差要报告并传播到silver标注质量估计。
4. **Enginuity的教训**：token-overlap指标低估技术领域模型能力2-6倍，评测指标本身要用LLM-as-judge校准——即"评测的评测"不可省。

### 2.5 标注量测算

| 用途 | 需求 | 依据 |
|------|------|------|
| Alternative Annotator Test | ≥50条 | ACL 2025 |
| 每类型per-type F1 | 每类≥20条×7类=140 | 223条调研结论(每类10-20最低线) |
| 检测≥10pp的F1差异 | 总量200+ | McNemar估算(95%置信,80%功效) |
| **目标** | **200条**（75已有+125新增，分歧采样+配额补采） | |

## 三、检测方法升级路线图

### 3.1 短期（0-1个月）：替换粗糙组件

| 组件 | 现状 | 升级 | 依据 |
|------|------|------|------|
| 实体/参数提取 | 正则（HTML残留） | GLM-5结构化抽取(JSON schema输出) + BT-APE式自动prompt优化 | BT-APE (arXiv:2607.00427)：APE在需求分类上以72%更少token达到与PE2相同准确率；正则是S3CDA中LLM碾压NLP方法的反面——领域术语靠正则必死 |
| 语法层检测 | 7项167条 | 扩到12项（编号连续性/图表交叉引用完整性/caption与正文引用一致） | 现有GJB规则库120条，7项只用了子集 |
| NLI baseline | 无 | API-LLM zero-shot三分类（一致/矛盾/无关）跑600+文本对，先拿到上界和错误分布 | 任何本地模型选型前必须先有LLM上界参照 |
| 值比较 | 字符串相等 | 类型感知比较（数值容差/单位族归一/日期格式） | srs_kb.json已有10单位族 |

### 3.2 中期（1-3个月）：语义层+多模态双线

**语义层：属性级比对管线**

```
条目对 → LLM实体抽取(参数名,值,单位,条件) → 实体规范化(同义词表+单位归一)
       → 属性对齐(同名参数跨位置匹配) → 分型比对:
           值型: 数值/单位 → Z3数值约束
           名型: 词典+编辑距离+上下文嵌入
           逻辑型: 允许vs禁止 → 规则模板
       → 中文NLI模型复核(LLM与规则分歧的样本)
```

**NLI模型选型（回答"Erlangshen-110M可行吗"）**：

| 方案 | 定位 | 理由 |
|------|------|------|
| GLM-5/Qwen API zero-shot | 上界baseline+分歧仲裁 | S3CDA证明领域退化存在，但作为参照系必须先测 |
| Erlangshen-RoBERTa-330M-NLI（非110M） | 廉价预筛（600+对全量跑） | 110M版本容量不足；330M在CMNLI约80%，军事术语会退化到60-70%——**只配做预筛，不配做判定** |
| Qwen2.5-1.5B/3B微调 | 中期主力（若需要本地部署） | 用策略B的注入对微调，可控成本；JSynFlow证明合成数据微调有效 |
| DeBERTa-Chinese-NLI | 备选预筛 | 本地调研已提及，与Erlangshen二选一即可 |

**多模态：结构化解析路线（三条递进）**

```
Level 1(已有): Visio源提取 — 直接得到节点+边,跳过感知 (sc2: 89/90, 81.6%)
Level 2(补齐): 检测式pipeline — YOLO类节点检测+OCR+箭头方向分析
              FlowExtract(arXiv:2604.06770)在ISO 5807流程图上节点检测高精度、
              边抽取超过VLM baselines; Arrow-Guided VLM(arXiv:2505.07864)箭头编码+9pp
Level 3(兜底): VLM端到端解析 — Qwen3-VL系(中文文档断层领先,CHaystack)
              + 结构化prompt(FloCA模式: VLM只做感知,拓扑推理交给确定性图执行器)
```

FloCA（arXiv:2602.14035）的模式特别值得抄：**LLM负责意图理解和生成，流程图拓扑推理交给外部图执行工具**——"VLM感知+程序推理"的分工直接规避了VLM拓扑幻觉。我们的检测器同样应该是"VLM把图转成结构→图匹配算法做一致性判定"，而不是"VLM看图直接回答是否一致"。

图-表一致性判定的具体形式化：用例图节点集 vs 用例表行集的**双向覆盖检测**（图有表无=孤儿节点；表有图无=幽灵行）+ 流程图分支 vs 异常流行对应。这比模糊的"图文匹配"可评测得多。

### 3.3 长期（3-6个月）：逻辑层与端到端

1. **逻辑层**：Z3（数值约束）+ LTL（时序/流程约束）。新证据：LLM直接从非结构化需求生成LTL公式已实用化（arXiv:2608.06287，6个LLM在15条异构需求上pass@k可达实用水平）——"子模块时间之和≤总预算"这类约束可以先LLM形式化再Z3/LTL验证，形成**神经-符号混合**。
2. **神经-符号分层验证**：OOMRAM工作（arXiv:2607.26220）在三值逻辑(T/I/F)框架下用确定性符号层消除LLM生成需求的结构不一致（37案例中35个完全消除）——检测器输出也应三值化：**一致/矛盾/不确定**，不确定样本走人工，这同时是分歧采样的信号源。
3. **端到端**：聚合（方向A）→ 分层检测（方向B）→ 证据链输出的agentic管线。SAFER（arXiv:2601.06335）的结论背书这个方向："GenAI必须被形式模型增强并被系统化查询，才能产出有意义的安全需求分析"。

## 四、与SOTA方法的差距分析

### 4.1 竞品更新（2025-08至2026-08新增）

在2026-08-05调研认定的唯一直接竞品TSRCDF-SS（arXiv:2511.23007，句对级冲突检测）之外，本次检索新发现：

| 工作 | 方法 | 与我们的差异 |
|------|------|--------------|
| SAFER (arXiv:2601.06335, IEEE Aero 2026) | MBSE+GenAI检测安全需求矛盾/重复/缺口 | 输入是需求模型（非原始文档）；无多模态；无中文 |
| QRS'25 Hybrid Framework | 多图合并+LLM检测多样性需求矛盾 | 利益相关方图合并视角；纯文本；3案例验证无定量评测 |
| Boilerplate Ontology (ECE'25) | HermiT推理器+SPARQL查模板需求本体不一致 | 精度1.00/召回0.92但需预先构建本体；句级 |

### 4.2 空白仍然成立，但窗口在收窄

三个空白（文档级条目聚合、SRS多模态一致性、中文/军事GJB）截至本次检索**依然无人占位**：
- arXiv "requirement inconsistency" 全库仅3条结果，无文档级工作
- 多模态文档理解热点（CiteVQA/DocTrace/DeCoRAG）全部在QA/摘要/证据定位，**无人做一致性校验**
- 最接近的是Enginuity（美军工程图零件表）——做抽取和QA不做一致性，但说明军事域图表数据开始被关注

**风险信号**：(a) CiteVQA的Attribution Hallucination发现（模型答对但证据区域指错，最强模型SAA仅76.0）意味着我们的多模态检测如果只报P/R/F1不做证据定位，审稿人会质疑；(b) LLM4RE年产出已114+篇（arXiv检索"requirements engineering"+"LLM"），句级任务正在被快速填满——文档级是我们最后的窗口。

## 五、评测体系设计

### 5.1 防数据泄漏的协议设计

1. **真实/注入严格分域**：训练与消融可用注入对；主表结果只在真实对上报告；两者分开建目录，评测脚本强制隔离。
2. **Leave-one-doc-out**：16份文档的跨文档泛化实验（223条调研已指出缺失）——每轮留1份文档全部条目做测试，其余15份做开发。这是"真实SRS泛化能力"的唯一可信测法。
3. **模型族隔离**：微调/评测所用的检测模型不得与标注用的LLM同族（防self-preference，MT-Bench结论）。
4. **prompt泄漏检查**：注入样本的mutation算子描述不得出现在检测prompt中（防止检测器"背答案"）。

### 5.2 指标体系（P/R/F1之外）

| 指标 | 定义 | 依据 |
|------|------|------|
| Per-type F1（7类） | 每类不一致类型单独P/R/F1 | 75条分布不均的教训；每类≥20条 |
| Alignment Accuracy | 条目聚合的准确率（配对正确率） | 方向A的独立指标——聚合错了检测必然错，需单独归因 |
| Strict Attributed Accuracy | 判定正确**且**证据位置（章节/单元格/节点）正确 | CiteVQA（最强模型SAA仅76 vs 答案准确率高得多）——证据定位是独立能力，必须单独测 |
| Consistency Score | 文档级连续分数（条目一致比例） | 面向最终交付的报告型指标 |
| 检测粒度覆盖 | 触发检测的层（语法/语义/逻辑/多模态）× 类型矩阵 | 组件贡献可视化的基础 |
| 人工审核节省率 | 自动判定高置信比例×其准确率 | 工业价值论证（MBSE SLR指出仅12.9%工业部署——这是卖点） |

### 5.3 Ablation设计

| 消融 | 目的 | 做法 |
|------|------|------|
| 聚合质量→检测质量传导 | 证明方向A的必要性 | 用oracle聚合 vs 自动聚合分别喂同一检测器，量化差距 |
| 每个检测层的边际贡献 | 证明分层设计 | 逐层去除（-语法/-语义/-逻辑/-多模态） |
| Visio源 vs VLM感知 | 证明结构化路线 | 同一批图分别用Level1/2/3解析，比下游一致性检测F1 |
| 注入数据的作用 | 证明合成训练价值 | 有/无注入微调对比（留真实对做测试） |
| NLI模型规模 | 选型依据 | 110M/330M/API三档在同一预筛任务上的P/R/延迟 |
| Mutation类型难度 | 数据集分析 | 按算子类型分桶报告检测难度（CommitEval的type-wise analysis模式） |

### 5.4 统计规范

- 所有F1差报告bootstrap 95% CI（223条调研：小样本CI很宽，Deutsch TACL 2021）
- 主对比用McNemar检验（200条可可靠检测≥10pp）
- 注入样本结果单独成表，永不与真实样本混合平均

## 六、优先级行动计划

### P0（本周起，2周内）——先把"已知答案"的资产做出来

1. **确定性Mutation注入引擎**（策略B核心）：先做3类最高频算子（ID/名称/值），基于现有Visio源+表格CSV。验收标准：注入样本可被程序验证（diff符合预期）+双LLM可检测率>80%。
   - 理由：它同时是训练数据、检测器单元测试、L0锚点、judge上界标定——**一个引擎解决四个评测缺口**，且不依赖任何标注。
2. **Gold Standard扩展启动**：75→200条的人工标注任务包生成（分歧采样+类型配额）。复用`gen_human_annotation.py`，新增分歧样本优先队列。
   - 理由：这是所有P/R/F1计算的前提，且人工标注周期长，必须最早启动。

### P1（第2-6周）——组件替换与数据扩展

3. **Visio映射扩展**到sc1/sc3/sc4/sc5（脚本已有，改参数）。验收：映射对≥200，平均匹配度≥75%。
4. **LLM结构化实体提取**替换正则（GLM-5 + JSON schema + 少量few-shot）。验收：在75条标注涉及的实体上P/R≥正则基线+20pp。
5. **API-LLM NLI上界baseline**跑600+文本对。产出：错误分布分析（哪些类型LLM不行→指导本地模型选型和规则设计）。

### P2（第6-12周）——两条检测线成型

6. **多模态检测v1**：图→结构化解析（Visio优先，Level2 pipeline兜底）→图表双向覆盖检测（孤儿节点/幽灵行）。在sc1/sc2上验收。
7. **语义层属性比对管线**：实体对齐+类型感知比较+Erlangshen-330M/Qwen小模型预筛。在版本冲突+参数冲突两任务上验收。
8. **leave-one-doc-out评测框架**搭好（16折），所有后续结果跑在此协议上。

### P3（第12周后）——深度与形式化

9. 逻辑层（Z3数值约束→LTL时序）。
10. 三值输出+不确定样本人工路由（工业价值论证）。
11. 完整ablation矩阵+论文实验章节。

### 依赖关系

```
P0.1注入引擎 ──→ P1.5 NLI上界(用注入样本标定judge) ──→ P2.7语义层(注入微调)
P0.2 GS扩展 ──→ P2.8 评测框架(真实对+统计检验) ──→ P3.11 ablation
P1.3 Visio扩展 ──→ P2.6 多模态检测v1 ──→ P3.9 逻辑层
```

### 不做清单（同样重要）

- ❌ 传统主动学习框架（2026证据不支持，分歧采样替代）
- ❌ LLM自由生成需求文本做数据集（Korn证明不可行）
- ❌ Erlangshen-110M做主检测器（容量不足，最多做预筛二选一）
- ❌ 纯VLM端到端一致性判定（结构化解析路线是差异化，且证据支持）
- ❌ 在注入样本上报告主结果（评测可信度生命线）
