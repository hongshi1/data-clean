> 调研目标:梳理学术界从自然语言需求文档构建结构化需求图谱的方法——节点类型、边/关系类型、构建方法、数据集与评测,并指出对 GJB SRS 一致性验证项目的可借鉴之处。
>
> 检索来源:arXiv API(多组查询)、Semantic Scholar API(部分成功)、DuckDuckGo Web、项目既有文献库(`docs/srs_project/literature_survey/`)。
> 检索时间:2026-07-30。重点覆盖 2022–2026 年工作。
>
> **可信度声明**:标注 ✅arXiv 的条目为直接抓取 arXiv 元数据与摘要核实;标注 S2 的条目为 Semantic Scholar 检索摘要(部分作者/venue 信息未取全);标注「既有」的来自项目已有调研。**未能在任何来源核实到的"QUARE/RENER 标注数据集"已明确标为存疑,未臆造任何数字。**

## 0. 最重要的前置结论(请先读)

用户原始问题中描述的 **"QUARE/RENER 实体关系标注体系(Actor/Action/Object/Condition/Constraint/Goal 实体;depends-on/refines/conflicts-with 关系;4000 句、30000 标注)"在公开文献中未能被核实为一个真实存在的单一数据集。** 该 schema 极可能是将「目标模型实体类型(i*/KAOS)+ 标准需求关系类型」拼合而成的复合描述。经多源检索,真实存在的"QUARE/RENER"实体如下:

| 名称 | 真实含义 | 来源 | 是否=用户描述 |
|------|---------|------|--------------|
| **QUARE (elicitation)** | 面向需求获取的问答模型 *"QUARE: towards a question-answering model for requirements elicitation"* | Web/S2 检索 | ❌ 是 QA 获取模型,非 ERE 标注集 |
| **QuARE (ERE-via-QA)** | 通用"用问答做实体关系抽取"的工具(GitHub `tengxiaoliu/QuARE`) | Web | ❌ 通用 ERE,非需求专属 |
| **QUARE (2026)** | 多智能体辩证式质量感知需求分析 *QUARE: Quality-Aware Requirements Analysis through Multi-Agent Dialectical Negotiation* | ✅arXiv:2603.11890 | ❌ 多智能体系统 |
| **RENER** | **未找到任何需求专属的"RENER"数据集**;同名命中均为通用 NER 论文(Retrieval-Enhanced NER / NERetrieve / OpenNER) | arXiv+Web | ❌ 不存在 |

> 结论:不存在可引用的"QUARE/RENER 4000 句/30000 标注"基准。本报告改为汇总**真实存在**的需求图谱节点/边/数据集(见第 6–8 节)。若用户已知该数据集的真实出处,请补充链接以便核实。

## 1. QUARE / RENER 相关工作(真实版本)

### 1.1 QUARE: Quality-Aware Requirements Analysis (2026) ✅arXiv:2603.11890
- **作者/年份**:2026
- **问题**:需求质量分析需平衡多个相互冲突的质量属性,现有 LLM 方法多依赖任务分解或隐式聚合。
- **方法**:多智能体辩证式协商(multi-agent dialectical negotiation),显式平衡冲突质量属性,保留 stakeholder 意图。
- **与图谱关系**:虽非"标注数据集",但其"显式聚合/可审计"思路与需求图谱冲突检测的可解释性目标一致。
- **对本项目**:可借鉴其"显式 accept/reject + 可审计"思想,作为 GJB 军工可审计性要求的对照。

### 1.2 需求专属 NER 的真实代表(替代"RENER")
公开文献中需求领域的命名实体/本体抽取工作主要有:
- **Ontology Extraction from Software Requirements Using Named-Entity Recognition**(2022, S2, cit≈5):用 NER 从需求抽取本体——最接近"需求 NER"概念的真实工作。
- **Generative Language Models Potential for Requirement Engineering Applications**(✅arXiv:2412.00959, 2024):评估 ChatGPT/Gemini 在需求工程(含分类/抽取)上的能力边界。
- **PURE 数据集**(Public Requirements):本项目已在用(`data/srs_requirements/`),提供需求分类标注,是需求 IE 的主流公开基准。

> 即:需求领域**没有**名为"RENER"的公认基准;最接近的是 PURE(分类)+ 上述 NER-→ontology 工作。

## 2. Goal Model Extraction(从 NL 需求生成目标模型)

目标模型(Goal Model)是需求图谱最成熟的一种形态,源于 GORE(Goal-Oriented RE)。

### 2.1 代表性论文

| 论文 | 年份/venue | 方法 | 验证状态 |
|------|-----------|------|---------|
| Automated Goal Model Extraction from User Stories Using NLP | 2020, IEEE RE, cit≈39 | NLP 从 user story 自动抽目标模型 | S2(经典基线) |
| A Comparative Study of Large Language Models for Goal Model Extraction | 2024, ACM/IEEE, cit≈9 | 对比多个 LLM 做目标模型抽取 | S2 |
| Generative Goal Modeling | 2025, ✅arXiv:2509.01048(Sharfudden & Breaux) | 生成式/LLM 从访谈转录抽取目标模型,含 refinement 与冲突分析 | ✅arXiv |
| Constructing a Goal Model from Requirements Descriptions Based on Extraction Rules | 2017, Asia Pacific RE | 基于抽取规则 | S2 |
| Data-Dependent Goal Modeling for ML-Enabled Law Enforcement Systems | 2026, ✅arXiv:2601.06237(Alrajeh et al.) | KAOS 框架应用于 ML 系统 | ✅arXiv |

### 2.2 Goal Model 节点类型(综合 i*/Tropos/KAOS)
- **Goal**(硬目标)、**Softgoal**(软目标/质量目标)
- **Task / Operation**(任务/操作,目标的实现手段)
- **Resource**(资源)
- **Actor / Agent**(参与者/代理)
- **Obstacle**(障碍,KAOS 特有)

### 2.3 Goal Model 边类型
- **Decomposition**(AND/OR 分解):goal → sub-goal
- **Means-ends**(手段-目的):task → goal
- **Contribution**(贡献):+ / − / ++ / −−(softgoal 间)
- **Dependency**(依赖):actor → actor
- **Refinement**(细化)、**Conflict**(冲突)

### 2.4 从 NL 提取的方法演进
- **2017 规则法**:手写抽取规则 + 句法模板。
- **2020 NLP 法**:依存句法 + 分类器,从 user story("As a X, I want Y so that Z")抽 goal/actor。
- **2024–2025 LLM 法**:*Generative Goal Modeling* 用 LLM 直接从访谈转录生成结构化目标模型,并做 refinement(把高层 goal 映射到软件 operation)与冲突检测;*Comparative Study* 系统对比 LLM 在该任务上的能力。

## 3. 需求关系抽取(Requirement Relation Extraction)

### 3.1 综述锚点:Automated Requirements Relation Extraction ✅arXiv:2401.12075
- **作者**:Quim Motger, Xavier Franch
- **出处**:*Handbook on Natural Language Processing for Requirements Engineering*, Springer, 2025, Ch.7(DOI:10.1007/978-3-031-73143-3_7)
- **内容**:该领域**最系统的综述**。明确分类:
  - **关系识别技术**:句法(syntactic) vs 语义(semantic)
  - **关系抽取方法**:检索式(retrieval-based) vs 机器学习(ML-based)
  - 汇总最常见的需求关系类型(见 3.2)

### 3.2 常见需求关系类型(综合该综述 + 经典 RE 文献 Dahlstedt & Karlsson / Heindl)
| 关系 | 含义 | 方向性 |
|------|------|--------|
| **depends-on** | 依赖(实现/验证需先满足另一需求) | 有向 |
| **refines** | 细化(更具体版本) | 有向 |
| **conflicts-with** | 冲突(无法同时满足) | 对称 |
| **duplicates** | 重复(语义等价) | 对称 |
| **requires** | 前置要求 | 有向 |
| **relates-to / similar** | 相关/相似 | 对称 |
| **explains / elaborates** | 解释/详述 | 有向 |
| **constraints** | 约束(限制另一需求的取值/范围) | 有向 |

### 3.3 代表性方法工作
| 论文 | 年份 | 方法 | 验证 |
|------|------|------|------|
| Automating the Detection of Requirement Dependencies Using Large Language Models | 2026, ✅arXiv:2602.22456(Darif, Niu, Abdellatif, Briand et al.) | LLM 检测需求依赖(应对 NL 歧义与持续变更) | ✅arXiv |
| Towards Energy-aware Requirements Dependency Classification: Knowledge-Graph vs. Vector-Retrieval Augmented | 2026, ✅arXiv:2603.23954(Patil et al.) | **KG 增强 vs 向量检索增强**对比,面向小模型节能 | ✅arXiv |
| (本项目既有) Helmeczi 2022 prompt-based few-shot 冲突检测 | 2022, ✅arXiv:2211.02709 | prompt few-shot 检测需求间冲突(含参数级) | 既有报告已收录 |

### 3.4 方法分类
- **规则/句法**:依存解析 + 模板(2017 类);正则匹配显式引用(本项目 `srs_data_governance` 方向3)。
- **检索式**:相似度检索 + 句嵌入(T-SimCSE,本项目已采用做相似需求聚类)。
- **ML/编码器**:分类器/BERT 微调做关系分类;*Knowledge-Graph vs Vector* 工作专门对比 KG 增强与向量增强。
- **LLM**:few-shot prompt(2022)→ 全自动依赖检测(2026)。

## 4. 需求图谱在一致性/冲突检测中的应用

### 4.1 代表性论文
| 论文 | 年份 | 方法 | 验证 |
|------|------|------|------|
| A transfer learning approach for automatic conflicts detection in software requirement sentence pairs based on dual encoders | 2025, ✅arXiv:2511.23007(Wang et al.) | 双编码器 + 迁移学习,应对不平衡数据 | ✅arXiv |
| ArgRE: Formal Argumentation for Conflict Resolution in Multi-Agent Requirements Negotiation | 2026, ✅arXiv:2604.23124(Cheng et al.) | **形式论证(argumentation)** 做冲突解决,显式 accept/reject 提升可审计性 | ✅arXiv |
| QUARE: Quality-Aware Requirements Analysis (Multi-Agent) | 2026, ✅arXiv:2603.11890 | 多智能体辩证协商平衡冲突质量属性 | ✅arXiv |
| (本项目既有) Safety Conflict Analysis in Medical CPS Using an SMT-Solver | 2015, SE | **Z3/SMT** 检测医疗 CPS 安全冲突(人工遗漏) | 既有 |
| (本项目既有) Bendík 2017 增量 SAT | 2017 | **利用需求间依赖关系缩减 SAT 搜索空间**,增量式仅重检受影响子集 | 既有 |

### 4.2 图谱如何支撑冲突检测
- **依赖图剪枝**:Bendík 2017 用需求依赖关系图限定 SAT/SMT 求解的搜索空间,只重检受变更影响的需求子集 → 大规模可扩展。**这正是"图谱 + symbolic reasoning"的组合范式**。
- **冲突定位**:UNSAT 反例 → 在图上回溯标注冲突条目对(本项目 `约束满足检查与需求形式化验证文献调研.md` 已绘出此管线)。
- **可审计性**:*ArgRE* 用形式论证把"为何冲突、如何取舍"显式化,契合军工 SRS 可审计要求。

### 4.3 Symbolic Reasoning (Z3/SMT) + Graph 组合
- **已在本项目既有调研中覆盖**:`约束满足检查与需求形式化验证文献调研.md` 系统梳理了 Z3/SMT、KAOS、UPPAAL、Alloy 等在需求一致性中的应用,并给出本项目管线:`[抽取层] 参数化条目{参数名,op,数值,单位,类型,引用关系} → [建模层] Z3 约束 → [求解层] UNSAT 反例 → 矛盾报告`。
- **本项目 `srs_consistency_checker_v2.py` 已集成 Z3 实际求解**(同值/文本-表格/逻辑三层)。

### 4.4 评测指标
- 句对冲突检测:Precision / Recall / F1(对齐 Gold Standard),本项目 `srs_eval.py` 已就绪。
- 形式化方法:UNSAT 检出率、反例可解释性、增量检查的加速比(Bendík)。

## 8. 【交付物 3】构建方法分类(规则/ML/LLM/混合)

| 方法范式 | 代表工作 | 适用环节 | 优缺点 |
|---------|---------|---------|--------|
| **规则/句法** | 2017 抽取规则;本项目正则显式引用;HanLP/LTP 依存解析 | 显式引用、结构化模式 | 高精度低召回;不可泛化 |
| **检索式** | T-SimCSE 句嵌入检索;retrieval-based RE | 相似/重复关系 | 召回高;需阈值调优 |
| **ML/编码器** | 分类器/BERT 微调;Knowledge-Graph vs Vector(2603.23954);双编码器迁移学习(2511.23007) | 关系分类、冲突检测 | 需标注;不平衡数据挑战 |
| **LLM** | Helmeczi 2022 few-shot;Darif 2026 依赖检测;Generative Goal Modeling 2025;Graph-RAG(2412.08593) | 复杂语义、长尾、文档级 | 灵活;但过度自信/校准低(本项目已决策"LLM 只做长尾+校验") |
| **图谱+符号推理(混合)** | Bendík 2017 增量 SAT+依赖图;医疗 CPS SMT;本项目 v2 检查器(Z3) | 冲突检测、一致性证明 | 可审计、可解释;需准确建模 |
| **Graph-RAG** | 2412.08593;TVR(2504.15427) | 文档级追溯、合规 | 跨章节链接;依赖切块质量 |

**演进趋势**:规则(2017)→ 检索/ML(2020)→ LLM few-shot(2022)→ 全自动 LLM(2025–2026)→ KG/Graph-RAG + symbolic(2026)。本项目"规则兜底 + 领域 BERT 主力 + LLM 长尾 + Z3 符号求解"四层架构与该趋势一致且更完整。

## 10. 【交付物 5】对 GJB SRS 一致性验证项目的可借鉴之处

### 10.1 直接可复用
1. **节点 schema 已领先**:本项目 `{参数名, 运算符, 数值, 单位, 条目类型, 引用关系}` + Neo4j 的 `REFERS_TO/DEFINED_IN/VERIFIED_BY/DEPENDS_ON`,已覆盖主流需求图谱节点/边类型,且针对 GJB 数值约束更细。**建议直接作为论文的 schema 贡献点**。
2. **Z3 + 依赖图组合已被验证**:Bendík 2017 的"依赖图剪枝 SAT 搜索 + 增量检查"是可引用的先例;本项目 `srs_consistency_checker_v2.py` 的 Z3 集成可对标此范式,补上"增量/受影响子集"优化以提规模可扩展性。
3. **Graph-RAG 做文档级追溯**:2412.08593 与 TVR(2504.15427)证明 Graph-RAG 在强监管域(航空/汽车)SRS 合规有效——与 GJB 军工场景高度同构,可作方法对照与基线。

### 10.2 应补强
4. **冲突检测的可审计性**:*ArgRE*(形式论证)+ *QUARE*(显式 accept/reject)都强调"为何冲突"的可解释性。军工可审计要求下,建议本项目 Z3 检出冲突后,**输出 UNSAT core + 图上回溯路径**作为证据链(本项目报告已设计但可强化为论文卖点)。
5. **不平衡数据冲突检测**:2511.23007 指出句对冲突检测在不平衡数据上精度低,建议 Gold Standard 扩展时**刻意构造负样本比例**,并报 macro-F1。
6. **KG 增强 vs 向量增强对比**:2603.23954 提供了现成的对照实验设计——本项目可补做"纯向量检索 vs 知识图谱增强"在 GJB 需求依赖识别上的消融,强化图谱必要性论证。

### 10.3 论文定位建议
7. **差异化叙事**:学术界 Goal Model 抽取多面向 user story / 访谈(软需求);本项目面向**GJB 438C 格式化 SRS(数值参数 + 表格 + 跨章节引用)**,是更"硬"、更结构化的需求图谱构建场景——这是新颖性所在。
8. **明确澄清 QUARE/RENER**:若论文 related work 提及,须引用真实版本(Motger&Franch 综述 2401.12075 + PURE),**不要引用不存在的"QUARE/RENER 标注集"**,以免被审稿人质疑。

### 10.4 待核实/后续检索
9. Semantic Scholar API 本次持续 429 限流,部分 2024 目标模型抽取论文的作者/venue 未取全;建议后续用 API key 重跑 `aris-semantic-scholar` 补全引文元数据。
10. 若用户确实持有"QUARE/RENER 4000 句/30000 标注"数据集,请提供链接/DOI 以核实——否则按本报告以 PURE+PROMISE 为基准。
