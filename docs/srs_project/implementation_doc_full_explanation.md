## 一、第1章：场景背景与建设目标

### 1.1 业务背景（原文第5行）

文档首先确立 SRS 在武器装备科研生产中的地位：

> 软件需求规格说明是装备软件设计、开发、测试、定型验收的核心纲领性文件，直接决定后续软件研制的合规性、完整性与可追溯性。

然后陈述**两条问题链**：

**问题链1：传统人工编制模式的缺陷**
```
资料梳理繁琐 → 需求提取碎片化 → 跨文件参数冲突频发 → 国军标适配度低 → 人工校核成本高昂
```

**问题链2：通用大模型的不足**
```
缺乏军工垂域专业数据支撑
  → 专业幻觉（生成不符合领域常识的内容）
  → 条款缺失（需求条目不完整）
  → 规范不符（不符合国军标格式/内容要求）
  → 逻辑矛盾（生成的需求自相矛盾）
  → 无法满足军工型号软件正式交付要求
```

这两条问题链共同构成了本文档的存在理由：**既不能靠人工，也不能靠通用大模型，需要"垂域微调数据 + 四大核心技术"组合解决**。

### 1.2 建设目标（原文第7行）

文档明确提出"四个实现 + 一个产出 + 一个验证"：

| 维度 | 内容 |
|------|------|
| 实现1 | 科研数据快速归集治理 |
| 实现2 | 专家知识赋能增强 |
| 实现3 | 多层级一致性校验 |
| 实现4 | 全维度质量评估闭环 |
| 产出 | 适配军工SRS编制场景的专属微调数据集 |
| 验证 | 全面验证项目四大核心技术的工程落地适用性 |

⚠ **关键观察**：最后一句"验证四大核心技术的工程落地适用性"表明，本场景不仅是业务建设，也是**技术的工程验证场**。这意味着技术方案的成熟度、可部署性、可量化评测都是本场景的考核维度。

## 二、第2章：业务现状与需求分析

### 2.1 业务现存痛点（原文第13-21行，共5条）

| # | 痛点 | 根因 |
|:-:|------|------|
| 1 | 通用大模型（千问、Deepseek）垂域适配差 | 无定制化高质量微调数据 |
| 2 | 微调数据集构建无手段支撑 | 高度依赖人工，周期长成本高 |
| 3 | 数据知识化程度不足 | 样本仅为原始文本切片，未融入专家隐性经验 |
| 4 | **数据一致性缺失** | 多源资料参数存在隐性冲突，人工排查难全覆盖 |
| 5 | 数据质量无标准化评判依据 | 缺乏量化评估体系 |

**痛点4是本科研项目（方向A+方向B）的直接动因**：多源资料中软件功能、性能、接口、环境约束等参数存在隐性冲突，人工排查难以全覆盖，易导致生成文档逻辑矛盾。

### 2.2 整体功能需求（原文第25行）

文档用一句话定义了**闭环数据应用体系**：

```
数据构建 ──→ 专家知识赋能 ──→ 校验优化 ──→ 质量管控 ──→ 迭代演进
   ↑                                                              │
   └──────────────────────── 反馈回流 ──────────────────────────┘
```

四大核心能力对应四大研究内容：
1. 多源科研数据快速构建微调样本
2. 专家知识赋能数据结构化升级
3. 多层级跨维度数据一致性智能校验
4. 场景化数据质量量化评估

最终目标：支撑垂域大模型输出**合规、准确、完整、统一**的军工软件需求内容。

### 2.3 非功能需求（原文第29行）

四个维度的约束：

| 维度 | 要求 |
|------|------|
| 保密合规 | 涉密数据隔离、敏感内容筛查、全程日志审计 |
| 标准合规 | 国军标软件工程规范、军工文档编制标准 |
| 工程属性 | 高稳定性、可迭代性、可复用性，支持数据集持续更新 |
| 部署环境 | 适配军工内网，数据处理/模型微调/文档生成全程合规可控 |

## 三、第3章：场景化核心功能设计（四大技术详解）

本章是文档主体，逐一描述四大研究技术在本场景中的功能需求，并附带大量指令-输出样本示例。

### 3.1 技术一：科研生产领域微调数据集快速构建技术（原文第33-79行）

#### 目标
解决软件需求生成场景多源数据杂乱、样本构建低效问题，实现全流程自动化数据治理与样本生成。

#### 两项核心需求

**需求1：从上游顶层文件"由上至下生成需求"**

| 输入 | 输出 |
|------|------|
| 总体方案、作战任务文件、系统技术要求、接口规范、顶层研制要求 | 软件需求条目 |

样本示例（原文第45-55行）：

```
【指令】
某光电探测装备总体要求：
- 软件需要接收外部导航组件输出的位置、速度信息
- 支持在-40℃～+65℃工作温度下稳定解析导航数据
- 导航数据接收周期不大于100ms
- 数据发生校验错误时软件应当记录故障日志并维持原有导航输出，不触发整机复位
请依据上述总体约束，生成对应的软件需求规格条目。

【输出】
功能需求：软件能够接收外部导航组件下发的位置、速度信息并完成解析处理。
性能需求：导航数据接收处理周期≤100ms；软件在环境温度-40℃～+65℃范围内可正常完成导航数据解析。
可靠性与故障处理需求：当导航数据校验出现错误时，软件自动记录故障日志；
  软件保持上一周期有效导航信息持续输出，不引发整机软件复位。
```

**需求2：从历史成熟SRS教会模型输出符合制式规范的文档文本**

样本示例（原文第61-79行）：给定指令"编写外部接口需求章节"，输出包含6要素的标准化接口描述：
1. 接口名称
2. 接口类型
3. 输入数据
4. 输出数据
5. 通信周期
6. 约束条件

#### 样本格式特征
- **单轮 SFT 格式**：【指令】+【输出】
- 指令 = 场景化约束描述（自然语言）
- 输出 = 分条目标准化需求（功能/性能/可靠性分类）

### 3.2 技术二：专家经验驱动的微调数据知识化构建与自组织演进机制（原文第81-231行）

这是篇幅最大的技术章节。核心命题：**把专家脑中的隐性知识显性化，嵌入微调数据集**。

#### 8项功能要求（原文第89-115行）

| # | 功能 | 价值 |
|:-:|------|------|
| 1 | 补齐隐性知识 | 总体方案只给宏观指标，缺边界条件/异常处理/故障降级；专家补齐这些隐性约束 |
| 2 | 引导掌握"顶层→软件需求"的转化逻辑 | 不只是文本仿写，而是正向推演能力，面对新总体方案能合理拆解 |
| 3 | 提升需求完备性 | 依托检查清单与历史缺陷案例，覆盖易忽略的需求维度 |
| 4 | **强化逻辑校验能力** | 识别跨文档隐性矛盾，降低人工校核工作量 |
| 5 | 统一行文规范 | 约束模型规避模糊、口语化描述 |
| 6 | 建立需求可追溯思维 | 生成需求时自然建立与上层总体要求的关联 |
| 7 | 形成数据集自组织演进 | 业务试用中的错误→专家判别根因→转化为新增样本与约束规则→持续迭代 |
| 8 | 明确支持的专家经验类型 | 见下方6类 |

#### 6类专家经验（原文第119-165行）

这是本技术章节的核心内容，定义了专家经验的类型学：

**第1类：需求转化类专家经验**
- ① 顶层总体指标 → 软件功能/性能/接口需求的转换规则
- ② 作战任务描述、系统能力要求 → 细分软件需求条目的拆解方法
- ③ 硬件约束、机械边界、电气时序约束 → 软件限制条件的映射规则
- ④ 区分"系统级需求"与"软件专属需求"的判定准则

**第2类：需求完备性检查类专家经验**
- ① 国军标强制要求的需求条目检查清单（功能、性能、接口、可靠性、安全性、环境适应性、维护性、涉密安全等）
- ② 容易遗漏的边界工况、异常场景、故障降级、容错处理、极限工作条件
- ③ 多交联分系统之间容易缺失的交互时序、冲突避让需求

**第3类：需求一致性与冲突识别专家经验** ⭐（直接对应研究方向B）
- ① 同类技术指标在总体方案、接口文件、软件需求中常见矛盾形式
- ② 参数范围、通信周期、精度指标、响应时间容易出现前后不统一的典型情形
- ③ 功能互斥、资源竞争、时序冲突等隐性逻辑冲突识别经验

**第4类：文档规范与术语标准化经验**
- ① 标准章节划分、条目撰写范式、专业术语统一表述规范
- ② 禁止口语化、模糊化描述判定标准（如"尽快处理""适当优化"的识别与修正）
- ③ 需求可追溯链路构建规则

**第5类：工程评审与归零经验**
- ① 型号评审高频提出的需求缺陷、常见错漏问题库
- ② 以往测试暴露的因需求定义不清引发软件缺陷的典型案例
- ③ 需求定义模糊、边界不清晰导致后期变更的典型场景

**第6类：保密与合规管控经验**
- ① 涉密敏感参数识别、表述边界控制规则
- ② 满足装备软件安全性、信息保密要求必须补充的相关约束需求

#### 5个样本示例（原文第169-231行）

**示例1：顶层指标→软件需求转化**
```
【指令】某装备总体要求：系统收到目标捕获指令后，需在500ms内完成图像预处理与
目标初步识别；当图像信噪比低于阈值时，应当降低识别置信度门限，不直接剔除可疑目标。
请依据上述总体约束，提炼对应的标准化软件需求条目。

【输出】
①性能需求：处理时延≤500ms
②功能与容错需求：信噪比低于阈值时下调置信度门限，保留可疑目标
```

**示例2：需求完备性检查（补充边界/故障工况）**
```
【指令】现有软件需求仅描述正常工况下的数据接收功能，请补充对应的异常工况、故障处置类需求。

【输出】
① 通信链路短时中断：缓存近期有效数据，恢复后补齐缺失数据包
② 连续多次校验错误：记录故障时间、错误帧计数，输出链路异常状态标志，不触发重启
③ 接收数据越界：限幅保护并生成异常日志
```

**示例3：规范表述优化（消除模糊用语）**
```
【指令】将"软件收到指令后尽快完成数据处理"改写为可测试的标准化需求。

【输出】性能需求：响应时延≤200ms；时延指标可通过外部测试设备进行定量考核。
```

**示例4：冲突排查与修正** ⭐（方向B典型任务）
```
【指令】识别如下两段需求存在的矛盾并给出修正方案：
① 软件周期200ms向外输出状态数据
② 紧急模式下状态数据输出周期调整为50ms
③ 软件仅支持固定200ms发送周期

【输出】
冲突点：需求③固定200ms vs 需求②紧急模式50ms 存在逻辑矛盾。
修正方案二选一：
  方案1：删除紧急模式50ms输出周期要求
  方案2：修改基础约束，支持软件根据工作模式动态切换50ms/200ms两种输出周期
```

**示例5：需求溯源构建**
```
【指令】基于"装备需具备全天候目标探测能力"这条系统级总体要求，
生成对应的软件需求，并建立溯源关联描述。

【输出】
溯源来源：系统总体要求——装备具备全天候目标探测能力。
软件功能需求：软件支持白天可见光通道、夜间红外通道数据融合处理，
  依据光照条件自动切换成像处理算法，保障全天候目标探测功能可用。
```

#### 本技术小结
专家经验知识化的本质是**将人脑中的隐性工程经验转化为可计算、可注入、可迭代的显性知识**，覆盖"转化规则、完备性检查、冲突识别、规范术语、评审归零、保密合规"六个维度。

### 3.3 技术三：面向武器装备科研数据的多层级跨模态一致性校验技术（原文第233-423行）

**这是全文最核心、篇幅最大的章节**，也是与本科研项目（方向A+方向B）最直接对应的部分。

#### 总体定位（原文第239行）

文档用一段长文定义了本技术的总体定位，包含5个要点：

1. **四层校验体系**：术语层级 + 参数指标层级 + 业务逻辑层级 + 国军标合规层级
2. **量化要求**：给出4个指标的合格率（每层一个合格率指标）
3. **跨文档跨资料比对**：精准识别功能定义矛盾、接口参数冲突、性能指标不一致、需求条款缺失、标准引用错误
4. **闭环回流**：异常/冲突/可疑样本自动标记、分类归档、人工复核修正，结果回流至数据清洗治理环节
5. **三重角色**：本技术兼作
   - 数据质量审校规则
   - 负样本构造规则
   - 问答对过滤标准

**四大作用**：
- ① 过滤低质、存在需求矛盾、不合规的原始问答对
- ② 构造正样本（规范、自洽、满足四层一致性）
- ③ 构造困难负样本（存在术语冲突、指标矛盾、逻辑漏洞、国军标缺陷）
- ④ 引导模型生成自洽、无冲突、符合军工规范的软件需求规格说明书

#### 四层校验体系总览

| 层级 | 核心目标 | 子检查数 | 占比 |
|:----:|---------|:---:|:---:|
| 1. 术语层级 | 统一实体命名、概念定义、枚举集合 | 8 | 20% |
| 2. 参数指标层级 | 保证量化指标在多模态载体间无冲突 | 10 | 25% |
| 3. 业务逻辑层级 | 验证功能流程、事件触发、模式切换在多模态中自洽 | 11 | 27.5% |
| 4. 国军标合规层级 | 对照GJB标准校验需求条目规范度与完备性 | 11 | 27.5% |
| **合计** | | **40** | 100% |

#### 层级1：术语层级跨模态一致性校验（原文第241-277行）

**核心目标**：统一全部模态载体中的实体命名、概念定义、枚举集合，消除同义异名、同名异义、概念边界冲突。这是所有校验的基础。

**8项子检查**：

| # | 子检查 | 示例 | 冲突类型 |
|:-:|------|------|:------:|
| ① | 同义异名校验 | 文本"目标捕捉指令" vs 框图"目标捕获指令" | 命名不一致 |
| ② | 同名异义校验 | "安全模式"一处指电源低压保护，一处指跟踪丢失降级 | 概念歧义 |
| ③ | 枚举集合一致性 | 文本3种工作模式 vs 状态迁移图2种模式 | 枚举缺失 |
| ④ | 状态/告警术语统一 | 文本"通信异常告警" vs 接口字段"链路故障标志" | 术语不统一 |
| ⑤ | 指令名称全局一致性 | 顶层"复位指令" vs 模块"软复位/整机复位"未区分 | 术语模糊 |
| ⑥ | 量纲单位一致性 | 0.2秒 vs 200ms（等效，不冲突）；≤0.2s vs ≤20ms（冲突） | 单位换算冲突 |
| ⑦ | 信号接口命名一致性 | 框图"导航信息输入接口" vs SRS"导航数据接收端口" | 命名不统一 |
| ⑧ | 缩写代号一致性 | 全文Conf vs 部分段落CF/置信系数 | 缩写不规范 |

**关键区分**：第⑥项特别强调"数值等效不冲突"与"数值冲突"的区别——这是语义层校验的精髓，不能简单字符串匹配。

#### 层级2：参数指标层级跨模态一致性校验（原文第279-323行）

**核心目标**：保证时延、精度、阈值、周期、资源上限、值域范围等所有量化指标，在文本需求、时序图、接口表、仿真参数、测试指标之间无冲突、无丢失、无放宽。

**10项子检查**：

| # | 子检查 | 示例冲突 | 模态载体 |
|:-:|------|---------|---------|
| ① | 时间约束跨模态冲突 | 文本≤200ms vs 时序图300ms | 文本↔时序图 |
| ② | 周期参数一致性 | 功能需求固定200ms vs 场景描述"繁忙时可延长" | 文本↔文本 |
| ③ | 阈值边界一致性 | 文本有阈值 vs 数据字典缺下限 | 文本↔数据字典 |
| ④ | 多源融合时间对齐 | 需求≤10ms vs 仿真配置20ms | 文本↔仿真 |
| ⑤ | 资源占用指标 | 可靠性≤50% vs 架构设计60% | 文本↔架构文档 |
| ⑥ | 参数值域范围 | 接口0~1200m/s vs 报文体最大800m/s | 接口表↔报文结构 |
| ⑦ | 存储容量与保存时长 | 需求30天 vs 存储方案15天 | 文本↔配置表 |
| ⑧ | 同步守时精度 | 需求≤100ms/h vs 时钟模块≤200ms/h | 文本↔设计文档 |
| ⑨ | 降级触发阈值 | 文本<10% vs 配置表5% | 文本↔配置表 |
| ⑩ | 故障判定持续时长 | 需求5s vs 流程图3s | 文本↔流程图 |

**三类问题模式**：
- **冲突**：同一指标在不同载体中数值不同（①④⑤⑥⑦⑧⑨⑩）
- **丢失**：某载体缺失某指标定义（③）
- **放宽**：下层指标比上层约束更宽松（⑧——顶层约束被放宽）

#### 层级3：业务逻辑层级跨模态一致性校验（原文第325-373行）

**核心目标**：验证功能流程、事件触发关系、模式切换规则、异常处置策略、数据流走向、权限互斥逻辑，在文字描述、流程图、状态机、时序模型中保持自洽。

**11项子检查**：

| # | 子检查 | 示例冲突 | 涉及模态 |
|:-:|------|---------|---------|
| ① | 模式切换优先级逻辑 | 应急指令最高优先级 vs 状态机允许自动模式夺回控制权 | 文本↔状态机 |
| ② | 异常处置策略一致性 | 单路异常剔除数据继续融合 vs 流程图任意异常停止融合 | 文本↔流程图 |
| ③ | 事件时序逻辑 | 文本：采集→处理→输出→日志 vs 流程图：输出→日志→采集 | 文本↔流程图 |
| ④ | 数据流流向一致性 | 框图单向输入 vs 文本提及软件向导航输出校正指令 | 框图↔文本 |
| ⑤ | 工况分支完备性 | 需求覆盖3类场景 vs 流程图缺长期链路失效分支 | 文本↔流程图 |
| ⑥ | 互斥控制逻辑 | 人工控制时禁止自动 vs 模型允许两路并行 | 文本↔模型 |
| ⑦ | 任务切换原子性 | 需求失败自动回滚 vs 流程未设计回滚分支 | 文本↔流程 |
| ⑧ | 数据冗余仲裁逻辑 | 双路不一致选用有效通道 vs 模型直接用通道A | 文本↔模型 |
| ⑨ | 权限访问控制逻辑 | 普通操作员无法修改校准参数 vs 界面流程允许普通用户进入校准页 | 文本↔界面流程图 |

**本层特征**：所有检查都是**文本描述 vs 图/模型**的跨模态比对，需要先理解图的语义才能判断一致性。这正是方向A（多模态上下文聚合）要解决的前置问题。

#### 层级4：国军标合规层级跨模态一致性校验（原文第375-423行）

**核心目标**：对照国军标软件需求相关标准（GJB 841、GJB 2438、GJB 438C等），校验需求条目规范度、安全性、可测试性、文档要素、可靠性条款完备性；同时保证文字需求、模型、接口定义在合规要求上统一。

**11项子检查**：

| # | 子检查 | 不合规示例 | 对应标准要求 |
|:-:|------|---------|------------|
| ① | 可测试性合规 | "软件运行稳定"（模糊需求） | GJB 438C可测试性 |
| ② | 故障容错需求完备性 | 仅描述正常工况，缺异常/通信/存储故障容错 | 可靠性需求规范 |
| ③ | 安全访问控制合规 | 未划分操作权限等级、无越权拦截 | 软件安全性国军标 |
| ④ | 审计日志合规 | 仅记录告警，缺关键操作/参数修改/权限变更审计 | 审计追溯合规 |
| ⑤ | 需求可追溯性合规 | 多条需求无法溯源至系统总体要求（"无根需求"） | 需求追溯管理 |
| ⑥ | 异常报警要素合规 | 告警缺时间戳/故障位置/故障等级/处置建议 | 告警标准规范 |
| ⑦ | 软件自检条款合规 | 缺上电启动自检、周期运行自检 | 嵌入式可靠性通用要求 |
| ⑧ | 掉电数据保护合规 | 无关键配置/任务状态掉电保存需求 | 装备持续工作合规 |
| ⑨ | 输入数据防护合规 | 未定义非法报文/越界参数/畸形输入拦截 | 输入安全防护 |
| ⑩ | 版本升级安全合规 | 升级流程缺升级包校验、失败自动回滚 | 软件维护性要求 |
| ⑪ | 降级运行合规 | 故障场景仅停机保护，无分级降级策略 | 连续工作可靠性规范 |

**本层特征**：与前3层不同，合规层不是"两个载体之间的冲突"，而是"内容 vs 标准要求"的缺失检测。本质是**完备性检查**——检查需求是否覆盖了国军标强制要求的条款。

#### 40项校验的类型学分析

从检测方法角度，40项校验可归纳为4种检测模式：

| 检测模式 | 含义 | 涉及子检查 | 占比 |
|---------|------|---------|:---:|
| 跨载体冲突检测 | 同一实体/指标在不同载体中值或定义不一致 | 术语①②④⑤⑦⑧、参数①②④⑤⑥⑦⑧⑨⑩、逻辑①②③④⑥⑦⑧⑨⑩⑪ | 60% |
| 跨载体缺失检测 | 某载体缺少其他载体已有的元素 | 术语③、参数③、逻辑⑤ | 7.5% |
| 内容合规检测 | 内容是否符合国军标条款要求 | 合规①-⑪全部 | 27.5% |
| 语义等价判定 | 数值/表述不同但语义等价（非冲突） | 术语⑥ | 2.5% |
| 模糊表述检测 | 表述不可测试、不可量化 | 合规① | 2.5% |

**关键洞察**：60%的检查是"跨载体冲突检测"，这要求系统必须先完成**多模态上下文聚合**（方向A），把同一实体在不同载体中的表述聚集到一起，才能进行比对。**方向A是方向B的前置条件**。

### 3.4 技术四：面向科研生产领域微调数据集的质量评估（原文第425-465行）

#### 三大类指标体系

文档定义了3个维度、9个二级指标的质量评估体系：

#### 维度1：输入-输出语义对齐质量（防答非所问）

**目标**：防止模型脱离input原始需求素材，凭空编造需求、遗漏原始约束。

| 二级指标 | 指标说明 | 计算方式 |
|---------|---------|---------|
| 需求约束召回率 | 原始input中所有功能、指标、模式约束，在output中全部被覆盖的样本占比 | 约束完整召回样本/有效样本 |
| 无约束虚构需求占比 | output出现input不存在的新增功能、指标、接口等虚构需求的样本占比 | 虚构样本/有效样本 |
| 指令遵从率 | output符合instruction指定任务（生成SRS/一致性缺陷评审），不跑偏任务类型 | 遵从指令样本/有效样本 |

#### 维度2：军工软件需求工程规范质量（领域适配指标）

**目标**：聚焦SRS撰写工程规范，适配GJB 438C、GJB 841装备软件工程要求。

| 二级指标 | 指标说明 | 计算方式 |
|---------|---------|---------|
| 需求可测试性占比 | output生成需求不含"稳定、可靠"等模糊描述，具备量化判定条件 | 可测试需求样本/总需求条目 |
| 需求可追溯完备率 | 软件需求能够向上关联系统顶层约束，无孤立无根需求样本占比 | 具备追溯关系样本/有效样本 |
| 非功能需求覆盖率 | 包含可靠性、安全性、日志审计、故障降级、权限管控等非功能需求样本占比 | 覆盖非功能需求样本/有效样本 |

#### 维度3：任务多样性与样本均衡指标（防数据集偏置）

**目标**：避免数据集全部为简单正向样本，缺少冲突评审、故障场景、边界工况。

| 二级指标 | 指标说明 | 计算方式 |
|---------|---------|---------|
| 任务类型均衡度 | 正向SRS生成样本、缺陷一致性评审样本比例偏离预设配比程度；**理想配比：生成类60%，评审类40%** | 各类样本数量标准差统计 |
| 缺陷类型分布均衡度 | 缺陷样本内部：术语缺陷、参数指标缺陷、业务逻辑缺陷、合规缺陷四类样本数量分布均衡程度 | 各类缺陷样本计数 |
| 工况场景覆盖率 | 覆盖正常工况、通信故障、存储异常、模式切换、降级运行等典型装备场景样本占比 | 覆盖多场景样本/总样本 |

#### 质量评估体系特征
- **9个指标全部可量化**，有明确计算方式
- 覆盖**样本级**（语义对齐）、**内容级**（领域规范）、**数据集级**（任务均衡）三个层次
- 明确给出**理想配比**（生成类60%/评审类40%），为数据集构造提供量化目标
- 缺陷类型分布与四层校验体系（术语/参数/逻辑/合规）一一对应

### 4.2 样本格式标准化

文档所有示例统一采用**单轮SFT格式**：

```
【指令】<场景化约束描述，自然语言>
【输出】<分条目标准化需求，分类列举>
```

这种格式的设计意图：
- 指令端包含**多类型约束**（功能、性能、环境、故障处理），模拟真实总体方案
- 输出端**分类列举**（功能需求/性能需求/可靠性需求），符合SRS制式
- 强调**约束召回**（output必须覆盖input所有约束）和**零虚构**（output不能有input没有的内容）

### 4.3 "跨模态"的真正含义

文档标题强调"跨模态一致性校验"，这里的"模态"指：

| 模态载体 | 在SRS文档中的形式 |
|---------|-----------------|
| 自然语言文本 | 章节正文、需求条目 |
| 表格 | 接口表、参数表、配置表、数据字典 |
| 流程图 | 业务流程图、异常处置流程 |
| 状态机/状态迁移图 | 模式切换图 |
| 时序图 | 接口时序、事件时序 |
| 框图 | 系统框图、数据流框图 |
| 行为模型 | 仿真模型、架构设计文档 |
| 界面流程图 | 交互流程 |

**跨模态校验的本质**：同一实体/指标/逻辑在不同模态载体中的表述是否一致。这要求校验系统具备**多模态理解能力**——能解析图、表、文本，并在语义层面比对。

### 4.4 "一致性"的三种问题形态

从40项子检查中归纳，"不一致"有三种表现：

| 问题形态 | 含义 | 典型示例 | 检测难度 |
|---------|------|---------|:------:|
| 冲突 | 同一事物在不同位置有矛盾的定义/数值 | 文本≤200ms vs 时序图300ms | 中（需跨载体比对） |
| 缺失 | 某位置缺少应有的事物 | 文本3种模式 vs 状态图2种模式 | 中（需完备性判断） |
| 放宽 | 下层指标比上层约束更宽松 | 需求≤100ms/h vs 设计≤200ms/h | 高（需理解层级关系） |

### 4.5 校验与负样本构造的双重角色

文档明确要求技术三兼作**负样本构造规则**（原文第239行）。这意味着：

- **正样本**：规范、自洽、满足四层一致性的问答对
- **困难负样本**：存在术语冲突、指标矛盾、逻辑漏洞、国军标缺陷的问答对
- **过滤规则**：用四层校验过滤掉低质、矛盾、不合规的原始问答对

这是一种**自举式数据增强**思路：用校验技术既保证数据质量，又构造训练信号（负样本），一举两得。

文档中提到的8种模态载体（文本/表格/流程图/状态机/时序图/框图/行为模型/界面流程图）定义了方向A需要处理的**模态空间**。

### 5.5 对Gold Standard构建的启示

文档要求"给出4个指标的合格率"（每层一个），意味着：
- Gold Standard需要覆盖四层，每层有独立的评测指标
