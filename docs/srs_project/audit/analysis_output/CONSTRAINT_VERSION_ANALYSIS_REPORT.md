## 二、真实矛盾清单(附原文)

### 2.1 约束层面的真实矛盾(共1处)

**【矛盾#1】02界面集成文档:首屏加载时间/用户响应时间跨子章节不一致**

```
doc#1  02界面集成框架软件需求规格说明-终稿
  参数: 支持首屏加载时间  (单位:秒)
    sec=1.8.2.1    ≥ 2.0   原文: "支持首屏加载时间不小于2秒,用户响应时间不小于3秒。"
    sec=1.8.3.2    ≥ 2.0   原文: 同上(重复出现)

    sec=1.8.5.2    ≥ 3.0   原文: 同上

    sec=1.8.3.2    ≥ 3.0

### 2.3 数据录入错误(原始文档错误,非提取错误)

**【录入错误#1】CPU主频单位错误**
```

## 三、"合理差异"的分类与判断标准

### 3.1 合理差异的4种类型

| 类型 | 示例 | 出现次数 | 判断依据 |
|------|------|----------|----------|
| **A. 多档硬件配置共存** | CPU≥1.5GHz(16核)/≥2.0GHz(i7四核)/≥2.5GHz(i7双核)/≥1.2GHz(四核)/≥2.2GHz(4核) | 38组(占"冗余"100%) | 同一表格内不同行对应不同设备形态 |
| **B. 不同产品线的版本差异** | 银河麒麟V5(云平台) vs V10(操作系统) | ~5处 | 软件名相同但产品定位不同 |
| **C. 运行环境vs部署环境的格式性重复** | 3.9.1节与3.10.1节的硬件配置表完全一致 | 63组(占跨章节重复83%) | GJB 438C格式要求3.9和3.10都列硬件 |
| **D. 不同设备形态的容量差异** | 桌面版支持≥1000个服务注册;平板版≥200;手持版≥100 | 用例动作约束列(未提取) | 原文明确标注设备形态 |

### 3.2 区分"合理差异"与"真实矛盾"的判断标准

**5条判别规则**(按优先级):

1. **同表多行 = 合理差异**: 若多条约束来自同一表格的连续行,且每行对应不同设备形态/配置档位 → 合理差异(类型A)
2. **章节语义不同 = 合理差异**: 3.9(运行环境)与3.10(部署环境)的相同约束 → 格式性重复(类型C)
3. **产品名限定 = 合理差异**: "银河麒麟云平台V5"与"银河麒麟操作系统V10" → 不同产品(类型B)
4. **设备形态限定词 = 合理差异**: 原文含"桌面版/平板版/手持版/便携式/服务器"等限定词 → 合理差异(类型D)
5. **无限定词的同章节跨节冲突 = 真实矛盾**: 如02界面的1.8.2 vs 1.8.5首屏加载时间,无设备形态限定 → 真实矛盾

**关键洞察**: 当前763条约束中,**真正可能成为"真实矛盾"的检测对象只有约5-10条**(§2.1的1处 + 版本矛盾的6处),其余95%以上是合理差异或格式性重复。这意味着**不一致性检测的Precision面临严峻挑战** — 如果不能先识别"合理差异",会产出大量误报。

## 四、约束提取质量问题

### 4.1 质量问题汇总

| 问题类型 | 数量 | 占比(相对763) | 严重性 |
|----------|------|---------------|--------|
| **参数名含HTML标签残留** | 370 | 48.5% | 严重 |
| **参数名含标点/序号残留** | 589 | 77.2% | 严重 |
| **同section内重复提取** | 149组 | 19.5% | 中等 |
| **单位丢失(原文有单位)** | 128 | 16.8% | 严重 |
| **泛化参数名(配置/存储/内存)** | 5 | 0.7% | 低 |
| **短参数名(≤2字)** | 7 | 0.9% | 低 |
| **非数值约束值** | 0 | 0% | — |

### 4.2 参数名提取灾难(48.5%含HTML残留)

**典型错误**:
```
param = "p><p>内存："       ← 应为 "内存"
param = "p><p>存储："       ← 应为 "存储"
param = "p>CPU主频："       ← 应为 "CPU主频"
param = "p>显示分辨率："    ← 应为 "显示分辨率"
param = "><li>内存："       ← 应为 "内存"
param = "；⑥网络适配器："   ← 应为 "网络适配器"
param = "口（含光模块），"  ← 应为 "万兆光口"
```

**根因**: 约束提取器(正则)在HTML片段上直接匹配"参数名+操作符+值",未先清洗HTML标签。`<p>内存：不小于16GB</p>` 被切成 `p><p>内存：` + `不小于` + `16` + `GB`。

**影响**: 这直接导致§2的跨章节一致性分析失效 — 同一参数"内存"被拆成`p><p>内存：`、`><li>内存：`、`配置`等多个不同的param名,**真正的同参数跨章节冲突被掩盖**。

### 4.3 单位丢失问题(128条)

**典型错误**:
```
param=进行标准转换速度  val=2000  unit=''   ← 原文"2000条/秒",单位"条/秒"丢失
param=总核数            val=128   unit=''   ← 原文"128核",单位"核"丢失
param=分辨率            val=1920  unit=''   ← 原文"1920*1080",单位丢失
param=最大交换容量      val=1.2   unit=''   ← 原文"1.2Tbps",单位"Tbps"丢失
```

**根因**: 提取器的单位正则只覆盖了`GB/GHz/MB/ms`等常见单位,**未覆盖复合单位(条/秒、帧/秒、Tbps、Mbps)和非标准单位(核、台、颗、路)**。

### 4.4 同section内"重复"提取(149组,但多为假阳性)

149组"重复"中,绝大多数是**同一表格内不同设备形态的多档配置**,因param名过泛(`内存：`/`存储：`)而碰撞:
- `p><p>内存： val=8.0` 在sec=1.16.1出现3次 → 实际是i7四核/i7双核/4核三个不同设备都要求8GB
- 真正的重复提取(同一原文片段被切两次)只有约10-15组,如`进行标准转换速度`在3.2.3.1被提取2次(HTML片段边界不同)

### 4.5 用例表格"动作约束"列大量遗漏(**最严重**)

这是本次分析发现的最严重问题:

```
419个用例描述表
  → 237个"动作约束"列非空
    → 59个含数值约束
      → 仅15个被提取到all_constraints  (提取率 25.4%)
      → 44个被完全遗漏                  (遗漏率 74.6%)
```

**遗漏的典型约束**:
```
"获取的数据资源不少于19种"              ← 未提取
"支持同时集成的界面组件数量不少于80个"  ← 未提取
"基于2个键值组合的快捷键种类不少于36种" ← 未提取
"桌面版支持不少于1000个服务的注册;平板版200;手持版100" ← 未提取(且含合理差异)
"系统对服务异常状态检测时间不大于10秒"  ← 未提取
```

**根因**: 用例描述表是合并单元格的伪结构化表,headers只有`['Use Case名称','Actors']`,真正的"动作约束"列在第3-4行才出现,提取器只看headers未扫描数据行定位列。

**影响**: 这批遗漏的约束恰好是**最真实的"功能行为约束"**(区别于3.9/3.10的硬件配置),是方向B(不一致性校验)最该检测的对象。

## 五、逻辑约束可行性分析

### 5.1 Z3可检测的范围

**检测结果**: 0个逻辑冲突(形式为 `A≥v1 且 A≤v2 且 v1>v2`)

**原因分析**:
1. **操作符极度偏斜**: 94.8%是`≥`,只有5.2%是`≤`,几乎没有"上下界同时存在"的参数
2. **`=`约束完全缺失**: 没有精确等式,Z3的等式推理无用武之地
3. **串行约束未提取**: SRS中"各子模块时间之和≤总预算"这类约束以自然语言描述,未结构化为可求解形式

**Z3能检测到的**:
- 同参数(同单位)的 `≥v1 且 ≤v2 且 v1>v2` — 但本数据集0个
- 同参数的 `=v1 且 =v2 且 v1≠v2` — 但本数据集0个`=`约束

**Z3不能检测到的**:
- 单位不一致的矛盾(2.2Hz vs 2.2GHz)
- 合理差异vs真实矛盾(需语义判断)
- 跨参数的逻辑关系(子模块时间和≤总预算,需先建立参数间依赖)
- 自然语言描述的隐式约束(用例表动作约束列)

### 5.2 同参数同操作符不同值(38组,全部为合理差异)

这38组中:
- **36组是硬件配置多档位**(CPU/内存/存储的不同设备形态) — 合理差异类型A
- **2组是首屏加载时间**(§2.1的真实矛盾) — 真实矛盾

**关键**: 单纯的"同参数不同值"规则会产生 **36/38 = 94.7%的假阳性**。必须结合§3.2的判别规则才能区分。

### 5.3 逻辑层矛盾的真正难点

SRS中的逻辑矛盾不是"显式约束冲突",而是**隐式依赖未满足**:

| 隐式矛盾类型 | 示例 | 检测难度 |
|--------------|------|----------|
| 单位错误 | 2.2Hz的CPU(应为GHz) | 需领域知识 |
| 合理差异误判 | 多档配置被当矛盾 | 需结构识别 |
| 跨参数依赖 | 子模块时间和≤总预算 | 需建立参数依赖图 |
| 版本一致性 | 同软件不同章节版本不同 | 需归一化+语义判断 |
| 自然语言约束 | "动作约束"列未被提取 | 需表格列定位 |

## 六、约束作为检测对象的难点与建议

### 6.1 四大核心难点

**难点1: 参数名提取不可靠**
- 48.5%含HTML残留,77.2%含标点残留
- 同一参数"内存"有5种不同param名(`p><p>内存：`/`><li>内存：`/`配置`/`内存`/`内存槽`)
- 正则提取的F1估计<0.5,LLM提取可能更好但成本高

**难点2: "合理差异"占主导(>95%)**
- 真实矛盾仅5-10条,合理差异+格式重复占95%+
- 不能直接"同参数不同值=矛盾",会产出海量误报
- 必须先做"合理差异识别"才能做"矛盾检测"

**难点3: 约束分布极度偏斜**
- 82.7%是硬件配置(3.9/3.10),只有7%是功能约束(3.2)
- 真正有检测价值的功能约束大量遗漏在用例表"动作约束"列(74.6%遗漏)
- 当前763条约束中,真正有检测价值的可能不到50条

**难点4: 单位异构**
- 31%约束无单位,其中又有128条原文实际有单位
- 不同单位(ms/s, KB/MB, Hz/GHz)的约束无法直接比较
- "2.2Hz"这种录入错误需要领域知识识别

### 6.2 对方向A(上下文关联)的建议

1. **先清洗param名**: 用LLM或规则清洗HTML/标点残留,将`p><p>内存：`统一为`内存`,这是所有后续分析的前提
2. **建立"设备形态"维度**: 同一表格内的多行约束,应聚合为"一个参数×多个设备形态"的结构,而非扁平的多条约束
3. **关联3.9与3.10**: GJB格式要求3.9(运行环境)与3.10(部署环境)列相同硬件,应识别为"同一实体的格式性重复",不重复检测
4. **提取用例表动作约束列**: 这是当前最大的遗漏,需扫描表格数据行定位"动作约束"列

### 6.3 对方向B(不一致性校验)的建议

1. **分层检测策略**:
   - **L1语法层**: param名HTML残留、单位丢失、同section重复 → 可用规则自动检测
   - **L2语义层**: 同参数跨章节值不一致、版本号归一化冲突 → 需结合§3.2的5条判别规则
   - **L3逻辑层**: Z3可检测显式矛盾(本数据集0个),自然语言隐式约束需NLI/LLM

2. **优先检测版本号矛盾**: 版本号归一化简单(V前缀去除+大小写统一),冲突判定明确,本数据集有6处真实矛盾,是性价比最高的检测对象

3. **不要过度依赖Z3**: 本数据集的矛盾几乎都不是显式逻辑矛盾,Z3能做的很有限。更适合的是**基于规则+LLM的混合检测**:
   - 规则: 同参数跨章节值对比、版本号归一化对比
   - LLM: 判断"合理差异vs真实矛盾"(用§3.2的5条规则作为prompt)

4. **Gold Standard构建重点**: 真实矛盾稀缺(5-10条),建议:
