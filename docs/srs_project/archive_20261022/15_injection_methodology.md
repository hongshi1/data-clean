## 二、注入方法详解

### 2.1 术语层（8项）

#### TERM-01 同义异名 ✅ 可信

**注入方式**：从功能名中找到同义词映射（如"获取"→"采集"），在位置A保留原始名称，位置B替换为同义词。

**数据来源**：Pair Dataset的func_names（913个功能名实体）

**示例**：
```
原始：界面监控功能
注入：界面监测功能（监控→监测）
位置A(table): 界面监控功能
位置B(text): 界面监测功能
```

**可信度**：✅ 高。同义词替换是确定性的字符操作，注入值与原始值确实不同，LLM能检测到。

---

#### TERM-02 同名异义 ❌ 不可信

**注入方式**：同一名称在位置A定义为概念X，位置B定义为概念Y。

**当前实现**：
```python
defs = ["低功耗运行模式", "故障保护模式", "数据加密模式", "维护诊断模式"]
d1, d2 = rng.sample(defs, 2)
# original = name, injected = name (完全相同！)
# extra = {"def_a": d1, "def_b": d2}
```

**问题**：original和injected**完全相同**——都是功能名本身。定义差异放在extra字段中，但这个字段不会呈现给检测器/LLM。occurrences中所有位置的content都是同一个名称，无法检测到不一致。

**应该怎么做**：需要在occurrences中显示不同位置的definition字段：
```
位置A(table): name="安全模式", definition="低功耗运行模式"
位置B(text): name="安全模式", definition="故障保护模式"
```

**可信度**：❌ 低。当前实现完全无效。

---

#### TERM-03 枚举集合 ✅ 可信

**注入方式**：从VLM流程图提取的nodes列表中删除最后一个元素。

**示例**：
```
原始：["手动模式", "自动模式", "应急模式"]
注入：["手动模式", "自动模式"]  (删除"应急模式")
位置A(text): 支持3种模式
位置B(image/flowchart): 只有2个节点
```

**可信度**：✅ 高。集合差异可检测。

---

#### TERM-04 状态告警术语 ⚠️ 部分可信

**注入方式**：从功能名中找到告警术语（如"告警"→"警示"），替换。

**问题**：映射表只覆盖了有限的关键词，很多功能名中没有告警相关词汇。

**可信度**：⚠️ 中。映射表需要扩大。

---

#### TERM-05 指令名称 ⚠️ 数据不足

**注入方式**：从功能名中找到指令动词（如"启动"→"开启"），替换。

**问题**：只生成了1条，因为大部分功能名不包含指令动词。

**可信度**：⚠️ 低。需要从接口表中提取专门的指令名称。

---

#### TERM-06 量纲单位 ❌ 未实现

**注入方式**：位置A"≤0.2s"，位置B"≤20ms"（冲突，非等效）。

**问题**：需要数值参数（带单位），但numeric_param类型的entity只有3个，且其中没有带"秒/ms"单位的。

**应该怎么做**：从chunks中按PARAM_PATTERNS的time类型提取数值参数（有28个），然后做单位替换。

**可信度**：❌ 未实现。但设计方案是正确的——区分"等效不冲突"（0.2秒=200ms→正例）和"冲突"（≤0.2s vs ≤20ms→负例）。

---

#### TERM-07 信号接口命名 ❌ 未实现

**注入方式**：同一接口在位置A叫"数据传输接口"，位置B叫"数据传送接口"。

**问题**：interface类型的entities有159个，但IFACE_MAP的关键词（"接口"→"通道"等）在接口名中没有匹配到。

**应该怎么做**：扩大映射表，或直接对接口名做字符替换。

**可信度**：❌ 未实现。

---

#### TERM-08 缩写代号 ✅ 可信

**注入方式**：取功能名前4字的unicode编码生成缩写。

**示例**：
```
原始：结构化数据归集
注入：BDBBDABDDDBBE5BDBE (unicode十六进制)
```

**问题**：缩写不是真正的拼音缩写（如"SDG"），而是unicode编码，不够真实。

**可信度**：⚠️ 中。注入值与原始值确实不同，但缩写方式不够真实。

### 2.2 参数层（10项）— ❌ Z3 gate有bug

#### 注入方式

```python
# 当前实现
val = p["val"]  # 从chunks提取的真实数值
injected_val = val * 2 if rng.random() > 0.5 else val * 0.5
conflict_op = {"ge": "lt", "le": "gt", "gt": "le", "lt": "ge"}.get(op, "lt")
constraints_b = [(conflict_op, injected_val)]
z3_ok = z3_gate(ptype, constraints_a, constraints_b)
```

#### Z3 gate的bug

**问题**：注入值方向和操作符方向不匹配，导致约50%的Z3验证不通过。

| 原始操作符 | 原始约束 | conflict_op | 注入值方向 | Z3结果 | 原因 |
|:---:|---|:---:|---|:---:|------|
| ge(≥) | x≥256 | lt(<) | val*0.5=128 | ✅ unsat | x≥256且x<128→矛盾 |
| ge(≥) | x≥256 | lt(<) | val*2=512 | ❌ sat | x≥256且x<512→x=300可满足 |
| le(≤) | x≤6 | gt(>) | val*2=12 | ✅ unsat | x≤6且x>12→矛盾 |
| le(≤) | x≤6 | gt(>) | val*0.5=3 | ❌ sat | x≤6且x>3→x=4可满足 |
| gt(>) | x>6 | le(≤) | val*0.5=3 | ✅ unsat | x>6且x≤3→矛盾 |
| gt(>) | x>6 | le(≤) | val*2=12 | ❌ sat | x>6且x≤12→x=8可满足 |
| lt(<) | x<1 | ge(≥) | val*2=2 | ✅ unsat | x<1且x≥2→矛盾 |
| lt(<) | x<1 | ge(≥) | val*0.5=0.5 | ❌ sat | x<1且x≥0.5→x=0.7可满足 |

**修复方案**：根据操作符方向选择注入值方向：
- ge/gt（≥/>）→ 注入值必须更小（val*0.5）
- le/lt（≤/<）→ 注入值必须更大（val*2）

#### 当前Z3验证统计

```
Z3验证通过: 6/35条 (17%)
Z3验证失败: 29/35条 (83%)
```

**83%的Z3验证不通过**——这意味着大部分参数注入的"矛盾"不是真正的矛盾，Z3认为约束可满足。

**可信度**：❌ 低。Z3 gate没有真正发挥验证作用。

---

### 2.3 逻辑层（11项）— ⚠️ 部分可信

#### LOGIC-01~05 基于VLM数据 ✅ 可信

| 项 | 数据来源 | 注入方式 | 可信度 |
|---|---|---|:---:|
| LOGIC-01模式切换 | VLM流程图branches | "应急最高" vs "自动可夺回" | ✅ |
| LOGIC-02异常处置 | VLM流程图nodes | "切换备用" vs "重试3次" | ✅ |
| LOGIC-03事件时序 | VLM流程图nodes | 交换前两个节点 | ✅ |
| LOGIC-04数据流 | VLM流程图data_flow_direction | "双向" vs "单向" | ✅ |
| LOGIC-05工况分支 | VLM流程图branches | 删除最后一个分支 | ✅ |

**可信度**：✅ 高。基于真实的VLM提取数据，注入方式合理。

---

#### LOGIC-06~11 硬编码 ❌ 不可信

| 项 | 注入方式 | 问题 |
|---|---|---|
| LOGIC-06互斥控制 | 硬编码"A和B互斥" vs "A和B并行" | 不是从真实文档提取的 |
| LOGIC-07任务切换原子性 | 硬编码"不可中断" vs "可中断" | 同上 |
| LOGIC-08数据冗余仲裁 | 硬编码"主用优先" vs "备用优先" | 同上 |
| LOGIC-09权限访问控制 | 硬编码"仅管理员" vs "普通用户可进入" | 同上 |
| LOGIC-10故障恢复 | 硬编码"自动恢复" vs "手动恢复" | 同上 |
| LOGIC-11追踪重搜 | 硬编码"全库重搜" vs "增量搜索" | 同上 |

**问题**：这6项的original和injected都是硬编码的字符串，不是从真实SRS文档中提取的。它们没有occurrences字段，没有关联到具体的文档位置。

**应该怎么做**：需要从SRS文档中提取真实的逻辑约束，然后在不同的位置注入矛盾。例如：
- 从正文中提取"任务切换为原子操作不可中断"
- 从流程图中VLM提取到"任务切换可被中断"的步骤
- 构造跨位置矛盾

**可信度**：❌ 低。硬编码的数据不反映真实文档中的不一致。

### 2.4 GJB合规层（11项）— ❌ 注入太简单

#### 当前注入方式

```python
# GJB-02 故障容错完备性
clause = rng.choice(gjb_clauses["faulttolerant"])  # 从chunks找到含"容错"的句子
return _build("GJB-02", "faulttolerant_missing", None,
             sentence[:60], "(条款缺失)",
             f"故障容错条款缺失: 删除'容错'", "gold")
```

**问题**：
1. **original是HTML碎片**——很多是`</p></td></tr><tr><td colspan="3"><p>主事件流</p></td></tr>`这种HTML标签，不是有意义的需求条款
2. **injected统一为"(条款缺失)"**——没有真正展示"删除了什么内容"
3. **注入方式太简单**——只是标记"删除关键词"，没有实际构造"缺失条款"的文档片段
4. **没有跨位置对比**——GJB合规应该是"位置A有条款，位置B缺失"，但当前只有单条记录

**应该怎么做**：
- GJB-01可测试性：在真实需求中注入模糊表述（"系统响应时间≤200ms"→"系统响应快速"）
- GJB-02故障容错：构造两个位置——位置A有容错条款，位置B缺失
- GJB-05可追溯性：构造追溯表——位置A有完整映射，位置B某行缺失

**可信度**：❌ 低。注入方式不反映真实的合规缺陷。
