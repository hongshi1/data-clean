## 第一部分：Visio XML检测管线深度解析（已实现✓）

### 1.1 容器解剖：从.doc到page1.xml的四层嵌套

一个.doc文件里的流程图，物理上经历了四层包装：

```
第1层  .doc (OLE2复合文档, 魔数 D0CF11E0)
        └── word/embeddings/oleObjectN.bin (每个嵌入对象一个流)
第2层  oleObjectN.bin (又是一个OLE2容器)
        └── Package 流 (Word对嵌入对象的通用包装)
第3层  Package流内容 = ZIP (魔数 PK)
        └── visio/pages/page1.xml, visio/masters/*.xml, ...
第4层  page1.xml (Visio 2012 XML格式)
        └── Shape树 + Cell属性 + Connect记录
```

**为什么文本提取要这么绕**：Word把Visio对象作为OLE嵌入保存，外层是.doc的复合文档格式；Visio文件本身（.vsdx）就是个ZIP。所以解析链是：ZIP解包.doc → 定位embeddings流 → 二次OLE解包 → 取Package流 → 三次ZIP解包 → 拿到XML。

**判定条件（每层都有明确的魔数检查）**：
- `data[:4].hex() == 'd0cf11e0'` → 是OLE2
- `pkg[:2] == b'PK'` → Package流里是ZIP
- ZIP里有 `visio/pages/` 前缀 → 确实是Visio文件（排除Excel/PowerPoint等其他嵌入对象）

### 1.2 page1.xml的数据模型：三种核心元素

**（a）Shape树（图的节点来源）**

```xml
<Shape ID='5750' Name='状态.5750' Type='Shape' Master='39'>
  <Cell N='PinX' V='0.65'/>      ← 中心X坐标（英寸，页面坐标系）
  <Cell N='PinY' V='2.69'/>      ← 中心Y坐标（注意：原点在左下角）
  <Cell N='Width' V='1.29'/>
  <Cell N='Height' V='0.44'/>    ← 可为负（翻转），取绝对值
  <Shapes>                        ← 子Shape集合（嵌套）
    <Shape ID='5753' Name='Name' Master=''>
      <Text>点击顶部菜单栏的系统设置</Text>   ← 文本在子Shape里！
    </Shape>
  </Shapes>
</Shape>
```

三个关键事实（每个都对应我们踩过的坑）：
1. **坐标存在Cell属性的N/V对里**，不是XML元素——`<Cell N='PinX' V='0.65'/>`，要用`findall('v:Cell')`后按N属性匹配，而不是找名为PinX的元素（旧代码的bug1：坐标全为0）
2. **文本在子Shape里**——状态/过程节点的文字放在名为`Name`的子Shape中（旧代码的bug2：78%节点"空文本"）
3. **子Shape坐标是父局部坐标系**——目前只取文本不做坐标变换，嵌套组内的坐标未变换到页面系（已知限制）

**（b）Connect记录（图的边来源）**

```xml
<Connect FromSheet='5764' FromCell='BeginX' ToSheet='5754' ToCell='Connections.X4'/>
<Connect FromSheet='5764' FromCell='EndX'   ToSheet='5750' ToCell='Connections.X1'/>
```

语义：**FromSheet是连接线Shape的ID**（不是节点！），FromCell说明连接线的哪一端（Begin=尾/箭头出发点，End=头/箭头指向），ToSheet是被粘合的节点Shape ID。一条连接线通常产生**两条**Connect记录（Begin粘一个节点、End粘另一个节点）。

所以语义边重建规则：**按FromSheet分组 → 组内找Begin的目标和End的目标 → 边 = (Begin目标 → End目标)**（旧代码的bug3：把每条半连接当成一条边，边的两端根本不是节点对节点）

**（c）PageSheet（页面尺寸，坐标归一化用）**

```xml
<PageSheet><Cell N='PageWidth' V='8.5'/><Cell N='PageHeight' V='11.0'/></PageSheet>
```

用于把绝对坐标归一化到[0,1]（`rx = PinX/PageWidth, ry = 1 - PinY/PageHeight`，Y翻转因为图像坐标系原点在左上）。归一化坐标是后续与PNG图像空间对齐、跨图比较的基础。

### 1.3 五步解析算法（M0完整逻辑）

```
Step 1  遍历嵌入对象 → 解包到page1.xml（1.1的链路）
Step 2  解析PageSheet取页面尺寸
Step 3  递归遍历Shape树:
          - 收集全部Shape到注册表 {id: {name, master, cells, is_child}}
          - 顶层Shape → 语义节点候选
          - 节点文本 = 自身Text + 全部后代Shape的Text合并去重（修bug2）
          - 节点类型 = Name前缀规则表匹配（状态→state, 任务→process,
            序列流→connector, 参与者→actor, 用例→usecase, 矩形→process...）
          - 坐标/尺寸 = Cell N=匹配（修bug1）, 尺寸取abs
Step 4  Connect重建有向边（修bug3）:
          - 按FromSheet(连接线)分组
          - Begin目标→源, End目标→汇 → 有向边(源→汇)
          - 边标签 = 连接线Shape自身的Text
          - 单端粘合/端点不在语义节点集 → 计入悬空统计
Step 5  几何边恢复（未粘合连线）:
          - 对每个无Connect记录的1D Shape（有BeginX/EndX的）
          - 端点吸附到最近节点bbox（距离≤0.35英寸）
          - Begin端→源, End端→汇（与粘合边同一方向约定）
```

### 1.5 已知限制（诚实清单）

| 限制 | 根因 | 影响与缓解 |
|------|------|-----------|
| 未粘合连线部分不可恢复 | 作者画线不贴形状，无Connect记录；几何恢复要求1D Shape有Begin/End Cell | 边召回偏低→edge_extra_rate虚高24.1%的一部分；缓解：骨架化图像级验证（设计稿，见4.2） |
| 嵌套组内坐标未变换 | 子Shape坐标是父局部系 | 深层嵌套图（UML组合图）的几何恢复不准；当前只影响边吸附，节点文本不受影响 |
| Master引用未解析 | 类型靠Name前缀，未查masters1.xml的Master定义 | 少数自定义母版名的图分类为other；缓解：加masters1.xml解析（工作量小时级） |
| 多页取最优页 | 多页Visio按"文本节点最多"取一页 | 跨页流程图的完整结构可能被截断；sc2集影响极小（多为单页） |
| 渲染一致性未验证 | XML源与文档实际渲染的PNG可能有时间差（源改了图没更新） | 这**正是provenance drift的检测机会**而非缺陷（见第三部分） |

## 第二部分：XML与文本的语法化匹配——"文档AST"方法设计

### 2.1 编译器前端类比：为什么AST是对的抽象

编译器把源代码变成可分析对象，走的是一条成熟的流水线：

```
字符流 → [词法] → token流 → [语法] → AST → [语义] → 带类型的IR → [分析] → 检查/优化
```

我们的问题同构：**SRS文档的图、表、文是三种"源语言"，要变成可比较的中间表示**：

```
PNG图   → [感知]  → 节点/边列表    ┐
表格CSV → [语法]  → 步骤/异常流图  ├→ 统一IR(元素宇宙Ω) → [比对] → 类型化分歧Δ
正文    → [抽取]  → 约束/参数     ┘
```

关键区别：编译器的AST是**无损**的（语法保证了等价性），我们的每层转换都**有损有噪**——这正是ACDD把"噪声"作为一等公民的原因。但AST的分层思想直接适用：**为每种模态定义语法，语法保证结构合法性，结构合法才能做可靠的语义比较**。

### 2.2 三层中间表示（IR）设计

**物理层（已实现✓）**：Visio XML的Shape/Cell/Connect直接映射——忠实但不可比较（PNG侧没有对应物）。

**逻辑层（部分实现）**：带类型的有向标记图 `X = (V, E, ℓ, τ, γ)`——节点类型τ（process/decision/start/end/actor/usecase）、标签ℓ（文字）、边条件γ（是/否/E1）。锚点和VLM提取都已输出这个形态。

**语义层（部分实现）**：元素宇宙Ω——把"比较"分解为类型化元素：
```
Ω = {exst(节点存在), lab(标签), type(类型), dir(边方向), cond(条件值), act(参与者), val(参数值)}
```
每个元素是二元比较的原子单元，带观测值（图侧）和真值（表侧）。

**当前缺口**：κ_T表格编译器用正则解析，没有正式语法。这导致过两个bug（约束列污染、跨步骤吞并）——**用正则解析有格式的文档，等于用字符串匹配解析程序**。

### 2.3 升级方向：给GJB用例表定义正式语法【设计稿】

GJB用例描述表是一个**有严格结构的语言**，完全可以用表格文法（table grammar）定义：

```
UseCaseTable ::= Header MainFlow ExceptionFlows PostCondition
Header       ::= "Use Case 名称：" NAME "," "Actors：" ActorList
MainFlow     ::= "主事件流" ColumnHeader StepRow+
StepRow      ::= (StepText | "") "," (StepText | "") "," (Constraint | "")
StepText     ::= NUMBER SEPARATOR Sentence        ← 步骤号边界是token级的
ExceptionFlows ::= ("异常流" EID "：" Sentence)+
```

用这个语法驱动解析器（手写递归下降即可，格式简单）代替正则，三个收益：
1. **步骤号边界成为语法单元**——跨步骤吞并类bug在语法层就不可能发生
2. **动作约束列在语法上被隔离**——污染类bug同样消失
3. **解析错误成为可报告的语法层不一致**——"步骤3没有内容但编号存在"本身就是一种检测信号（编号断裂=文档自身的语法错误，GJB规则R-007的直接实例）

同理，Visio侧的"语法"就是Shape树+类型规则（连接线两端必须粘节点=类型检查规则，违反即为悬空）。

### 2.4 结构匹配方法谱系（调研）

有了两边的AST/图，怎么匹配？方法谱系按严格性排序：

| 方法 | 出处/工具 | 适用性 | 在我们场景的定位 |
|------|----------|--------|----------------|
| 图同构（VF2） | networkx GraphMatcher | 精确同构判定 | 太严格：图文粒度差异使精确同构几乎不成立 |
| 子图同构 | ISMAGS | 包含关系 | 部分场景（表是图的子流程时） |
| **图编辑距离GED** | nx.graph_edit_distance | 最小编辑操作序列 | **当前ORDER_CONFLICT/缺失检测的本质**——我们的Δ就是"编辑脚本"的简化版 |
| 树编辑距离 | Zhang-Shasha | 层次结构比较 | 用例表的步骤树 vs 图的嵌套？ |
| 属性文法 | Knuth 1968传统 | 属性传播+约束检查 | GJB规则库120条的正式化载体【设计稿】 |
| 图文法/图变换 | Ehrig代数法；AGG/Groove工具 | 图上的产生式规则 | 一致性规则="禁止的产生式"（如"decision节点必须有两条出边"） |
| 二部匹配 | 匈牙利算法 | 节点对齐 | 已用于μ（词法+embedding代价矩阵） |

**我们的定位**：不追求完整GED（NP难，且图文粒度差异使编辑代价难以定义），而是**用类型化元素宇宙做"语义化简的编辑脚本"**——每个Δ条目对应一种编辑操作（节点缺失=删除、方向矛盾=边反转），保持了可解释性又控制了复杂度。这与GED的关系是"把编辑操作类型化后独立检测"。

### 2.5 一个具体的设计：属性文法驱动的检测规则【设计稿】

GJB规则库的120条规则目前是JSON描述（人读），可以升级为属性文法（机器执行）：

```
规则R-0082（每个能力应逐一列出需求）:
  属性文法形式:
    capability_table ::=
      TABLE with attr {rows: N, ids: Set}
      constraint { ids唯一 ∧ 编号连续 ∧ N≥1 }
  违反 → 语法层不一致（类型: id_inconsistency / section_shift）
```

每个规则的违反=一次可检测的编辑操作，直接进Δ。**这把120条规则从"文档合规检查"升级为"语法层不一致检测"**——与语义层（NLI）、逻辑层（Z3）共用同一个Δ-译码框架。

## 第三部分：不依赖视觉模型的初版设计（确定性路径）

### 3.1 核心洞察：锚点图上根本不需要感知

对于有Visio源的图（当前语料373/381≈98%），**整个感知问题不存在**——XML直读就是100%保真的图结构。所以一个纯确定性的初版系统是可行的：

```
确定性初版（无任何模型）:
  输入: .doc文档
  ①  M0解析: 嵌入Visio XML → 锚点图结构（确定性）
  ②  κ_T编译: 用例表 → 结构化图（表格文法解析, 确定性）
  ③  N规范化: 同义词典+单位族归一（词典驱动, 确定性）
  ④  μ对齐: 词法+编辑距离匹配（匈牙利算法, 确定性; 可选embedding）
  ⑤  Δ提取: 类型化分歧（规则, 确定性）
  ⑥  报告: 分歧清单+证据（无需概率——因为没有感知噪声, Tier1=无噪层）
```

**这个初版检测什么**：锚点图 vs 表格的结构性分歧——步骤缺失、异常流缺失、方向矛盾、参与者缺失。它就是ACDD的Tier 1，**检测能力上限受κ_T/N的质量限制，但不受感知噪声限制**。

### 3.2 初版的独立价值：provenance drift挖掘

纯确定性系统还独占一类检测：**嵌入源与文档陈述的漂移**。XML源是作者意图的最终态，表格/正文是文档其他位置的陈述——两者分歧时，要么文档演化不同步（改了源忘了改表），要么写作错误。这类真实不一致：
- 零感知误差（两边都是确定性读取）
- 免疫"你注入了自己的bug"质疑（演化残留，不是人造的）
- 当前实测：3条ORDER_CONFLICT方向矛盾候选（2_001/2_008/2_041，双LLM裁决2_001确认为real_bug）

### 3.3 无锚点图的确定性降级路径

约2%的图没有Visio源（截图/扫描）。确定性降级选项（按成本排序）：
1. **跳过+标记**（初版推荐）：unanchored标记，交给后续版本
2. **经典CV管线**：PaddleOCR文字块聚类→节点候选 + Hough线段→边候选 + 几何吸附（零训练，技术谱系见`diagram_extraction_technology_spectrum.md`方向3；预计边F1 40-60%）
3. **规则版面分析**：对GJB规整图（垂直流程），文字块按列/行聚类的纯规则恢复（更弱但完全可审计）

### 3.4 初版的能力边界：什么时候必须引入VLM

| 场景 | 确定性初版够吗 | 需要什么 |
|------|--------------|---------|
| 有锚点图的图文一致性 | ✓ 够（Tier1全功能） | — |
| 嵌入源vs正文漂移 | ✓ 够（独占能力） | — |
| 无锚点图（2%） | ✗ | 经典CV或VLM |
| 语义级矛盾（"≤5s"vs"≥8s"这类值的冲突） | 部分（词法+单位归一能抓一部分） | NLI/Z3 |
| 语义改写识别（"加载到内存"vs"载入储存器"） | ✗ 词法失败 | embedding/VLM |
| 部署到无嵌入源的文档生态（普通PNG文档） | ✗ | VLM成为主通道，锚点降级为校准器 |

**结论**：初版是"本语料上的完整系统+其他语料上的校准器"。ACDD的完整形态（Tier2+译码）是为后者准备的。

## 第四部分：VLM协同方法设计（仅设计，不实现）

### 4.1 Visio辅助标注：silver label生成管线【设计稿】

锚点结构可以系统性地转化为训练标注：

```
坐标转换（关键一步）:
  XML页面坐标(inch) → PNG像素坐标
  需要: 图像尺寸(img_w, img_h) + 页面尺寸(pw, ph)
  px = cx / pw * img_w
  py = (1 - cy / ph) * img_h        ← Y翻转
  风险: Word渲染可能有边距/缩放 → 用2-3个已知节点标定仿射变换（最小二乘）
        验证: 转换后bbox与OCR文字块的重叠率（IoU>0.7为通过）

生成的标注类型:
  (a) 检测标注: {bbox, class}×N —— YOLO训练集（节点检测）
  (b) 边标注: {(src_bbox, dst_bbox), label} —— 边方向分类训练集
  (c) 端到端标注: (image, {nodes, edges} JSON) —— VLM微调的SFT数据
  (d) SoM标注: 在图上给节点编号叠图 —— 视觉提示训练数据

规模: 373图 × 平均14节点/图 ≈ 5200节点标注 + 2671边标注（零人工）
增广: 同一XML重渲染（改字体/线宽/颜色/布局微扰）→ 1:N扩容，
      且保持结构标签不变（渲染不变性是免费的数据增强）
```

**注意**：236对低可信映射的锚点用于训练前需要重对齐（sc2教训：67%错位）。可以先用高可信的sc2集训练检测器，再用检测器结果验证其他场景的映射（自举）。

### 4.2 VLM交互协议：结构化提取的分层设计【设计稿】

当前实现（M2）是最简单的单轮协议。完整的协议谱系按复杂度递增：

```
L0  单轮约束JSON（当前✓）:
    prompt要求逐字提取+JSON schema约束 → 实测节点召回94.4%
L1  双图输入（EdgeFlow式）:
    原图 + Canny边缘图一起输入，边缘图作结构先验
    文献报告对流程图→Mermaid有零训练提升
L2  SoM叠图（Set-of-Mark）:
    先用检测器/OCR给节点编号并叠加在图上 → VLM按编号报边
    把"自由生成"变成"确认/否认候选边"——拓扑错误率大幅下降
    我们的锚点可以直接生成SoM标注（无需检测器）
L3  迭代精化（extract-render-verify循环）:
    VLM输出结构 → Graphviz/mermaid渲染回图片 → 与原图比对（确定性相似度）
    → 差异反馈给VLM修正 → 循环2-3轮
    渲染比对可以用锚点做裁判（有锚点图上）
L4  证据引用输出:
    要求VLM每条边引用两端节点的原文片段（span），
    span不在OCR文字集中 → 幻觉标记（Recall_OCR质量闸门）
```

**推荐组合**：L0+L2+L4（SoM用锚点生成、span用OCR校验）——全部有确定性组件兜底，VLM的自由度被压缩到最小。

### 4.3 Visio信号注入模型：蒸馏方案谱系【设计稿】

373个(图像, 完美结构)对是天然的训练信号。注入方式按侵入性排序：

```
方案A  检测器蒸馏（最保守）:
  训练YOLO检测器 on silver labels（4.1a）
  → 检测器接管锚点覆盖不了的图
  → 检测器的错误率在（未来出现的）新锚点上持续校准
  训练量: ~5000节点标注, 单卡数小时, YOLOv8s级别

方案B  投影头对齐（轻量）:
  冻结VLM视觉编码器, 训练projection head:
    图像embedding → 图结构空间（节点集合的embedding）
  损失: 对比损失（同图的XML结构为正样本, 异图结构为负样本）
  用途: 无锚点图的"结构相似度"检索/粗筛
  训练量: 373对, 只训投影层, 小时级

方案C  受限解码注入（中等）:
  VLM生成节点列表时, 解码约束到OCR识别的文字集合
  （VLM只能"选择"OCR看到的文字, 不能凭空生成）
  锚点数据训练这个"选择器"（哪些OCR块是节点、哪些是标签/噪声）
  效果: 幻觉率从1.0%进一步压向0, 且不依赖微调

方案D  LoRA微调（最激进）:
  在(image, structure JSON)对上微调开源VLM（Qwen-VL级）
  数据增广: XML重渲染（4.1）从373扩到数千
  风险: 合成渲染与真实文档的domain gap（谱系调研的已知警告）
  缓解: 真实图像的锚点对始终作为验证集（防过拟合到渲染风格）
```

**推荐路线**：A（立即可做、独立可用）→ C（与ACDD译码框架天然契合：选择器错误率可校准）→ B/D（仅当无锚点图成为主要场景时投入）。

### 4.4 与ACDD的融合：注入后的通道升级路径

所有4.3方案的产出都是**新通道或升级通道**，接入ACDD的方式统一且优雅：

```
新通道ĉ → 在锚点上校准θ̂_ĉ（M3流程直接复用）
        → 加入CI因子化融合（M6流程直接复用）
        → 锚遮蔽协议评测（M4/M5流程直接复用）
```

**这是架构的核心红利**：通道升级不需要改方法本体——译码器、校准协议、评测协议全部复用。VLM进步（scaling）或新感知模型出现，都只是"更好的测量仪器"插进同一个框架。

### 4.5 通道选择决策树（工程部署视角）

```
输入一张图:
  ├─ 有嵌入XML源? ──是──→ 确定性锚点路径（Tier1, 零成本零噪声）
  │                      └─ XML vs 渲染图的一致性 = provenance drift检测
  └─ 无源 ──→ 图上有清晰文字?
              ├─ 是 ──→ 高价值/低批量? ──是──→ VLM通道(L0+L2协议) + OCR通道
              │                                  → CI融合译码（ACDD完整形态）
              │              └─否──→ 经典CV管线（Hough+聚类, 批量粗筛）
              └─ 否（扫描/照片）──→ 修复图像后同上, 或弃权送人工
```
