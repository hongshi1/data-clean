## 1.0 输入与预处理

### 输入：srs_chunks.json（5231条结构化切片）

每条chunk长这样：
```json

  "section": "1.8.3.4",        // 切片器跟踪出的章节号
```

```python
# ① 章节树: doc → 该文档所有出现过的章节号集合
section_trees = {

# ② 图编号表: doc → 该文档"定义过"的图编号集合
```

## 1.1 规则S1：章节编号连续性

### 目标
同层级的章节编号应该连续：有3.1就该有3.2、3.3，不允许3.7直接跳到3.9。

### 算法（两级检查）

```python
def check_section_continuity():
    for doc, secs in section_trees.items():
        # 一级章节: 取所有章节号的第一段数字
        l1 = sorted({int(s.split(".")[0]) for s in secs if s.split(".")[0].isdigit()})
        # 例: {"1","2","3","4","5","6"} → [1,2,3,4,5,6]

        for i in range(1, len(l1)):
            if l1[i] != l1[i-1] + 1:    # 相邻不连续
                报错(f"一级章节编号跳跃: {l1[i-1]} → {l1[i]}, 缺少{l1[i-1]+1}")

        # 二级章节: 只查第3章的二级编号
        l2 = sorted({int(s.split(".")[1]) for s in secs
                     if s.split(".")[0] == "3" and s.split(".")[1].isdigit()})
        for i in range(1, len(l2)):
            if l2[i] != l2[i-1] + 1:
                报错(f"3.x章节编号跳跃: 3.{l2[i-1]} → 3.{l2[i]}, 缺少3.{l2[i-1]+1}")
```

### 真实检出（1条）

```
[LOW] 11语音综合处理软件需求规格说明-终稿
      sec=3.9: 3.x章节编号跳跃: 3.7 → 3.9, 缺少3.8
```

**数据流追踪**：
```
11号文档的章节树中, 属于3.x的二级章节号:
  3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 3.7, 3.9  ← 3.8缺失!
排序后: [1,2,3,4,5,6,7,9]
遍历: 7 后面是 9 → 9 != 7+1 → 报错"缺少3.8"
```

### 设计决策与理由
| 决策 | 理由 |
|------|------|
| 只查一级+3.x二级 | 深层章节（3.2.1.5）常因剪裁不连续，查了全是误报 |
| 严重度MEDIUM/LOW | 编号跳跃非致命，但反映编写不规范 |
| 用set去重 | 同一章节号可能出现在多个chunk，去重避免重复报 |

## 1.2 规则S2：需求ID重复定义 ★核心规则

### 目标
同一个需求ID出现在**多个章节标题**中 = 同一需求被定义了多次 = 很可能是名称不一致。

### 关键设计：区分"定义"与"引用"

这是S2最核心的工程决策。需求ID在文档中出现有两种性质：

```
定义位置: 章节标题 —— 如 "1.8.3.4 快捷操控（PZXQ-GN-JMJCKJ-JMJC-KJCK）"
         含义: "这个ID代表的功能叫快捷操控"
         每个ID理论上只应有一个定义

引用位置: 正文/表格 —— 如 "该功能（PZXQ-GN-JMJCKJ-JMJC-KJCK）支持..."
         含义: "提到了这个ID", 不算重复

判定标题的规则:
  text以 "数字编号+空格" 开头   AND  文本长度<80字符
  例: "1.8.3.4 快捷操控（...）" → 是标题
      "本功能实现创建服务工程，用户可通过..." → 不是标题(太长)
```

### 算法

```python
def check_id_unique():
    title_ids = Counter()          # (doc, ID) → 标题中出现次数

    for doc, chunks in docs.items():
        for chunk in chunks:
            text = chunk["text"]
            is_title = (re.match(r"^\d+(\.\d+)*\s+\S", text) and len(text) < 80)
            if not is_title:
                continue
            for m in ID_RE.finditer(text):
                iid = m.group(0)
                if len(iid) > 15:           # 只查完整ID(防截断误匹配)
                    title_ids[(doc, iid)] += 1

    for (doc, iid), cnt in title_ids.items():
        if cnt > 1:
            报错(f"需求ID重复定义: {iid} 出现在{cnt}个章节标题")
```

### 真实检出（15条）+ 关键案例追踪

```
[01数据获取转换分系统] SJHQZHFW-GN-SJZH-DXYYZTKG     出现在3个章节标题
[02界面集成框架软件]   PZXQ-GN-JMJCKJ-JMJC-KJCK      出现在2个章节标题  ★
[02界面集成框架软件]   PZXQ-GN-JMJCKJ-JMJC-JMPZBC    出现在3个章节标题
[04数据统一访问服务]   PZXQ-GN-SQLFW-BLOBSJCZ        出现在2个章节标题
[06运行支撑服务]       PZXQ-YXZCFW-GN-XTJCXXWH-YHJCXXCX 出现在3个章节标题
...共15条
```

**★案例完整追踪（PZXQ-GN-JMJCKJ-JMJC-KJCK）**：
```
chunk A: {"section": "1.8.3.4", "type": "text",
          "text": "1.8.3.4 快捷操控（PZXQ-GN-JMJCKJ-JMJC-KJCK）"}   → 标题, ID+1
chunk B: {"section": "1.8.5.4", "type": "text",
          "text": "1.8.5.4 触摸操控（PZXQ-GN-JMJCKJ-JMJC-KJCK）"}   → 标题, ID+1

title_ids[("02界面集成框架...", "PZXQ-GN-JMJCKJ-JMJC-KJCK")] = 2 > 1 → 报错
```

**交叉印证（为什么这条可信）**：
```
Gold Standard人工标注 (scene1_gold_standard.json):
  {"entity_id": "PZXQ-GN-JMJCKJ-JMJC-KJCK",
   "correct_name": "快捷操控", "wrong_names": ["触摸操控"],
   "source": "real", "subtype": "typo"}

→ 机器检出: 同一ID出现在2个标题, 名称分别是"快捷操控"和"触摸操控"
→ 人工标注: 该ID的正确名称是"快捷操控", "触摸操控"是错误名称
→ 两条独立路径得出同一结论: 这是真实矛盾 ✓
```

### 版本演进（为什么从482条变成15条）

```
v1: 全文统计ID出现次数 → 检出482条"重复"
   问题: 绝大多数是正常引用(正文提到/表格提到), 误报率极高

v2: 只统计章节标题中的ID → 检出15条
   精度: 482 → 15, 误报减少96.9%
   且15条中8条与人工Gold Standard矛盾实体重合(53.3%命中率)
```

## 1.3 规则S4：图/表引用完整性 ★检出最多

### 目标
正文写"见图N/见表N"时，文档里必须真有图N/表N。

### 关键设计：区分"定义"与"引用"（与S2同思想）

```
定义(图实际存在的地方):
  · chunk类型 = image → 图注, 该图编号算存在
  · chunk类型 = table → 表, 该表编号算存在
  · 文本以"[图"/"图"开头 → 图注

引用(正文提到图/表的地方):
  · 正则匹配 "图\s*(\d+)" / "表\s*(\d+)"
  · 且前面3个字是"见图"或"如下" → 确定为引用
  · 其他出现(如"图1所示")也算引用, 但排除定义位置
```

### 算法

```python
def check_fig_table_refs():
    for doc, chunks in docs.items():
        figs = figures.get(doc, set())       # 预索引②
        tables = tables.get(doc, set())      # 预索引③

        for chunk in chunks:
            text = chunk["text"]
            if chunk["type"] in ("table", "image"):
                continue                      # 跳过定义位置

            for m in FIG_REF_RE.finditer(text):      # "图N"
                num = int(m.group(1))
                before = text[max(0, m.start()-3):m.start()]
                if before in ("见图", "如下"):        # 是引用不是定义
                    if num not in figs:
                        报错(f"引用的图{num}未找到(已知图: {sorted(figs)[:5]})")

            for m in TABLE_REF_RE.finditer(text):     # "表N"
                num = int(m.group(1))
                if num not in tables:
                    报错(f"引用的表{num}未找到(已知表: {sorted(tables)[:5]})")
```

### 真实检出（90条）

```
[01数据获取转换分系统] 3.16节: 引用的表67未找到(已知表: [1,2,3,4,5,...])
[04数据统一访问服务]   3.2.1.1.1.2节: 引用的表6未找到(已知表: [1,2,3,4,5,...])
...共90条
```

### 为什么检出这么多（90条=总检出80%）

```
可能原因分析:
① 文档引用"表67"但其实指向附录表格 → MinerU把附录表格编号单独计, 与正文编号脱节
② 文档引用跨章节表格, 编号不连续 → 如正文说"见表6", 但表6在别的章节
③ 表格编号重复使用 → 两个表都叫"表1", 集合去重后编号丢失
④ 真实缺失 → 文档确实引用了不存在的表

诚实结论: 90条里哪些是真缺失、哪些是解析范围不全, 需要人工复核
        (已列入待办: 人工抽检S4检出)
```

### 设计决策
| 决策 | 理由 |
|------|------|
| 只查"见图/如下"前的引用 | 减少把"图1所示"这种普通提及当引用的误报 |
| 严重度LOW | 引用缺失可能是解析问题, 不确定度较高 |
| 输出已知图表集合 | 便于人工核对"是不是真的缺" |

## 1.4 规则S5：章节结构完整性

### 目标
GJB 438C规定SRS必须有6章，缺章即结构不合规。

### 标准结构
```
1 范围          2 引用文档     3 需求
4 合格性规定     5 需求可追踪性  6 注解
```

### 算法（极简）

```python
SRS_SECTIONS = ["1", "2", "3", "4", "5", "6"]

def check_structure():
    for doc, secs in section_trees.items():
        l1 = {s.split(".")[0] for s in secs if s.split(".")[0].isdigit()}
        for must in SRS_SECTIONS:
            if must not in l1:
                报错(f"缺少GJB要求的第{must}章(标准: 1范围/2引用/3需求/4合格性/5可追踪/6注解)")
```

### 真实检出（5条，全部在02号文档）

```
[02界面集成框架软件] 缺少第2章(引用文档)
[02界面集成框架软件] 缺少第3章(需求)
[02界面集成框架软件] 缺少第4章(合格性规定)
[02界面集成框架软件] 缺少第5章(需求可追踪性)
[02界面集成框架软件] 缺少第6章(注解)
```

### 交叉印证（重要）

```
人工判定 (AGENTS.md): "13份结构完整(6章+3.1~3.18), 3份格式异常"
机器检出 (S5): 02号文档缺第2/3/4/5/6章

→ 02号文档正是人工判定"格式异常"的文档之一!
→ 机器检出的结构异常 = 人工判定的格式异常 → 互相印证 ✓
```

### 为什么S5用一级章节判断
GJB的6章是最顶层结构，缺章是**结构性**问题（HIGH）。二级章节缺失（如缺3.8）属于剪裁，不算违规——S1负责查连续性，S5只查顶层完整性，职责分离。

## 1.5 规则S7：交叉引用完整性

### 目标
正文写"见X.X.X节"时，该章节必须存在。

### 关键设计：父章节宽容

```
引用"3.2.5节", 文档只有"3.2" → 也算存在(3.2是3.2.5的父章节)
引用"3.2.5节", 文档连"3.2"都没有 → 报错
```

### 算法

```python
def check_cross_refs():
    for doc, chunks in docs.items():
        all_secs = section_trees.get(doc, set())

        for chunk in chunks:
            text = chunk["text"]
            for m in re.finditer(r"(\d+\.\d+(?:\.\d+)*)\s*节", text):
                ref = m.group(1)               # 如 "3.2.5"
                if ref not in all_secs:
                    # 宽容: 检查父章节
                    parents = [ref[:i] for i in range(len(ref), 0, -1)
                               if ref[:i] in all_secs]
                    if not parents:            # 父章节也不存在
                        报错(f"引用的章节{ref}不存在(已知章节: {sorted(all_secs)[:5]})")
```

### 真实检出（1条）

```
[02界面集成框架软件] 1.18节: 引用的章节3.2不存在
                    (已知章节: ['1.1','1.10','1.10.1',...])
```

### 与S5互相印证
```
S5检出: 02号文档缺第3章
S7检出: 02号文档1.18节引用"3.2节" → 当然不存在(第3章都没有)

两条规则从不同角度指向同一事实: 02号文档结构异常 ✓
```

### 局限
正则 `(\d+\.\d+(?:\.\d+)*)\s*节` 只匹配"3.2.1节"格式。写"见第三章"、"见3.2"（无节字）会漏检。

# 第二部分 语义层校验（7种图方法超详解）

## 2.0 问题形式化

### 检测目标
找出"同一需求ID在不同位置出现**不同名称**"的实体。

### 输入数据结构：entity_names

```
entity_names = {
  "PZXQ-GN-JMJCKJ-JMJC-KJCK":   {"快捷操控", "触摸操控"},     ← 矛盾(2个名)
  "PZXQ-GN-JMJCKJ-JMJC-JMPZBC": {"界面配置保存", "资源占用监控", "语音交互"},  ← 矛盾(3个名)
  "ZZSJHQZHFW-GN-SJHQ":         {"数据获取"},                 ← 一致(1个名)
  ...
}
```
来源：ID-Graph的每个实体ID，从各mention context提取名称（`extract_name`），过滤出现<2次的ID → 508个实体。

### Gold Standard（评测基准）

```python
gold_conflicts = load_gold_conflicts('scene1')
# = scene1 negatives中 source=='real' 的 entity_id 集合
# = {PZXQ-GN-JMJCKJ-JMJC-KJCK, ...} (16个真实矛盾实体)
```

### 评测指标定义

```
对每个实体 rid:
  pred = 检测器是否判定rid有矛盾
  gold = rid是否在gold_conflicts中

TP = pred=True & gold=True      (正确检出矛盾)
FP = pred=True & gold=False     (误报: 一致实体被判矛盾)
FN = pred=False & gold=True     (漏报: 矛盾实体没检出)

P  (精确率) = TP / (TP+FP)      "检出的矛盾里, 多少是真矛盾"
R  (召回率) = TP / (TP+FN)      "真实矛盾里, 检出多少"
F1 = 2PR / (P+R)                "综合"
```

## 2.1 基础组件（所有方法的公共地基）

### 文本相似度 text_sim（编辑距离归一化）

```python
def text_sim(a, b):
    if a == b: return 1.0
    ml = max(len(a), len(b))
    return 1 - levenshtein(a, b) / ml

# 例: text_sim("快捷操控", "触摸操控")
#   levenshtein = 2 (两处字不同)
#   ml = 4
#   sim = 1 - 2/4 = 0.5
```

### 语义图 build_semantic_graph（最基础的图）

```
节点: 所有名称 (508个实体的全部名称, 去重后约1000+个)
边:   两个名称长度差≤4 且 text_sim ≥ 0.55 → 连边, 权重=sim

例: "快捷操控" --0.5--> "触摸操控"  (长度差0, sim=0.5... 0.5<0.55不连?)
    实际: 阈值0.55, "快捷操控"vs"触摸操控" sim=0.5 → 不连边!
    → 这就是为什么纯规则方法召回率受限(矛盾对相似度常<阈值)
```

### 异构图 build_hetero_graph + metapath_embed（本文方法核心）

```
异构图:
  实体节点 E:{rid} (type=entity)     ← 508个
  名称节点 M:{name} (type=name)      ← 1000+个
  边: E→M (type=has_name)           "实体拥有名称"

metapath随机游走:
  从实体节点出发, 交替走 E→M→E→M... (不走同类节点)
  30次游走 × 100起点 × 12步长

共现矩阵 → PPMI (正点互信息):
  PMI(w,c) = max(0, log( count(w,c)×N / (row(w)×col(c)) ))
  → 捕捉"哪些名称经常出现在同一实体的上下文"

SVD降维 → 32维嵌入:
  embeddings[M:名称] = U[:,:32] × √S[:32]
  → 每个名称变成32维向量, 相似名称向量相近

拓扑相似度 topo_sim(a,b) = 嵌入向量点积
```

**为什么用metapath而不是普通随机游走**：
- 普通游走会在名称节点间乱跳，混合不同实体的信息
- metapath强制E→M→E交替，保证"同一实体的名称"在共现窗口内——**名称-名称相似性由"是否属于同一实体"驱动**，这正是我们要的信号

## 2.2 方法B1：连通分量（规则基线）

### 思想
名称连成的图里，如果某个实体的名称们**不在同一个连通分量** → 矛盾。

### 算法

```python
def detect_connected_components():
    detected = set()
    for rid, names in entity_names.items():
        if len(names) < 2:
            continue
        comps = list(nx.connected_components(G.subgraph(names)))
        if len(comps) > 1:          # 名称散落在多个分量 → 矛盾
            detected.add(rid)
    return detected
```

### 数据流示例

```
实体 PZXQ-GN-JMJCKJ-JMJC-KJCK: {快捷操控, 触摸操控}
  text_sim("快捷操控","触摸操控") = 0.5 < 0.55 → 无边!
  G.subgraph({"快捷操控","触摸操控"}) = 2个孤立节点 = 2个分量
  len(comps)=2 > 1 → 检出矛盾 ✓

实体 ZZSJHQZHFW-GN-SJHQ: {数据获取}
  len(names)=1 < 2 → 跳过(不可能矛盾)
```

### 评测结果
```
B1: P=1.0, R=0.75, F1=0.857, TP=12, FP=0, FN=4
```

### 解读
- **P=1.0（零误报）**：能连成一个分量的名称必然相似，判一致不会错
- **R=0.75（漏4个）**：真实矛盾对如果相似度<0.55（如"快捷操控"vs"触摸操控"=0.5），无边可连，漏检——**规则阈值的天花板**

## 2.3 方法B2：Louvain社区（无监督图聚类）

### 思想
不预设"同一实体的名称"应该连成什么样，让算法自动发现图的社区结构。某实体的名称们如果被分到**多个社区** → 矛盾。

### 算法

```python
def detect_louvain():
    comms = community.louvain_communities(G, weight='weight', seed=42)
    n2c = {node: ci for ci, comp in enumerate(comms) for node in comp}
    detected = set()
    for rid, names in entity_names.items():
        if len(names) < 2:
            continue
        communities_of_names = {n2c.get(n, -1) for n in names}
        if len(communities_of_names) > 1:   # 名称跨多个社区 → 矛盾
            detected.add(rid)
```

### 与B1的区别
- B1: 用**连通性**（有无路径）
- B2: 用**社区归属**（名称被分到哪类）——即使有边连着，如果被社区检测拆开，也算矛盾

### 评测结果
```
B2: P=1.0, R=0.688, F1=0.815, TP=11, FP=0, FN=5
```

### 解读
- 比B1召回略低（R 0.75→0.688）：Louvain的社区边界与实体边界不完全一致
- 仍然零误报：社区内名称相似度高，不会把一致实体拆开

## 2.4 方法B3：谱聚类（谱方法）

### 数学原理（完整推导）

```
① 相似度矩阵 S (n×n):
   S[i,j] = text_sim(名称i, 名称j)  (只填上三角, 对称)

② 度矩阵 D = diag(S.sum(axis=1))

③ 归一化拉普拉斯: L_norm = I - D^(-1/2) S D^(-1/2)
   (D^(-1/2) = diag(1/√diag(D)), 加1e-9防除零)

④ 特征分解: L_norm = U Λ U^T  (scipy.linalg.eigh)
   取第2~11个特征向量 → 10维嵌入

⑤ 层次聚类: 嵌入向量算余弦距离 → average linkage → 100簇
   labels = fcluster(linkage, 100, criterion='maxclust')

⑥ 判定: 名称们落在>1个簇 → 矛盾
```

### 评测结果
```
B3: P=0.625, R=0.625, F1=0.625, TP=10, FP=6, FN=6
```

### 解读（为什么最差）
- **P=0.625（6个误报）**：谱聚类把一些名称强行拆到不同簇，即使它们属于同一实体——聚类是"全局最优"不是"实体最优"
- 谱方法的**簇数量是超参数**（我们设100），与实际实体数不匹配
- 教训：无监督全局聚类不适合"按实体分组"的任务

## 2.5 方法B4：学习型LR（监督特征学习）

### 思想
不用固定阈值，而是**从Gold Standard学习**"什么样的名称对算矛盾"。

### 特征设计（5维）

```
对名称对 (a,b):
  f1 = 1 - levenshtein(a,b) / max(len(a),len(b))   编辑距离归一化
  f2 = levenshtein(a,b)                             原始编辑距离
  f3 = |len(a)-len(b)| / max(len)                   长度差比例
  f4 = |set(a)∩set(b)| / |set(a)∪set(b)|            字符集合Jaccard
  f5 = 1 if a[:2]==b[:2] else 0                     前2字相同

例: ("快捷操控", "触摸操控")
  f1 = 1-2/4 = 0.5
  f2 = 2
  f3 = 0
  f4 = 0 (字符完全不同: {快,捷,操,控}∩{触,摸,操,控}={操,控}→2/4=0.5)
  f5 = 0 ("快捷"≠"触摸")
```

### 训练（手写逻辑回归, 500轮梯度下降）

```python
训练集:
  负例对(矛盾): 从scene1 negatives取 correct_name vs wrong_names → label=1
  正例对(一致): 从scene1 positives取 name vs name → label=0
  (注意: 正例是同名对, 因为一致实体的名称相同)

特征标准化: Xn = (X - mean) / std

模型: p = sigmoid(Xn @ w + b)
更新: w -= 0.1 × (Xn.T @ (p-y) / n)
      b -= 0.1 × (p-y).mean()
```

### 预测

```python
def predict(a, b):
    if a == b: return False          # 同名一定一致
    prob = sigmoid(标准化后的特征 @ w + b)
    return prob > 0.5                # 概率>0.5 → 判矛盾
```

### 评测结果
```
B4: P=0.571, R=1.0, F1=0.727, TP=16, FP=12, FN=0
```

### 解读
- **R=1.0（不漏）**：学习的阈值比固定0.55更聪明，能识别出"快捷操控"vs"触摸操控"这种编辑距离小但语义不同的对
- **P=0.571（12个误报）**：训练集正例太少（正例只有同名对），模型学不到"相似但一致"的样本 → 把相似的一致对误判为矛盾
- 监督方法的数据依赖：**正例质量决定误报率**

## 2.6 方法B5：手写GCN（图神经网络）

### 思想
用图卷积让每个名称的表示**聚合邻居信息**——名称的最终向量不仅来自自身字符，还来自它连接的其他名称。

### 数学原理（完整推导）

```
① 邻接矩阵 A:
   A[i,j] = text_sim(名称i, 名称j) if sim ≥ 0.5 else 0
   A = A + I                          (加自环)

② 归一化: A_hat = D^(-1/2) A D^(-1/2)   (对称归一化)

③ 节点特征 X (字符bigram向量):
   对每个名称, 统计相邻2字符(bigram)出现次数
   例: "快捷操控" → {快捷:1, 捷操:1, 操控:1}
   归一化: X = X / X.sum(axis=1)

④ 两层图卷积:
   H1 = ReLU(A_hat @ X @ W1)      W1: bigram数×64
   H2 = A_hat @ H1 @ W2           W2: 64×32
   embeddings = L2归一化(H2)

⑤ 拓扑相似度: gcn_sim(a,b) = embeddings[a] · embeddings[b]

⑥ 判定矛盾: gcn_sim > 0.7 AND text_sim < 0.6
   (拓扑上很近, 但字面上不相似 → 可疑!)
```

### 为什么是"手写"
- 权重W1/W2是**随机初始化**（seed=42），没有反向传播训练——是"随机特征映射"而非"学习"
- 作用：**拓扑传播**——即使两个名称字面不相似，如果它们的邻居相似，嵌入也会靠近

### 评测结果
```
B5: P=1.0, R=0.5, F1=0.667, TP=8, FP=0, FN=8
```

### 解读
- 零误报（拓扑近+字面远 的双重条件很严格）
- 召回低（漏8个）：随机权重没有针对性，"拓扑近"的门槛太高

## 2.7 方法O1：图注意力（学习边权重）★最优

### 思想
B1用固定阈值建图，O1**学习**边权重：训练一个"名称对→矛盾概率"的分类器，用它重构图，再做连通分量。

### 特征设计（5维, 比B4多一维）

```
edge_feats(a,b):
  f1 = 1 - levenshtein/max_len     编辑距离归一化
  f2 = levenshtein                 原始距离
  f3 = |set(a)∩set(b)|/|set(a)∪set(b)|   字符Jaccard
  f4 = 1 if a[:2]==b[:2] else 0    前2字相同
  f5 = min(len(a),len(b))/max_len  长度比
```

### 训练数据（正+负对构造）

```python
pos: 同一实体的不同名称对 → label=1
     (来自entity_names, 同一rid内两两配对)
neg: 不同实体的名称对 → label=0
     (取前200个实体, 相邻实体的第一个名称配对)
     ← 注意: 这是"跨实体名称", 天然是负例
```

### 训练（300轮梯度下降, 与B4同款逻辑回归）

### 预测+构图

```python
edge_prob(a,b) = sigmoid(标准化特征 @ w + b)

G_learn: 全连接图, 边权重=预测的矛盾概率
  for 所有名称对:
      if edge_prob > 0.5:
          add_edge(a, b, weight=prob)

判定: 某实体的名称们在G_learn中 >1个连通分量 → 矛盾
```

### 与B4的区别（关键）
- B4: 直接对实体内的名称对做预测，**一对**判矛盾就报
- O1: 先用预测重构**全图**，再做连通分量——**利用传递性**（A~B相似, B~C相似, 则A,B,C聚一团）

### 评测结果
```
O1: P=1.0, R=0.812, F1=0.897, TP=13, FP=0, FN=3
```

### 解读（为什么最优）
- **P=1.0**：连通分量判定天然零误报（能连一起的必相似）
- **R=0.812**：学习的边概率>固定阈值0.55，识别出更多真实矛盾对（如"快捷操控"vs"触摸操控"概率>0.5被连上）
- **F1=0.897 = 7种方法最优**

## 2.8 方法O2：双空间（拓扑嵌入+文本）★本文方法

### 思想
B1-O1都在**文本相似度**这一个空间工作。O2把名称映射到**两个空间**：
- 拓扑空间：metapath嵌入（名称在异构图中的位置）→ 拓扑相似度
- 文本空间：编辑距离 → 文本相似度
**两个空间同时看**，拓扑近但文本远 = 强烈矛盾信号。

### 算法

```python
def detect_dual_space():
    # ① 构建异构图: 实体节点 + 名称节点
    G_hetero, _ = build_hetero_graph(entity_names)

    # ② 加名称-名称相似边(阈值0.5, 比语义图的0.55宽松)
    for 名称对(a,b) with 长度差≤4 and text_sim≥0.5:
        G_hetero.add_edge(M:a, M:b, type='similar', weight=sim)

    # ③ metapath随机游走嵌入 → 32维向量
    emb = metapath_embed(G_hetero, seed=42)

    # ④ 判定: 拓扑近 AND 文本远 → 矛盾
    for rid, names in entity_names.items():
        for 名称对(a,b) in names:
            topo = emb[M:a] · emb[M:b]      # 拓扑相似度
            text = text_sim(a, b)           # 文本相似度
            if topo > 0.7 and text < 0.6:   # 双条件
                detected.add(rid); break
```

### 数学原理（metapath嵌入, 见2.1）

```
为什么"拓扑近+文本远"是矛盾信号:
  同一实体的两个名称 → 通过 E:rid 连接 → metapath游走常共现
  → 嵌入向量方向接近 → topo高 ✓
  但如果它们文本也相似 → 可能只是排版差异(如"数据获取"vs"获取数据")
  → 需要 text < 0.6 排除这种"字面相近"情况
  两个名称拓扑近(同一实体) + 文本远(完全不同写法)
  → 大概率是真实的名称不一致矛盾!
```

### 评测结果
```
O2: P=1.0, R=0.75, F1=0.857, TP=12, FP=0, FN=4
```

### 解读
- 与O1相比召回略低（0.812 vs 0.75），因为双条件更严格
- 但**方法论价值**：展示了"拓扑+文本双空间"的检测思路——这是从"文本相似度"到"图结构理解"的跃迁
