# 技术框图理解与多模态一致性校验——技术方案调研报告

> 基于 pair_dataset（7场景、366多模态对）的内容理解与一致性校验技术路线调研
> 调研日期：2026-08-23
> 调研方式：文献调研（arXiv/基准测试）+ 本地实证试点（Visio源提取 / kimi-k2.6 VLM / RapidOCR）

---

## 0. 执行摘要（最重要的三个发现）

**发现1（决定性）：366张框图图片的"源文件"就藏在.doc里，可直接提取矢量结构**

16份.doc文件内嵌 **363个Visio XML(.vsdx)包 + 17个原生Visio(.vsd)对象 = 380个图形源**，与366张图片数量吻合。Visio XML中的 `visio/pages/page1.xml` 包含**精确的Shape文本、坐标和Connect连接关系**——这意味着框图的节点/边提取可以做到100%保真，完全绕开图像识别的不确定性。

**发现2（实证）：VLM/OCR对正常尺寸框图的节点文本提取已接近完美，但小图和拓扑提取仍是短板**

本地试点（kimi-k2.6 + RapidOCR vs Visio真值，见§1.5）：
- 用例图(11节点)：VLM P=1.00 R=1.00；OCR P=1.00 R=1.00
- 流程图(12节点)：VLM P=0.92 R=0.83；OCR P=0.93 R=0.92
- 小尺寸功能组成图(30节点，339×497px)：R≈0.20（两者都差）
- VLM边提取：召回Visio全部6条显式边，但多生成9条"逻辑合理但图中未必有"的边（过生成）

**发现3（方法论）：文献一致证明端到端VLM做框图结构化不可靠，主流是"视觉→中间文本表示→符号推理"两段式**

TextFlow (2412.16420)、SRA (2602.13771)、FloCA (2602.14035) 均采用 "Vision Textualizer → Mermaid/Graphviz中间表示 → Textual Reasoner" 架构，显著优于端到端VLM。我们的Visio源提取恰好是这一架构的"完美Vision Textualizer"。

## 1. 技术框图理解：四条路线对比

### 1.1 路线α：VLM直接理解

**文献证据**：

| 基准 | 结论 | 出处 |
|------|------|------|
| FlowLearn (ECAI 2024) | GPT-4V节点计数仅58%准确率；Claude OCR任务83%；无单一模型全面领先 | 2407.05183 |
| FlowVQA (ACL 2024 Findings) | 2272流程图+22.4K QA，空间推理是主要失败模式 | 2406.19237 |
| SADU (2026) | 软件架构图理解：最佳模型gemini-3-flash仅70.18%，gpt-4o-mini仅17.77% | 2604.04009 |
| ERUnderstand (2026) | ER图常见元素F1>0.74，但弱实体0.28、N元关系0.07 | 2607.24707 |
| Code-Vision (2025) | 流程图→代码：GPT-4o硬题79.3%，开源最好仅15% | 2502.11829 |
| C&P冲突 (EMNLP 2025) | GPT-4o的认知-感知一致性仅75.26% | 2411.07722 |

**本地实证**（kimi-k2.6，3张图 vs Visio真值）：
- 节点文本提取：正常尺寸图 P=0.92~1.00，R=0.83~1.00（远好于文献中的计数/推理任务，因为"抄节点文字"比"计数/推理"容易）
- 小图(339×497)：R=0.20 —— **120/366张图短边<300px，是VLM/OCR共同瓶颈**
- 边提取：召回6/6，但生成15条边（过生成9条）——拓扑可靠性不足

**结论**：VLM适合做**图类型分类、整体摘要、粗粒度元素列举**（团队已有 `vlm_image_analyzer.py` 输出163条流程图提取），**不适合作为一致性校验的唯一结构来源**——节点漏检会直接制造假阳性"不一致"。

### 1.2 路线β：OCR + 规则/几何结构化

**文献证据**：
- **FlowExtract** (2604.06770)：YOLOv8节点检测 + EasyOCR + 箭头方向分析（分析箭头朝向+回溯连线到源节点），边提取**显著超过VLM基线**
- **Arrow-Guided VLM** (2505.07864)：箭头感知检测+OCR+结构化prompt，整体准确率80%→89%，"下一步"问题25/30→30/30
- **RapidOCR/PaddleOCR**：文字检测+识别成熟，但不含拓扑

**本地实证**（RapidOCR onnx版，PaddleOCR 3.7.0已装但缺paddlepaddle框架）：
- 用例图：P=1.00 R=1.00（所有节点文字完整识别）
- 流程图：P=0.93 R=0.92（换行节点"调用Vscode\n开发编译"被切断成两条）
- 小图：R=0.17

**优点**：便宜、快、节点文本可靠、每个文字带bbox坐标（可用坐标做行/列聚类恢复层级）
**缺点**：无线条/箭头语义；换行文本需合并；小图仍需放大预处理

### 1.3 路线γ：专业图表解析工具（Mermaid/PlantUML生态）

- **TextFlow** (2412.16420)：VLM生成中间文本表示（Graphviz/Mermaid/PlantUML）→转为可执行图对象→LLM推理，FlowVQA/FlowLearn SOTA。**这是当前框图理解的主流架构**
- **SRA** (2602.13771)：在Mermaid边上附加语义关系标签（条件/因果），升级中间语言
- Mermaid/PlantUML解析器：`mermaid.ink`、`mermaid-cli`渲染，`plantuml`解析——**只处理已结构化的DSL，不做图像识别**；作用是把VLM/源文件输出规范化、可校验（编译通过=语法合法）
- 团队已有 `mermaid_render.py`、`vlm_flowchart_extract.py`（输出nodes/edges JSON）

**结论**：专业工具链的价值在**后端规范化与验证**，不在前端识别。

### 1.4 路线δ（本项目独有）：.doc内嵌Visio源直接提取 ★推荐主路线

**已验证的事实**：
```
16份.doc → ObjectPool → 363个Package流（全部是Visio XML .vsdx）+ 17个VisioDocument流（.vsd）
doc05: 19包+10原生vsd = 29个图形源；pair_dataset中doc05的图片可逐一文本匹配映射
```

**提取方法**（已验证可行的代码路径）：
1. `olefile` 打开.doc → 遍历 `ObjectPool/*/Package` 流
2. Package流是ZIP（PK头）→ 解压得 `visio/pages/page1.xml`
3. 解析XML：`<Shape>`含`<Text>`（节点文字，含换行）+ PinX/PinY坐标；`<Connect FromSheet/ToSheet/FromCell/ToCell>`含连接关系
4. 原生.vsd（17个）用LibreOffice转.vsdx后同法处理

**已知坑（试点发现）**：
- Connect记录只覆盖部分边（试点：流程图36条Connect记录只还原6条显式边）——其余连接线是几何摆放未"粘附"，需按坐标做端点吸附（Connecter的BeginX/EndY ↔ 最近Shape包围盒）
- 多个pair样本共享同一Visio源（如doc05的"开发集成"用例图与功能图引用同一包）——映射用**文本重叠匹配**可行（OCR文本∩包文本），需人工抽验

**意义**：
- 为**方向A（上下文关联）**提供完美聚合锚点：Visio源=同一实体的结构化定义
- 为**评测**提供天然Gold Standard：节点/边真值无需人工标注
- 论文定位：相当于XML-driven路线 (2502.04389，从xlsx/pptx源文件提取图形元数据绕过VLM) 在GJB SRS场景的实例化，同时VLM路线作为"无源文件的一般化方案"保留对比实验

## 2. 多模态对齐与一致性判断

### 2.1 总体架构：结构化中间表示 + 三类匹配

对齐的前提是三模态都转成**可比较的中间表示**（参考TextFlow/ProfiliTable设计）：

```
image.png ──(路线δ: Visio源 / 路线αβ: VLM+OCR)──> Graph{nodes[], edges[], node_types[]}
table.csv ──(结构化解析)──────────────────────> Rows[{名称, 标识, 属性...}]
text.txt ──(LLM抽取)──────────────────────────> Claims{功能列表, 步骤序列, 约束}
```

### 2.2 匹配方法一：集合匹配（sc1功能完整性 / sc3接口一致性）

**问题形式化**：G_nodes = {n₁...nₖ}（图中节点）vs T_rows = {t₁...tₘ}（表行名）
**核心是实体对齐**（中文短名词，无上下文）：

| 方法 | 适用 | 说明 |
|------|------|------|
| 精确匹配+规范化 | 第一层 | 去空格/全半角/换行后相等（试点显示多数可直接匹配）|
| 编辑距离/字符重叠 | 第二层 | 容忍OCR/VLM抄写差异（"调用Vscode"vs"调用vscode"）|
| 语义向量匹配 | 第三层 | bge-small-zh-v1.5（本地models/已有）余弦相似度，处理"数据获取"vs"数据引接汇聚" |
| LLM仲裁 | 兜底 | 相似度灰色地带(0.6~0.85)交LLM判断"是否同一功能"（DataFlow-MM的VLM Yes/No层思想）|

**输出**：`{matched_pairs, image_only(图中多余), table_only(表中有图无)}` → 不一致候选
**注意**（来自meta.json观察）：sc1用例图中含Actor（"开发人员""文件"）等非功能节点，需先做节点类型过滤（用例图椭圆=功能，小人=Actor，通过Visio master shape类型或VLM识别区分），否则"Actor不在表中"全是假阳性。

**文献支撑**：ProfiliTable (KDD 2026, 2605.12376)的Profiler→Evaluator→Summarizer闭环：Evaluator用**非LLM脚本**做确定性比对（GT隔离保证客观），Summarizer用ReAct复核"合理差异vs真实矛盾"——直接可借鉴为"集合差异的判定器"。

### 2.3 匹配方法二：流程/序列匹配（sc2流程一致性 / sc7用例步骤一致性）

**问题形式化**：
- 图侧：有向图G（流程图拓扑，来自Visio Connect+几何吸附）
- 表侧：主事件流步骤序列 S = [s₁...sₙ]（sc2表"Actor的动作/系统的动作"两列交错编号）
- text侧：正文叙述的动作顺序

**方法**：
1. **节点对齐**（同§2.2）建立图节点↔步骤的映射
2. **拓扑一致性**：对G做拓扑排序得所有线性路径；检查S是否是G中某条s-t路径的子序列（动态规划/图搜索，确定性算法，可用networkx）
3. **缺失检测**：S中步骤在G无对应节点 → 步骤缺失；G中节点不在任何S路径 → 图多余分支
4. **顺序矛盾**：S中sᵢ→sⱼ (i<j) 但G中只存在j→i路径 → 顺序不一致

**文献支撑**：
- FloCA (2602.14035)：把流程推理外包给"拓扑约束的图执行器"，LLM只做意图理解——证明**显式图+符号执行**比LLM直接推理可靠，正是我们要的架构
- Arrow-Guided VLM：方向错误是VLM主要失败模式，Visio Connect的FromCell/ToCell给出**权威方向**，彻底规避

**sc2特有的坑**（试点观察2_001）：
- 用例描述表CSV结构混乱：行内含"1.开发人员打开... 2．在工程中找到..."多步骤挤在一格，全角/半角句点混用（"1."与"2．"），需先做步骤切分规范化
- "异常流E1/E2"是流程图的分支出口，匹配时主事件流与异常流要分开比对

### 2.4 匹配方法三：语义蕴含匹配（NLI层，图文/文表）

**问题形式化**：text.txt的叙述 vs 图/表的结构化事实，判断是否矛盾

**DataFlow-MM参考设计**（references/README.md，三层漏斗）：
```
NLI层(bart-large-mnli, 阈值0.35) → CLIP/LongCLIP层 → VLM Yes/No层
"图文一致性"转化为"caption+question→answer的文本蕴含"
```

**本项目适配**（中文+SRS场景）：
1. **事实原子化**：把图/表结构化结果转成自然语言断言列表（"图3包含名为'结构化数据归集'的功能"），把正文也抽成断言
2. **中文NLI**：本地 `models/nli/` 只有config(BertForSequenceClassification)+vocab、**无权重**，需下载（推荐 `IDEA-CCNL/Erlangshen-Roberta-330M-NLI` 或 `hfl/chinese-roberta-wwm-ext`微调版；OCNLI/CMNLI数据集）
3. **LLM-as-NLI兜底**：GLM-5/kimi做三分类(蕴含/矛盾/中立)+证据引用，中文NLI模型做批量低成本初筛
4. **数值/标识比对兜底层**（DataFlow-MM README明确指出需补）：正则抽取编号（ZZSJHQZHFW-GN-SJHQ-*）、数值、单位，做确定性字符串/数值比对——这类不一致NLI抓不住，但规则百分百可靠

### 2.5 各场景的匹配类型矩阵

| 场景 | 对数 | 主匹配方法 | 辅助方法 | 已知难点 |
|------|------|-----------|---------|---------|
| sc1 用例图+能力表 | 141 | 集合匹配 | 节点类型过滤(Actor) | Actor/系统边界框误入集合 |
| sc2 流程图+用例表 | 90 | 流程序列匹配 | 步骤切分规范化 | CSV多步骤一格、异常流分支 |

## 3. 评测方案设计

### 3.1 核心思路：三层评测体系

**第一层：提取质量评测（能力评测，有真值）**

Visio源提取结果作为**免费Gold Standard**，评测VLM/OCR路线的：
- 节点级：Precision/Recall/F1（文字规范化后匹配）
- 边级：有向边F1（Visio Connect+几何吸附结果为真值）
- 图类型分类准确率（sc8的20张+全量）
- 中间表示合法性：VLM输出Mermaid能否通过mermaid-cli编译（TextFlow的校验思路）

这直接回应"无Gold Standard如何评测"——**提取层的真值问题被Visio源解决了**。

**第二层：一致性检测评测（任务评测，需标注）**

- **构建方法**：对366对跑全流水线→输出不一致候选→人工复核标注（每对标注：是否真不一致/不一致类型/严重度）。人工只复核机器候选，标注成本低
- **注入式合成**（参考旧gold_standard 3份合成SRS的做法+2606.25550的教训：LLM合成不一致不可靠，需人工复核）：对一致的样本做受控扰动（删表中一行/改图中一节点名/交换两步骤）生成已知不一致，保证评测有正例
- **match_quality分层报告**：strong(276)/medium(70)/none(20)分别报告，medium对（弱关联）是主要误差来源，单列分析
- **指标**：
  - 不一致检出：Recall(不一致对)、Precision、F1；按类型(sc1功能完整性...)分桶
  - 定位能力：不一致的**具体条目**（哪个节点/哪行/哪步）是否指对（item-level F1，比pair-level更严格）
  - 误报分析：合理差异（同义词、层级展开）被误判率

**第三层：端到端QA评测（可选，面向应用）**

团队已有 `gen_multimodal_qa.py`/`gen_qa_all_pairs.py`——多模态QA准确率作为下游任务指标（参考FlowVQA的任务设计：信息定位/决策/逻辑推进三类问题）。

### 3.2 参考基准与指标设计

| 基准 | 可借鉴点 |
|------|---------|
| FlowLearn/FlowVQA | 节点计数/定位/推理的分题型评测；人工验证流程 |
| M2-Verify (2604.01306) | 多模态断言一致性二分类+复杂度分级(低/高难度分开报告) |
| Recall_OCR+Precision_VE (2602.13376，已撤稿但方法可用) | 无参考质量监控：OCR覆盖率+视觉蕴含查幻觉——适合生产环境监控VLM提取质量 |
| SADU | counting+retrieval两类任务设计，11个VLM横评协议 |
| Requirement Smells (1611.08847等) | smell类型学+severity/frequency工业评估问卷设计 |

### 3.3 VLM选型评测（建议先做）

用Visio真值对以下模型做提取能力横评（每模型抽50张分层抽样图）：
- kimi-k2.6（已有API，实测正常尺寸图节点P/R≈1.0）
- GLM-5端点（ep-glsztk-…，需先验证是否支持image_url输入）
- 可选：GPT-4o/Claude/Qwen-VL-Max（若可及）

评测维度：节点P/R、边P/R、小图(<300px)专项、幻觉率(图中不存在的节点)、输出JSON格式稳定性。

## 4. 推荐技术路线

### 4.1 架构总览

```
                    ┌────────────────────────────────────────────┐
                    │  Layer 0: 源提取 (deterministic)           │
  16份.doc ──────►  │  olefile → Visio XML → {nodes,edges,pos}  │  ★主路线
                    │  (17个.vsd → LibreOffice转.vsdx)           │
                    └──────────────────┬─────────────────────────┘
                                       │ 结构真值 + 聚合锚点
   image.png ──► VLM(kimi-k2.6)+RapidOCR ──► Graph(候选)          │ ◄对比/兜底
   table.csv  ──► CSV规范化解析 ──► Rows                          │
   text.txt   ──► GLM-5断言抽取 ──► Claims                        │
                                       ▼
                    ┌────────────────────────────────────────────┐
                    │  Layer 1: 对齐 (alignment)                  │
                    │  规范化→精确/编辑距离→bge-zh向量→LLM仲裁    │
                    └──────────────────┬─────────────────────────┘
                                       ▼
                    ┌────────────────────────────────────────────┐
                    │  Layer 2: 一致性判定 (三层漏斗)              │
                    │  ① 规则层: 编号/数值/集合差(确定性脚本)      │
                    │  ② 符号层: 拓扑路径/networkx序列比对        │
                    │  ③ 语义层: 中文NLI → LLM三分类+证据         │
                    └──────────────────┬─────────────────────────┘
                                       ▼
                    ┌────────────────────────────────────────────┐
                    │  Layer 3: 复核 (Summarizer, 借鉴ProfiliTable)│
                    │  合理差异vs真实矛盾 仲裁 + 证据引用输出      │
                    └────────────────────────────────────────────┘
```

### 4.2 关键设计决策及理由

| 决策 | 理由 |
|------|------|
| Visio源为主、VLM为辅 | 源提取100%保真；VLM作为(a)无源文件场景的一般化方法(b)源缺失时的兜底(c)论文对比基线 |
| 节点文本用OCR复核而非替代 | OCR对正常图P=1.0且便宜；VLM做类型分类+边提取辅助 |
| 规则层在前、LLM在后 | 编号(ZZSJHQZHFW-*)/数值/集合差异用确定性脚本零幻觉（ProfiliTable的GT隔离思想）；LLM只处理语义灰色地带，可解释、可复现 |
| 中文NLI本地模型+LLM双层 | 批量初筛低成本（DataFlow-MM漏斗思想），LLM兜底+给证据 |
| 借助网络时序保留**图片↔Visio源映射表** | 一切评测的前提基础设施，文本重叠匹配已验证可行 |

## 5. 具体实施步骤（建议4个里程碑）

### M1：基础设施——源提取与映射（~3天，全部确定性工作）
1. `tools/visio_source_extract.py`：16份.doc → 380个图形源 → `data/gjb_438c/visio_sources/{doc}/{obj_id}.json`（nodes含坐标/类型、edges含方向、master shape类型）
2. .vsd→.vsdx转换（LibreOffice headless批处理17个）
3. 图片↔源映射：OCR全量366图 → 文本重叠匹配（源文本∩OCR文本评分）→ 映射表+置信度；低置信度人工抽验；产出 `pair_dataset/*/source.json`
4. Connect几何吸附：无Connect记录的连接线按BeginX/EndY坐标吸附最近Shape → 补全边
5. **产出**：`visio_groundtruth.json`（366对的节点/边真值）——后续一切评测的地基

### M2：提取能力评测（~2天，决定VLM选型）
1. 分层抽样50图（按场景×尺寸分桶），kimi-k2.6/GLM-5(若支持视觉)做节点+边提取
2. vs Visio真值算P/R/F1（节点、边、分尺寸分桶）
3. 小图专项：放大预处理(2-4x LANCZOS)前后对比
4. **产出**：VLM能力报告+选定配置；论文的"框图理解难度"实证章节素材

### M3：对齐与一致性检测流水线（~5天）
1. `tools/pair_align.py`：三模态→中间表示（Graph/Rows/Claims）；实体对齐四层（精确/编辑距离/bge/LLM仲裁）
2. `tools/consistency_rules.py`：规则层——集合差异、编号格式（GJB规则库正则）、数值比对、方向(发送方/接收方)比对
3. `tools/consistency_flow.py`：符号层——networkx拓扑排序+路径子序列比对（sc2/sc7）
4. `tools/consistency_nli.py`：语义层——断言原子化+中文NLI（先下载Erlangshen-NLI权重）+LLM三分类
5. `tools/consistency_review.py`：Summarizer复核（合理差异vs矛盾，输出证据引用）
6. **产出**：366对全量检测结果JSON

### M4：Gold Standard与评测报告（~4天）
1. 人工复核机器候选：标注每对{真/假不一致, 类型, 严重度, 定位是否正确}
2. 受控扰动注入合成不一致（表删行/图换节点/步骤交换各50例）
3. 计算指标：pair-level与item-level的P/R/F1，按场景×match_quality×不一致类型分桶
4. 消融：去规则层/去NLI层/去符号层/VLM-only vs Visio源
5. **产出**：评测报告（论文实验章节素材）

**总计约14个工作日**，M1完成即可解锁M2/M3并行。

## 6. 风险与开放问题

| 风险 | 缓解 |
|------|------|
| 图片↔Visio源映射错误（试点已见：同一图被多节引用、功能图可能引用多包） | 映射置信度分级；低置信度用渲染对比（vsdx→PNG像素相似度）二次校验；映射表人工抽验5% |
| 部分功能组成图疑似对应原生.vsd或跨包组合 | LibreOffice转换覆盖；仍失败的列入"无源"名单走VLM路线（保留论文一般化叙事） |
| Connect几何吸附在交叉线多的接口图上出错 | 吸附结果与VLM边提取交叉验证，不一致的边降置信度 |
| 中文NLI模型质量 | M3先用LLM-as-NLI跑通，本地NLI作为降本优化项后置 |
| sc2用例表CSV结构混乱（多步骤一格、全半角混用） | 先写CSV规范化预处理（步骤切分正则），属于M3第一步 |
| medium对(70个)的弱关联导致大量假阳性 | 分层报告；Summarizer复核层重点处理；必要时medium单独阈值 |
