## 一、项目概况

### 1.1 目标

基于16份真实军事信息系统SRS文档，解决两个正交问题：


| 方向                    | 问题                                                          | 产出                           |
| ----------------------- | ------------------------------------------------------------- | ------------------------------ |
| **方向A：上下文关联**   | 同一需求分散在正文/表格/图片/追溯表多处，如何聚合成一个条目？ | 聚合条目（实体+所有出现位置）  |
| **方向B：不一致性检测** | 给定聚合条目，如何检测其中的矛盾？                            | 检测结果（语法/语义/逻辑三层） |

### 1.2 技术栈（全部复用成熟开源技术）


| 组件       | 技术                                      | 来源                           |
| ---------- | ----------------------------------------- | ------------------------------ |
| 文档解析   | MinerU + textutil(Apple官方) 双源独立解析 | 开源+系统工具                  |
| 结构化切片 | 章节感知切片(500token窗口+50重叠)         | 借鉴GraphRAG TokenTextSplitter |
| 知识图谱   | LightRAG 1.5.6 (图+向量双通道)            | HKU开源                        |
| LLM        | kimi-k2.6 (moonshot)                      | 商用API                        |
| VLM        | kimi-k2.6 视觉 (图片理解)                 | 商用API                        |

| 逻辑求解   | Z3 (SMT求解器)                            | 微软开源                       |

## 二、数据管道（16份.doc → 结构化资产）

```
16份.doc (GJB 438C)
  │
  ├─ textutil 独立解析 ──→ dual_source/*.html   (交叉验证用)
  │
  └─ MinerU 深度解析 ──→ content_list.json (结构化条目流: 文本/表格/图片)
        │
        ├─ 基于章节感知切片 ──→ srs_chunks.json      (5231条: 3643文本+1207表格+381图片)
        │
        ├─ VLM图片理解 ──→ srs_image_analyses.json (379张: 图类型+图内实体)
        │
        ├─ ID-Graph构建 ──→ id_document_graph.json (2181节点: 568实体+1613提及)
        │
        └─ LightRAG索引 ──→ lightrag_store/ (11872实体+23449关系, 13/16份)
```

**关键设计**：

- **双源独立解析**（MinerU与textutil互不相关）——为可信度奠基

- **中文领域适配**：实体类型定制为`软件功能/需求编号/接口/数据项/硬件设备`

## 三、方向A：上下文关联（核心工作）

### 3.1 方法：双图融合聚合器（4通道召回）

给定实体名或需求ID，从4个互补通道召回该实体的**所有出现位置**：

```
查询(实体名/ID)
  │
  ├─① ID-Graph硬桥     ID → 8类位置(正文/能力表/接口表/合格性表/追溯表/用例表)
  │                     · GJB需求ID是全局唯一锚点 → 零误报确定性关联
  │
  ├─② LightRAG语义图   实体名 → 所在chunks + 关系邻居
  │                     · 语义泛化(中英/缩写变体)
  │
  ├─③ VLM图片匹配      实体名 ∈ 379张图的关键元素
  │                     · 图文实体对齐(图内"结构化数据归集"与正文同一实体)
  │
  └─④ 结构化chunks     实体名/ID/关键词三层匹配
                        · 精确位置(章节)+类型(文本/表格)
  │
  ▼
聚合条目 = {entity, entity_id, occurrences[{location,section,snippet,doc}],
            chain_completeness}
```

**聚合示例**（实体"创建服务工程"）：

```
[table@3.2.1]  能力标识表   创建服务工程（PZXQ-GN-FWKFZC-CJFWGC）
[text@3.2.1.1] 正文        3.2.1.1 创建服务工程（PZXQ-GN-FWKFZC-CJFWGC）
[text@3.2.1.2] 正文        3.2.1.2 修改服务工程
[text@3.2.1.3] 正文        3.2.1.3 删除服务工程
[figure]       用例图      图4 创建服务工程用例描述
→ chain_completeness = 2/3 = 0.67
```

### 3.2 评测：300条查询对，5方法对比

**评测集构建**（LLM生成+确定性标注）：

- 从图谱采样100实体（60%有ID实体+40%语义实体）
- kimi为每个实体生成3种问法（功能定义/结构/溯源）→ 300查询
- 三通道确定性标注期望召回（chunks/sections/locations）

**结果**：


| 方法                  | avg_recall | 耗时/查询 |
| --------------------- | :--------: | :-------: |
| M1 纯向量检索         |   0.577   |   0.04s   |
| M2 图谱邻域           |   0.652   |   0.50s   |
| M3 图+向量混合        |   0.654   |   0.52s   |
| M4 ID硬桥(单独)       |   0.000*   |   0.00s   |
| **M5 双图融合(Ours)** | **0.809** | **0.01s** |

*M4得0分系评测集设计限制（300条查询仅3条含ID），非方法失效——这正说明**双图融合的互补价值**：ID桥需要名称侧通道配合才有用。

**结论**：双图融合比最强单方法(mix)提升 **+15.5个百分点**，速度快 **52倍**，且完全可复现（无LLM调用）。

### 3.3 为什么可信


| 可信度论据     | 说明                                               |
| -------------- | -------------------------------------------------- |
| 确定性算法     | 4通道均为预计算索引+规则匹配，无随机性，结果可复现 |
| 评测集独立标注 | 期望召回由三通道确定性合并，非LLM自评              |
| 多模态验证     | 48条图文QA全部通过图片存在性校验(48/48)            |
| 领域锚点       | GJB需求ID是规范定义的全局唯一标识，ID桥零误报      |

## 四、方向B：不一致性检测（三层校验）

### 4.1 检测体系

```
方向A聚合条目 → 方向B三层检测
  │
  ├─ 语法层: 格式/编号/结构合规 (GJB 438C规则库驱动)
  ├─ 语义层: 同一实体不同位置的值/名称/描述是否一致
  └─ 逻辑层: 约束是否可满足 (专家知识+知识图谱+Z3)
```

### 4.2 语法层检测（112条检出）


| 规则 | 检测内容                 | 检出数 |
| ---- | ------------------------ | :----: |
| S1   | 章节编号连续性           |   1   |
| S2   | 需求ID重复定义(标题位置) | **15** |
| S4   | 图/表引用完整性          |   90   |
| S5   | 章节结构完整性(GJB 6章)  |   5   |
| S7   | 交叉引用完整性           |   1   |

**亮点**：S2检出的`PZXQ-GN-JMJCKJ-JMJC-KJCK`重复定义，**正是人工Gold Standard中的真实矛盾对**（"快捷操控"vs"触摸操控"）——语法层信号与语义层标注交叉印证。

### 4.4 逻辑层检测（专家知识+知识图谱+LLM）


| 规则             | 方法                                       |            检出            |
| ---------------- | ------------------------------------------ | :------------------------: |
| L1 参数约束冲突  | 专家词典(23参数+4硬件)识别→区间交集→矛盾 | 1真实("存储"256GB vs 56GB) |
| L2 允许/禁止矛盾 | 规则初筛→**kimi语义验证**(消除语境误报)   |    0(2候选均判语境差异)    |

### 5.3 合成方法细节（为什么可信）

**Gold Standard合成**：

```
真实矛盾(79条): 同一需求ID出现≥2个不同名称 → 双源+双模型确认
注入矛盾(91条):  对一致实体注入5种子类型名称
  · typo错字:  "触摸操控"→"触摸操拄"
  · multiname:  多名一用
  · truncation: "服务工程创建"→"服务工程"
  · semantic:   允许vs禁止同操作
  · charorder:  "数据获取"→"获取数据"
```

**描述级合成（单点扰动，保证可控性）**：

```
正例: 273条原始描述
负例: 每条描述只改一个点
  · "支持FTP" → "不支持FTP"
  · "响应时间≤100ms" → "响应时间≥100ms"
→ 保证负例与正例仅差一个语义点，检测难度可控
```

### 5.4 质量验证矩阵（多源互证）


| 验证              | 方法                             |                 结果                 |
| ----------------- | -------------------------------- | :----------------------------------: |
| V1 双源交叉       | MinerU+textutil**独立解析源**    |             31/31 = 100%             |
| V2 双模型标注     | kimi+claude**独立模型**判断132对 |              92.4%一致              |
| V3 VLM-OCR        | tesseract**独立OCR**验证图片实体 |           抽样10/10无幻觉           |
| V5 语法×语义交叉 | S2重复ID vs GS矛盾实体           |               8/15命中               |
| V6 评测协议       | 分层+holdout(解封前不可见)       |              综合97.5%              |
| V7 基线对比       | vs 字符级基线                    | 名称级F1=0.969(与基线相同→需描述级) |

**可信度论证（为什么这套数据可信）**：

1. **独立性**：数据真实性由3个互不相关的来源交叉验证（MinerU/textutil/tesseract）
2. **确定性**：合成采用规则化扰动（单点修改），每个负例可追溯到修改点
3. **领域锚点**：真实矛盾以GJB需求ID为锚，ID是规范定义的全局唯一标识
4. **防假高**：评测协议含10% holdout（评测前不可见）+ 难度分层
5. **交叉印证**：语法层机器检出 ↔ 语义层人工标注 相互验证（KJCK样本）
