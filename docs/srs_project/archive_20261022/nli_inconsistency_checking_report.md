# SRS跨模态不一致性检测方案
## ——基于自然语言推理（NLI）的分歧复核方法

> 版本: 2026-09-13（面向未接触本项目的读者；文中不使用任何内部代号，
> 概念在首次出现处定义；全部数字经当日重跑核实，附录给出可复现入口）

---

## 1 我们要检测什么

### 1.1 背景

本项目的数据是**16份真实军事信息系统需求规格说明书**（GJB 438C格式，
约44MB的Word文档）。这类文档有一个显著特点：**同一个功能会在多个
位置、以多种模态被描述**——

- 3.2节用**表格**列出"功能划分/能力标识"（每个功能有名称和唯一标识ID）；
- 3.2.x节配**图**（用例图/流程图/接口图，以OLE方式内嵌Visio绘制）；
- 同节的**正文**段落再描述一遍（"本功能提供XX，包括A、B、C"）。

表格、图、正文**本应互相一致**，但真实文档中经常出现矛盾：表格列了8个
功能、图里只画了6个；正文说异常处理走流程E2、图里画的分支指向E1；
表格中"删除数据"的发送方是应用软件、图里箭头方向相反。

**我们要检测的"不一致性"就是这些跨模态矛盾。**

### 1.2 检测单元

文档被解析后切分为**证据对（pair）**：每个pair =（一张表、一张图、
一段正文），共**366对**，覆盖7种场景：

| 场景 | 对数 | 含义 |
|---|---|---|
| 用例图 ↔ 能力表 | 141 | 功能列表与用例图 |
| 流程图 ↔ 用例描述表 | 90 | 步骤序列与流程图 |
| 接口图 ↔ 接口表 | 30 | 接口清单与接口拓扑图 |
| 流程图 ↔ 能力表 | 49 | 功能列表与流程图（步骤改写） |
| 功能结构图 ↔ 子功能表 | 27 | 子功能树与结构图 |
| 用例图 ↔ 用例描述表 | 9 | 用例模型双视图 |
| 纯图（无表无正文） | 20 | 不参与本方案（无对照物） |

**参与检测的为前六类共346对**（纯图无对照物不参与）。
**诚实说明覆盖范围**：场景组合均为"表↔图"对照；正文模态当前只在
两处间接参与（声明构造的语境线索、银标裁决的证据上下文），**正文
与表格/图的独立比对（如"正文说4类功能、表格只有3行"）尚未作为
独立检测对象**——这是已知的能力边界，不是笔误。

### 1.3 一个关键事实：图是"数字原生"的

这批文档中的图以**OLE对象内嵌Visio源文件**——这意味着不需要"看图
识别"，直接解析XML就能得到**零误差的图结构**（节点、文字、边、坐标）。
我们称其为**锚点**（anchor）：373张图、3759个节点、2680条边，全部
从Visio XML确定性解析获得。这个事实是整个方案的地基——**图侧证据
逐字可信，识别误差不存在**。

## 2 总体方法：三阶段流水线

不一致性检测被组织成三个阶段，各自解决一个性质不同的问题：

```
┌─────────────────────────────────────────────────────────────┐
│ 阶段一·发现     阶段二·复核       阶段三·裁决              │
│ 词法比对       NLI语义核对       LLM惯例判断                │
│ (本文重点)                                                        │
│                                                                 │
│ 输入: 证据对    输入: 分歧清单    输入: 复核后的分歧          │
│ 输出: 分歧      输出: 矛盾信号    输出: 三分类标签            │
│ "表有图无"     "内容是否真的     "差异是否构成缺陷"          │
│                不一致"                                        │
└─────────────────────────────────────────────────────────────┘
```

**为什么需要三个阶段**——每类问题需要不同的能力：

| 问题 | 需要什么 | 谁来做 |
|---|---|---|
| 表格与图哪里对不上 | 字面匹配（快、确定、免费） | 词法比对 |
| 差异是真实存在还是匹配误报 | **语义判断**（图文内容是否真矛盾） | **NLI（本文重点）** |
![图1 三阶段流水线：每阶段的输入输出与责任划分](figures/nli_pipeline.svg)

*图1 三阶段流水线：每阶段的输入输出与责任划分（矢量图，浏览器打开可缩放）*


| 真实差异是否违反文档惯例 | 领域知识（UML/GJB绘图惯例） | LLM裁决+人工 |

本文重点报告阶段二的NLI方法；阶段一、三作为上下文简要说明。

## 3 阶段一：分歧发现（词法比对）

把每对pair的表格与图做**结构化对齐**：

1. **表格编译**：将表格解析为结构化条目（功能名+ID、步骤序列、
   接口名+发送方/接收方等）；
2. **匹配打分**：表格条目与图节点逐一做确定性词法匹配，得分体系为：
   精确相同（1.0）> 一方是另一方子串（0.9）> 剥离功能词后包含（0.88）
   > 同义字归一后包含（0.88）> 接口名解包匹配（0.86）> 单字编辑容错
   （0.85）> 字符重叠度（按4字窗口Jaccard计），阈值0.5，词法不过再走
   语义向量余弦补充（阈值0.62）；
3. **产出分歧**：匹配不上的条目成为**分歧**（如"表格项『半结构化
   数据源引接』在图中无匹配"）。346对共产生**1005条分歧**
   （sc1/3/4/5场景579条 + sc2场景426条）。

分歧≠不一致——它是**嫌疑清单**，混杂着三种性质完全不同的情况
（见§5.1），后续阶段负责甄别。

## 4 阶段二：NLI分歧复核（本文重点）

### 4.1 动机：直接用NLI判不了SRS的枚举矛盾

自然语言推理（NLI）模型判断"前提是否蕴含/矛盾于假设"，看似天然
适合一致性检测。我们部署了两个本地NLI模型：**mDeBERTa-v3-base**
（560MB，多语言，XNLI+200万样本训练）与**Erlangshen-RoBERTa-110M**
（中文专用，对照用）。但**零样本直接使用会系统性失败**——我们用
真实SRS语句对做了验证（14条，mDeBERTa）：

| 前提 | 假设 | 期望 | NLI实际判定 |
|---|---|---|---|
| 功能包括：插入、删除、查询 | 功能包括：插入、删除、查询 | 蕴含 | 蕴含 ✓ |
| 功能包括：插入、删除、查询 | 功能包括：修改、查询、插入 | **矛盾** | **蕴含 ✗** |
| 查询最多1000条 | 查询最多500条 | 矛盾 | 矛盾 ✓ |
| A调用B的接口 | B调用A的接口 | 矛盾 | 矛盾 ✓ |

**失败模式**：枚举集合的成员替换（删除↔修改）被判为蕴含。机理是
NLI训练数据（XNLI类）中"部分重叠"不算矛盾——但需求文档中**子功能
清单是穷举语义**，换一个成员就是规格变更。

### 4.2 方法一：闭世界声明模板

我们把每条分歧编译为**自然语言声明对**，关键技巧是在被验证侧声明
加上"**除此之外没有其他……**"的闭世界后缀，把集合差异显式化为
NLI可判的矛盾：

```
前提（表格侧）: 能力表规定，「X」的子功能共2项，包括：A、B，除此之外没有其他子功能。
假设（图侧）:   图中显示，与「X」直接相连的节点共1个，包括：A，除此之外没有其他相连节点。
```

实测对照（同日复现验证）：

| 声明形式 | 计数缺失型差异 | 结论 |
|---|---|---|
| 裸枚举（"包括A、B" vs "包括A"） | 判蕴含（失败） | 不可用 |
| **闭世界模板** | **判矛盾，置信1.00，双向一致** | 修复生效 |

闭世界模板的可解释之处
![图2 闭世界声明模板与双向对称准则](figures/nli_closed_world.svg)

*图2 闭世界声明模板与双向对称准则（矢量图，浏览器打开可缩放）*

：它把文档的隐含约定（"功能清单是完整注册表"）
显式写进声明，使逻辑上本就成立的矛盾（声明了只有A、B却只画了A）
进入NLI的判定范围。

**模板的边界（如实报告）**：闭世界修复的是**计数/缺失型**矛盾；
**成员替换**（声明{A,B}，图中是{A,C}，计数相同）NLI仍判中立——
这在逻辑上是对的（两个不同子功能可以共存，非必然矛盾），成员身份
核对需要编辑距离/词法工具，属于能力分工而非缺陷。

### 4.3 方法二：分歧驱动的声明构造

每条分歧按其类型构造专门的声明对（构造率649/664=97.7%）：

| 分歧类型（条数） | 声明构造方式 |
|---|---|
| 表格项在图中缺失（225） | 前提="「X」是「父功能」的子功能"，假设=图的全部节点闭世界枚举 |
| 参与者在图中缺失（125） | 前提="本用例的参与者(Actor)包括「X」"，假设=图节点闭世界 |
| 步骤在图中缺失（100） | 前提="本用例的执行步骤包括「X」"，假设=图节点闭世界 |
| 异常流在图中缺失（63） | 前提="本用例的异常流包括「X」"，假设=图节点闭世界 |
| 图中多余元素（109） | 双侧闭世界计数对照（表格条目清单 vs 图节点清单） |
| 接口组件缺失（39） | 前提="接口表包含条目「X」"，假设=图节点闭世界 |
| 步骤顺序矛盾（1） | 前提=表格顺序声明，假设=图顺序声明 |
| 用例名不一致（2） | 前提=表侧用例名，假设=图侧用例名（同指性判断） |

假设侧的图节点清单**直接来自Visio锚点**（§1.3），因此**不存在
"识别错误污染声明"的风险**——声明忠实于文档字面。

**实体名提取**：分歧记录中的证据文本（如"表格项『半结构化数据源
引接』在图中无匹配"）用正则提取「」中的实体名。层级关系（"X是
哪个功能的子功能"）从表格的ID前缀结构恢复（子功能ID=父功能ID的
延长，如 `父ID-JGSJGJ` → `父ID-JGSJGJ-RWZD`）。

**截断文本对齐**：Visio图中约30%的节点文字被绘制时截断（如
"半结构化数据归集"→"半构化数据归集"，缺中间字）。我们实现了
**离散子序列对齐**：若节点文字是表格名的保序子序列（非连续包含），
判为同一实体（固定得分0.92，经验值——介于"连续包含"与"编辑容错"
之间以避免与兄弟名混淆），区别于连续包含的兄弟名（如
"结构化数据归集"是"半结构化数据归集"的连续子串但语义为不同功能）。
这使NLI声明的实体两侧能正确对上。

### 4.4 方法三：双向对称矛盾准则

NLI方向敏感（前提→假设 ≠ 假设→前提）。我们对每对声明做**双向
推理**：

- `sym_contra`（**双向均为矛盾**）= 强矛盾信号——**评测与使用的
  工作点**即"sym_contra=真"判矛盾（该工作点的指标见§6.1）；
- `contra_score = min(正向矛盾概率, 逆向矛盾概率)` = 排序分
  （AUC指标基于此分数）。

双向下界天然抑制单向模型偏置：实测中观察到的单向"矛盾"案例
（正向矛盾概率高、逆向近零）经人工核查均为假阳性，对称准则将其
自动过滤（逻辑上矛盾应当对称）。

### 4.5 阶段二的产出

对每条分歧输出：矛盾/中立/蕴含判定+双向矛盾概率+对称矛盾标志。
它回答的问题是"**内容是否真的不一致**"（复核），不回答"差异是否
合理"（那需要阶段三的惯例知识）。

## 5 标签从哪里来（数据集与可信度）

这是本方案最需要说清楚的部分：**我们的评测标签不是人工标注的**，
是在没有标注预算的约束下，用一套可审计的协议构造的**LLM聚合银标**。
下面完整陈述其构建过程、判定标准、可信度证据与已知偏差。

### 5.1 标签的语义定义：分歧的责任归属

阶段一产出的分歧，本质上是三种**责任归属完全不同**的情况：

| 标签 | 含义 | 责任方 | 需求工程师该做什么 |
|---|---|---|---|
| `real_bug` 真实缺陷 | 文档该表示的内容图里确实缺失/矛盾 | 文档作者 | 修文档 |
| `benign_variation` 合理差异 | 差异来自绘图惯例与粒度取舍 | 无责任人 | 不需要修 |
| `compiler_bug` 引擎误报 | 图中实际有对应元素，表述差异导致自动匹配没认出来 | 我们的匹配引擎 | 无需人工处理，应被自动消化 |

**每类一个真实实例**（取自裁决记录）：

- `real_bug`：某文档"用户管理"用例描述表规定了登录失败三次锁定的
  异常流E3，流程图中无对应分支——文档声称流程图完整描述该用例，
  异常分支确实缺失 → 判定真实缺陷，需修图；
- `benign_variation`：某文档接口表列出30个接口，接口图只画了主要
  接口——GJB绘图惯例允许"图示主要项、表格为完整清单" → 合理差异；
- `compiler_bug`：图中存在节点"半结构化数据源引"（文字被截断），
  词法匹配失败产生"表格项在图中无匹配"的分歧——图里实际有该
  元素 → 引擎误报（§6.1中NLI自动消化的正是这类）。

### 5.2 标签构建协议（三步）

> **先说清一件事**：银标生产用的双LLM裁决，本身就是阶段三"裁决"
> 在评测集上的一次运行。这构成本方案内部的明确切割——**本文评测的
> 是阶段二（NLI复核）**：NLI不看图、不看两个LLM的任何意见，与
> 银标生产过程无信息接触，因此"用银标评NLI"不存在循环评测；
> 但若将来要评测阶段三本身（LLM裁决质量），必须另建人工金标，
> 不能用这份银标。

**第一步·双LLM异构独立裁决**。对每条分歧，两个**信息源不同的**LLM
独立做三分类：

- **kimi-k2.6**：看**渲染后的图片**（模拟"人看图"）；
- **GLM**：只看**锚点结构与表格**（**不看图**）。

> 为什么强调"异构"？如果两个模型看同样的输入，一致只是"复读"。
> 视觉通道与结构通道的信息源不同，一致意见才有交叉验证的价值。

覆盖1005条分歧中的**702条**（覆盖范围如实说明：sc2场景的426条
裁决了417条（9条因提取错误排除）；sc1/3/4/5场景的579条裁决了
285条——**只覆盖"表格项/组件在图中缺失"两类的高置信子集**，
"图中多余元素"型211条及缺失型的其余83条未纳入双LLM裁决——当时的裁决预算优先给了举证方向明确的"缺失型"（该不该画由文档声明判定），"图多余是否合理"的裁决被延后），
双方一致率**51.6%**（362/702）——一致部分直接采纳为该条标签（362条）。

**第二步·分歧票集成**。双方意见不一致的条目进入**五路投票**，
五票刻意设计为互补视角：

| 票 | 视角 |
|---|---|
| 1 | kimi看图（首轮意见） |
| 2 | GLM看结构（首轮意见） |
| 3 | kimi增强（图+粒度判定规则+正文上下文） |
| 4 | GLM简化（"表格项X在图节点清单中有对应元素吗"——单问题直查） |
| 5 | kimi纯文本（无图视角） |

**≥3/5多数才裁决**，否则保持"未决"。此步解决302条。

**第三步·账目闭环**。裁决702条 = 362（双LLM一致）+ 302（五票多数）+
38（五票无多数，最终保持未决，**不进入评测**）。未裁决的303条
（1005−702，见§5.2覆盖说明）同样不进入评测。最终银标664条：

| 标签 | 条数 | 占比 |
|---|---|---|
| benign_variation | 378 | 56.9% |
| real_bug | 176 | 26.5% |
| compiler_bug | 110 | 16.6% |

（"真实不一致率"π=0.265，即约四分之一的分歧是真实缺陷。）

**判定给LLM的标准**（三轮裁决的提示词逐步细化，最终版判定细则，
按优先级）：

1. 图中存在与该项**语义对应**的元素（表述不同但同一事物）→
   `compiler_bug`（匹配失败）；
2. 图按文档惯例本就不画此类内容（用例图不画异常流分支/表格是完整
   清单而图只画主要项）→ `benign_variation`；
3. 文档声称图覆盖该项所属类别（如"图描述全部用例"）而图确实缺失 →
   `real_bug`；
4. 拿不准时倾向`benign_variation`——**举证责任在"报缺陷"一方**
   （差异不构成缺陷是默认假设）。

### 5.3 可信度论证（正面回答"为什么可用"）
![图3 标签账目闭环：1005→702→664全链路](figures/nli_label_lineage.svg)

*图3 标签账目闭环：1005→702→664全链路（矢量图，浏览器打开可缩放）*



**支持银标可信的证据**：

1. **协议设计**：异构信息源（看图vs看结构）+ 多数投票 + 举证责任
   约定——三重机制抑制单模型偏差；
2. **独立复核的反向验证**：本方案的NLI复核器（**不看图、不看LLM
   意见**，只对声明对做语义推理）在"误报复核"任务上与银标一致性
   达AUC=0.795（§6.1）——一个完全独立的第三意见与银标高度一致，
   反向支持银标在compiler/真差异这一划分上的质量；
3. **账目可审计**：每条标签可追溯至裁决记录（双方原始意见+理由
   均保留在案），664+38=702全账目对平，无黑箱数字。

**已知偏差（如实陈述）**：

1. kimi系统偏宽松（倾向benign）、GLM偏严格（倾向real）——五票中
   kimi系3票/GLM系2票，集成结果可能略偏benign；
2. 银标未经人工金标校验——51.6%的双LLM一致率意味着近半数条目是
   "投票决定"而非"共识"；人工抽检尚未完成；
3. 评测集是**词法比对筛过的分歧子集**（有分歧才有标签），天然排除了
   "词法已匹配一致"的pair——这是选择偏差，NLI在无分歧pair上的表现
   未测。

**改进承诺**：38条未决+160条抽检样本的人工仲裁清单已备好，完成后
银标可升级为金标，全部评测脚本可直接重跑对照。

## 6 实验结果

### 6.1 误报复核（NLI的核心价值）

**任务定义**：对每条分歧，判断"内容是否真的不一致"——
引擎误报（图里其实有）vs 真差异（图里确实没有/不同）。

**评测范围**：664条银标中，NLI可构造出声明对的**649条**（97.7%；
排除的15条：9条分歧证据里的实体名提取失败——如接口表"接收方=高"
的优先级值被分歧记录误当组件名、4条该对表格本身解析失败、2条图侧
无从提取名称）。下表数字均在这649条上计算（引擎误报109条+真差异
540条）。**工作点="双向均为矛盾"判矛盾**。

| 指标 | 值 | 说明 |
|---|---|---|
| 精确率 | **0.971** | 判矛盾时97%确实是真差异 |
| **召回率** | **0.548** | **真差异中仅54.8%产生双向矛盾信号（见漏检分析）** |
| F1 | 0.701 | |
| AUC | 0.795 | 双向矛盾概率下界的排序能力（软信号） |
| 混淆矩阵 | tp=296 / fp=9 / fn=244 / tn=100 | 真差异→矛盾296；误报→矛盾9；真差异→非矛盾244；误报→非矛盾100 |
| **引擎误报自动消化** | **100/109（91.7%）** | **核心成果** |

**9条误报被误判为矛盾的构成**（当日从实验记录逐条核验）：3条
表格项缺失型（图中有该功能但图形/名称差异大，NLI误认图中没有，
如"语音合成"）、3条步骤缺失型、3条图中多余型。无系统性模式。

**漏检分析（244条真差异未产生矛盾信号——如实披露）**：
从实验记录核验其构成——**186条（76%）为"单向矛盾"**（正向推理
判矛盾、逆向不矛盾，被双向对称准则过滤）、57条判中立、1条判蕴含。
即漏检的主体**不是NRI完全没识别，而是对称准则的保守性**：该准则
以牺牲召回换取精确（正向矛盾含模型偏置，双向一致才可信）。若采用
"正向矛盾"作为工作点，召回率上升而精确率下降——AUC=0.795的排序
信号支持按应用场景选择工作点（高置信自动化用双向，人机协作用单向）。

**工程意义**：银标664条中16.6%是引擎误报，NLI在本地GPU上对649条
声明对推理共3.7秒，**免费**消化其中91.7%——这些原本要消耗LLM裁决
预算（该银标的生产约消耗2300次LLM调用，按账目：双LLM首轮702×2
=1404次+五票集成补投302×3=906次；NLI复核同等覆盖的边际成本为零，
且本地可复现）。典型被消化案例：图中明明有"半结构化数据源引接"
节点（文字截断导致词法匹配失败），NLI对声明"前提：X是子功能/
假设：图节点含X"正确判定为非矛盾。

### 6.2 缺陷判定（诚实报告：弱）

**任务定义**：真差异内部再分——真实缺陷（real）vs 合理差异（benign）。

总体AUC=0.578（接近随机）。分分歧类型看有一个亮点：

| 分歧类型 | AUC | 解读 |
|---|---|---|
| 参与者缺失 | **0.706** | 真缺陷型Actor缺失的矛盾信号更强 |
| 步骤缺失 | 0.599 | 弱判别力 |
| 其余类型 | 0.46~0.49 | 无判别力 |

**结论**：NLI回答"是否真不一致"（任务一）可靠；回答"差异是否合理"
（任务二）需要UML/GJB**绘图惯例知识**（"流程图省略Actor是惯例"），
这是NLI模型不具备的、也不应假装具备的——任务二归属阶段三（LLM/人工）。

### 6.3 消融

| 配置 | 精确率 | 召回率 | F1 | AUC |
|---|---|---|---|---|
| **多语言mDeBERTa+闭世界模板** | **0.971** | **0.548** | **0.701** | **0.795** |
| 同模型+裸枚举模板 | 0.972 | 0.326 | 0.488 | 0.778 |
| 中文Erlangshen+闭世界 | 0.898 | 0.082 | 0.149 | 0.574 |

- **闭世界模板贡献召回+0.222**（把计数/缺失型真差异从"蕴含"改判
  "矛盾"）——方法学贡献的量化证据；
- 中文专用小模型召回崩溃（几乎不输出矛盾），多语言模型是唯一可用
  选择。

## 7 局限（全部如实）

1. **评测标签是LLM银标**（§5.3）——所有指标是"与银标的一致性"，
   不是绝对准确率；
2. 分歧类型样本量小的类别（组件缺失n=25等）结论不可外推；
3. NLI复核信号回到分歧粒度，不做"表格第几行↔图哪个节点"的元素级
   定位（元素级对齐是另一个模块的职责）；
4. 成员替换型矛盾（计数不变、成员互换）闭世界模板不覆盖，归词法/
   术语通道；
5. 选择偏差（§5.3已知偏差3）——无分歧pair上的表现未测。
