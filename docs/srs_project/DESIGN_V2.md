# SRS一致性检测：问题分析与多角度方案设计

> 日期: 2026-07-24
> 基于真实GJB SRS数据的深度分析

---

## 0. 核心问题

**一句话**: 给定一份GJB 438C格式的SRS文档，自动检测文档内部的不一致。

关键词是**内部**——不是与外部标准比对，而是文档自己跟自己矛盾。

---

## 1. 难点剖析（从真实数据出发）

### 1.1 约束的多样性

从调度器SRS提取的真实约束：

| 原文 | 类型 | 难点 |
|---|---|---|
| "默认25ms" | 默认值 | 不是硬约束，是配置参数 |
| "以25ms固定周期驱动" | 设计参数 | 多处出现，需确认一致 |
| "单次定时误差不超过±2ms" | 对称容差 | ±2ms = |error| ≤ 2，不是error ≤ 2 |
| "连续运行1000个周期后总时间误差不超过50ms" | 累积约束 | 有时间维度(1000周期)和累积量(总误差) |
| "单循环执行时间不超过5ms（含电池模型计算）" | 复合约束 | "含"表示包含子项，需要分解 |
| "前10秒恒流10A，接着5秒脉冲50A" | 时序约束 | 时间序列，不是单值 |
| "当执行时间超过25ms时进入超时告警" | 条件约束 | if-then结构，不是简单的≤ |

**难点**: 现有的正则/LLM提取方法只能处理"参数≤数值"这种简单模式。上面7种约束类型，每种都需要不同的解析策略。

### 1.2 文本-表格关系的复杂性

调度器SRS有5个表格，但它们的内容和用途完全不同：

| 表格 | 内容 | 与正文的关系 |
|---|---|---|
| 修改页 | 空模板 | 无关系 |
| 引用文档 | GJB 438C, 电池SRS | 无直接约束关系 |
| 合格性规定 | REQ-3.2.1→单元测试→关键 | **需求名称需与正文章节标题一致** |
| 正向追踪 | "25ms周期驱动"→REQ-3.2.4 | **指标值需与正文约束一致** |
| 逆向追踪 | REQ-3.2.4→"25ms周期驱动电池模型" | 同上，反向 |

**难点**: 不是"正文说X，表格说Y"这么简单。真正的矛盾是：
- 合格性表说需求名是"高精度定时器"，正文3.2.1标题也是"高精度定时器"→需验证名称一致
- 追踪表说"25ms周期驱动"，正文说"25ms固定周期"→需语义匹配判断是否一致
- 合格性表说REQ-3.2.1的级别是"关键"，但正文没有提及级别→不是矛盾，是信息缺失

### 1.3 图片引用的缺失

调度器SRS有7张图片，但正文中**没有找到"如图X所示"的引用**。

```
grep "图" scheduler_srs.md → 无图片引用
```

**难点**: 
- 图片可能没有文字引用（GJB标准要求"每个附录都应在正文中被引用"，但图片不一定）
- 图片类型未知（流程图？架构图？界面截图？）
- 没有引用就无法建立文本-图片配对
- 需要先分类图片，再判断是否有对应的文字描述

### 1.4 逻辑约束的隐含关系

正文中的约束不是独立的，存在**隐含的逻辑关系**：

```
显式约束:
  C1: 周期 = 25ms
  C2: 单循环执行时间 ≤ 5ms
  C3: 补偿计算时间 ≤ 0.01ms
  C4: 查询时间 ≤ 0.01ms
  C5: 超时阈值 = 25ms (执行时间>25ms时告警)

隐含关系:
  R1: 执行时间 = 补偿时间 + 查询时间 + 模型计算 + 其他开销
  R2: 执行时间 < 周期 (否则超时)
  R3: C2中的"含电池模型计算" → 模型计算 ⊆ 执行时间
  R4: C5的超时阈值 = C1的周期 (同一值25ms)
```

**难点**: 
- R1-R4都没有在文档中显式写出，需要领域知识推理
- Z3只能检查显式约束的矛盾，不能发现隐含关系的违反
- 如何让LLM提取隐含关系是关键挑战

### 1.5 同值多现的一致性

"25ms"在文档中出现了至少5次：

| 位置 | 原文 | 语境 |
|---|---|---|
| 系统概述 | "以25ms固定周期驱动" | 功能描述 |
| 初始化状态 | "定时器初始化（设定25ms周期）" | 状态描述 |
| 正常运行 | "主循环以25ms周期执行" | 运行描述 |
| 3.2.1高精度定时器 | "确保平均周期为25ms" | 性能要求 |
| 3.2.1输入 | "定时周期（默认25ms）" | 接口参数 |
| 追踪表 | "25ms周期驱动电池模型" | 追踪关系 |

**难点**: 这6个"25ms"指的是同一个参数吗？应该是。但如果其中一个是"30ms"，是矛盾还是有意为之（比如不同模式下的不同周期）？需要上下文理解。

## 2. 多角度方案设计

### 角度A: LLM端到端 (最简单)

**思路**: 把整个SRS扔给LLM，让它找不一致。

```
Prompt: 
  "你是GJB 438C SRS审查专家。
   以下是SRS文档全文。
   请找出文档内部的所有不一致，包括:
   1. 同一参数在不同位置的不同值
   2. 正文与表格的矛盾
   3. 约束之间的逻辑冲突
   每条不一致请给出: 位置、矛盾内容、GJB条款。"

Input: SRS全文 (约400行Markdown)
Output: 不一致列表
```

**优点**: 实现最简单，LLM能理解上下文和隐含关系
**缺点**: 
- 不可控（LLM可能幻觉）
- 无法精确定位（行号/表格位置）
- 难以评测（没有中间步骤可量化）
- 长文档可能超出上下文窗口
- **论文novelty不足**（只是prompt engineering）

**适合**: 快速原型验证，作为baseline

### 角度B: 结构化提取 + 规则检查 (最可控)

**思路**: 先用LLM提取结构化约束，再用确定性规则检查一致性。

```
Step 1: LLM提取约束 → JSON
  {param: "周期", value: 25, unit: "ms", location: "3.2.1", type: "default"}
  {param: "执行时间", operator: "≤", value: 5, unit: "ms", location: "3.2.4", type: "max"}
  
Step 2: 规则检查
  - 同参数同值检查: 所有"周期"的值都是25ms?
  - 逻辑检查: 执行时间(5) < 周期(25)? ✓
  - 表格匹配: 追踪表中的"25ms"与正文一致?
```

**优点**: 可控、可评测、可定位、可复现
**缺点**: 
- 提取质量决定一切（之前正则提取了39条，49个文档为0）
- 规则需要人工定义，覆盖不全
- 隐含关系难以规则化
- **论文novelty在提取方法**（如果提取好，检查部分比较straightforward）

**适合**: 作为主要方案，重点是约束提取的质量

### 角度C: 多Agent协作 (最灵活)

**思路**: 不同Agent负责不同类型的一致性检查，最后汇总。

```
Agent 1 (参数提取): 从正文提取所有参数约束 → 约束库
Agent 2 (表格理解): 解析表格内容，提取表格中的约束/需求
Agent 3 (图文配对): 定位图片引用，建立图文对应关系
Agent 4 (一致性判断): 比较正文约束 vs 表格约束 vs 图片内容
Agent 5 (逻辑推理): 检查约束集合的逻辑可满足性
Agent 6 (报告生成): 汇总所有Agent的发现，关联GJB条款
```

**优点**: 模块化、每个Agent可独立优化、可并行
**缺点**: 
- Agent间通信成本高
- 错误传播（提取Agent出错→判断Agent出错）
- 系统复杂度高
- **论文novelty在协作机制**（如何让多Agent有效协作）

**适合**: 系统工程方向，强调架构设计

### 角度D: 对比学习 (最有学术深度)

**思路**: 把一致性检测建模为"文本对对比"问题。

```
输入: (文本片段A, 文本片段B)
输出: consistent / contradictory / neutral

训练数据: 从GJB SRS中构造正负样本
  正样本: "周期为25ms" vs "25ms固定周期" → consistent
  负样本: "周期为25ms" vs "周期为30ms" → contradictory
  中性: "周期为25ms" vs "误差不超过2ms" → neutral (不同参数)
```

**优点**: 有学术深度，可发表ML论文
**缺点**: 
- 训练数据不足（只有3份SRS）
- 需要标注大量正负样本
- 不适用于逻辑层检测
- **与LLM方案相比优势不明显**（LLM已经能做NLI）

**适合**: 如果有大量标注数据，可以作为论文贡献

### 角度E: 知识图谱推理 (最有系统性)

**思路**: 把SRS文档转换为知识图谱，在图上做一致性推理。

```
SRS文档 → 知识图谱
  节点: 参数(周期=25ms), 需求(REQ-3.2.1), 状态(正常运行), 表格(合格性表)
  边: 定义于(3.2.1), 出现于(系统概述/初始化/运行), 追踪到(REQ-3.2.4)

一致性检查 = 图查询
  - 同值检查: 所有"周期"节点的value相同?
  - 逻辑检查: "执行时间"节点的value < "周期"节点的value?
  - 追踪检查: "REQ-3.2.1"在正文和表格中都存在?
```

**优点**: 系统性强、可视化、支持复杂查询
**缺点**: 
- 图谱构建质量决定一切
- 复杂约束（时序、条件）难以用图表示
- 可能过度工程化
- **论文novelty在图谱schema设计**

**适合**: 知识工程方向

## 3. 推荐方案: B+C混合 (结构化提取 + 多Agent协作)

### 3.1 为什么选B+C

| 角度 | 可控性 | Novelty | 实现难度 | 适配数据 |
|---|:---:|:---:|:---:|:---:|
| A: LLM端到端 | ★☆☆ | ★☆☆ | ★☆☆ | ★★★ |
| B: 结构化+规则 | ★★★ | ★★☆ | ★★☆ | ★★★ |
| C: 多Agent | ★★☆ | ★★★ | ★★★ | ★★☆ |
| D: 对比学习 | ★★☆ | ★★★ | ★★★ | ★☆☆ |
| E: 知识图谱 | ★★☆ | ★★☆ | ★★★ | ★★☆ |

**B+C混合**: 用B的结构化提取保证可控性，用C的多Agent架构处理不同类型的一致性检查。Novelty在于：
1. 针对中文GJB SRS的约束提取方法
2. 多Agent协作的一致性检测框架
3. 隐含逻辑关系的LLM推理

### 3.3 每个Agent的核心挑战

#### Agent 1: 约束提取

**挑战**: 7种约束类型（见1.1节），每种都需要不同的解析策略

**方案**: 分类型提取
```python
# 对每个章节，用LLM提取约束
prompt = """
从以下SRS章节中提取所有约束，按类型分类:

1. 数值约束: 参数名, 运算符, 数值, 单位
   例: "单次定时误差不超过±2ms" → {param: "定时误差", op: "|≤|", value: 2, unit: "ms"}
   
2. 时序约束: 阶段, 持续时间, 动作
   例: "前10秒恒流10A" → {phase: "阶段1", duration: 10, unit: "s", action: "恒流10A"}
   
3. 条件约束: 条件, 动作
   例: "执行时间超过25ms时进入超时告警" → {if: "执行时间>25ms", then: "超时告警"}
   
4. 默认值: 参数名, 默认值
   例: "默认25ms" → {param: "定时周期", default: 25, unit: "ms"}

5. 设计参数: 参数名, 值 (不是约束，是设计决策)
   例: "以25ms固定周期驱动" → {param: "周期", value: 25, unit: "ms", type: "design"}

章节内容:
{section_text}
"""
```

**评测**: 人工标注3份SRS的所有约束作为gold standard，计算提取的P/R/F1

#### Agent 2: 同值一致性

**挑战**: 同一参数多处出现，需判断是否指同一事物

**方案**: 
1. 按参数名聚类所有出现的约束
2. 对每对同参数约束，用LLM判断是否指同一事物
3. 如果是，比较值是否一致

```python
# "25ms"的6次出现
occurrences = [
    {location: "系统概述", text: "以25ms固定周期驱动", value: 25},
    {location: "初始化", text: "设定25ms周期", value: 25},
    {location: "正常运行", text: "主循环以25ms周期执行", value: 25},
    {location: "3.2.1", text: "确保平均周期为25ms", value: 25},
    {location: "3.2.1输入", text: "默认25ms", value: 25},
    {location: "追踪表", text: "25ms周期驱动电池模型", value: 25},
]

# LLM判断: 这6个"25ms"是否都指同一个"定时周期"?
# 如果是 → 检查值是否都相同
# 如果有不同值 → 报告矛盾
```

#### Agent 3: 文本-表格一致性

**挑战**: 不是简单的值比较，是语义层面的匹配

**方案**:
1. 提取正文中的需求结构: {章节号, 标题, 约束}
2. 提取表格中的需求结构: {需求ID, 需求名称, 章节号, 方法, 级别}
3. 按章节号配对
4. 检查: 正文标题 vs 表格需求名称（语义匹配）
5. 检查: 正文约束值 vs 追踪表中的指标值（值匹配）

#### Agent 4: 文本-图片一致性

**挑战**: 调度器SRS没有图片引用！需要先解决"是否有图片需要检查"的问题

**方案**:
1. 检查图片引用: 如果没有引用，检查GJB是否要求引用
2. 如果有引用: 解析引用 → 定位图片 → VLM判断
3. 如果没有引用但有图片: 检查是否是模板图片（修改页等）

**注意**: 这个Agent可能在这3份SRS上无活可干。需要看其他SRS是否有图片引用。

#### Agent 5: 逻辑一致性

**挑战**: 隐含关系需要领域知识推理

**方案**: 两步走
1. LLM提取显式约束 + 推理隐含关系
2. Z3检查约束集合的可满足性

```python
# Step 1: LLM提取约束和隐含关系
prompt = """
从以下SRS约束中，提取:
1. 所有显式约束 (数值/条件/时序)
2. 约束之间的隐含关系 (如: 执行时间 < 周期)
3. 约束的组成关系 (如: 执行时间 = 补偿 + 查询 + 模型计算)

约束列表:
- 周期 = 25ms
- 单循环执行时间 ≤ 5ms (含电池模型计算)
- 补偿计算时间 ≤ 0.01ms
- 查询时间 ≤ 0.01ms
- 超时: 执行时间 > 25ms

输出:
显式约束: [周期=25, 执行时间≤5, 补偿≤0.01, 查询≤0.01]
隐含关系: [执行时间 < 周期, 执行时间 ≥ 补偿+查询+模型计算]
"""

# Step 2: Z3求解
# 将显式约束 + 隐含关系转为Z3表达式
# 如果UNSAT → 报告矛盾 + unsat core
```

## 5. 我们要做的事（明确清单）

### 必须做的
1. **约束提取**: 从3份GJB SRS中提取所有约束，人工标注gold standard
2. **同值一致性检测**: 检测同一参数多处出现是否一致
3. **文本-表格一致性检测**: 正文需求 vs 合格性表/追踪表
4. **逻辑一致性检测**: 约束集合的可满足性检查

### 可选做的
5. 文本-图片一致性检测（取决于SRS是否有图片引用）
6. 语法层检测（章节完整性等，比较straightforward）
7. 合成SRS生成（用于扩充测试数据）
