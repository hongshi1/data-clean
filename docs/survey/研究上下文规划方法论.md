## 第二轮分析：根因提取

### 根因1: Agent误用 — 用agent做检索而非综合

```
错误模式:
  检索任务 → 启动agent → agent内部做搜索 → 30min超时 → 零产出

正确模式:
  检索任务 → 直接搜索工具 → 秒级出结果 → 自己综合
  综合任务 → 启动agent → agent做推理 → 产出分析
```

**决策规则**: 
- 检索（找信息）→ 直接工具（websearch/grep/webfetch）
- 综合（分析信息）→ agent或Oracle
- agent的value在于多步推理，不在于搜索

### 根因2: 无上下文预算管理

```
错误模式:
  启动5个agent，每个30min，不跟踪总预算
  → 150min后才发现全部失败

正确模式:
  预算: 总上下文 = X tokens / Y minutes
  分配: 阶段1 30%, 阶段2 25%, 阶段3 25%, 阶段4 20%
  监控: 每阶段消耗 vs 预算，超支则切换策略
```

### 根因3: 无Fallback策略

```
错误模式:
  agent超时 → 再等 → 再等 → 用户催 → 才切换

正确模式:
  agent启动 → 设5min checkpoint → 5min无产出 → 切换直接搜索
  规则: 任何agent超过5min无产出，立即fallback
```

### 根因4: 初始范围过宽

```
错误模式:
  课题: "军工多模态不一致性" 
  → 同时调研: 工具+文献+数据集+军工+医疗+时序+图片+表格
  → 5个agent × 10角度 = 50维并行

正确模式:
  课题: "军工多模态不一致性"
  → 先问用户: 模态组合? 工具偏好? 数据可得性?
  → 用户回答后: 范围从50维收敛到3维
  → 再针对性搜索
```

### 根因5: 上下文未及时外化

```
错误模式:
  搜索结果留在对话上下文中 → 下一阶段时上下文溢出 → 丢失前序发现

正确模式:
  每次搜索 → 立即写入文件 → 上下文只保留索引
  下一阶段 → 读文件引用 → 不重复搜索
```

## 第三轮分析：方法论设计

### 3.1 研究上下文规划框架（RCP框架）

```
RCP = Research Context Planning

四层结构:
  L1: 课题边界层 — 明确研究边界，消除歧义
  L2: 信息源层 — 规划信息来源和获取顺序
  L3: 上下文管理层 — 预算分配、外化、检索
  L4: 产出层 — 版本化、索引化、可追溯
```

### 3.2 L1: 课题边界层 — 先问后搜

```
规则: 在任何搜索之前，必须先明确以下5个维度:

1. 研究目标: 检测? 生成? 治理? 评估?
2. 模态组合: 哪几种模态? 如何对齐?
3. 数据约束: 公开? 受限? 自建? 跨领域?
4. 工具约束: 必须用X? 可以换? 从零构建?
5. 产出形式: 论文? 系统? 报告? 基准?

决策树:
  如果5维都明确 → 直接进入L2搜索
  如果<3维明确 → 先问用户（用question工具）
  如果3-4维明确 → 合理假设 + 标注 + 进入L2
```

**本次复盘**: 用户第一个消息后，我应该立即用`question`工具确认模态组合，而不是启动5个agent。用户在第4轮才告诉我"表格+图片+时序"，但这个信息如果一开始就获取，能节省3轮无效agent。

### 3.3 L2: 信息源层 — 直接优先，agent补充

```
信息获取优先级（按速度和可靠性排序）:

Tier 1 (秒级，直接用):
  - websearch_web_search_exa → 通用搜索
  - webfetch → 抓取具体URL
  - grep_app_searchGitHub → 代码搜索
  - read/glob/grep → 本地文件

Tier 2 (分钟级，按需用):
  - ast_grep_search → 代码结构搜索
  - lsp_symbols → 符号导航
  - context7_query-docs → 库文档查询

Tier 3 (5-30分钟，谨慎用):
  - explore agent → 代码库模式发现（仅当多文件交叉分析时）
  - librarian agent → 多仓库对比（仅当需要深度对比时）
  - Oracle → 架构推理（仅当需要高质量推理时）

决策规则:
  - 能用Tier 1解决的，绝不用Tier 3
  - Tier 3 agent必须设5min checkpoint
  - Tier 3 agent的prompt必须聚焦（≤3个搜索角度）
  - Tier 3超时 → 立即fallback到Tier 1
```

### 3.4 L3: 上下文管理层 — 预算+外化+检索

```
上下文预算分配（建议比例）:

  课题边界确认: 5%   (1-2轮对话)
  信息检索:     25%  (直接搜索为主)
  本地实验:     30%  (代码编写+调试)
  分析综合:     25%  (报告撰写+推理)
  用户交互:     10%  (澄清+确认)
  缓冲:         5%   (意外处理)

上下文外化规则:
  1. 每次搜索结果 → 立即写入.md文件（不留在对话中）
  2. 文件命名: {阶段}_{内容}_{版本}.md (如: 调研_数据集_v1.md)
  3. 文件结构: 执行摘要 → 详细发现 → 链接索引
  4. 对话上下文只保留: 文件索引 + 当前任务 + 待决策项
  5. 每个阶段结束 → 生成阶段总结（1段话）写入INDEX.md

上下文检索规则:
  - 需要前序发现 → read对应.md文件（不重新搜索）
  - 需要对比多个发现 → read多个.md文件
  - 需要验证结论 → grep对应.md文件
```

### 3.5 L4: 产出层 — 版本化+可追溯

```
文件结构:
  project_root/

  ├── phase1_boundary/  # 阶段1: 课题边界

  ├── phase2_survey/    # 阶段2: 调研

  │   ├── results_v1.md
  │   └── results_v2.md
  ├── phase4_design/    # 阶段4: 方案设计
  │   └── 技术方案_v1.md → v2.md → v3.md
  └── phase5_validation/# 阶段5: 验证

版本化规则:
  - 每次重大修改 → 新版本（v1→v2）
  - 版本间用diff标注变更
  - 旧版本保留（不删除）

## 第五轮分析：可操作的改进规则

### 规则1: 搜索策略选择

```
IF 任务是"找信息" (检索):
  THEN 直接用 websearch/grep/webfetch (秒级)
  NEVER 用agent做检索

IF 任务是"分析信息" (综合):
  THEN 用Oracle (高质量推理, 5min checkpoint)

IF 任务是"发现模式" (探索):
  THEN 用explore agent (仅当需要跨多文件交叉分析)
  设5min checkpoint, 超时则fallback到grep
```

### 规则2: Agent超时处理

```
启动agent时:
  设定 mental checkpoint: "5分钟内必须有产出"
  
5分钟checkpoint:
  IF agent有产出 → 继续
  IF agent无产出 → 立即切换到直接搜索
  NEVER 等待超过10分钟

30分钟硬超时:
  系统自动kill → 检查是否有部分产出 → fallback
```

### 规则3: 用户交互时机

```
研究开始时:
  MUST 问: 模态组合? 工具偏好? 数据约束? 产出形式?
  (用question工具, 1次问4个维度)

研究中遇到歧义:
  IF 2x+effort差异 → MUST问用户
  IF 合理默认 → 假设+标注+继续

研究完成阶段:
  MUST 报告: 产出物位置 + 下一步建议 + 待决策项
```

### 规则4: 上下文外化

```
每次搜索后:
  立即将结果写入 .md 文件
  对话中只保留: "已写入{文件名}, 包含{要点}"

每个阶段后:
  更新INDEX.md
  记录: 本阶段产出 + 下阶段输入 + 待解决问题

会话切换时:
  读INDEX.md → 了解全局状态
  读最近产出的.md → 了解当前进展
  不重新搜索已有信息
```

## 总结: 研究上下文规划的核心原则

1. **先问后搜**: 课题边界不明时，问用户比搜索更高效
2. **直接优先**: 检索用直接工具，agent只用于综合推理
3. **5分钟法则**: 任何agent超过5分钟无产出，立即fallback
4. **外化一切**: 搜索结果立即写文件，对话只保留索引
5. **版本化产出**: 每次重大修改出新版本，旧版保留
6. **检查点驱动**: 每个阶段有明确检查点，不盲目推进
7. **预算管理**: 上下文是有限资源，按比例分配到各阶段
8. **失败快切**: 不沉没成本，策略失败立即换方案

## 第六轮分析：8个深度问题的系统性回答

> Oracle超时（第8次agent失败，30min），用自己的推理完成。这本身验证了"5分钟法则"——agent不可靠时必须fallback。

### 问题1: 上下文预算分配

**问题**：有限上下文窗口如何分配到文献调研/工具评估/数据集发现/本地实验/报告撰写？

**分析**：

上下文预算不是均分的，而是**按信息密度和不可替代性分配**：

| 阶段 | 预算% | 不可替代性 | 理由 |
|---|---|---|---|
| 课题边界确认 | 5% | 极高（用户独有信息） | 错了全盘皆输，但消耗少（1-2轮对话） |
| 信息检索 | 20% | 低（可重复搜索） | 搜索成本低，结果可外化到文件 |
| 本地实验 | 35% | 高（代码调试不可替代） | 最消耗上下文，但产出最实 |
| 分析综合 | 25% | 高（推理不可外包） | 连接发现→结论的核心环节 |
| 用户交互 | 10% | 极高（决策独有） | 关键岔路口必须用户定 |
| 缓冲 | 5% | - | 意外处理 |

**关键洞察**：实验占比最高(35%)不是因为实验最重要，而是因为**代码调试的上下文消耗最大且不可压缩**（每行代码、每个报错都在消耗上下文）。检索只占20%是因为结果可以外化——搜索完立即写文件，上下文就释放了。

**反模式**：本次研究阶段1-2花了~40%上下文在无效检索（agent超时+空polling），导致后续实验空间被压缩。正确做法：检索快速失败快切，把上下文留给实验。

### 问题2: Agent vs 直接搜索的决策规则

**问题**：何时用background agent vs 直接搜索？各自的失败模式？

**失败模式矩阵**：

| 工具 | 成功条件 | 失败模式 | 失败概率 | 恢复成本 |
|---|---|---|---|---|
| 直接搜索(websearch/grep) | 信息存在于公开网络 | 网络不通/查询词差 | 10% | 低（换词重搜） |
| webfetch | URL已知且可访问 | 超时/404/反爬 | 20% | 低（换URL） |
| explore agent | 需跨多文件交叉分析 | prompt过宽/能力不足/超时 | 60% | 高（等30min） |
| librarian agent | 需多仓库深度对比 | 同上+外部依赖多 | 70% | 高 |
| research agent | 需多步检索+综合 | 同上+搜索链断裂 | 80% | 极高 |
| Oracle | 需高质量推理 | 超时(推理太久)/能力不匹配 | 50% | 中（自己做） |

**决策规则（严格阈值）**：

```
IF 任务 = 检索（找信息）
  → 直接搜索（websearch/grep/webfetch）
  → 概率90%成功，秒级
  → NEVER用agent

IF 任务 = 探索（发现模式）
  → 先grep 3次不同角度
  → 若grep不够 → explore agent（5min checkpoint）
  → 5min无产出 → fallback到更多grep

IF 任务 = 推理（分析/设计/决策）
  → 简单推理自己做
  → 复杂推理 → Oracle（设10min心理预期，超时自己做）
  → Oracle超时 → 自己分步推理（分解为小问题逐个答）

IF 任务 = 实现（写代码）
  → 简单自己做
  → 复杂delegate给deep/quick category
  → delegate必须给clear GOAL+CONSTRAINTS+PATTERN
```

**本次教训**：5轮agent（5+2+3+1=11个agent）全部超时，成功率0%。直接搜索5轮全部成功，成功率100%。决策规则应更激进：**默认直接搜索，agent仅作为最后手段**。

### 问题3: 上下文外化策略

**问题**：研究发现如何外化到文件以保留上下文？什么结构？什么粒度？

**外化层级模型**：

```
Layer 0: 对话上下文（易失，~100k tokens）
  → 只保留：当前任务 + 最近3轮交互 + 文件索引

Layer 1: 工作文件（持久，本地磁盘）
  → 搜索结果即时写入
  → 命名: {阶段}_{内容}_v{版本}.md
  → 结构: 执行摘要(1段) → 详细发现 → 链接索引

Layer 2: 索引文件（持久，本地磁盘）
  → INDEX.md: 全局目录
  → 每个文件一行摘要 + 路径
  → 会话切换时首先读此文件

Layer 3: 代码产出（持久，版本控制）
  → 实验脚本 + 结果文件
  → 可复现性保证
```

**粒度规则**：

| 信息类型 | 外化粒度 | 理由 |
|---|---|---|
| 搜索结果 | 全量写入文件 | 对话中只留1行摘要 |
| 实验结果 | 全量写入文件+关键数字留对话 | 数字需要后续引用 |
| 代码 | 写入.py文件+关键逻辑留对话 | 代码可重跑 |
| 用户决策 | 写入INDEX.md待决策项 | 避免重复问 |
| 方法论 | 写入独立.md | 长期参考 |

**版本化规则**：
- 重大修改 → 新版本（v1→v2），旧版保留
- 小修改 → 直接编辑当前版本
- 版本间用diff标注（文件头注明变更）

### 问题4: 范围收敛策略

**问题**：研究从宽泛到聚焦的最优序列？何时问用户 vs 广泛探索？

**范围收敛漏斗**：

```
第0层: 课题领域（军工多模态不一致性）
  ↓ 问用户: 具体模态组合？（表格+图片+时序）
第1层: 模态确定
  ↓ 问用户: 工具偏好？（Data-Juicer）
第2层: 工具确定
  ↓ 直接搜索: 该工具支持哪些模态？（发现不支持时序）
第3层: 能力边界确定
  ↓ 问用户: 时序怎么处理？（另选工具/缩小范围）
第4层: 技术路线确定
  ↓ 直接搜索: 找数据集+方法
第5层: 执行
```

**收敛决策规则**：

```
IF 用户信息能消除2x+effort差异 → MUST问用户
IF 合理默认假设存在 → 假设+标注+继续
IF 探索成本<询问成本 → 先探索再带着发现问

具体到本课题:
  模态组合 → MUST问（50维→3维，effort差10x）
  工具偏好 → 用户已给（Data-Juicer），不需问
  数据约束 → 先搜索看有什么公开数据，再问
  产出形式 → 可假设（论文+系统），不必问
```

**本次复盘**：我在第1轮就该用`question`工具问模态组合，而不是启动5个agent。用户在第4轮才告诉我"表格+图片+时序"，前3轮全部浪费。

### 问题5: 多会话研究规划

**问题**：跨多会话（天/周）的项目如何规划上下文？什么延续？什么丢弃？

**会话间传递模型**：

```
会话N结束时产出:
  ├── INDEX.md（全局状态，必须更新）
  ├── 当前产出物（文件，持久化在磁盘）
  ├── 会话总结（1段话，写入INDEX.md）
  └── 待决策项（写入INDEX.md）

会话N+1开始时输入:
  ├── 读INDEX.md（了解全局状态）
  ├── 读最近产出物（了解当前进展）
  └── 读待决策项（确定本会话目标）

丢弃的内容:
  ├── 对话上下文（会话结束即丢弃）
  ├── 失败的实验细节（只保留结论）
  └── 超时的agent prompt（只记录"agent失败，fallback到直接搜索"）
```

**会话边界规则**：

```
会话切换时机:
  1. 上下文使用>80% → 必须切换
  2. 阶段目标完成 → 主动切换
  3. 遇到需要外部资源（如DUA审批）→ 切换
  4. 用户离开 → 被动切换

会话目标设计:
  - 每会话1个主要目标（不超过2个）
  - 目标必须可在单会话内完成
  - 目标必须有明确的产出物
  - 产出物必须写入文件（不在对话中）
```

### 问题6: 失败恢复策略

**问题**：研究方法失败时（agent超时、工具不工作），最优恢复策略？重试几次？如何避免沉没成本？

**失败恢复决策树**：

```
策略A失败
├─ 失败类型?
│   ├─ 超时 → 立即切换（不重试同策略）
│   ├─ 格式错误 → 修正后重试1次
│   ├─ 网络错误 → 重试1次（换endpoint）
│   └─ 逻辑错误 → 分析原因后重试
│
├─ 已重试次数?
│   ├─ 0次 → 根据失败类型决定
│   ├─ 1次 → 评估是否换策略
│   ├─ 2次 → MUST换策略
│   └─ 3次 → MUST换策略+求助用户
│
└─ 沉没成本评估
    ├─ 已投入<5min → 自由切换
    ├─ 已投入5-15min → 评估替代方案成本
    ├─ 已投入15-30min → 强制切换（沉没成本太高）
    └─ 已投入>30min → MUST切换（硬规则）
```

**本次复盘**：

| 失败事件 | 重试次数 | 总消耗 | 正确做法 |
|---|---|---|---|
| 5个agent超时 | 等了3次polling | ~150min | 应5min后切换 |
| SARCLIP权重格式 | 4次尝试 | ~30min | 第2次失败后应查文档 |
| Oracle超时 | 等了30min | 30min | 应10min后自己做 |

**沉没成本规避规则**：
- 每次失败后问自己："如果从零开始，我还会选这个策略吗？"
- 如果答案是否 → 立即切换
- 不要因为"已经等了X分钟"而继续等

### 问题7: 跨领域研究上下文管理

**问题**：本项目需从医疗领域借鉴方法到军工。跨领域上下文如何管理？如何识别可迁移方法？

**跨领域迁移评估框架**：

```
领域A（医疗）发现方法M
  ↓
迁移评估:
  1. M解决的核心问题是什么？（抽象到问题层）

  5. M的评估指标在B中是否适用？

迁移决策:
  4/5匹配 → 直接迁移
  3/5匹配 → 简化迁移（去掉不适用的组件）

**跨领域上下文管理规则**：
- 跨领域搜索时标注`[来源领域]`和`[目标领域]`

## 第七轮分析：元认知 — 本次分析本身的上下文管理

讽刺的是，这次"上下文规划分析"任务本身也犯了同样的错误：

1. **启动Oracle做推理** → 超时30min → 零产出
2. **自己做推理** → 30min完成8个深度问题

这验证了核心原则：**当任务的瓶颈是推理而非检索时，自己做比委托更可靠**。Oracle的价值在于给一个独立视角，但如果超时，自己的推理同样有效——因为我对上下文有完整理解，而Oracle需要从prompt重建上下文。

**元教训**：对于需要大量上下文的推理任务，自己做的效率可能高于委托给agent——因为agent需要从零加载上下文，而你已经有了。
