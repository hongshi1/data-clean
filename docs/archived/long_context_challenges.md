# 长程上下文关联——技术难点与实现方案

## 核心挑战

SRS文档的上下文关联不是简单的"同章节聚合"，而是**跨章节、跨模态、长程的语义关联**。以下是4个核心难点：

### 难点1: 超长上下文（文档级）

**问题**：单份SRS文档4000+行(~50KB)，远超LLM上下文窗口(通常4K-32K token)。模型无法一次性"看到"整个文档。

**影响**：无法用LLM直接做"给定整个文档，找出所有不一致"的端到端检测。

**解决思路**：
- 不依赖LLM看全文，而是**构建文档级结构索引**（章节树+参数索引+需求ID索引）
- 用索引快速定位"同一事物的所有出现位置"，只把相关片段送给LLM/embedding
- 参考QA-GraphRAG的RAPTOR树：不同层级聚合不同粒度，简单查询走摘要层、复杂查询走叶层

### 难点2: 长程关联（跨章节）

**问题**：同一参数（如"达梦数据库版本"）在3.9.1(行3405)和3.10.3(行3524)出现，相隔120行。同一功能（如"服务开发支撑"）在3.2概述(行82)、3.2.1专节(行317)、第4章合格性表(行800+)、第5章追溯表(行900+)出现，跨章节距离上千行。

**影响**：局部窗口（如滑动窗口500行）无法覆盖同一事物的所有出现位置。

**解决思路**：
- **全局参数索引**：扫描全文，按参数名/需求ID构建倒排索引{param_name → [(section, line, value, context)]}
- **Embedding辅助关联**：对每个参数出现位置的上下文做embedding，用余弦相似度发现"名称不同但语义相同"的参数
- **章节号容错**：第4章合格性表的章节号可能比第3章整体偏移±1，需要序列对齐检测

### 难点3: 多模态关联（文字+表格+图片）

**问题**：同一需求"数据获取功能"的描述分布在：3.2.1文字段落 + 用例描述表(表SEQ格式) + 接口图(OLE嵌入) + 合格性表行 + 追溯表行。这5种模态需要聚合成一个条目。

**影响**：纯文本处理无法关联表格行和图片。

**解决思路**：
- **多模态条目结构**：条目= {文字片段[], 表格行[], 图片引用[], 章节位置[], 语义角色}
- **表格解析**：Word SEQ表格(表 SEQ 表 * ARABIC N)需要特殊解析，提取行列结构
- **图片关联**：OLE嵌入图片只能靠章节归属关联（无markdown引用）

### 难点4: 上下文感知的关联判断

**问题**：如何判断两段文字描述的是"同一事物"？不能只靠字符串匹配——"故障探测预警"和"故障预警修复"是同一功能但名称不同；"SJCS"和"SJCSKZ"是同一需求的两个ID。

**影响**：单一信号(ID/名称/章节号)都不可靠，需要多信号融合。

**解决思路**：
- **多信号融合**：ID归一化(0.4) + Embedding名称匹配(0.3) + 章节号容错(0.2) + 位置邻接(0.1)
- **Embedding做语义匹配**：用embedding API计算名称相似度，>0.85判定为同一实体
- **semantic_role区分**：threshold(阈值必须一致) vs config(配置可以不同) vs capacity(能力可以不同)
