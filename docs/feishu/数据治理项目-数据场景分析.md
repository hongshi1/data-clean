# 数据治理项目\-数据场景分析

## 各场景所需数据集详述

## 场景 1 ｜数智研发领域·软件需求规格设计

业务定位：依据 GJB 438C\-2021《军用软件开发文档通用要求》，将历史沉淀的非结构化软件需求规格文档（SRS）转化为可被垂域大模型微调的高质量数据集，实现需求智能抽取、结构化转化与辅助生成。

数据模态：文本（SRS 自然语言正文）\+ 表格（数据字典、接口定义表、性能指标表）→ 对应课题三模态框架的"表格"模态。

所需数据集：

1. 历史 SRS 文档库（遵循 GJB 438C\-2021，含功能需求、性能指标、接口定义、数据字典、运行环境、安全保密要求、验收准则等，数据总量 \>50 TB）。

2. 结构化需求条目库（从 SRS 抽取的参数化条目，含条目 ID、类型、数值、单位、引用关系）。

3. GJB 438C\-2021 标准条文库（用于合规性比对）。

4. 专家经验/设计准则结构化数据（隐性知识显性化）。

不一致性检测：

- 重点检测模态对：文本 ↔ 表格（主要）；文本 ↔ 文本跨条目/跨文档（次要）

1. 性能指标正文 ↔ 指标表数值矛盾：正文叙述的阈值与"性能指标表"数值不符（如正文"≤50ms"，表格"≤100ms"）。

2. 接口定义正文 ↔ 接口表字段矛盾：正文协议类型/字段与"接口定义表"不符（如正文 RS422，表标 RS232；字段类型/字节序矛盾）。

3. 数据字典 ↔ 正文术语不一致：正文引用的参数名/单位与数据字典定义不匹配（单位换算矛盾、术语漂移）。

4. 功能/性能/接口/安全性条目间参数矛盾：跨条目参数级冲突（对应 GJB 准则"各条目之间参数不能存在矛盾"）。

数据准则要点：需符合 GJB 438C\-2021，条目间参数无矛盾，功能要求不含参数信息。

## 场景 2 ｜引信领域·科研生产方案设计

业务定位：基于引信产品设计技术要求，开展 SysML 九视图建模与总体/详细方案设计，实现设计技术要求 → SysML 模型 → 详细方案的智能生成与映射。

数据模态：文本（设计技术要求）\+ 结构化模型（SysML 九视图）\+ 时序仿真（Simulink/SystemVue/Mworks 动态行为）→ 对应课题"表格 ↔ 时序"模态组合。

所需数据集：

1. 各类型号产品的设计技术要求（含功能要求、性能要求、工作流程、接口要求、通用质量特性 5 部分；需符合 GJB、参数无矛盾、功能要求不含参数信息）。

2. 总体方案：SysML 九视图（工作流程模型、功能分配模型、产品组成模型），需满足全部功能要求。

3. 详细方案：Matlab/Simulink/SystemVue/Mworks 原理框图（结构方案、电路方案、算法方案），需满足全部设计技术要求。

4. 设计技术要求与具体设计实现的对应关系（要求 → 实现映射 \+ 方案内部指标传递关系，需具备逐条抽取展示能力）。

不一致性检测：

- 重点检测模态对：结构化模型\(SysML 九视图\) ↔ 时序仿真\(Simulink/SystemVue\)（主要）；文本要求 ↔ 结构化视图（次）

1. 设计技术要求 ↔ 总体方案覆盖性矛盾：某条功能/性能要求在 SysML 九视图中无对应元素（要求 → 实现断裂）。

2. 静态视图参数 ↔ 动态仿真行为冲突：SysML 参数视图的阈值与 Simulink 仿真输出的实际行为超差（静态 ↔ 动态不一致）。

3. 跨视图指标传递断裂：参数从需求视图 → 结构视图 → 行为视图 → 参数视图的传递链中出现数值丢失/篡改。

数据准则要点：标准条文与设计元素精准映射，跨视图数据全链路可追溯（需求—结构—行为—参数）。

## 场景 3 ｜引信领域·科研生产质量缺陷溯源

业务定位：针对引信部件/整机检测出的故障现象，结合工艺规程反向溯源，定位造成故障的生产工艺环节，自动生成质量缺陷溯源报告。

数据模态：文本（故障现象报告/溯源报告）\+ 表格（工艺规程及要素/故障树底事件）→ 对应课题"表格"模态。

所需数据集：

1. 产品生产过程中的工艺规程及各要素（各工艺状态为不可分解的底事件，可通过试验直接验证；明确"可直接排除/需排查/最终确认"的底事件；底事件间无逻辑矛盾）。

2. 产品部件及整机检验时出现的各种故障现象（须明确检验过程、检验工况、故障现象、引信主要组成及工作原理）。

3. 工艺规程及各要素与故障现象的对应关系。

4. 辅助数据：故障现象台账、工艺参数记录、检验工况数据、不合格品处置记录、工艺规程文件等多维数据库。

不一致性检测：

- 重点检测模态对：文本\(故障报告\) ↔ 表格\(工艺规程/故障树\)（主要）

1. 故障现象 ↔ 工艺底事件对应缺失：记录的故障现象在工艺规程中找不到可解释的底事件（对应关系断裂）。

2. 故障树底事件间逻辑矛盾：底事件存在"既可直接排除又需排查"的矛盾状态（违反"无逻辑矛盾"准则）。

3. 底事件排查结论 ↔ 影响因素确定矛盾：排查结论排除了某底事件，但最终确认的影响因素仍指向它。

数据准则要点：模型最终需输出含 9 部分要素的溯源报告（缺陷问题、引信介绍、技战术指标、排查过程、排查情况、底事件排查及故障定位、故障机理分析、故障复现、采取措施）。

## 场景 4 ｜航空发动机维护保障

业务定位：以时序运行数据为核心，搭建面向故障诊断、寿命预测、维护决策的微调数据集智能体，实现发动机智能维护保障。

数据模态：时序（振动/温度/转速/压力传感器）\+ 文本（故障工单/维护手册/维护记录）\+ 图像（拆解图像/孔探图像）→ 课题三模态最齐全场景，对应"时序 ↔ 文本"主、"时序 ↔ 图像"次。

所需数据集（3 类智能体对应 3 类样本）：

1. 故障诊断指令微调样本：输入 = 时序运行数据 \+ 故障工单；输出 = "给定运行片段 → 故障类型/原因"指令样本。

2. 维护知识问答样本：输入 = 维护手册 \+ 历史工单；输出 = "用户提问 → 维护专家回答"多轮对话样本。

3. 健康状态预测样本：输入 = 时序运行数据；输出 = "历史时序 → 未来健康状态/剩余寿命"监督样本（滑窗切分，过去 N 小时 → 未来 M 小时）。

4. 多模态辅助数据：拆解图像/孔探图像及损伤标注（用于时序 ↔ 图像一致性校验）。

不一致性检测：

- 重点检测模态对：时序\(传感器\) ↔ 文本\(故障工单\)（主要）；时序 ↔ 图像\(拆解\)（次要，研究空白？）

1. 时序异常段 ↔ 工单故障类型不匹配：时序检测到的异常模式与工单记录的故障类型不一致（如振动谱异常但工单记"电气故障"）。

2. 时序异常时间戳 ↔ 工单登记时间矛盾：传感器异常发生时刻与工单登记的故障发现时间严重偏移。

3. 健康预测标签 ↔ 实际维护/拆解记录冲突：滑窗标签预测"健康"，但后续拆解图像见严重损伤（时序 ↔ 图像不一致）。

4. 多传感器物理约束违反：温度升高但转速无相应变化等冗余通道间物理关系断裂（时序内部不一致）。

数据准则要点：补齐真实工况实测数据，扩充罕见故障样本（现占比 \<5%），完善多模态标注体系（传感器时序 \+ 文本维修记录 \+ 图像/视频拆解数据）。
