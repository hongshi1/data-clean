## 一、总体说明

### 1.1 职责

- 厂商：采集→脱敏→结构化→交付
- 我方：收数据→检测不一致性→出报告

### 1.2 数据类型标注

文档中用以下标注区分数据类型：

| 标注 | 含义 | 交付格式 |
|---|---|---|
| 【文本】 | 自然语言正文 | Word/PDF/JSONL中的text字段 |
| 【表格】 | 结构化表格（行列形式） | Word/PDF中的表格，或JSONL中的结构化字段 |
| 【时序】 | 传感器时间序列 | CSV |
| 【图像】 | 拆解/孔探照片 | JPG/PNG + JSONL标注 |
| 【模型】 | SysML/XMI模型文件 | .sysml/.xmi |

### 1.3 通用JSONL规范

所有JSONL每行一条记录，UTF-8编码，结构统一：

```json
{"id": "唯一ID", "text": "【文本】自然语言内容", "meta": {结构化字段}}
```

- `id`：全局唯一
- `text`：【文本】类型数据放这里（可为空）
- `meta`：【表格】类型数据放这里（键值对）
- `meta`中引用附件用路径，如`"related_csv": "timeseries/ENG001_FL012.csv"`

## 二、场景1：软件需求规格设计

### 2.1 背景

兵器工业某研究所按GJB 438C编写SRS文档。文档中【文本】正文描述性能/接口要求，【表格】结构化表格记录参数值。检测正文的参数和表格的参数是否矛盾。

### 2.2 数据包结构

```
场景1_数据包/
├── srs_documents/          ← 【文本+表格】SRS原始Word/PDF（保留表格）
│   ├── SRS_型号A.docx
│   └── ...
├── doc_structure/          ← 【表格】文档结构说明JSON
│   └── SRS_型号A.json
└── README.md
```

### 2.3 SRS文档格式

#### 2.3.1 文档必须含7个章节，其中3个含【表格】

| 章节 | 名称 | 数据类型 | 检测用途 |
|---|---|---|---|
| 3.1 功能需求 | 【文本】 | NER提取功能条目 |
| 3.2 性能指标 | 【文本+表格】 | 正文参数↔表格参数比对 |
| 3.3 接口定义 | 【文本+表格】 | 正文接口↔表格接口比对 |
| 3.4 数据字典 | 【文本+表格】 | 正文术语↔字典定义比对 |
| 3.5-3.7 | 环境/安全/验收 | 【文本】 | — |

#### 2.3.2 三个关键【表格】的列定义

**表格A：性能指标表**（放在3.2节，【表格】类型）

| 列名 | 数据类型 | 必填 | 说明 |
|---|---|---|---|
| 参数名 | string | 是 | 如"响应时间" |
| 运算符 | string | 是 | ≤ ≥ = < > |
| 数值 | number | 是 | 如50 |
| 单位 | string | 是 | 如ms、tps |
| 说明 | string | 否 | — |

样例（Word文档中的表格）：

| 参数名 | 运算符 | 数值 | 单位 |
|---|---|---|---|
| 响应时间 | ≤ | 50 | ms |
| 吞吐量 | ≥ | 1000 | tps |

**表格B：接口定义表**（放在3.3节，【表格】类型）

| 列名 | 数据类型 | 必填 | 说明 |
|---|---|---|---|
| 接口名 | string | 是 | 如"串口1" |
| 接口类型 | string | 是 | 串行/并行/网络 |
| 协议 | string | 是 | RS422/RS232/TCP |
| 字段名 | string | 是 | 数据帧/状态帧 |
| 数据类型 | string | 是 | int/float/struct |
| 波特率 | number | 否 | 串行接口才有 |

**表格C：数据字典表**（放在3.4节，【表格】类型）

| 列名 | 数据类型 | 必填 | 说明 |
|---|---|---|---|
| 参数名 | string | 是 | 标准术语名 |
| 数据类型 | string | 是 | float/int/bool |
| 单位 | string | 是 | ms/tps/路 |
| 取值下限 | number | 否 | — |
| 取值上限 | number | 否 | — |

#### 2.3.3 【文本】正文与【表格】的对应关系

检测核心：从【文本】正文提取参数三元组，与【表格】逐行比对。

【文本】正文样例（3.2节）：
> "系统响应时间应≤50ms，吞吐量应≥1000tps。"

对应【表格】（表3-1性能指标表）：

| 参数名 | 运算符 | 数值 | 单位 |
|---|---|---|---|
| 响应时间 | ≤ | 50 | ms |
| 吞吐量 | ≥ | 1000 | tps |

检测逻辑：正文{响应时间,≤,50ms} = 表格{响应时间,≤,50,ms} → 一致。

### 2.4 文档结构说明JSON

每份SRS附一个JSON，告诉机器"哪个章节在哪页、哪个表格在哪"。

```json
{
  "doc_id": "SRS_型号A",
  "doc_file": "srs_documents/SRS_型号A.docx",
  "sections": [
    {"section_id": "3.2", "title": "性能指标", "page": 7, "has_table": true, "table_refs": ["表3-1"]},
    {"section_id": "3.3", "title": "接口定义", "page": 9, "has_table": true, "table_refs": ["表3-2"]}
  ],
  "tables": [
    {"table_id": "表3-1", "type": "性能指标表", "section": "3.2", "page": 7, "headers": ["参数名","运算符","数值","单位"], "rows": 15}
  ]
}
```

### 2.5 检测点映射

| 检测点 | 检测什么 | 数据类型 | 检测逻辑 |
|---|---|---|---|
| 1 | 正文性能值↔指标表 | 【文本】↔【表格】 | 提取正文参数三元组，与表3-1逐行比对 |
| 2 | 正文接口↔接口表 | 【文本】↔【表格】 | 提取正文接口描述，与表3-2逐行比对 |
| 3 | 正文术语↔数据字典 | 【文本】↔【表格】 | 正文参数名与表3-3匹配，检查单位/范围 |
| 4 | 跨条目参数矛盾 | 【表格】↔【表格】 | 同名参数在性能表和字典表中取值矛盾 |

### 2.6 交付量

SRS文档 ≥20份，每份含3个【表格】，每份 ≥20页。

## 三、场景2：引信方案设计

### 3.1 背景

西安机电信息技术研究所设计引信：先写【文本】设计技术要求，再建【模型】SysML九视图，再跑【时序】仿真。检测要求→SysML→仿真这条链上参数是否完整传递、数值是否一致。

### 3.2 数据包结构

```
场景2_数据包/
├── 型号A/
│   ├── design_requirement.docx    ← 【文本】设计技术要求
│   ├── sysml_model.xmi           ← 【模型】SysML九视图
│   ├── model_structure.json      ← 【表格】模型结构说明
│   ├── simulation/
│   │   └── output.csv           ← 【时序】仿真输出
│   └── traceability.jsonl       ← 【表格】要求→模型→仿真映射
└── README.md
```

### 3.3 设计技术要求【文本】

Word/PDF文档，5个部分：

| 部分 | 内容 | 数据类型 | 含参数? |
|---|---|---|---|
| 功能要求 | 引信做什么 | 【文本】 | 否 |
| 性能要求 | 阈值/时序/距离 | 【文本】 | 是 |
| 工作流程 | 状态/条件 | 【文本】 | 是 |
| 接口要求 | 协议/电气 | 【文本】 | 是 |
| 通用质量特性 | MTBF/MTTR | 【文本】 | 是 |

【文本】样例：
```
2 性能要求
  2.1 引爆阈值：≥5V
  2.2 解保延时：≤3s
4 接口要求
  4.1 通信接口：RS422，波特率115200
```

### 3.4 SysML九视图【模型】

#### 3.4.1 九视图与检测对应

| 视图 | 数据类型 | 检测用途 |
|---|---|---|
| 需求视图 | 【模型】 | 要求条目定义，通过satisfy链接到结构 |
| 工作流程模型 | 【模型】 | 动作定义，通过allocate分配到部件 |
| 功能分配模型 | 【模型】 | 功能→部件映射 |
| 产品组成模型 | 【模型】 | 部件和属性（参数定义在这里） |
| 接口视图 | 【模型】 | 接口连接 |
| 状态行为视图 | 【模型】 | 状态转移条件 |
| 参数视图 | 【模型】 | **数学约束——检测点2核心比对对象** |
| 时序交互视图 | 【模型】 | 消息序列 |
| 任务场景视图 | 【模型】 | 用例覆盖 |

#### 3.4.2 必须保留的追溯关系

【模型】中以下5种链接是检测依据，不能丢：

| 链接 | 从→到 | 数据类型 | 检测用途 |
|---|---|---|---|
| satisfy | 需求→部件 | 【模型】 | 要求是否在模型中实现 |
| allocate | 动作→部件 | 【模型】 | 功能是否分配到部件 |
| derive | 需求→需求 | 【模型】 | 总要求→子要求推导链 |
| verify | 需求→测试 | 【模型】 | 辅助覆盖性检测 |
| binding | 参数→参数 | 【模型】 | 参数跨视图传递链 |

### 3.5 仿真输出【时序】

CSV格式，列名必须与SysML参数视图中的参数名一致。

```csv
#engine=型号A, sampling_rate=100Hz
timestamp,threshold,voltage,fired,delay
0.0,5.0,0.0,false,3.0
0.1,5.0,0.5,false,3.0
3.1,5.0,5.2,true,3.0
```

| 列名 | 数据类型 | 来源 | 说明 |
|---|---|---|---|
| timestamp | float | 【时序】 | 仿真时间(秒) |
| threshold | float | 【模型】 | 引爆阈值，与SysML一致(5.0) |
| voltage | float | 【时序】 | 仿真实际电压——检测点2的动态侧 |
| fired | bool | 【时序】 | 是否引爆 |
| delay | float | 【模型】 | 解保延时，与SysML一致(3.0) |

检测点2：SysML定义threshold=5.0，仿真voltage在3.1s达5.2，fired变true，但delay=3.0s→3.1>3.0超差。

### 3.6 要求→模型→仿真映射【表格】

JSONL格式，每条记录描述一条完整映射链：

```json
{
  "id": "MAP-001",
  "meta": {
    "model_id": "型号A",
    "requirement": {"id": "PR-001", "text": "引爆阈值≥5V", "param": "引爆阈值", "op": "≥", "value": 5, "unit": "V"},
    "sysml": {"element_id": "BLK-001.threshold", "view": "参数视图", "param_name": "threshold", "param_value": 5.0},
    "simulation": {"csv_column": "threshold", "csv_file": "simulation/output.csv", "actual_value": 5.0},
    "status": "covered"
  }
}
```

| 字段 | 数据类型 | 说明 |
|---|---|---|
| requirement | 【文本】 | 从设计要求中提取的参数 |
| sysml | 【模型】 | SysML中对应的元素和参数值 |
| simulation | 【时序】 | 仿真CSV中的列名和实际值 |
| status | string | covered / not_covered（检测点1依据） |

### 3.7 检测点映射

| 检测点 | 检测什么 | 数据类型 | 检测逻辑 |
|---|---|---|---|
| 1 覆盖性 | 要求↔SysML | 【文本】↔【模型】 | 检查每个要求在映射中status=covered |
| 2 静态↔动态 | SysML参数↔仿真 | 【模型】↔【时序】 | 比对sysml.param_value与simulation.actual_value |
| 3 传递链 | 跨视图参数 | 【模型】 | 追踪binding/allocate/derive链是否完整 |

### 3.8 交付量

≥5个型号，每型号≥20条要求，≥50个SysML元素，≥5个仿真通道，映射≥100条。

## 四、场景3：引信质量缺陷溯源

### 4.1 背景

引信检验发现故障，构建故障树溯源。【文本】故障报告描述现象，【表格】工艺规程记录底事件。检测故障描述与底事件的对应关系、底事件状态逻辑矛盾。

### 4.2 数据包结构

```
场景3_数据包/
├── fault_reports.jsonl         ← 【文本】故障现象报告
├── process_specs.jsonl         ← 【表格】工艺规程及底事件
├── fault_process_mapping.jsonl ← 【表格】故障↔工艺对应关系
└── README.md
```

### 4.3 故障现象报告【文本】

JSONL，text字段是故障现象的自然语言描述，meta是结构化信息。

```json
{
  "id": "FR-2024-001",
  "text": "引信FUSE-A在例行检验中出现瞎火故障。检验工况：常温25℃常压101.3kPa。检验过程：按GJB XXXX进行引爆测试，连续3发未引爆。引信由安全机构、发火机构、传爆序列组成。",
  "meta": {
    "fault_part": "点火电路",
    "fault_mode": "瞎火",
    "severity": "serious",
    "product_model": "FUSE-A",
    "inspection_condition": "常温25℃常压101.3kPa",
    "related_process_spec_id": "PS-2024-001",
    "related_basic_events": ["BE-001", "BE-003"]
  }
}
```

| 字段 | 数据类型 | 必填 | 说明 |
|---|---|---|---|
| text | 【文本】 | 是 | 故障现象全文，从中NER提取部位/模式 |
| meta.fault_part | string | 是 | 故障部位，与底事件process_step比对 |
| meta.fault_mode | string | 是 | 故障模式，与底事件event_name比对 |
| meta.related_basic_events | array | 是 | 关联底事件ID列表 |
| meta.related_process_spec_id | string | 是 | 关联工艺规程ID |

### 4.4 工艺规程及底事件【表格】

JSONL，每条记录是一个工序，包含底事件和逻辑门。

```json
{
  "id": "PS-2024-001",
  "meta": {
    "step_no": 3,
    "step_name": "引线焊接",
    "process_params": {"温度": "350℃", "时间": "3s"},
    "basic_events": [
      {"event_id": "BE-001", "event_name": "焊接虚焊", "state": "需排查", "confirmed_cause": null},
      {"event_id": "BE-002", "event_name": "装配偏差", "state": "可直接排除", "confirmed_cause": false},
      {"event_id": "BE-003", "event_name": "调试超差", "state": "最终确认", "confirmed_cause": true, "evidence": "延时3.5s超出≤3s要求"}
    ],
    "logic_gates": [
      {"gate_type": "OR", "events": ["BE-001", "BE-002", "BE-003"]}
    ]
  }
}
```

底事件三态状态（检测点2的检测对象）：

| state值 | 含义 | confirmed_cause应取值 |
|---|---|---|
| 可直接排除 | 工序正常 | false |
| 需排查 | 待验证 | null |
| 最终确认 | 确认为故障原因 | true |

如果同一个底事件同时标"可直接排除"和"需排查"→检测点2逻辑矛盾。

| 字段 | 数据类型 | 必填 | 说明 |
|---|---|---|---|
| step_name | string | 是 | 工序名 |
| process_params | 【表格】 | 是 | 工艺参数键值对 |
| basic_events | 【表格】 | 是 | 底事件列表 |
| basic_events[].state | string | 是 | 三态之一 |
| basic_events[].confirmed_cause | bool/null | 是 | 是否确认原因 |
| logic_gates | 【表格】 | 是 | 逻辑门(AND/OR) |

### 4.5 故障↔工艺对应关系【表格】

```json
{
  "id": "MAP-001",
  "meta": {
    "fault_report_id": "FR-2024-001",
    "process_spec_id": "PS-2024-001",
    "basic_event_id": "BE-001",
    "relation_type": "associated",
    "relation_basis": "焊接虚焊可导致点火电路断路, 进而引发瞎火"
  }
}
```

### 4.6 检测点映射

| 检测点 | 检测什么 | 数据类型 | 检测逻辑 |
|---|---|---|---|
| 1 对应缺失 | 故障↔底事件 | 【文本】↔【表格】 | 故障描述的现象在底事件中是否有对应 |
| 2 逻辑矛盾 | 底事件状态 | 【表格】 | 同一底事件是否有矛盾状态 |
| 3 排查↔确认 | 结论↔确认 | 【表格】 | confirmed_cause=false但仍在最终确认中 |

### 4.7 交付量

故障报告 ≥100条，工艺规程 ≥50条，对应关系 ≥200条，底事件 ≥300个。

## 五、场景4：航空发动机维护保障

### 5.1 背景

中国航发控制系统研究所维护航发。每次飞行产生【时序】传感器数据，出现异常填【文本】故障工单，拆检拍【图像】。检测时序异常与工单类型是否匹配、时间是否矛盾、预测与拆解是否冲突。

### 5.2 数据包结构

```
场景4_数据包/
├── timeseries/              ← 【时序】传感器CSV（每次飞行一个文件）
│   ├── ENG001_FL012.csv
│   └── ...
├── work_orders.jsonl        ← 【文本】故障工单
├── inspection_images/       ← 【图像】拆解/孔探照片
│   └── *.jpg
├── image_annotations.jsonl  ← 【表格】图像标注
└── README.md
```

### 5.3 传感器时序【时序】

CSV格式，timestamp精确到毫秒。

```csv
#engine_id=ENG001,flight_id=FL012,date=2024-03-20,sampling_rate=100Hz
timestamp,vibration_x,vibration_y,temp_exhaust,temp_bearing,rpm,pressure_oil,fuel_flow
2024-03-20T14:35:00.000,0.05,0.04,520.3,85.1,8000,3.2,120.5
2024-03-20T14:35:00.010,0.15,0.12,521.0,85.5,7998,3.1,121.0
```

| 列名 | 数据类型 | 单位 | 说明 |
|---|---|---|---|
| timestamp | 【时序】 | — | 精确到毫秒，单调递增 |
| vibration_x/y | 【时序】 | g | 振动——健康最敏感指标 |
| temp_exhaust | 【时序】 | ℃ | 排气温度 |
| temp_bearing | 【时序】 | ℃ | 轴承温度 |
| rpm | 【时序】 | r/min | 转速——物理约束核心 |
| pressure_oil | 【时序】 | bar | 滑油压力 |
| fuel_flow | 【时序】 | kg/h | 燃油流量 |

检测点4：温度↑但转速无变化→物理约束违反。

### 5.4 故障工单【文本】

JSONL，text是工单描述，meta关联时序文件和图像。

```json
{
  "id": "WO-2024-001",
  "text": "发动机ENG-001第12架次飞行后发现振动异常。排查：检查压气机叶片发现第3级裂纹。处置：更换叶片。结论：叶片裂纹导致振动超标。",
  "meta": {
    "engine_id": "ENG001",
    "flight_id": "FL012",
    "fault_type": "压气机叶片裂纹",
    "fault_component": "压气机-第3级",
    "discovery_time": "2024-03-20T14:35:00",
    "registration_time": "2024-03-20T15:00:00",
    "related_timeseries": "timeseries/ENG001_FL012.csv",
    "related_images": ["inspection_images/ENG001_crack_001.jpg"]
  }
}
```

| 字段 | 数据类型 | 必填 | 说明 |
|---|---|---|---|
| text | 【文本】 | 是 | 工单全文（故障+排查+处置+结论） |
| meta.fault_type | string | 是 | 故障类型——与【时序】异常模式比对 |
| meta.discovery_time | datetime | 是 | 发现时间——与【时序】异常时刻比对 |
| meta.registration_time | datetime | 是 | 登记时间——与discovery_time偏移检测 |
| meta.related_timeseries | string | 是 | 关联的【时序】CSV路径 |
| meta.related_images | array | 否 | 关联的【图像】路径列表 |

检测点1：【时序】振动异常模式 ↔ 工单fault_type="压气机叶片裂纹"是否匹配。
检测点2：【时序】异常时刻14:35:00 ↔ 工单discovery_time 14:35:00 是否吻合。

### 5.5 拆解/孔探图像【图像】


| 字段 | 数据类型 | 必填 | 说明 |
|---|---|---|---|
| images | 【图像】 | 是 | 图片路径列表 |
| meta.defect_type | string | 是 | 缺陷类型——与【时序】预测结果比对 |
| meta.defect_location | string | 是 | 缺陷位置 |
| meta.related_work_order | string | 是 | 关联工单ID |
| meta.related_timeseries | string | 是 | 关联【时序】文件 |

检测点3：【时序】预测"健康"但【图像】defect_type="crack"→预测与拆解冲突。

### 5.6 检测点映射

| 检测点 | 检测什么 | 数据类型 | 检测逻辑 |
|---|---|---|---|
| 1 类型不匹配 | 时序异常↔工单类型 | 【时序】↔【文本】 | 时序异常模式与工单fault_type比对 |
| 2 时间矛盾 | 时序时间↔工单时间 | 【时序】↔【文本】 | 时序异常时刻与工单discovery_time比对 |
| 3 预测↔拆解 | 预测结果↔拆解图像 | 【时序】↔【图像】 | 时序预测健康但图像有损伤 |
| 4 物理约束 | 多通道关系 | 【时序】↔【时序】 | 温度↑但转速不变等冗余通道违反 |
