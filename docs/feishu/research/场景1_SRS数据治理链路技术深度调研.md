## 0. 概述

### 0.1 场景定位

将 >50TB 遵循 GJB 438C-2021 的历史软件需求规格文档（SRS），治理为高质量微调数据集，训"北极星"垂域大模型，实现需求智能抽取、结构化转化与辅助生成。

### 0.2 五步治理链路全景

```
原始SRS(Word/PDF, >50TB) + GJB标准条文 + 专家经验(隐性)
    │
  ①标准化预处理   文档解析→表格抽取→章节切分→涉密脱敏
    │              → 归一化SRS(统一章节结构)
    ↓
  ②结构化转化     正文NER→参数化条目 / 表格→结构化 / 引用→关系图
    │              → 结构化需求条目库(#2)
    ↓
  ③一致性校验     4类检测点(规则+LLM两路) → 标记冲突不删
    │              → 条目库+冲突标记
    ↓
  ④质量评估       完整性/一致性/合规性/准确性/可用性/隐私性打分
    │              → 分级数据集(A/B/C级)
    ↓
  ⑤知识融合       GJB条文映射 + 专家经验显性化 + 知识图谱约束
    │              → 知识增强微调数据集
    ↓
  微调数据集 → 北极星垂域大模型 → 回灌SRS全链路9环节 → 闭环迭代
```

### 0.3 数据模态

文本（SRS正文）+ 表格（性能指标表/接口定义表/数据字典）→ 对应课题三模态框架的"表格"模态。**无图像、无时序**，这是5个场景中模态最简单的。

### 0.4 军用场景硬约束（贯穿5步）

| 约束 | 含义 | 影响 |
|---|---|---|
| 数据不出域 | 全程本地推理，禁外发API | 优先开源可私有化模型 |
| 可审计 | 每步产出可追溯依据 | 规则层优先，模型层带置信度 |
| 可追溯 | 条目保留来源span+页码 | 满足GJB 5000B配置管理 |
| 涉密脱敏 | 密级标识/型号代号/战术指标需脱敏 | 脱敏后仍需可用于微调 |

## 1. ①标准化预处理

> 详见子报告: `SRS文档解析技术调研报告.md` + 脱敏报告

### 1.1 文档解析与版面分析

**核心问题**：把杂乱 Word/PDF 解析成统一结构化内容（标题/段落/列表/表格）。

| 工具 | 原理 | 中文 | 表格 | 许可 | 推荐度 |
|---|---|---|---|---|---|
| **Word直抽(python-docx)** | 读取OOXML段落/样式/表格对象 | ★★★★★ | ★★★★★(合并无损) | MIT | ★★★★★(首选) |
| **MinerU** | DocLayout-YOLO+PaddleOCR+UniMERNet流水线 | ★★★★ | ★★★★ | Apache(核心) | ★★★★★(PDF首选) |
| **PP-Structure** | 版面+表格+OCR一体化 | ★★★★★ | ★★★★ | Apache-2.0 | ★★★★★(国产替代) |
| LayoutLMv3 | 多模态Transformer版面分类 | ★★(需微调) | 仅分类 | MIT | ★★★ |
| Nougat | 端到端图像→Markdown(学术PDF) | ★(英文) | ★★ | Apache | ★(不适用) |
| GOT-OCR2.0 | 统一端到端OCR-2.0 | ★★★★ | ★★★ | Apache | ★★★★ |

**推荐**：Word走 `python-docx` 直抽（精度上限）；PDF走 MinerU（DocLayout-YOLO版面 + PaddleOCR中文OCR）；纯国产替代用 PP-Structure 全栈。

**关键论文**：MinerU(arXiv:2409.18839) / DocLayout-YOLO(arXiv:2410.12628) / LayoutLMv3(arXiv:2204.08387) / GOT-OCR2.0(arXiv:2409.01704)

### 1.2 表格抽取与结构化

**核心问题**：从文档检测表格、识别结构（行列/合并单元格/表头）、输出结构化数据。

**分层策略（精度优先，由易到难）**：

```
1) Word源文件(.docx) → python-docx原生直抽(合并单元格无损)    [主路径]
2) PDF有文本层+有框线 → Camelot(lattice)直抽                  [轻量高精]
3) PDF扫描件/无框线  → PaddleOCR表格 / StructEqTable           [模型法]
4) 极复杂嵌套/表头   → UniTable / Table Transformer + 人工校验  [兜底]
```

| 工具 | 原理 | 合并单元格 | 无框线 | 许可 | 推荐度 |
|---|---|---|---|---|---|
| Word原生直抽 | 读OOXML表格对象 | ★★★★★ | — | MIT | ★★★★★ |
| Camelot | PDF线框/空白检测 | ★★ | ★★(stream弱) | MIT | ★★★(有框线) |
| PaddleOCR表格 | 端到端表格结构→HTML | ★★★★ | ★★★★ | Apache | ★★★★★ |
| StructEqTable | 视觉大模型→LaTeX/HTML | ★★★★ | ★★★★ | Apache | ★★★★ |
| UniTable | 自监督统一框架SOTA | ★★★★ | ★★★★ | MIT | ★★★★(兜底) |
| Table Transformer | DETR检测+结构识别 | ★★★ | ★★★ | MIT | ★★★(基线) |

**关键论文**：UniTable(arXiv:2403.04822) / PubTables-1M(arXiv:2110.00061) / PP-OCR(arXiv:2009.09941)

### 1.3 章节切分（对齐GJB 7大块）

**核心问题**：按GJB 438C-2021的7大块（功能需求/性能指标/接口定义/数据字典/运行环境/安全保密/验收准则）自动切分。

| GJB语义块 | 典型章节号 | 关键内含表格 |
|---|---|---|
| 功能需求 | 3.x | 功能/接口需求表 |
| 性能指标 | 3.x/4.x | **性能指标表** |
| 接口定义 | 5.x | **接口定义表** |
| 数据字典 | 6.x | **数据字典表** |
| 运行环境 | 7.x | 环境约束表 |
| 安全保密 | 8.x | 安全要求表 |
| 验收准则 | 9.x | 验收项表 |

**推荐**：**规则法为主（编号正则 + GJB七大块锚点词典）+ 版面模型兜底 + LLM仅离线复核**。

- GJB模板高度规范，编号体系稳定，规则法可达95%+切分准确率，且完全可审计
- 切分流程：①编号正则建章/节/条树 → ②GJB锚点映射语义块 → ③完整性校验(缺块告警) → ④表格按"最近章节"归属挂载

### 1.4 涉密信息识别与文本脱敏

**核心问题**：识别密级标识/型号代号/战术指标等敏感信息并脱敏，脱敏后仍需可用于微调。

**三级级联识别**：

| 级 | 方法 | 抓什么 | 优势 |
|---|---|---|---|
| 1 | 规则/正则 | 密级标识(机密★/秘密★)、型号代号格式 | 零样本、可审计、召回稳 |
| 2 | 自定义军事NER | 装备型号、部队番号、战术指标描述 | 识别未登录实体、上下文感知 |
| 3 | LLM语义识别 | 作战场景描述、意图级敏感 | 捕获语义级敏感(规则/NER遗漏的) |

> SurrogateShield(arXiv:2606.29567) 验证此级联架构在22类PII上 F1≈98.87%。

**分层脱敏算子（关键设计：不一刀切）**：

| 敏感实体 | 脱敏算子 | 语义保留度 | 对微调影响 |
|---|---|---|---|
| 密级标识 | **删除(redact)** | 低 | 大(但无语义价值) |
| 装备型号代号 | **伪名化**(EQUIP_01确定性映射) | 高(保共指一致性) | 极小 |
| 战术性能数值 | **泛化为区间**(≥50km→[40,60)km) | 中高(保量级分布) | 小 |
| 作战场景描述 | **合成替换**(生成等价虚构场景) | 高(保语义结构) | 小 |
| 接口参数名/数据字典项 | **保留**(非敏感) | — | —(微调必需) |

> SurrogateShield实证：合成替换 vs 占位符遮罩，BERTScore从81.59%→94.85%(+13.26pp)，且对手LLM无法恢复原始值。

**推荐工具**：Presidio V2（开源、可私有化部署、YAML no-code配置、支持自定义Recognizer/Operator）。Google DLP仅作架构参考(云服务不适用)。

**可用性评估**：脱敏前后BERTScore语义相似度 + 下游微调任务指标保持率 + k-匿名重识别风险 + canary记忆化审计。

**关键论文**：SurrogateShield(arXiv:2606.29567) / DP-Prompt(arXiv:2410.00751) / 1-Diffractor MLDP(arXiv:2405.01678) / Kapelinski DP-SGD(arXiv:2606.28479)

### 1.5 ①推荐Pipeline

```
SRS.docx ──→ python-docx直抽 ──┐
                                ├──→ 统一IR(章节树+结构化表) ──→ GJB七大块映射
SRS.pdf  ──→ MinerU/PP-Structure┘         │
                                           ↓
                                   涉密脱敏(Presidio三级级联+分层算子)
                                           │
                                           ↓
                                     归一化SRS(脱敏后)
```

**落地优先级**：P0吃Word源(80%+) → P1 PDF有框线(Camelot) → P2 PDF扫描件(MinerU全栈) → P3兜底增强 → P4质量闭环。

## 2. ②结构化转化

> 详见子报告: `SRS数据治理技术调研报告.md`

### 2.1 领域NER与参数抽取

**核心问题**：把"系统响应时间应≤50ms"→ `{param:响应时间, op:≤, value:50, unit:ms, type:性能}`。本质是实体+关系+数值属性联合抽取。

| 方案 | 代表方法 | 准确率 | 标注成本 | 可解释性 | 适用场景 |
|---|---|---|---|---|---|
| **a)规则/正则+模板** | 自定义DSL、spaCy ruler | 高(格式固定>95%) | 低 | 极高(可审计) | "≤50ms""8路"等模式化表述 |
| **b)预训练模型微调NER** | RoBERTa-wwm+CRF | 中高(F1 85-92%) | 中高 | 中 | 术语边界模糊、多义词 |
| **c)生成式UIE/指令IE** | UIE、DeepKE、GoLLIE | 中高 | 低(少样本) | 中 | schema多变、低资源 |
| **d)通用LLM抽取** | Qwen2.5/DeepSeek few-shot→JSON | 中(zero)/高(few) | 极低 | 低(黑盒) | 冷启动、原型验证 |

**推荐**：**规则兜底 + RoBERTa-wwm微调主力 + LLM处理长尾/校验** 的三层pipeline。

- 规则层：正则模板库 `(?P<param>...)(?P<op>[≤≥<>≈])(?P<val>\d+\.?\d*)\s*(?P<unit>ms|Mbps|路|℃)` → 高召回+可审计
- 模型层：RoBERTa-wwm-ext + CRF 标注 `[PARAM][OP][VALUE][UNIT][PROTO]`，GJB语料领域续训(MLM)
- LLM层：Qwen few-shot 抽取规则未覆盖的复杂句式 + GoLLIE风格guideline校验

> 警示：Li et al.(arXiv:2304.11633)证实LLM抽取过度自信、校准低，必须人工复核。

**关键论文**：UIE(arXiv:2203.12277,ACL2022) / DeepKE(arXiv:2201.03335,EMNLP2022) / GoLLIE(arXiv:2310.03668,ICLR2024) / InstructIE(arXiv:2305.11527,ISWC2024)

### 2.2 表格结构化与字段映射

**核心问题**：把三类表格（性能指标表/接口定义表/数据字典）映射到统一schema；表头识别、列类型推断、术语归一化。

| 方案 | 表头识别 | 跨表对齐 | 术语归一化 | 中文 |
|---|---|---|---|---|
| **规则+模板匹配** | 高(GJB固定表头) | 弱(硬编码) | 弱 | 强 |
| **TableLlama** | 高 | 高 | 高 | 中高 |
| TAPAS/TabBERT | 中高 | 中 | 中 | 弱(英文) |
| 知识图谱对齐 | — | 高 | 高 | 中 |

**推荐**：**规则模板匹配表头 + TableLlama列类型推断 + 同义词典+向量归一化**。

- GJB表头固定但术语写法不统一（"响应时间"vs"反应时间"vs"时延"）
- 构建**军工参数同义词典** + 向量相似度做表-文术语对齐
- Table Meets LLM(arXiv:2305.13062)结论：表格序列化为Markdown+标注关键值，显著提升LLM表格理解

**关键论文**：TableLlama(arXiv:2311.09206,NAACL2024) / Table Meets LLM(arXiv:2305.13062,WSDM2024) / TAMA(arXiv:2501.14693,ACL2025)

### 2.3 交叉引用解析与关系建模

**核心问题**：解析"见3.2节""如表4所示""参见GJB 438C第5.3条"，构建条目间引用关系图。

| 方案 | 锚点识别 | 指向解析 | 复杂句 | 可解释性 |
|---|---|---|---|---|
| **正则+规则** | 高(编号固定) | 高(查索引表) | 弱 | 极高 |
| 依存句法(HanLP/LTP) | 中高 | 中 | 中 | 高 |
| LLM引用抽取 | 高 | 中高 | 高 | 低 |
| 图数据库(Neo4j) | — | — | — | 高(存储查询) |

**推荐**：**正则解析为主(覆盖90%+显式引用) + HanLP依存句法补强 + Qwen处理隐式引用 + Neo4j存储关系图**。

- GJB编号高度规范，正则即可高覆盖
- Neo4j建模：节点(需求条目/参数/接口/表/外部标准)，边(REFERS_TO/DEFINED_IN/VERIFIED_BY/DEPENDS_ON)
- 支撑GJB 5000B的**需求可追溯性矩阵(RTM)**自动生成

### 2.4 ②推荐Pipeline

```
归一化SRS(文本+表格)
    ├──文本支路──→ 规则参数抽取 → NER微调 → UIE联合生成 → LLM长尾+校验
    ├──表格支路──→ 表头模板匹配 → TableLlama列推断 → 术语归一化
    │
    └──条目融合去重 → 交叉引用解析(正则+依存+LLM) → Neo4j关系图
                                                    ↓
                              参数化需求条目库(#2) + 引用关系图 + RTM
```

## 3. ③一致性校验

> 来源: `子课题3技术方案_三层治理对标.md` + `medical_operators.py`(已验证原型) + `数据场景分析.md:23-34`

### 3.1 三层治理体系

仓库已验证的三层递进式校验体系（`子课题3技术方案:10-101`）：

| 层 | 校验什么 | 业内技术 | 开源工具 | 场景1对应 |
|---|---|---|---|---|
| **L1语法一致性** | 字段格式/范围/类型 + 多字段联合约束 + 跨记录 | SHACL约束验证 | Great Expectations, Cleanlab, Pandera | 检测点1(数值)、检测点3(术语) |
| **L2语义一致性** | 跨模态对齐 + 知识图谱事实核验 + 多粒度 | CLIP对齐, DEFAME核查 | CLIP, DEFAME, FAMDR | 检测点2(接口语义)、检测点3(术语语义) |
| **L3逻辑一致性** | 专家知识形式化 + 时序逻辑 + 约束求解 | 本体工程, 流程挖掘 | Easy Dataset, Z3 Solver, PM4Py | 检测点4(跨条目参数约束) |

### 3.2 四检测点技术方案

| 检测点 | 检测对象 | 对什么比 | 治理层 | 检测路线 | 规则来源 |
|---|---|---|---|---|---|
| **1 性能正文↔指标表** | 性能指标条目 | 正文阈值 vs 表数值 | L1b多字段联合约束 | **规则库**(数值+运算符直接比) | GJB"条目间参数无矛盾" |
| **2 接口正文↔接口表** | 接口定义条目 | 正文协议/字段 vs 接口表 | L2语义一致性 | **LLM直判**(非数值语义比对) | GJB接口规范 |
| **3 数据字典↔正文术语** | 术语条目 | 正文参数名/单位 vs 字典定义 | L1a字段+L2术语对齐 | **规则库**(术语归一化+单位换算后比) | 术语规范+单位换算 |
| **4 跨条目参数矛盾** | 功能/性能/接口/安全性条目 | 同参数跨条目取值 | L3多要素协同约束 | **规则库+约束求解**(同参数跨条目比) | GJB"各条目参数不能矛盾" |

**两条检测路线**（互补，参考 `medical_operators.py` 已验证原型）：

| 路线 | 实现 | 原理 | 覆盖检测点 | 优势 |
|---|---|---|---|---|
| **规则库三层** | medical_operators.py风格 | 知识库驱动L1→L2→L3递进 | 1,3,4(数值/术语/跨条目) | 确定性高、可解释、可审计 |
| **LLM直判** | unified_operators.py风格 | 条目喂LLM判断一致性→JSON | 2(语义级)+补充 | 灵活、覆盖规则盲区 |

### 3.3 规则库设计（GJB版，参考 medical_kb.json 结构）

仓库已验证的 `medical_kb.json` 采用三层规则库结构，场景1需构建GJB版：

```json
{
  "L1_param_ranges": {
    "响应时间": {"normal_op": "<=", "normal_val": 50, "unit": "ms", "severity_high": [{"threshold": 100, "level": "HIGH"}]},
    "吞吐量": {"normal_op": ">=", "normal_val": 1000, "unit": "tps", "severity_high": [{"threshold": 500, "level": "HIGH"}]}
  },
  "L2_term_diagnosis_rules": [
    {"param": "响应时间", "op": ">", "threshold": 50, "unit": "ms", "conflict_if": "性能指标表值不一致", "severity": "HIGH"}
  ],
  "L3_cross_param_rules": [
    {"name": "输入路数一致", "conditions": [{"param":"功能要求.输入路数","op":"==","val":"性能要求.输入路数"}], "severity": "CRITICAL"}
  ]
}
```

**关键设计**：
- L1：单参数范围规则（参数名→正常范围+严重度阶梯）
- L2：参数↔表格跨位置比对规则（同参数正文值 vs 表格值不一致→冲突）
- L3：跨条目参数约束规则（同参数在不同条目取值必须一致）

### 3.4 校验运作机制（四阶段管道，`unified_operators.py` 已验证）

```
结构化条目库 → ①抽取(NER只拆不判) → ②检测(规则+LLM两路) → ③解释(定位冲突位置) → ④置信度
```

**关键设计**：**只标记不删数据**（`process_single` 恒返回 True）。冲突样本挂到 `stats` 上出报告——因为冲突样本本身是高价值微调数据。

## 4. ④质量评估

> 来源: 脱敏+质量评估报告 + 仓库 `子课题3技术方案:109-117`

### 4.1 质量评估维度（对齐SRS/GJB场景）

| 维度 | 定义 | SRS场景具体指标 | 评估方法 |
|---|---|---|---|
| **完整性** | 必需内容是否齐全 | GJB七大块覆盖；字段缺失率 | Great Expectations期望 |
| **一致性** | 内部无矛盾 | 4类冲突检测通过率 | ③校验管道输出 |
| **合规性** | 符合标准 | GJB 438C-2021条目对标率 | 标准模板对标 |
| **准确性** | 参数值/术语正确 | 术语库命中率；参数值合理性 | Cleanlab置信学习 |
| **可用性** | 脱敏后能否微调 | 脱敏后BERTScore语义保持度 | 效用-隐私权衡评估 |
| **隐私性** | 脱敏彻底度 | 残留敏感实体数；k-匿名 | Presidio复检 |
| **多样性** | 覆盖分布均衡 | 装备类型/场景分布 | 分布统计 |

### 4.2 评估工具与框架

| 工具 | 核心机制 | 适用维度 | 仓库验证 | 学术依据 |
|---|---|---|---|---|
| **Great Expectations** | 规则驱动声明式Expectation | 完整性/一致性/合规性 | ✅已验证 | — |
| **Cleanlab** | 置信学习估计标签噪声 | 准确性(标签错误) | ✅已验证 | Northcutt, JAIR 2021(arXiv:1911.00068) |
| **TADS** | 任务感知数据选择(质量+相关度+多样性) | 多样性/任务对齐 | ❌ | arXiv:2602.05251 |
| **UniFilter** | 多模态质量分类器(合成训练) | 多模态质量 | ❌ | EMNLP 2025(arXiv:2510.15162) |
| **AIDRIN** | AI数据就绪度框架(含隐私/公平) | 全维度参考 | ❌ | arXiv:2406.19256 |
| **自定义GJB评分模型** | 加权综合打分→分级 | 全维度(中枢) | 待建 | Data Readiness Report(arXiv:2010.07213) |

### 4.3 质量分级标准

| 等级 | 分数 | 判定条件 | 用途 | 处置 |
|---|---|---|---|---|
| **A级** | ≥85 | 七大块齐全、4类冲突0、GJB对标率≥95%、脱敏语义保持≥90%、无残留敏感 | **直接微调** | 入库+dataset card |
| **B级** | 70-84 | 个别字段缺失/少量冲突(≤3)/对标率80-95%/语义保持75-90% | **人工复核后可用** | 标记问题→修正/降级 |
| **C级** | <70 | 大块缺失/冲突>3/对标率<80%/语义损失大/残留敏感 | **退回重做** | 退回数据源+记录缺陷 |

**评分模型**：加权综合分 = w1·完整性 + w2·一致性 + w3·合规性 + w4·准确性 + w5·可用性 + w6·隐私性。**隐私性为一票否决项**（残留敏感直接降C）。

**分层评估架构**：

```
数据集
  ├─ L1规则层(GX)：完整性(七大块)+一致性(4类冲突)+合规性(GJB对标) → 自动评分
  ├─ L2标签层(Cleanlab)：指令-响应标签置信度 → 噪声标记
  ├─ L3语义层(LLM抽样)：合规性/准确性语义复核 → 抽样报告
  ├─ L4隐私层(Presidio复检+k匿名)：残留敏感 → 一票否决
  └─ 汇总 → 自定义评分模型 → A/B/C分级 → 路由处置
```

## 5. ⑤知识融合

> 来源: `子课题3技术方案:77-101` + `entity_research.md:80-110` + `DKG-CMR框架落地映射.md` + `深度科研调研报告.md:351-362`

### 5.1 GJB标准条文结构化

**核心问题**：把GJB 438C-2021标准条文（PDF/Word）转成可执行规则，用于合规比对和冲突判定。

| 方法 | 工具 | 原理 | 仓库验证 |
|---|---|---|---|
| **文档→结构化规则** | Easy Dataset | 上传标准文档→解析分块→LLM提取规则→结构化规则库 | ✅已克隆 |
| **本体编辑** | Protégé | 手动构建武器装备本体(OWL) | ❌待建 |
| **知识表示** | OWL/RDF/SHACL | 本体→SHACL形状→可执行约束 | ❌待建 |

**技术路线**（`子课题3技术方案:87-101`）：

```
GJB标准文档(PDF/Word)
    ↓ Easy Dataset + LLM提取
结构化规则库(条文→参数约束→合规规则)
    ↓ 转化为

    ↓ 用于
③一致性校验的规则基准 + ④合规性评估
```

### 5.2 专家经验显性化

**核心问题**：把散落在专家脑中的设计准则、评审经验、常见错误，转成结构化知识标签挂到条目上。

| 知识类型 | 来源 | 形式化方法 | 用途 |
|---|---|---|---|
| 设计准则 | 专家经验/历史评审记录 | 规则模板→L3约束规则 | ③校验的L3层规则来源 |
| 常见错误模式 | 历史缺陷台账 | 错误模式库→冲突检测规则 | ③校验的检测规则补充 |
| 参数约束 | 领域知识(如"响应时间军用≤50ms") | 参数范围规则→L1规则库 | ③校验的L1层规则来源 |
| 合规要求 | GJB条文+所内规范 | 条文→条目映射→合规标签 | ④合规性评估基准 |

**方法论**（`典型场景:90`）：多轮迭代 → 可解释诊断 → 专家校验 → 规则增强 → 模型反馈闭环。专家确认的新规则写回知识库，持续扩充规则覆盖。

### 5.3 知识图谱构建与约束验证

**核心问题**：构建武器装备/SRS领域的知识图谱，用本体约束传播验证条目间一致性。

**KG在冲突检测中的真实角色**（`entity_research.md:80-110` 关键结论）：

> 标准ontology（如SNOMED CT）**没有显式"contradicts"矛盾边**。KG的真实用法是：**规范化 + 关系推理**，配合LLM或嵌入做矛盾判断，不是直接查"矛盾边"。

**场景1的KG设计**：

```
节点：需求条目 / 参数 / 接口 / 表格 / GJB条文 / 装备型号
边：  DEFINED_IN(参数→数据字典)
      REFERS_TO(条目→条目/表/标准条文)
      VERIFIED_BY(需求→验收准则)
      CONSTRAINED_BY(参数→GJB条文)
      DEPENDS_ON(性能指标→接口定义)
```

**约束验证流程**：
1. 条目库实体链接到KG（参数名→KG节点，术语归一化）
2. KG本体定义约束（如"口径×类型×重量"物理耦合关系，`子课题3:17`）
3. 约束传播推理检测违反领域知识的冲突
4. 记录推理路径（证据溯源）

**工具选型**：

| 功能 | 首选 | 备选 | 仓库验证 |
|---|---|---|---|
| 本体编辑 | Protégé | OWL API | ❌待建 |
| 约束验证 | pySHACL | Great Expectations | ❌待验证 |
| KG推理 | DEFAME | OpenKE | ❌ |
| KG存储 | Neo4j | — | ②已推荐 |
| 文档→规则 | Easy Dataset | LLM提取 | ✅已克隆 |

**关键论文**：KGDMC(ACM 2025, DOI:10.1145/3696410.3714813) / SNOMED CT+Neo4j(arXiv:2510.16899) / DEFAME(多模态事实核查)
