## 0. 概述

### 0.1 场景定位

针对引信部件/整机检测出的**故障现象**，结合**工艺规程**反向溯源，定位造成故障的生产工艺环节（底事件），自动生成含 **9 部分要素**的质量缺陷溯源报告，用于引信科研生产质量闭环。

与场景1（SRS需求治理，"设计阶段"）不同，场景3聚焦**生产/检测阶段的质量回溯**——输入是"已经出了什么故障"，输出是"哪个工艺环节造成的、机理是什么、怎么改"。两者的共同点是模态同为"文本↔表格"，但场景3的核心结构是**故障树**（一棵由底事件→中间事件→顶事件组成的逻辑树），而非场景1的参数化条目库。

### 0.2 五步治理链路全景

```
故障现象报告(Word/PDF) + 工艺规程文件 + 故障树台账 + 辅助数据(检验工况/工艺参数记录/不合格品处置)
    │
  ①标准化预处理   文档解析→故障树表/工艺规程表抽取→故障现象切分→涉密脱敏
    │              → 归一化故障-工艺数据(统一结构)
    ↓
  ②结构化转化     故障现象NER→故障要素 / 工艺规程→底事件 / 故障树→逻辑图
    │              → 结构化底事件库(#2)+故障树关系图
    ↓
  ③一致性校验     3类检测点(规则+LLM两路) → 标记冲突不删
    │              → 底事件库+冲突标记
    ↓
  ④质量评估       9要素完整性/一致性/合规性/准确性/可追溯性打分
    │              → 分级溯源数据(A/B/C级)
    ↓
  ⑤知识融合       故障机理映射 + 工艺经验显性化 + 故障树KG约束
    │              → 知识增强溯源微调数据集
    ↓
  溯源数据集 → 溯源垂域模型 → 自动生成9要素溯源报告 → 回灌闭环
```

### 0.3 数据模态

文本（故障现象报告/溯源报告/检验记录）+ 表格（工艺规程及要素表/故障树底事件表/检验工况数据表）→ 对应课题三模态框架的"表格"模态。**无图像、无时序**，与场景1同为5个场景中模态最简单的。但场景3的表格承载的是**树形逻辑结构**（故障树），比场景1的扁平参数表结构更复杂。

### 0.4 军用场景硬约束（贯穿5步）

| 约束 | 含义 | 影响 |
|---|---|---|
| 数据不出域 | 全程本地推理，禁外发API | 优先开源可私有化模型 |
| 可审计 | 每步产出可追溯依据 | 规则层优先，模型层带置信度 |
| 可追溯 | 底事件保留来源工序/工步/参数记录 | 满足GJB 5000B配置管理与不合格品控制 |
| 涉密脱敏 | 型号代号/战术指标/工艺参数需脱敏 | 脱敏后仍需可用于溯源推理 |
| 质量闭环 | 溯源结论须回灌工艺改进 | 溯源报告→纠正措施→工艺规程修订闭环 |

> 与场景1相比，场景3多了"质量闭环"约束——溯源不是终点，纠正措施须回写到工艺规程，形成PDCA闭环。这要求溯源系统与工艺规程管理系统双向打通。

## 1. ①标准化预处理

> 文档解析部分与场景1共用技术栈（`SRS文档解析技术调研报告.md`），此处仅列场景3特有内容。

### 1.1 故障报告与工艺规程文档解析

**核心问题**：把杂乱的故障现象报告（Word/PDF）+ 工艺规程文件解析成统一结构化内容。

| 输入文档 | 典型格式 | 结构特点 | 推荐工具 |
|---|---|---|---|
| 故障现象报告 | Word(.docx) | 含检验过程/工况/现象描述/引信组成原理，半结构化叙述 | python-docx直抽 |
| 工艺规程文件 | Word/PDF | 含工序流程/工艺参数表/设备要求，表格密集 | Word直抽 + MinerU(PDF) |
| 故障树台账 | Excel/Word表格 | 底事件列表(编号/名称/状态/排查结论)，结构化 | pandas/openpyxl |
| 检验工况数据 | CSV/Excel | 传感器/仪器读数表格，结构化 | pandas |
| 不合格品处置记录 | Word/Excel | 处置意见/审批流程，半结构化 | python-docx + pandas |

**推荐**：与场景1一致——Word走 `python-docx` 直抽；PDF走 MinerU（DocLayout-YOLO版面 + PaddleOCR中文OCR）；Excel表格走 pandas 直读。

### 1.2 故障树表格与工艺规程表抽取

**核心问题**：故障树底事件表和工艺规程要素表是场景3的核心结构化数据，需精确抽取。

场景3的表格类型与场景1不同：

| 表格类型 | 典型列结构 | 抽取难点 | 推荐方案 |
|---|---|---|---|
| **故障树底事件表** | 底事件编号\|名称\|工艺状态\|排查结论\|影响因素 | 状态字段多值（排除/排查/确认），需枚举校验 | pandas直读(Excel) + 规则校验 |
| **工艺规程要素表** | 工序号\|工序名称\|设备\|工艺参数\|技术要求\|检验方式 | 工艺参数嵌套（温度×时间×压力），合并单元格多 | Word直抽(python-docx) + StructEqTable |
| **检验工况数据表** | 检验项\|工况条件\|实测值\|标准值\|判定 | 数值+文本混合，单位不统一 | pandas + 单位归一化 |
| **不合格品处置表** | 不合格项\|处置方式\|审批\|日期 | 审批流程跨行合并 | Word直抽 |

**分层策略**（同场景1，精度优先）：
```
1) Excel源文件 → pandas直读(结构化无损)                    [主路径]
2) Word(.docx)  → python-docx原生直抽(合并单元格无损)       [主路径]
3) PDF有框线    → Camelot(lattice)直抽                      [轻量高精]
4) PDF扫描件    → PaddleOCR表格 / StructEqTable              [模型法]
```

### 1.3 故障现象结构化切分

**核心问题**：故障现象报告是半结构化叙述文本，需按溯源逻辑切分为可对齐的语义块。

场景3的故障报告须包含（`数据场景分析.md:79`）：检验过程、检验工况、故障现象、引信主要组成及工作原理。切分目标：

| 语义块 | 对应溯源要素 | 切分锚点 | 典型内容 |
|---|---|---|---|
| 检验过程 | 排查过程(9要素之4) | "检验"/"测试"/"试验"章节标题 | 在什么条件下做了什么检测 |
| 检验工况 | 排查情况(9要素之5) | "工况"/"条件"/"环境" | 温度/湿度/振动/电磁等工况参数 |
| 故障现象 | 缺陷问题(9要素之1) | "现象"/"故障"/"异常" | 描述故障的具体表现 |
| 引信组成原理 | 引信介绍(9要素之2)/技战术指标(9要素之3) | "原理"/"组成"/"结构" | 引信工作原理与组成部件 |

**推荐**：**规则法为主（章节标题正则 + 锚点词典）+ LLM兜底**。工艺/故障文档结构相对规范，规则法可达90%+切分准确率，与场景1的GJB七大块切分思路一致。

### 1.4 涉密信息识别与文本脱敏

**核心问题**：识别型号代号/战术指标/工艺参数等敏感信息并脱敏，脱敏后仍需可用于溯源推理。

与场景1共用三级级联识别 + 分层脱敏算子（`SurrogateShield`, arXiv:2606.29567），场景3特有脱敏对象：

| 敏感实体 | 场景3典型 | 脱敏算子 | 对溯源影响 |
|---|---|---|---|
| 型号代号 | 引信型号XX-1 | 伪名化(FUZE_01确定性映射) | 极小(保共指一致性) |
| 战术性能数值 | 延时时间/作用距离 | 泛化为区间(≥50ms→[40,60)ms) | 小(保量级分布) |
| 工艺参数 | 焊接温度/装配力矩 | 泛化为区间 | 小(保工艺范围) |
| 故障现象描述 | 保留(非敏感) | — | —(溯源必需) |
| 底事件名称 | 保留(非敏感，工艺通用术语) | — | —(溯源必需) |

**推荐工具**：Presidio V2（开源、可私有化部署、YAML no-code配置），同场景1。

### 1.5 ①推荐Pipeline

```
故障报告.docx ──→ python-docx直抽 ──┐
工艺规程.docx/pdf ──→ python-docx/MinerU┤
故障树台账.xlsx ──→ pandas直读 ──────┤
                                     ├──→ 统一IR(故障语义块+结构化表) ──→ 故障现象切分
检验工况.csv ──→ pandas直读 ──────────┤
                                     ↓
                              涉密脱敏(Presidio三级级联+分层算子)
                                     ↓
                              归一化故障-工艺数据(脱敏后)
```

**落地优先级**：P0吃Excel台账+pandas(结构化最优) → P1 Word故障报告(python-docx) → P2 PDF工艺规程(MinerU) → P3兜底增强 → P4质量闭环。

## 2. ②结构化转化

> NER与表格映射技术栈与场景1共用（`SRS数据治理技术调研报告.md`），此处聚焦故障树/底事件特有结构化。

### 2.1 故障现象NER与要素抽取

**核心问题**：把故障现象叙述文本抽取为结构化要素 `{故障部位, 故障模式, 表现描述, 严重程度, 关联工序}`。本质是领域NER + 关系抽取。

| 方案 | 代表方法 | 准确率 | 标注成本 | 可解释性 | 适用场景 |
|---|---|---|---|---|---|
| **a)规则/正则+模板** | 故障模式词典 + 工序名匹配 | 高(术语固定时>90%) | 低 | 极高(可审计) | "引信瞎火""延期不合格"等模式化表述 |
| **b)预训练模型微调NER** | RoBERTa-wwm + CRF | 中高(F1 85-90%) | 中高 | 中 | 故障描述模糊、多义 |
| **c)生成式UIE/指令IE** | UIE、DeepKE | 中高 | 低(少样本) | 中 | schema多变 |
| **d)通用LLM抽取** | Qwen2.5/DeepSeek few-shot→JSON | 中(zero)/高(few) | 极低 | 低(黑盒) | 冷启动 |

**推荐**：**规则兜底 + RoBERTa-wwm微调主力 + LLM处理长尾**，与场景1同构。

- 规则层：构建**引信故障模式词典**（瞎火/早炸/延期超差/解除保险失败/安全失效等）+ **工序名匹配库**（焊接/装配/调试/灌封/检测等），正则抽取
- 模型层：RoBERTa-wwm-ext + CRF 标注 `[FAULT_PART][FAULT_MODE][PROCESS][PARAM][SEVERITY]`
- LLM层：Qwen few-shot 抽取规则未覆盖的复杂故障描述

**关键论文**：UIE(arXiv:2203.12277,ACL2022) / DeepKE(arXiv:2201.03335,EMNLP2022) / GoLLIE(arXiv:2310.03668,ICLR2024)

### 2.2 工艺规程结构化与底事件建模

**核心问题**：把工艺规程文件转为"底事件库"——每个工艺状态作为一个不可分解的底事件，带状态属性。

**底事件数据模型**（参照`数据场景分析.md:77`）：

```json
{
  "event_id": "BE-001",
  "event_name": "焊接工序-焊点虚焊",
  "process_step": "工序3-引线焊接",
  "process_params": {"温度": "350℃", "时间": "3s", "压力": "2N"},
  "state": "需排查",           // 可直接排除 / 需排查 / 最终确认
  "investigation_conclusion": null,  // 排查结论(排查后填)
  "confirmed_cause": null,     // 是否确认为影响因素
  "evidence": null,            // 试验验证证据
  "source_doc": "工艺规程v2.docx#工序3",
  "logic_relation": {"gate": "OR", "siblings": ["BE-002", "BE-003"]}
}
```

**底事件状态三态**（`数据场景分析.md:77`明确要求"可直接排除/需排查/最终确认"）：

| 状态 | 含义 | 后续处理 |
|---|---|---|
| **可直接排除** | 工艺记录证明该工序正常，无需排查 | 标记排除依据 |
| **需排查** | 该工序可能存在问题，需试验验证 | 安排排查试验 |
| **最终确认** | 排查后确认为故障原因 | 定位故障机理 |

**结构化方法**：工艺规程 → 工序切分(规则) → 每工序提取底事件(NER) → 构建底事件库。

### 2.3 故障树构建与关系建模

**核心问题**：把底事件按逻辑关系组织成故障树（FTA），支持从顶事件（故障现象）到底事件（工艺环节）的溯源推理。

**故障树标准**：IEC 61025《Fault Tree Analysis》定义的国际标准。

| 故障树要素 | 场景3对应 | 说明 |
|---|---|---|
| 顶事件(Top Event) | 故障现象 | "引信瞎火"等被溯源的故障 |
| 中间事件 | 故障模式分解 | "点火电路失效"→"能量不足"/"时序错误" |
| 底事件(Basic Event) | 工艺环节 | "焊接虚焊"/"装配偏差"/"调试超差" |
| 逻辑门 | AND/OR | AND=多因素同时发生; OR=任一因素即可导致 |

**构建方法对比**：

| 方法 | 原理 | 逻辑门识别 | 最小割集 | 可解释性 | 适用 |
|---|---|---|---|---|---|
| **规则+模板** | 预定义故障树模板(引信型号×故障模式) | 高(模板固化) | 高(模板预计算) | 极高 | 成熟型号、已知故障模式 |
| **专家构建+LLM辅助** | 专家画树 + LLM从报告抽取补充 | 中高 | 中 | 高 | 新型号、未知故障模式 |
| **LLM自动构建** | Qwen从故障报告+工艺规程生成故障树JSON | 中 | 低 | 低 | 冷启动、原型验证 |
| **图数据库存储** | Neo4j存储故障树拓扑 | — | Cypher查询 | 高 | 溯源推理与多跳查询 |

**推荐**：**规则模板为主(成熟型号) + LLM辅助构建(新型号) + Neo4j存储关系图**。

- 成熟引信型号的常见故障模式（瞎火/早炸/延期超差等）有标准化故障树模板，规则法覆盖率高
- 新型号或新故障模式用 LLM 从故障报告+工艺规程中抽取底事件与逻辑关系，生成故障树JSON
- Neo4j建模：节点(顶事件/中间事件/底事件/工序/工艺参数)，边(`CAUSED_BY`/`AND_GATE`/`OR_GATE`/`OCCURS_AT`)

**故障树存储示例**（Neo4j Cypher）：
```
(:TopEvent {name:"引信瞎火"})
  -[:CAUSED_BY]-> (:MidEvent {name:"点火电路失效"})
  -[:OR_GATE]-> (:BasicEvent {name:"焊接虚焊", state:"需排查", step:"工序3"})
  -[:OR_GATE]-> (:BasicEvent {name:"电容失效", state:"可直接排除", step:"工序5"})
```

**最小割集(MCS)分析**：故障树定性分析的核心——找出所有能导致顶事件发生的底事件最小组合。可用Neo4j Cypher多跳查询或专门FTA工具计算。

### 2.4 ②推荐Pipeline

```
归一化故障-工艺数据(文本+表格)
    ├──故障报告支路──→ 规则故障模式抽取 → NER微调 → LLM长尾抽取
    ├──工艺规程支路──→ 工序切分 → 底事件NER → 底事件库构建
    ├──故障树支路──→ 规则模板匹配 → LLM辅助构建 → Neo4j故障树图
    │
    └──底事件-故障现象对齐 → 对应关系建模(故障现象→底事件映射)
                                                     ↓
                              结构化底事件库(#2) + 故障树关系图 + 对应关系表
```

## 3. ③一致性校验

> 来源: `数据场景分析.md:85-94` + `子课题3技术方案_三层治理对标.md` + `medical_operators.py`(已验证原型)

### 3.1 三层治理体系

仓库已验证的三层递进式校验体系（`子课题3技术方案:10-101`），场景3映射：

| 层 | 校验什么 | 业内技术 | 开源工具 | 场景3对应 |
|---|---|---|---|---|
| **L1语法一致性** | 底事件字段格式/状态枚举/参数范围 + 多字段联合约束 | SHACL约束验证 | Great Expectations, Pandera | 检测点2(底事件状态枚举)、工艺参数范围 |
| **L2语义一致性** | 故障现象↔底事件对应关系 + 故障树逻辑一致性 | 知识图谱推理 + 规则核验 | pySHACL, DEFAME, Z3 | 检测点1(对应缺失)、检测点2(逻辑矛盾) |
| **L3逻辑一致性** | 排查结论↔影响因素确定的因果一致性 + 跨记录溯源链完整 | 约束求解 + 因果推断 | Z3 Solver, PM4Py | 检测点3(结论矛盾)、溯源链完整性 |

### 3.2 三检测点技术方案

| 检测点 | 检测对象 | 对什么比 | 治理层 | 检测路线 | 规则来源 |
|---|---|---|---|---|---|
| **1 故障现象↔底事件对应缺失** | 故障现象↔底事件映射 | 故障现象在工艺规程中是否有可解释的底事件 | L2语义一致性 | **规则库**(故障模式→底事件映射表) + LLM直判 | 故障树模板 + 工艺规程 |
| **2 底事件间逻辑矛盾** | 底事件状态 | 同一底事件是否"既可直接排除又需排查" | L1b多字段约束 + L2逻辑 | **规则库**(状态枚举校验) + Z3约束求解 | "底事件间无逻辑矛盾"准则 |
| **3 排查结论↔影响因素矛盾** | 排查结论↔确认因素 | 排查排除的底事件是否仍被确认为影响因素 | L3因果一致性 | **规则库**(结论-因素一致性) + Z3约束求解 | 排查逻辑一致性准则 |

**两条检测路线**（互补，参考 `medical_operators.py` 已验证原型）：

| 路线 | 实现 | 原理 | 覆盖检测点 | 优势 |
|---|---|---|---|---|
| **规则库三层** | medical_operators.py风格 | 知识库驱动L1→L2→L3递进 | 1,2,3(对应/状态/结论) | 确定性高、可解释、可审计 |
| **LLM直判** | unified_operators.py风格 | 故障报告+底事件喂LLM判断→JSON | 1(语义级对应)+补充 | 灵活、覆盖规则盲区 |

### 3.3 故障树底事件规则库设计（引信版，参考 medical_kb.json 结构）

仓库已验证的 `medical_kb.json` 采用三层规则库结构，场景3需构建引信故障树版：

```json
{
  "L1_event_state_rules": {
    "BE-001": {"event_name": "焊接虚焊", "valid_states": ["可直接排除", "需排查", "最终确认"], 
               "params": {"温度": {"normal_low": 340, "normal_high": 360, "unit": "℃"}}},
    "BE-002": {"event_name": "电容失效", "valid_states": ["可直接排除", "需排查", "最终确认"]}
  },
  "L2_fault_event_mapping": [
    {"fault_mode": "瞎火", "candidate_events": ["BE-001", "BE-002", "BE-005"], 
     "conflict_if": "无候选底事件", "severity": "HIGH", 
     "detail_template": "故障模式'{fault}'在工艺规程中找不到可解释的底事件"}
  ],
  "L3_investigation_consistency_rules": [
    {"name": "排查结论与影响因素一致", 
     "conditions": [{"event": "BE-001", "conclusion": "排除", "confirmed_cause": "是"}], 
     "conflict_if": "排查排除但确认为影响因素", "severity": "CRITICAL"}
  ]
}
```

**关键设计**（对应3个检测点）：
- **L1**：底事件状态枚举校验 + 工艺参数范围规则（检测点2的状态矛盾）
- **L2**：故障模式→候选底事件映射规则（检测点1的对应缺失）
- **L3**：排查结论→影响因素一致性规则（检测点3的结论矛盾）

### 3.4 校验运作机制（四阶段管道，`unified_operators.py` 已验证）

```
结构化底事件库 → ①抽取(NER只拆不判) → ②检测(规则+LLM两路) → ③解释(定位冲突位置) → ④置信度
```

**关键设计**：**只标记不删数据**（`process_single` 恒返回 True）。冲突样本挂到 `stats` 上出报告——因为冲突样本本身是高价值溯源数据（标记问题供人工复核）。

**三检测点的具体检测逻辑**：

**检测点1（故障现象↔底事件对应缺失）**：
```
对每个故障现象F:
  1. 从L2_fault_event_mapping查F.fault_mode的候选底事件列表
  2. 若候选列表为空 → 冲突(HIGH): "故障现象在工艺规程中找不到可解释的底事件"
  3. 若候选列表非空，逐一检查候选底事件是否在底事件库中存在
  4. LLM补充: 把故障现象+全部底事件喂Qwen，判断是否真的无对应(语义级)
```

**检测点2（底事件间逻辑矛盾）**：
```
对每个底事件BE:
  1. 检查BE.state是否在valid_states枚举内 → 不在则冲突(编码异常)
  2. 检查同一底事件在不同记录中是否有矛盾状态 
     (如台账A标"可直接排除"，台账B标"需排查") → 冲突(CRITICAL)
  3. Z3约束求解: state∈{排除,排查,确认}互斥 → 若同时满足互斥条件则冲突
```

**检测点3（排查结论↔影响因素矛盾）**：
```
对每个底事件BE(已排查):
  1. 若BE.investigation_conclusion=="排除" 且 BE.confirmed_cause=="是" → 冲突(CRITICAL)
  2. 若BE.investigation_conclusion=="确认" 且 BE.confirmed_cause=="否" → 冲突(HIGH)
  3. Z3约束: conclusion排除 ⟹ confirmed_cause≠是
```

### 5.3 故障树知识图谱与约束验证

**核心问题**：构建引信故障树知识图谱，用本体约束传播验证底事件间逻辑一致性。

**KG在溯源中的真实角色**（`entity_research.md:80-110` 关键结论）：

> 标准ontology没有显式"contradicts"矛盾边。KG的真实用法是：**规范化 + 关系推理**，配合LLM或约束求解器做矛盾判断，不是直接查"矛盾边"。

**场景3的KG设计**：

```
节点：顶事件(故障现象) / 中间事件(故障模式) / 底事件(工艺环节) / 工序 / 工艺参数 / 纠正措施
边：  CAUSED_BY(中间事件→顶事件)
      OR_GATE / AND_GATE(底事件→中间事件，逻辑门)
      OCCURS_AT(底事件→工序)
      PARAM_OF(工艺参数→工序)
      FIXED_BY(底事件→纠正措施)
      INVESTIGATED_AS(底事件→排查结论)
```

**约束验证流程**：
1. 底事件库实体链接到KG（底事件名→KG节点，工序归一化）
2. KG本体定义约束（如"同一底事件state互斥"、"排查排除⟹confirmed_cause≠是"）
3. 约束传播推理检测违反领域知识的冲突（用Z3或pySHACL）
4. 记录推理路径（证据溯源：顶事件→中间事件→底事件→工序→参数）

**约束求解示例**（Z3 Solver，检测点2+3）：
```python
from z3 import *
# 底事件BE-001的状态变量
state = String("BE-001_state")
confirmed = Bool("BE-001_confirmed_cause")
s = Solver()
# 约束1: state只能是三个合法值之一
s.add(Or(state == "可直接排除", state == "需排查", state == "最终确认"))
# 约束2: 若state=="可直接排除" 则 confirmed必须为False
s.add(Implies(state == "可直接排除", confirmed == False))
# 检查: 若输入state="可直接排除", confirmed=True → unsat → 冲突
```

## 8. 仓库已验证原型对照

场景3的技术路线在本仓库已有医疗领域的验证原型，可直接迁移：

| 场景3步骤 | 医疗原型 | 验证内容 | 迁移要点 |
|---|---|---|---|
| ③规则库L1 | `medical_operators.py: MedicalLabRangeFilter` | 单指标范围检测(知识库驱动) | 换底事件状态枚举+工艺参数范围规则 |
| ③规则库L2 | `medical_operators.py: LabDiagnosisConflictFilter` | 血检异常↔诊断标签冲突(1444条) | 换故障模式↔底事件对应缺失检测(检测点1) |
| ③规则库L3 | `medical_operators.py: CrossLabConsistencyFilter` | 多指标协同一致性 | 换排查结论↔影响因素一致性(检测点3) |
| ③诊断互斥 | `medical_operators.py: DiagnosisConsistencyFilter` | No Finding+其他诊断互斥 | 换底事件状态互斥(检测点2) |
| ③LLM直判 | `unified_operators.py: _llm_detect_medical` | LLM判断血检↔标签一致性→JSON | 换故障现象↔底事件语义对应判断prompt |
| ③四阶段管道 | `unified_operators.py: 3算子` | 抽取→检测→解释→置信度 | 直接复用架构，换领域模型 |
| ④质量评估 | `medical_operators.py: stats标记` | 冲突标记不删数据→报告 | 直接复用 |
| ⑤知识库 | `knowledge/medical_kb.json` | 三层规则库JSON结构 | 换引信故障树底事件规则库 |

**迁移结论**（`entity_research.md:236-238`）：
1. 不要从零写NER+规则——手写冲突规则不可扩展
2. NER作为辅助而非核心——用于定位和解释冲突
3. 三层规则库+LLM直判两路互补——已验证可行

**场景3与场景1/医疗原型的关键差异**：

| 维度 | 医疗原型(场景0) | 场景1(SRS) | 场景3(引信溯源) |
