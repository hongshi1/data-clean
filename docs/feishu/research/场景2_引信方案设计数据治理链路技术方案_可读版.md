## 场景定位与核心差异

**业务定位**：基于引信产品设计技术要求，开展 SysML 九视图建模与总体/详细方案设计，实现设计技术要求 → SysML 模型 → 详细方案的智能生成与映射。

**与场景1的核心差异**：

| 维度 | 场景1 (SRS) | 场景2 (引信方案) |
|---|---|---|
| 数据模态 | 文本 + 表格 | 文本 + **结构化模型(SysML)** + **时序仿真** |
| 模态复杂度 | 最简单（2模态） | 最复杂之一（3模态，含动态仿真） |
| 核心矛盾 | 文本↔表格数值矛盾 | **静态视图↔动态仿真行为冲突** |
| 检测点数 | 4个 | 3个（但每个更复杂） |
| 可复用架构 | 三层规则库+LLM直判 | 三层规则库+LLM直判+**形式化验证** |

**数据模态**：文本（设计技术要求）+ 结构化模型（SysML 九视图）+ 时序仿真（Simulink/SystemVue/Mworks 动态行为）→ 对应课题"**表格 ↔ 时序**"模态组合。

## ① 标准化预处理

**目标**：把异构的设计技术要求文档、SysML 模型文件、仿真模型文件，解析成统一格式的归一化资产。

### 细粒度点 1：设计技术要求文档解析

**问题**：设计技术要求是 Word/PDF 文档，含 5 大部分——功能要求、性能要求、工作流程、接口要求、通用质量特性。需要解析成结构化文本，为后续参数化提供干净输入。

**技术方案**：

**方案A：Word 原生直抽（python-docx）**
与场景1相同，设计技术要求文档以 Word 为主。用 `python-docx` 直接读取段落、样式、表格对象。.doc 旧格式先用 `libreoffice --headless --convert` 转 .docx。这是**主路径**，精度上限。

**方案B：MinerU / PP-Structure（PDF 主引擎）**
对于只有 PDF 的文档，复用场景1的 MinerU 流水线（DocLayout-YOLO 版面检测 + PaddleOCR 中文 OCR + StructEqTable 表格识别）。纯国产替代用 PP-Structure 全栈。

**方案C：LLM 辅助结构理解**
设计技术要求的 5 大部分结构高度规范，但不同型号产品的表述存在变体。用 Qwen2.5 few-shot 做章节语义识别，将变体表述映射到标准的 5 大块。仅用于离线复核。

**推荐**：Word 走 python-docx 直抽；PDF 走 MinerU；LLM 仅离线复核。与场景1共用解析栈。

### 细粒度点 2：SysML 九视图模型解析

**问题**：SysML 九视图是引信领域基于 OMG SysML 的领域特化建模方法论，来自 Cameo Systems Modeler / Eclipse Papyrus / MWorks.Sysbuilder 等工具。需要从 XMI/XML 导出文件中提取结构化元素。

**九视图映射**（领域特化，非标准 SysML 9 图的直接对应）：

| # | 视图名称 | SysML 图类型 | 核心内容 | 一致性检测角色 |
|---|---|---|---|---|
| 1 | 需求视图 | Requirement Diagram (req) | 系统需求条目、追溯关系 | DP1 覆盖性检测源端 |
| 2 | 任务场景视图 | Use Case Diagram (uc) | 任务、参与者、外部系统 | DP1 覆盖性检测 |
| 3 | **工作流程模型** | Activity Diagram (act) | 任务操作逻辑、输入→动作→输出 | DP3 传递链中间节点 |
| 4 | 时序交互视图 | Sequence Diagram (sd) | 系统-外部交互序列、接口需求 | DP1 接口覆盖检测 |
| 5 | 状态行为视图 | State Machine Diagram (stm) | 运行状态、状态转移条件 | DP2 静态-动态比对源端 |
| 6 | **产品组成模型** | Block Definition Diagram (bdd) | 系统分解层级（子系统/部件） | DP3 传递链结构节点 |
| 7 | 接口视图 | Internal Block Diagram (ibd) | 子系统间内部接口、外部接口 | DP1 接口覆盖检测 |
| 8 | **功能分配模型** | Activity Diagram (swimlanes) | 系统功能分配到子系统 | DP1 功能覆盖检测 |
| 9 | **参数视图** | Parametric Diagram (par) | 性能指标数学约束关系 | DP2 静态-动态比对源端 |

**技术方案**：

**方案A：pyEcore 解析 XMI（主路径）**
pyEcore 是 Eclipse EMF/Ecore 的 Python 实现，可直接加载 XMI 文件并遍历模型元素。Cameo/Papyrus/EA 均支持 XMI 2.1 导出。

```python
from pyecore.resources import ResourceSet, URI
rset = ResourceSet()
resource = rset.get_resource(URI('fuse_model.xmi'))
root = resource.contents[0]
for element in root.eAllContents():
    # 提取 Block/Requirement/Constraint/Activity/State 等
    print(element.eClass.name, element.name)
```

提取的结构化元素包括：Block（系统组件+属性+操作）、Requirement（需求条目+追溯关系）、Constraint（参数约束方程）、Activity/State（行为逻辑）、Port/Interface（接口定义）。

**方案B：PySysML2 解析 SysML 2.0 文本**
如果模型采用 SysML 2.0 文本格式（OMG 2023 发布），PySysML2 是专用 Python 解析器，将 SysML 2 模型解析为 Python 对象。SysML 2.0 的文本语法比 XMI 更人类可读、更易解析。

**方案C：Cameo/Papyrus 原生 API（备选）**
Cameo 提供 Java API（插件开发），Papyrus 基于 Eclipse EMF 提供 Java API。适合在建模工具内部直接提取，但不适合脱离工具的批量处理。

**关键挑战**：XMI 标准化不足——不同工具导出的 XMI 存在工具特化扩展，图表信息（diagram layout）在 XMI 交换中常丢失。模型元素和关系可可靠传递，但图形布局需重建。

**推荐**：pyEcore 解析 XMI 2.1 为主路径（工具无关、纯 Python）；SysML 2.0 用 PySysML2；Cameo/Papyrus 原生 API 仅用于工具内集成。

### 细粒度点 3：仿真模型解析

**问题**：详细方案以 Simulink/SystemVue/Mworks 原理框图形式给出，含结构方案、电路方案、算法方案。需要从仿真文件中提取：输入参数、输出行为轨迹、阈值约束、模块结构。

**技术方案（按仿真工具分层）**：

**Simulink (.slx) 解析**：

| 方案 | 原理 | 优势 | 限制 |
|---|---|---|---|
| **SimulinkInterface** | .slx 是 ZIP/OPC 容器，内含 XML。用 zipfile + xml.etree 解析 | 纯 Python、无需 MATLAB | 仅静态结构提取，无法获取仿真输出 |
| **MATLAB Engine API** | Python 调用 MATLAB 引擎，用 `get_param()`/`find_system()`/`sim()` | 全功能（含仿真执行） | 需 MATLAB 许可证 |
| **slxpy** | 通过 Embedded Coder 生成 Python 绑定 | 可在 Python 中执行仿真 | 需 MATLAB+Embedded Coder |

SimulinkInterface 提取的结构化数据：
- `block_list`：每个块的 Name/SID/BlockType/Parameters（Gain/SampleTime 等）/Mask
- `connection_list`：源-目标块的信号连接关系
- 子系统层级结构

**MWorks (苏州同元) 解析**：

MWorks 是国产 Modelica 建模仿真平台，是亚洲唯一独立 Modelica 内核。Modelica 模型是**文本格式**（.mo 文件），可直接解析：

```modelica
model FuseDetonator
  parameter Real threshold = 5.0 "引爆阈值(V)";
  Real voltage "输入电压";
  Boolean fired "是否引爆";
equation
  fired = voltage >= threshold;
end FuseDetonator;
```

| 方案 | 原理 | 优势 |
|---|---|---|
| **MWorks.SDK** | 三层 API（Kernel/Mo/Frame），结构化模型表示与操作 | 官方支持、含仿真结果读写 |
| **Modelica 文本解析** | .mo 文件按 Modelica 语法解析（ANTLR 语法可用） | 无需 MWorks 许可 |
| **FMI/FMU 导出** | 编译为 Functional Mockup Unit（ZIP+XML+C代码） | 跨工具互操作标准 |

**SystemVue (Keysight) 解析**：

SystemVue 无公开 Python API。通过 VBscript/Jscript 脚本自动化、COM 接口外部控制、或命令行批量执行+结果文件解析获取数据。

**跨工具互操作：FMI 标准**

FMI (Functional Mockup Interface) 3.0 是 Modelica Association 的免费标准，定义了 FMU 容器（ZIP+XML+C代码），被 **280+ 工具**支持（Simulink/Dymola/OpenModelica/SystemVue/Mworks 等）。波音、空客、西门子、MathWorks 均在顾问委员会——航空航天+国防领域广泛采用。

```
Simulink .slx ──→ FMU 导出 ──┐
MWorks .mo ────→ FMU 导出 ──┤──→ 统一 FMU 容器 → 跨工具仿真 + 参数提取
SystemVue ─────→ FMU 导出 ──┘
```

**推荐**：Simulink 用 SimulinkInterface（无 MATLAB 时）或 MATLAB Engine API（有 MATLAB 时）；MWorks 用 SDK 或 Modelica 文本解析；SystemVue 用脚本+COM；**FMI 作为跨工具统一交换标准**。

### 细粒度点 4：涉密信息识别与文本脱敏

**问题**：引信设计涉及型号代号、战术性能指标（引爆阈值、作用距离、安全距离等）、作战场景描述。需要脱敏后才能用于微调。

**复用场景1的三级级联识别 + 分层脱敏算子架构**，替换领域组件：

| 敏感实体 | 识别方法 | 脱敏算子 | 语义保留度 |
|---|---|---|---|
| 引信型号代号 | 规则正则 + 军事NER | 伪名化(FUSE_01确定性映射) | 高(保共指一致性) |
| 战术性能数值 | 自定义NER + 上下文 | 泛化为区间(≥5V→[4,6)V) | 中高(保量级分布) |
| 作战场景描述 | LLM语义识别 | 合成替换(等价虚构场景) | 高(保语义结构) |
| 设计参数名/接口定义 | — | 保留(非敏感) | —(微调必需) |

> 复用 Presidio V2 框架，替换Recognizer为引信领域NER模型。

**推荐**：伪名化/合成替换保语义 + DP-SGD 训练期兜底 + canary 审计验证。与场景1共用脱敏栈。

## ② 结构化转化

**目标**：把归一化的设计要求、SysML 视图、仿真模型，拆成参数化条目并构建要求→实现映射关系图。

### 细粒度点 1：设计技术要求参数化

**问题**：设计技术要求含 5 大部分，需要参数化为结构化条目 `{参数名, 运算符, 数值, 单位, 条目类型, 所属部分}`。

**5 大部分参数化结构**：

| 部分 | 条目类型 | 典型参数 | 参数化示例 |
|---|---|---|---|
| 功能要求 | FUNCTIONAL | 引信功能（保险/解保/引爆） | `{param:解保方式, value:电磁, type:功能}` |
| 性能要求 | PERFORMANCE | 阈值/时序/距离 | `{param:引爆阈值, op:≥, value:5, unit:V, type:性能}` |
| 工作流程 | WORKFLOW | 状态/时序/条件 | `{param:解保延时, op:≤, value:3, unit:s, type:流程}` |
| 接口要求 | INTERFACE | 协议/电气/机械 | `{param:接口类型, value:RS422, type:接口}` |
| 通用质量特性 | QUALITY | 六性指标 | `{param:MTBF, op:≥, value:10000, unit:h, type:质量}` |

**通用质量特性（六性）映射**：

| 六性 | GJB标准 | 典型参数化 |
|---|---|---|
| 可靠性 | GJB 450A | `{param:MTBF, op:≥, value:10000, unit:h}` |
| 维修性 | GJB 368A | `{param:MTTR, op:≤, value:0.5, unit:h}` |
| 测试性 | GJB 2547 | `{param:故障检测率, op:≥, value:95, unit:%}` |
| 安全性 | GJB 900 | `{param:安全距离, op:≥, value:50, unit:m}` |
| 保障性 | GJB 3872 | `{param:备件满足率, op:≥, value:90, unit:%}` |
| 环境适应性 | GJB 4239 | `{param:工作温度, range:[-40,70], unit:℃}` |

**技术方案**：复用场景1的三层 pipeline——规则正则（GJB 句式固定>95%）+ RoBERTa-wwm+CRF（F1 85-92%）+ LLM 长尾校验（GoLLIE 风格 guideline）。

### 细粒度点 2：SysML 九视图结构化抽取

**问题**：从 XMI 解析出的原始模型元素，需要按九视图分类、提取关键结构化数据。

**抽取结构**：

```
SysML九视图
├─ 需求视图(REQ)     → 需求条目: {id, text, type, priority, derived_from}
├─ 任务场景视图(UC)  → 用例: {id, name, actors, included_actions}
├─ 工作流程模型(ACT) → 活动: {id, name, inputs, outputs, control_flow, object_flow}
├─ 时序交互视图(SD)  → 交互: {id, participants, messages, sequence}
├─ 状态行为视图(STM) → 状态: {id, state_name, entry/action, transitions, guard_conditions}
├─ 产品组成模型(BDD) → 组件: {id, name, type, attributes, operations, composition_hierarchy}
├─ 接口视图(IBD)     → 接口: {id, source_port, target_port, interface_type, direction}
├─ 功能分配模型(ACT+) → 分配: {function_id, allocated_to_block_id}
└─ 参数视图(PAR)     → 约束: {id, constraint_expr, parameters[], units[]}
```

**技术方案**：

**pyEcore 遍历 + SysML 元模型映射**
用 pyEcore 加载 XMI 后，按 SysML 元模型（UML Profile）的类型标签分类提取：
- `«Requirement»` → 需求视图条目
- `«Block»` → 产品组成模型组件
- `«ConstraintBlock»` → 参数视图约束
- `Activity`/`State` → 行为视图条目
- `«Satisfy»`/`«Verify»`/`«Allocate»` → 跨视图关系

**关键论文**：Fu et al. (IEEE Access 2021, DOI:10.1109/access.2021.3115165) 提出 SysML 模型图构建方法，将 SysML 模型文件转为跨产品图用于知识复用——可直接迁移为场景2的图存储方案。

### 细粒度点 3：仿真参数与行为抽取

**问题**：从仿真模型中提取输入参数、输出行为轨迹、阈值约束，用于后续与 SysML 静态参数比对。

**抽取结构**：

```
仿真模型
├─ 输入参数: {param_name, value, unit, min, max, source_block}
├─ 输出轨迹: {signal_name, time_series[], unit, sample_rate}
├─ 阈值约束: {constraint_name, threshold, tolerance, actual_max, actual_min}
├─ 模块结构: {block_name, block_type, inputs[], outputs[], parameters{}}
└─ 仿真元数据: {solver, step_size, duration, tool}
```

**技术方案**：

**Simulink 参数提取**（SimulinkInterface）：
```python
model = SimulinkInterface.SimulinkModel("fuse_circuit.slx")
for block in model.block_list:
    params = block.get("Parameters", {})
    # 提取 Gain/Threshold/SampleTime 等参数
```

**仿真输出提取**（MATLAB Engine API）：
```python
eng = matlab.engine.start_matlab()
eng.load_system('fuse_circuit.slx')
out = eng.sim('fuse_circuit', 'ReturnWorkspaceOutputs', 'on')
# out.tout → 时间序列, out.yout → 输出信号
```

**MWorks 仿真结果**（SDK）：
MWorks.SDK 的 Kernel API 支持仿真结果读写，可提取变量轨迹和事件序列。

**FMI 统一接口**：
如果所有仿真模型都导出为 FMU，可用统一的 FMI API 提取参数和执行仿真：
```python
from fmpy import read_model_description, simulate_fmu
md = read_model_description("fuse_model.fmu")
# md.modelVariables → 参数/输入/输出变量列表
result = simulate_fmu("fuse_model.fmu")  # 执行仿真→输出轨迹
```

### 细粒度点 4：要求→实现映射构建

**问题**：设计技术要求的每条要求，需要在 SysML 九视图和仿真模型中找到对应实现。这是 GJB 5000B 可追溯性矩阵(RTM)的核心要求。

**映射关系结构**：

```
设计技术要求条目
    │
    ├─ «satisfy» → SysML需求视图条目
    │                ├─ «allocate» → 功能分配模型(子系统)
    │                │                ├─ 「实现于」 → 产品组成模型(部件)
    │                │                └─ 「验证于」 → 仿真模型(模块)
    │                └─ 「约束于」 → 参数视图(约束方程)
    └─ «verify» → 仿真输出(验证结果)
```

**技术方案**：

**方案A：SysML 原生追溯关系提取（主路径）**
SysML 标准定义了 `«satisfy»`/`«verify»`/`«deriveReqt»`/`«allocate»` 等追溯关系。从 XMI 中提取这些关系，直接构建映射图。覆盖率取决于建模规范性。

**方案B：NLP 追溯链恢复（补强）**
对缺少显式追溯关系的模型，用 NLP 方法自动恢复追溯链：
- **T-SimCSE**（arXiv:2603.11800, 2026）：对比预训练模型做追溯链恢复，无需标注数据，在 10 个公开数据集上验证。
- **BERT 嵌入 + 余弦相似度**：将设计要求文本和 SysML 元素文本编码为向量，计算相似度做匹配。
- **LLM 辅助语义对齐**（arXiv:2508.16181）：Li et al. 2025 用 GPT 做跨模型语义对齐，处理独立开发的 SysML 模型间的语义差异。

**方案C：Neo4j 关系图存储**
与场景1相同，用 Neo4j 存储映射关系图。节点（要求条目/SysML元素/仿真模块/参数），边（SATISFY/ALLOCATE/VERIFY/CONSTRAIN/IMPLEMENT）。

**关键论文**：
- Wheaton & Herber (arXiv:2410.21288, 2024)：INCOSE 派生的 SysML 元模型，将需求嵌入系统模型实现自动化 V&V。
- Guo et al. (arXiv:2405.10845, 2024)：需求追溯的 NLP 方法综述。

**推荐**：SysML 原生追溯关系提取为主 + NLP 追溯链恢复补强 + Neo4j 存储映射图。

## ③ 一致性校验

**目标**：在结构化条目库和映射图上检测 3 类矛盾，标记冲突不删数据——冲突样本本身是高价值微调数据。

### 细粒度点 1：检测点1——设计技术要求 ↔ 总体方案覆盖性矛盾

**问题**：某条功能/性能要求在 SysML 九视图中无对应元素——要求→实现断裂。

**技术方案**：**NLP 追溯链恢复 + 覆盖矩阵自动化**

**检测流程**：
1. 从设计技术要求抽取全部参数化条目（5 大部分）
2. 从 SysML 九视图抽取全部需求视图条目和功能分配条目
3. 构建覆盖矩阵：要求条目 × SysML 元素
4. 用 T-SimCSE/BERT 计算语义相似度，阈值匹配
5. 检查每条要求是否有至少一个 SysML 元素对应
6. 无对应 → 覆盖性矛盾（要求→实现断裂）

**三层检测**：

| 层 | 检测什么 | 方法 | 示例 |
|---|---|---|---|
| **L1 功能覆盖** | 功能要求 → 功能分配模型 | SysML `«satisfy»`关系 + NLP匹配 | 要求"电磁解保"但功能分配模型无对应活动 |
| **L2 性能覆盖** | 性能要求 → 参数视图 | 参数名匹配 + 约束方程存在性检查 | 要求"引爆阈值≥5V"但参数视图无 threshold 约束 |
| **L3 接口覆盖** | 接口要求 → 接口视图(IBD) | 接口类型/方向匹配 | 要求"RS422接口"但IBD无RS422端口 |

**效果参考**：T-SimCSE 在 10 个公开追溯链数据集上验证有效（arXiv:2603.11800）。NLP 追溯链恢复在工业实践中召回率 70-85%。

---

### 细粒度点 2：检测点2——静态视图参数 ↔ 动态仿真行为冲突

**问题**：SysML 参数视图的阈值（如"引爆阈值≥5V"）与 Simulink 仿真输出的实际行为超差（仿真显示实际触爆电压 4.2V）。**这是场景2最核心的检测点**——静态设计与动态行为的一致性。

**技术方案**：**参数比对 + 容差检查 + 形式化验证**

**检测流程**：
1. 从 SysML 参数视图提取约束方程和阈值
2. 从仿真模型提取对应参数的实际值和输出轨迹
3. 参数名归一化（同义词典+向量匹配，如"引爆阈值"↔"threshold"↔"trigger_voltage"）
4. 容差检查：`|设计值 - 仿真值| ≤ 容差` → 一致；否则冲突
5. 轨迹检查：仿真输出是否在设计约束范围内

**三层检测**：

| 层 | 检测什么 | 方法 | 示例 |
|---|---|---|---|
| **L1 阈值比对** | 设计阈值 vs 仿真实际值 | 数值直接比 + 容差检查 | 设计≥5V，仿真触爆4.2V → 冲突 |
| **L2 轨迹约束** | 设计约束范围 vs 仿真输出轨迹 | 轨迹极值/稳态值 vs 约束边界 | 设计温度≤70℃，仿真峰值82℃ → 冲突 |
| **L3 行为一致性** | SysML状态机 vs 仿真状态序列 | 状态转移序列匹配 | SysML定义"安全→解保→引爆"三态，仿真出现未定义的"安全→引爆"跳转 |

**形式化验证补强**：

**Simulink Design Verifier (SDV)**：MathWorks 的形式化验证工具，基于 SMT（可满足性模理论）求解器，对 Simulink/Stateflow 模型做属性证明和反例生成。可自动检测"设计要求某条件永远成立，但仿真模型存在违反该条件的执行路径"。

**Modelica_Requirements**：开源 Modelica 库（Otter et al. 2015, DOI:10.3384/ecp15118625），在仿真模型中嵌入形式化需求约束块（含容差带），仿真时自动评估需求满足度。

**效果参考**：
- Simulink Design Verifier 在工业实践中可自动发现安全关键属性违反（MathWorks 官方）
- Modelica_Requirements 在 Linköping 大学验证可行（30 引用）
- Chambers et al. (arXiv:2501.18514, 2025) 自动化物理推理验证 SysML 模型一致性

**检测点2的两路互补**（参考场景1架构）：

| 路线 | 实现 | 原理 | 覆盖 | 优势 |
|---|---|---|---|---|
| **规则库数值比对** | 参数名归一化+容差检查 | 设计值vs仿真值数值直接比 | L1,L2(数值级) | 确定性高、可解释、可审计 |
| **LLM 语义判定** | Qwen2:7b 本地直判 | 语义级理解"参数对应关系" | L3(行为级)+补充 | 灵活、覆盖规则盲区 |
| **形式化验证** | SDV/Modelica_Requirements | SMT求解+约束满足 | L3(属性级) | 数学证明、可穷举 |

### 细粒度点 3：检测点3——跨视图指标传递断裂

**问题**：参数从需求视图 → 结构视图 → 行为视图 → 参数视图的传递链中出现数值丢失/篡改。例如需求视图定义"引爆阈值≥5V"，传递到参数视图变成"≥4V"。

**技术方案**：**参数传递链追踪 + 约束传播验证**

**参数传递链**：

```
需求视图(REQ)          结构视图(BDD)         行为视图(STM/ACT)      参数视图(PAR)
┌──────────┐          ┌──────────┐         ┌──────────┐          ┌──────────┐
│ 引爆阈值  │─derive──→│ 解保电路  │─allocate→│ 解保状态  │─constrain→│ V≥5     │
│ ≥5V      │          │ 阈值参数  │         │ 转移条件  │          │          │
└──────────┘          └──────────┘         └──────────┘          └──────────┘
```

**检测流程**：
1. 从 Neo4j 映射图中提取参数传递链（`deriveReqt → allocate → constrain`）
2. 提取链条上每个节点的参数值
3. 逐节点比对：参数值是否一致传递
4. 发现值丢失/篡改/不一致 → 传递断裂

**规则库设计（引信版，参考 medical_kb.json 结构）**：

```json
{
  "L1_param_ranges": {
    "引爆阈值": {"normal_op": ">=", "normal_val": 5, "unit": "V",
                 "severity_high": [{"threshold": 4, "level": "HIGH"}]},
    "安全距离": {"normal_op": ">=", "normal_val": 50, "unit": "m",
                 "severity_high": [{"threshold": 30, "level": "CRITICAL"}]}
  },
  "L2_param_transfer_rules": [
    {"param": "引爆阈值", 
     "transfer_chain": ["需求视图", "结构视图", "行为视图", "参数视图"],
     "conflict_if": "链条上任一节点值≠源节点值",
     "severity": "HIGH"}
  ],
  "L3_cross_view_rules": [
    {"name": "解保延时一致",
     "conditions": [{"view":"需求视图.解保延时","op":"==","val":"参数视图.解保延时"}],
     "severity": "CRITICAL"}
  ]
}
```

**约束传播验证**：
用 SysML 参数视图的约束方程（ConstraintBlock），结合 Z3 Solver 做约束满足性检查。如果约束系统不可满足（UNSAT），说明存在参数矛盾。

**效果参考**：
- Lu et al. (IEEE TSMC 2021, DOI:10.1109/tsmc.2020.3048821) 验证了 MBSE 工具链中自动化参数值选择和灵活验证的可行性。
- Z3 Solver 在场景1已推荐用于检测点4（跨条目参数约束），可直接迁移到跨视图参数传递链检测。

### 校验运作机制（四阶段管道，复用场景1架构）

```
结构化条目库 + 映射关系图
    ↓
①抽取：SysML/仿真参数提取（只拆不判）
    ↓
②检测：规则库三层(L1→L2→L3) + LLM直判 + 形式化验证，三路互补
    ↓
③解释：定位冲突到具体视图/条目/参数/仿真模块
    ↓
④置信度：根据冲突严重度+检测方法+置信度，打 high/medium/low
```

**关键设计**：**只标记不删数据**（`process_single` 恒返回 True）。冲突挂到 `stats` 上出报告——冲突样本后续当微调数据，教模型"这种不一致要报出来"。

## ④ 质量评估

**目标**：给治理后的数据集打分分级，决定哪些能直接微调、哪些需人工复核、哪些退回重做。

### 细粒度点 1：质量评估维度（7维，对齐引信方案设计场景）

| 维度 | 定义 | 场景2具体指标 |
|---|---|---|
| **覆盖性** | 要求→实现覆盖率 | 5大部分要求在SysML/仿真中的对应率 |
| **一致性** | 内部无矛盾 | 3类冲突检测通过率 |
| **可追溯性** | 全链路可追溯 | 需求→结构→行为→参数传递链完整率 |
| **准确性** | 参数值/约束正确 | 参数值合理性；约束方程正确性 |
| **合规性** | 符合标准 | GJB引信相关标准对标率 |
| **完整性** | 必需内容齐全 | 5大部分齐全；九视图齐全 |
| **可用性** | 脱敏后能否微调 | 脱敏后BERTScore语义保持度 |

> 与场景1对比：新增"覆盖性"和"可追溯性"两个维度（场景2的核心需求），"隐私性"降为"可用性"子项（引信场景涉密程度低于SRS）。

---

### 细粒度点 2：评估工具选型

**复用场景1的工具栈**，新增场景2特有工具：

| 工具 | 核心机制 | 适用维度 | 场景2新增用途 |
|---|---|---|---|
| **Great Expectations** | 规则驱动声明式 | 完整性/合规性 | 检查5大部分齐全、九视图齐全 |
| **Cleanlab** | 置信学习 | 准确性 | 仿真参数标签噪声检测 |
| **Simulink Design Verifier** | SMT形式化验证 | 一致性/准确性 | 仿真模型属性证明 |
| **Eclipse OCL** | 约束语言验证 | 合规性/一致性 | SysML模型良构性检查 |
| **pySHACL** | SHACL约束验证 | 合规性 | KG本体约束验证 |
| **自定义评分模型** | 加权综合打分→分级 | 全维度(中枢) | 引信方案专用评分 |

**分层评估架构**：

```
数据集
  ├─ L1规则层(GX)：完整性(5部分+9视图)+合规性(GJB对标) → 自动评分
  ├─ L2覆盖层(NLP)：覆盖性(要求→实现)+可追溯性(传递链) → 覆盖矩阵
  ├─ L3一致层(③校验)：3类冲突检测通过率 → 冲突报告
  ├─ L4形式化层(SDV/OCL)：属性证明+良构性 → 形式化报告
  ├─ L5语义层(LLM抽样)：准确性/合规性复核 → 抽样报告
  └─ 汇总 → 评分模型 → A/B/C分级 → 路由处置
```

---

### 细粒度点 3：质量分级标准

| 等级 | 分数 | 判定条件 | 用途 |
|---|---|---|---|
| **A级** | ≥85 | 5部分齐全、9视图齐全、3类冲突0、覆盖率≥95%、追溯链完整率≥90%、GJB对标率≥95% | 直接微调 |
| **B级** | 70-84 | 个别部分缺失/少量冲突(≤3)/覆盖率80-95%/追溯链80-90% | 人工复核后可用 |
| **C级** | <70 | 大块缺失/冲突>3/覆盖率<80%/追溯链断裂 | 退回重做 |

**评分模型**：加权综合分 = w1·覆盖性 + w2·一致性 + w3·可追溯性 + w4·准确性 + w5·合规性 + w6·完整性。**可追溯性为一票否决项**（追溯链断裂直接降C——无法证明设计合规）。

### 细粒度点 2：专家经验显性化

**问题**：引信设计准则、评审经验、常见错误模式散落在专家脑中，需要结构化采集。

| 知识类型 | 来源 | 形式化方法 | 用途 |

### 细粒度点 3：引信领域知识图谱构建

**问题**：构建引信设计领域知识图谱，用本体约束传播验证跨视图一致性。

**KG 设计**：

```
节点：设计要求条目 / SysML元素(Block/Requirement/Constraint) / 仿真模块 / 参数 / GJB条文 / 引信型号
边：  SATISFY(要求→SysML需求)
      ALLOCATE(SysML功能→子系统)
      VERIFY(要求→仿真验证结果)
      CONSTRAIN(参数→约束方程)
      IMPLEMENT(SysML部件→仿真模块)
      DERIVE_REQT(需求→派生需求)
      CONFORMS_TO(条目→GJB条文)
```

**约束验证流程**：
1. 条目库+映射图实体链接到 KG
2. KG 本体定义约束（如"引爆阈值×安全距离×解保延时"物理耦合关系）
3. 约束传播推理检测违反领域知识的冲突
4. 记录推理路径（证据溯源）

**SysML → KG 转换**：

Fu et al. (IEEE Access 2021, DOI:10.1109/access.2021.3115165) 提出 SysML 模型图构建方法——将 SysML 模型文件转为跨产品图。可直接迁移为场景2的 SysML→Neo4j 转换方案。

**SHACL 约束验证**：

Westermann et al. (arXiv:2506.10678, 2025) 提出用 LLM+SHACL 自动验证工程约束——将非形式化工程约束文本转为 SHACL 形状，对 RDF 化的模型数据做验证。可直接迁移到引信 GJB 约束的自动验证。

**关键论文**：
- Gregory & Salado (INCOSE 2024, DOI:10.1002/iis2.13210)：系统工程本体栈，分层 OWL 本体支持可复用/互操作/推理。
- Lu et al. (IEEE Systems J. 2019, DOI:10.1109/jsyst.2019.2911418)：MBSE 工具链中的协同仿真设计本体——**最直接相关**：桥接 SysML 设计模型和协同仿真。
- Dunbar et al. (Systems Eng. 2023, DOI:10.1002/sys.21662)：通过本体语义集成驱动数字工程。

## 仓库已验证原型对照

场景2的技术路线在本仓库已有医疗/焊接领域的验证原型，可迁移：

| 场景2步骤 | 已验证原型 | 验证效果 | 迁移要点 |
|---|---|---|---|
| ①要求文档解析 | 场景1 python-docx+MinerU | Word直抽精度上限 | 直接复用 |
| ①涉密脱敏 | 场景1 Presidio三级级联 | F1≈98.87% | 换引信NER模型 |
| ②要求参数化 | 场景1 规则+RoBERTa+LLM | 正则>95%, NER F1 85-92% | 换引信参数模板 |
| ②映射图存储 | 场景1 Neo4j关系图 | 支撑RTM | 换SATISFY/ALLOCATE/VERIFY边 |
| ③规则库L1 | `MedicalLabRangeFilter` | 单指标范围检测 | 换引信参数范围规则 |
| ③规则库L2 | `LabDiagnosisConflictFilter` | 10000样本检出1444条冲突 | 换参数↔仿真比对 |
| ③规则库L3 | `CrossLabConsistencyFilter` | 多指标协同检测 | 换跨视图参数约束 |
| ③LLM直判 | `_llm_detect_medical` | Qwen2:7b本地JSON输出 | 换SysML↔仿真判断prompt |
| ③时序异常检测 | `TimeSeriesAnomalyFilter` | IsolationForest焊接时序 | 换仿真输出轨迹 |
| ③跨模态冲突 | `CrossModalConflictFilter` | CLIP+时序+标签冲突 | 换SysML参数+仿真输出 |
| ③四阶段管道 | `unified_operators.py` 3算子 | 抽取→检测→解释→置信度 | 直接复用架构 |
| ④质量评估 | `stats`标记机制 | 冲突标记不删→报告 | 直接复用 |
| ⑤知识库 | `medical_kb.json` | 三层规则库JSON结构 | 换引信参数约束规则 |

**迁移结论**：
1. 场景1的5步治理链路架构可直接复用——只需替换领域组件
2. 场景2新增"形式化验证"路线——SDV/Modelica_Requirements/OCL，这是场景1没有的
3. 场景2新增"SysML模型解析"和"仿真模型解析"——场景1的文档解析栈需扩展
4. 时序算子（`timeseries_operators.py`）已在焊接场景验证——可迁移到仿真输出轨迹分析
