# D类·临床知识一致性检测——方法详解（通俗版）

> 目标：让没有医学/AI背景的人也能看懂每个方法在干什么、为什么需要、怎么做的。
> 配合阅读：`医疗领域不一致检测方法谱系调研.md`（学术版详述）

---

## 先搞清楚D类在检测什么

**一句话**：检测"数据里写的"和"医学知识规定应该怎样的"之间对不对得上。

**具体场景**：一个患者的血检数据显示乳酸=6.2 mmol/L（正常值0.5-2.0，严重超标→提示酸中毒），但这个患者的诊断标签写的是"No Finding"（无异常）。这矛盾吗？按医学知识，乳酸>5.0就应该是酸中毒，诊断却写"无异常"——**要么血检数据错了，要么诊断漏了**。D类方法就是自动发现这种矛盾。

**为什么A/B/C类检测不了这个**：A类检测"图像vs报告"的矛盾，B类检测"报告内部"的矛盾，C类检测"标签vs图像"的矛盾。但"血检指标vs诊断标签"的矛盾需要**医学知识**来判断（你得知道乳酸>5.0意味着酸中毒，才知道它和"No Finding"矛盾）——这就是D类的独特价值。

## D1. 三层规则库法

### 一句话说在干什么

像体检报告的**自动审核系统**——把血检指标和诊断标签逐条比对，看有没有矛盾。规则是医生事先写好的。

### 为什么需要它

人工审核10000份病历太慢。血检有50项指标，每项有正常范围，超了就是异常。如果某项严重超标但诊断说"无异常"，很可能是漏诊。用规则库自动检测，10k样本检出1444条冲突。

### 怎么做的（三层递进）

**第一层（L1）：单指标体检——每个指标单独检查**

就像体检报告里每个指标后面都有正常范围：

```
乳酸：6.2 mmol/L    正常范围[0.5, 2.0]    → 超标！
       超过2.0 → MEDIUM（中度异常）
       超过5.0 → CRITICAL（严重异常）    ← 6.2落在这里
肌酐：0.9 mg/dL     正常范围[0.6, 1.2]    → 正常
血糖：110 mg/dL     正常范围[70, 140]     → 正常
pH：  7.38          正常范围[7.35, 7.45]  → 正常
```

仓库实测：10k样本中1000项指标超标（10%异常率）。

**第二层（L2）：指标和诊断比对——血检说有病，诊断说没病**

光知道指标超标还不够——也许是已知疾病正在治疗。关键是：**血检严重超标（提示某病）但诊断标签="No Finding"（无异常）** → 漏诊冲突。

```
规则1：乳酸>5.0 ∧ 诊断=No Finding → "乳酸酸中毒漏诊" (CRITICAL)
规则2：肌酐>2.0 ∧ 诊断=No Finding → "肾功能异常漏诊" (HIGH)
规则3：血糖>300  ∧ 诊断=No Finding → "高血糖漏诊" (MEDIUM)
规则4：钾>6.0    ∧ 诊断=No Finding → "高钾血症漏诊" (CRITICAL)
规则5：pH<7.20   ∧ 诊断=No Finding → "严重酸中毒漏诊" (CRITICAL)
```

仓库实测：10k样本中检出1368条L2冲突。

**第三层（L3）：多指标联合看——单个指标可能不超标，但组合起来就是病**

```
规则1：乳酸>5.0 ∧ pH<7.35 → "乳酸酸中毒伴酸血症" (CRITICAL)
  → 乳酸高说明组织缺氧，pH低说明酸中毒，两者同时出现=严重酸中毒

规则2：血糖>300 ∧ pH<7.35 → "糖尿病酮症酸中毒样" (CRITICAL)
  → 血糖高+酸中毒=DKA的典型表现

规则3：肌酐>2.0 ∧ 钾>6.0 → "肾衰竭伴高钾血症" (CRITICAL)
  → 肌酐高=肾排不出，钾高=肾排钾受阻，两者同时=肾衰竭

规则4：血糖>300 ∧ 钾>6.0 → "多代谢异常" (HIGH)

规则5：肌酐>2.0 ∧ 乳酸>5.0 → "多器官损害" (CRITICAL)
  → 肾+组织缺氧=多器官灌注不足
```

为什么需要L3：假设乳酸=4.8（没超5.0的L1阈值）、pH=7.36（没低于7.35的L1阈值）——单独看都"正常"，但两个都**擦着正常边界**，组合起来其实很危险。L3规则能抓住这种"单项正常但组合异常"的情况。

### 数字意味着什么

- 1444冲突/10k样本 = **14.4%的样本有矛盾**——每7个患者就有1个的血检和诊断对不上
- 1368条是L2漏诊冲突——绝大多数矛盾是"血检说有病但诊断说没病"
- 严重度分布：CRITICAL最多（乳酸酸中毒/高钾/酸中毒都是致命的）

### 局限

- **只覆盖规则写到的模式**——如果某种疾病关联没写进规则库，就检测不到
- **规则维护成本高**——临床指南更新了，规则库得跟着改
- **不理解语义**——规则只比数值大小，不理解"may represent"这种不确定表述

## D2. LLM+代码Guard法

### 一句话说在干什么

让AI（大语言模型）来判断血检和诊断是否矛盾，但AI看数字不靠谱，所以**加一层代码来核验数字**。

### 为什么需要它

D1规则库只能检测"预设好的规则模式"。但有些矛盾规则没覆盖——比如"血糖180是否算严重"需要结合患者上下文判断（糖尿病患者vs正常人，180的含义不同）。LLM能理解这种上下文语义，但LLM对数字比较不靠谱。

**实测发现**：LLM会把正常值报为冲突（"血糖110太高了！"——其实110是正常的），也会混淆数值方向（把"低于"说成"高于"）。

### 怎么做的

```
第一步：LLM语义判定
  输入：血检数据 + 诊断标签
  LLM判断："这两者是否矛盾？"
  LLM输出：is_conflict=true + "乳酸6.2超标但诊断No Finding，可能漏诊"

第二步：代码Guard核验
  LLM说is_conflict=true → 代码检查：乳酸真的超标了吗？
  代码：读medical_kb.json → 乳酸正常范围[0.5,2.0] → 6.2确实超标 → 保留冲突
  
  如果LLM说is_conflict=true但代码检查发现数值没超标 → 丢弃（LLM幻觉）
```

### 类比

就像让一个**语文老师**（LLM）判断体检报告有没有问题——老师能理解"乳酸高说明酸中毒"这个**语义**，但可能搞错"5.0是不是大于2.0"这种**数字比较**。所以让老师先判断语义，再用**计算器**（代码Guard）核验数字。

### 数字意味着什么

60个候选样本测试（5项指标×12个）：

| | 应检出 | LLM正确检出 | Guard前误报 | **Guard后误报** |
|---|---|---|---|---|
| 乳酸 | 6 | 6 | 0 | **0** |
| 血糖 | 6 | 6 | 2 | **0** ← Guard把2个误报干掉了 |
| 钾 | 6 | 4 | 1 | **0** ← Guard把1个误报干掉了 |

**Guard后误报归零**——LLM负责"理解意思"，代码负责"核对数字"，两者互补。

### 局限

- **LLM本身可能幻觉**——虽然Guard能核验数字，但LLM对非数字的语义判断仍可能错
- **依赖LLM质量**——不同LLM（Qwen2:7b vs GPT-4）的语义理解能力差异大
- **Guard只核验数字**——非数值的语义矛盾（如术语用错）Guard管不了

## D3. KG约束传播法（KGDMC）

### 一句话说在干什么

用**知识图谱**（一张"医学概念关系网"）来推理检验数据是否自洽。

### 什么是知识图谱

知识图谱就是把医学知识画成一张网：

```
[肌酐>2.0] ——indicates——→ [肾功能异常] ——causes——→ [高钾血症] ←——indicates—— [钾>6.0]
       ↑                                                                    ↑
   [检验指标]                    [诊断]                         [检验指标]
```

每个圆圈是一个概念（节点），每条线是关系（边）。有了这张网，就能做**推理**：肌酐高→肾功能异常→可能导致高钾。如果数据显示肌酐高但钾正常，说明推理链可能断了。

### 为什么要用KG

因为标准医学知识图谱（如SNOMED CT）**没有"contradicts"（矛盾）这种边**——它不会直接写"肌酐高和No Finding矛盾"。KG的真实用法是**规范化+关系推理**：把数据映射到KG节点上，然后沿关系边推理，看推理结果和数据是否一致。

### 怎么做的（两个组件）

**组件一：解耦VAE——把"可信的"和"可疑的"分开**

VAE（变分自编码器）是一种神经网络。KGDMC用它做"解耦"——把数据拆成两类特征：

- **模态不变特征**：血检和诊断都反映的同一件事（如"肾功能"这个概念）
- **模态特定特征**：只有血检才有的特征（如具体数值）、只有诊断才有的特征（如ICD编码）

然后用**诊断侧的模态不变特征**（通常更可靠，因为是医生写的）去**指导血检侧的跨模态重构**——如果血检数据重构不出来，说明血检可能有误。

**类比**：就像两个人描述同一件事——一个说中文（血检数值），一个说英文（诊断标签）。如果两个人的描述翻译成同一语言后对不上，至少有一个人说错了。VAE做的就是这种"跨语言比对"。

**组件二：多粒度三元组置信度——三个层次检查自洽性**

一个"三元组"就是KG中的一条事实：(头实体, 关系, 尾实体)，如(肌酐>2.0, indicates, 肾功能异常)。

KGDMC在三个层次检查这个三元组是否可信：

```
局部层：这条三元组本身可信吗？
  → (肌酐>2.0, indicates, 肾功能异常) 这条关系的置信度多少？

邻居层：这条三元组的"邻居"一致吗？
  → "肾功能异常"的其他邻居（如"需要透析""可能并发高钾"）是否也出现在数据中？
  → 如果肾功能异常但既不需要透析也没有高钾，可能不太对

路径层：从检验指标到诊断的完整推理路径走得通吗？
  → 肌酐>2.0 →(indicates)→ 肾功能异常 →(causes)→ 高钾血症 →(indicates)→ 钾>6.0
  → 如果路径上每一步都在数据中得到验证，整条推理链可信
  → 如果某一步断了（如肾功能异常但钾不高），推理链不完整
```

### 局限

- **解耦VAE工程门槛高**——需要训练神经网络，不像规则库即插即用
- **KG覆盖不全**——SNOMED CT覆盖疾病/症状术语，但**没有检验指标的正常范围**（那是LOINC的领域）。需要跨标准联合KG，目前不存在
- **没有量化指标**——论文未给出在医疗数据上的P/R/F1

## D4. 神经符号多层验证法（Hybrid-Code v2）

**出处**: arXiv:2512.23743, 2026

### 先搞懂几个前置概念

**什么是ICD-10编码？**

ICD-10是国际疾病分类标准（第10版），给每种疾病一个唯一编号。比如：

| ICD-10编码 | 含义 |
|---|---|
| E11.9 | 2型糖尿病（不伴有并发症） |
| N18.3 | 慢性肾脏病3期 |
| J18.9 | 肺炎（未特指） |
| I50.9 | 心力衰竭（未特指） |

**为什么要自动编码？** 每个患者出院时，病案室需要根据出院摘要（一段自然语言文本）手动查ICD-10编码本，给每个诊断分配编码。一个三甲医院每年几十万份病历，纯人工标注太慢。所以需要AI自动编码。

**什么是"幻觉"？** 在这个场景里，幻觉=AI生成了**无效的编码**。比如：
- 编了一个不存在的编码："X99.9"（ICD-10里根本没有X开头的编码）
- 编了一个存在但**文本里没证据**的编码：文本只写了"血糖偏高"，AI编了"E11.5"（2型糖尿病伴昏迷）——"偏高"不等于"伴昏迷"，这是过度编码

在医疗场景，错误编码直接影响**医保报销、质量控制、流行病学统计**，所以"零幻觉"至关重要。

**什么是"神经"和"符号"？**

- **神经**（Neural）= AI模型（神经网络），如ClinicalBERT/BioBERT/GPT-4。擅长理解文本语义、广撒网找出可能的编码，但会"编造"（幻觉）。
- **符号**（Symbolic）= 规则引擎/知识库（KB），用if-then规则严格检查。不会编造，但只会检查规则写到的内容。
- **神经符号**（Neuro-Symbolic）= 两者串联：神经先猜，符号再验。

### 一句话说在干什么

让AI先猜一批候选编码（广撒网），再用5道规则关卡逐个审查——哪道关过不了就毙掉，5道全过才输出。**AI负责"猜得全"，规则负责"验得准"**。

### 为什么需要它

| 方案 | 覆盖率 | 精确率 | 幻觉率 | 问题 |
|---|---|---|---|---|
| 纯规则系统 | 45% | 90% | 0% | 规则写不到的就覆盖不了，55%的编码漏了 |
| ClinicalBERT(纯神经) | 88% | 78% | 6-18% | 会编造不存在的编码，临床不可接受 |
| GPT-4(纯神经) | 85% | 80% | 6-18% | 同上 |
| **Hybrid-Code v2(神经+符号)** | **85%** | **92%** | **0%** | AI提供85%覆盖，规则拦住所有幻觉 |

**核心矛盾**：纯规则安全但覆盖少(45%)；纯AI覆盖高(88%)但不安全(6-18%幻觉)。Hybrid-Code v2把两者串联：AI出85%的候选(比纯规则45%高很多)，规则把关把幻觉压到0%。

### 怎么做的——用一个真实例子从头走一遍

**输入**：一段出院摘要（临床文本）

```
患者男性，58岁。因"多饮多尿3月，加重伴乏力1周"入院。
既往2型糖尿病史5年。入院查血糖18.6mmol/L，肌酐185μmol/L。
诊断为：2型糖尿病、慢性肾脏病3期。治疗予胰岛素降糖、护肾治疗。
否认肺炎、心力衰竭。好转出院。
```

---

**第一步：神经模型生成候选（"广撒网"）**

```
出院摘要 → ClinicalBERT → "我猜这些ICD编码可能对："
  → E11.9  (2型糖尿病不伴并发症)
  → N18.3  (慢性肾脏病3期)
  → J18.9  (肺炎未特指)        ← AI猜的，对不对要验证
  → I50.9  (心力衰竭未特指)     ← AI猜的，对不对要验证
  → E11.5  (2型糖尿病伴昏迷)    ← AI猜的，对不对要验证
```

AI很会猜——它读"2型糖尿病"就想到E11.9，读"慢性肾脏病3期"就想到N18.3。但它也会**过度联想**：读"否认肺炎"就想到了J18.9(肺炎编码)——文本说的是"否认"，不是"有"。这就是幻觉的来源。

---

**第二步：符号KB验证层——5道关卡逐个审查**

知识库（KB）里存着ICD-10的全部编码规则、编码与疾病的映射关系、排除规则等。每个候选编码必须通过5道关卡：

---

**关卡1：格式验证——编码本身合法吗？**

检查候选编码是否符合ICD-10的编码规范（字母+数字+小数点的格式）。

```
E11.9 → 格式合法 ✓（E是合法起始字母，11是数字，.9是亚分类）
N18.3 → 格式合法 ✓
J18.9 → 格式合法 ✓
I50.9 → 格式合法 ✓
E11.5 → 格式合法 ✓

假设AI生成了"X99.9" → X不是ICD-10合法起始字母 ✗ → 直接毙掉
假设AI生成了"E11" → 缺少小数点后的亚分类 ✗ → 毙掉（或补全为E11.9）
```

**这关干什么**：排除AI"编造"的不存在的编码格式。这是最简单的关卡——纯字符串匹配。

---

**关卡2：证据接地——文本里有证据支持这个编码吗？**

检查出院摘要中是否有文字证据支持每个候选编码。

```
E11.9(2型糖尿病) → 文本写了"2型糖尿病史5年""诊断为2型糖尿病" → 有证据 ✓
N18.3(慢性肾病3期) → 文本写了"慢性肾脏病3期""肌酐185" → 有证据 ✓
J18.9(肺炎) → 文本写了什么？
  → 搜索"肺炎" → 找到"否认肺炎"
  → "否认"不是证据支持，是证据否定 → 但是否定不算"有证据" → 需要进入关卡3判断
I50.9(心力衰竭) → 文本写了什么？
  → 搜索"心力衰竭" → 找到"否认心力衰竭"
  → 同上，"否认"不是支持 → 需要进入关卡3
E11.5(2型糖尿病伴昏迷) → 文本写了什么？
  → 搜索"昏迷" → 文本中没有"昏迷"这个词
  → 文本只写了"乏力"，没有昏迷的证据 → 没有证据 ✗ → 毙掉！
```

**这关干什么**：确保每个编码都能在文本中找到对应的文字证据。AI可能因为"糖尿病"就联想到"糖尿病伴昏迷"(E11.5)——但文本没提昏迷，这就是过度编码（幻觉）。

**怎么做的**：用NER（命名实体识别）从文本中提取疾病/症状实体，与ICD编码的标准描述做匹配。匹配到=有证据，匹配不到=无证据→毙掉。

---

**关卡3：否定检测——证据有没有被"否定"？**

关卡2发现文本里确实出现了"肺炎"和"心力衰竭"这两个词——但前面跟着"否认"。这一关专门检查证据是否被否定了。

```
J18.9(肺炎) → 文本写"否认肺炎"
  → "否认"是否定词 → 肺炎的证据被否定了 → 不应编码 ✗ → 毙掉！

I50.9(心力衰竭) → 文本写"否认心力衰竭"
  → "否认"是否定词 → 心力衰竭的证据被否定了 → 不应编码 ✗ → 毕掉！
```

**这关干什么**：这是医疗NLP的经典难题——"否定检测"。文本里出现"肺炎"不等于"有肺炎"——可能是"否认肺炎""排除肺炎""无肺炎证据"。如果不做否定检测，AI看到"肺炎"两个字就编码J18.9，会导致大量假阳性。

**怎么做的**：用依存句法分析（CheXpert Labeler的ngrex规则就是做这个的）检查疾病词前面的否定词。否定词包括："否认""无""排除""未发现""no evidence of""without""ruled out"等。

---

**关卡4：时序一致性——编码和患者时间线矛盾吗？**

检查编码对应的疾病是否与患者的就诊时间线一致。

```
E11.9(2型糖尿病) → 文本写"2型糖尿病史5年" + 本次入院仍在治疗 → 时序一致 ✓
N18.3(慢性肾病3期) → 文本写"诊断为慢性肾脏病3期" + 本次入院查肌酐185 → 时序一致 ✓

假设场景：文本写"患者2023年曾患肺炎，已治愈，本次入院无肺炎"
  → J18.9(肺炎) → 虽然文本提到了"肺炎"，但时间是2023年且已治愈
  → 本次就诊(2024年1月)没有肺炎 → 时序不一致 ✗ → 毙掉
```

**这关干什么**：防止把**历史疾病**误编为**本次就诊诊断**。出院摘要里经常提到既往史（"5年前曾患XX"），这些不应该编码为本次就诊的诊断。

**怎么做的**：解析文本中的时间表达（"5年前""本次""入院时""出院时"），与就诊日期做比对。只编码"本次就诊"的疾病。

---

**关卡5：排除规则——这个编码和已选的其他编码互斥吗？**

检查通过的编码之间是否有逻辑冲突。

```
当前已通过的编码：E11.9(2型糖尿病) + N18.3(慢性肾病3期)

排除规则检查：
  规则A：E11.9(糖尿病不伴并发症) 和 E11.5(糖尿病伴并发症) 互斥
    → 两者不能同时编码——要么伴并发症要么不伴
    → 但E11.5在关卡2已被毙掉了，不冲突 ✓

  规则B：N18.3(慢性肾病3期) 和 N18.9(慢性肾病未特指) 互斥
    → 不能同时编"3期"和"未特指"——已经明确了3期就不用编未特指
    → 当前没有N18.9 → 不冲突 ✓

  规则C：如果编了O24.0(妊娠糖尿病) → 患者必须是妊娠期
    → 当前没有O24.0 → 不涉及 ✓

  → 所有排除规则通过 ✓
```

**这关干什么**：ICD-10编码之间有逻辑约束——有些编码互斥（不能同时编），有些编码有前置条件（编A必须满足B）。这一关确保编码组合是逻辑自洽的。

**怎么做的**：KB中预存排除规则表`{(编码A, 编码B, "互斥原因")}`，检查已通过的编码集合中是否有互斥对。

---

**第三步：输出最终结果**

```
5道关卡全部通过的编码：
  → E11.9  (2型糖尿病) ✓✓✓✓✓ 全通过
  → N18.3  (慢性肾病3期) ✓✓✓✓✓ 全通过

被毙掉的编码：
  → J18.9  (肺炎) → 关卡3被毙(文本写"否认肺炎")
  → I50.9  (心力衰竭) → 关卡3被毙(文本写"否认心力衰竭")
  → E11.5  (糖尿病伴昏迷) → 关卡2被毙(文本无"昏迷"证据)

最终输出：E11.9 + N18.3
```

### "零幻觉"到底怎么实现的

**不是AI不犯错——AI仍然会生成错误编码(J18.9/I50.9/E11.5都是AI的错误猜测)。但5道关卡把错误全拦住了。**

关键在于：**符号验证层是"白名单"机制而非"黑名单"**——不是"检测到错误就排除"，而是"无法证明正确的就排除"。也就是说：

- 关卡2（证据接地）：**文本里找不到证据→毙**（宁可错杀不放过）
- 关卡3（否定检测）：**证据被否定了→毙**
- 关卡4（时序一致性）：**时间对不上→毙**
- 关卡5（排除规则）：**和别的编码冲突→毙**

这种"举证责任在AI"的设计——AI必须"证明"每个编码有文本证据、没被否定、时间一致、不互斥——才能输出。无法证明就毙掉。

### 代价：15%覆盖率损失

85%覆盖率意味着100个应该编码的疾病中，只有85个被自动编码了。剩下15个被5道关卡毙掉了——**但被毙掉的不一定是错的**：

- 可能是AI猜对了但**证据表述方式**不在KB的匹配规则中（如文本写了"血糖控制不佳"但KB只认"糖尿病"）
- 可能是AI猜对了但**否定词检测误判**（如"不排除肺炎"被误判为否定）

这15%需要人工处理——但比起纯人工编码100%，已经省了85%的工作量。

### 自动KB扩展——解决规则维护瓶颈

纯规则系统的死穴是：规则要人工写、人工维护。新疾病/新编码出现时规则库就过时了。

Hybrid-Code v2的**自动KB扩展**机制：

```
无标签临床文本(大量) → 信息抽取 → 发现新的"疾病-编码"映射模式
  → 例：从1万份出院摘要中发现"AKI"这个词经常和N17.9(急性肾损伤)一起出现
  → 自动提取规则：{文本含"AKI" → 候选编码N17.9}
  → 验证后加入KB
```

这解决了规则库的**可扩展性**问题——不需要人工逐条写规则，而是从数据中自动学习规则模式。但论文只在ICD编码上验证了这个机制，临床诊断规则（如"什么指标组合提示什么综合征"）的自动提取更复杂，尚未验证。

### 关键指标详解

| 指标 | 数值 | 含义 |
|---|---|---|
| 覆盖率 | 85% | 100个应该编码的疾病中，85个被自动编码，15个需人工 |
| 精确率 | 92% | 自动编码的85个中，92%(约78个)是正确的，8%(约7个)是错的 |
| I型幻觉率 | 0% | **不会输出任何无效编码**——所有输出的编码都通过了5道验证 |
| vs纯规则 | +40%覆盖 | 纯规则只覆盖45%，Hybrid-Code多覆盖了40个百分点 |
| vs神经基线 | -6~18%幻觉 | ClinicalBERT/GPT-4有6-18%幻觉，Hybrid-Code消除到0% |

注意：**精确率92%不等于100%**——虽然有0%的I型幻觉(不会输出无效编码)，但输出的编码中仍有8%是"有效但不准确"的。比如应该编E11.9(糖尿病不伴并发症)但编了E11.5(糖尿病伴昏迷)——两个都是合法编码，但后者不精确。5道关卡能拦截"无效编码"(格式错/无证据/被否定/时序错/互斥)，但**不能完全拦截"有效但不精确"的编码**。

### 局限

- **15%覆盖率损失**——被毙掉的不一定是错的，可能是"无法验证"。对于追求高覆盖的场景(如快速初筛)，15%的人工处理可能太多
- **只在ICD编码上验证**——ICD编码是**结构化任务**(编码有明确格式、证据是文本中的疾病词)。图像↔报告不一致检测是**非结构化任务**(矛盾的判断依赖语义理解)，5道关卡中"格式验证"和"排除规则"不直接适用。需要重新设计验证层：
  - "格式验证"→ 什么算图像/报告的"格式合法"？可能改为"图像质量检查"
  - "证据接地"→ 图像AI的概率输出是否构成"证据"？需要定义概率阈值
  - "否定检测"→ 仍然是文本NER的否定检测，可直接复用
  - "时序一致性"→ DICOM时戳校验，可直接复用
  - "排除规则"→ 疾病间的互斥/共现约束，可直接复用
- **自动KB扩展只在ICD上做了**——从无标签文本提取编码模式相对简单(疾病名→编码的映射)，但临床诊断规则(如"乳酸>5+pH<7.35=酸中毒")的自动提取更复杂——需要同时理解指标值、阈值和疾病关联
- **符号验证层依赖KB质量**——如果KB本身有错误(如错误的排除规则)，验证层会毙掉正确的编码或放过错误的编码。KB的质量是整个系统的天花板

### 和其他D类方法的关系

```
纯规则(D1)                  纯神经(LLM)                神经符号(D4)
  ↓                           ↓                           ↓
覆盖45%, 0%幻觉             覆盖88%, 6-18%幻觉          覆盖85%, 0%幻觉
  ↓                           ↓                           ↓
安全但不够全                 全但不可靠                   全且安全
  ↓                           ↓                           ↓
KB要人工维护                  AI不可控                    神经提供覆盖+符号保证安全
                                                        ↓
                                                        KB可自动扩展(D4的创新)
```

**D2(LLM+Guard)和D4(Hybrid-Code)的区别**：
- D2是"LLM判断+代码核验数字"——代码只检查数值大小(乳酸>5了没)，不检查语义
- D4是"神经生成+符号验证全部"——5道关卡检查格式/证据/否定/时序/排除，覆盖面更广
- D2适合数值型检测(血检指标)，D4适合编码/分类型检测(ICD编码)

## D5. 临床知识嵌入LLM审查法

### 一句话说在干什么

一篇**综述论文**，梳理了把临床知识塞进LLM的三条路径和五层知识来源——不是新方法，是知识地图。

### 三条路径（怎么把知识塞进LLM）

**路径1：训练式——把知识编进课本让AI背**

```
临床指南/医学文献 → 整理成训练数据 → 微调LLM
→ 知识编码在模型参数里
→ 优点：推理快（不用查外部资料）
→ 缺点：不可追溯（不知道AI从哪学到的）、可能过时（知识更新需重新训练）
```

**路径2：KG支持——考试时允许AI查百科全书**

```
临床知识 → 构建知识图谱(UMLS/SNOMED CT)
LLM推理时 → 遇到不确定的就查KG
→ KG提供显式可追溯的知识来源
→ 优点：可追溯（知道知识从哪来的）、可更新（更新KG即可）
→ 缺点：KG覆盖不全、查询有延迟
```

**路径3：RAG辅助——考试时给AI相关参考资料**

```
临床指南/文献 → 切分存入向量数据库
LLM推理时 → 检索最相关的文档片段作为上下文
→ 优点：灵活（不用重新训练）、知识量大
→ 缺点：检索质量依赖embedding模型、可能检索到过时信息
```

### 五层知识来源（从靠谱到不靠谱）

| 层级 | 来源 | 可靠度 | 例子 | 问题 |
|---|---|---|---|---|
| L1 | 临床指南(UpToDate/Mayo) | **最高** | "乳酸>5 mmol/L提示严重酸中毒" | 更新周期长(年度) |
| L2 | 医学KG(UMLS/SNOMED CT) | 高 | 疾病-症状-药物关系 | 覆盖不全 |
| L3 | 临床文献(PubMed) | 中 | 最新研究证据 | 可能被后续研究推翻 |
| L4 | 临床数据集(MIMIC) | 中 | 数据驱动的统计规律 | 有选择偏差 |
| L5 | LLM内部知识 | **最低** | 模型预训练获得 | 可能过时/错误/幻觉 |

### 怎么用于不一致检测

把LLM输出与L1-L4的外部知识源做**交叉验证**：如果LLM诊断与临床指南(L1)矛盾，或与KG(L2)中定义的疾病关系矛盾 → 标记为知识不一致。

### 局限

- **综述性质**——不提出新方法，只梳理现状
- **没有比较三条路径在不一致检测上的效果**——这是开放问题
- **LLM内部知识(L5)最不可靠但最常用**——大多数LLM推理时不用RAG/KG，纯靠内部知识

## D6. LLM编排合规性检查法

### 一句话说在干什么

以前要把临床指南翻译成计算机能懂的规则（很费时间），现在**直接让LLM读指南原文+患者数据，判断患者治疗是否符合指南**。

### 为什么需要它

传统临床合规性检查需要**CIG（Computer-Interpretable Guideline）**——把临床指南形式化为计算机可执行的规则：

```
传统方式：
  临床指南(PDF) → 人工形式化(数月) → CIG(GLIF/SAGE格式) → 执行引擎 → 合规性报告
  
  问题：形式化耗时数月，指南更新需重新形式化
  → 临床指南每年更新，形式化跟不上
```

D6提出**跳过形式化**，直接让LLM读指南：

```
LLM编排方式：
  临床指南(PDF) → LLM直接阅读理解
  + 患者临床数据(EHR)
  → LLM: 提取指南中的规则 → 与患者数据比对 → 生成合规性报告
  
  优点：无需CIG形式化，指南更新时LLM直接重新阅读
```

### 检查什么

- 患者治疗路径是否符合指南推荐（如"心梗患者应该先用阿司匹林再做PCI"）
- 用药剂量/频率是否在指南范围内（如"氨氯地平推荐5-10mg/日"）
- 检查项目是否按指南时机执行（如"糖尿病应每3月查一次HbA1c"）
- 诊断结论是否与检查结果一致

### 局限

- **LLM可能读错指南**——LLM本身有幻觉，可能误解指南含义
- **"用不可靠的LLM检查不可靠的LLM"的循环**——如果LLM理解指南的能力不可靠，它的合规性检查也不可靠
- **没有量化指标**——论文未给出合规性检查的准确率

## D7. RadGraph实体-关系奖励法

### 一句话说在干什么

用一份**标注好了"什么实体、什么关系"的胸片报告数据集**（RadGraph）来给AI生成的报告打分——生成的报告如果实体和关系跟标准对得上，就奖励；对不上就惩罚。通过反复打分让AI学会写事实正确的报告。

### 什么是RadGraph

RadGraph是一个数据集，把胸片报告标注成了**图结构**——每个实体是一个节点，实体间的关系是边：

```
报告原文："右侧胸腔积液较前增多。左肺清晰。"

RadGraph标注：
  [右侧]——located_at——→[胸腔积液]
                        [胸腔积液]——severity——→[增多]
                        [胸腔积液]——change——→[较前]
  [左肺]——finding——→[清晰]
```

有了这种结构化标注，就能精确比较"生成的报告"和"标准报告"在实体和关系层面是否一致。

### 怎么做的

```
第一步：生成报告
  胸片图像 → 报告生成模型 → 生成报告："左侧胸腔积液。心脏正常。"

第二步：用RadGraph模式打分
  奖励1·实体一致性：生成报告的实体 vs 参考报告的实体
    生成实体：{左侧, 胸腔积液, 心脏}
    参考实体：{右侧, 胸腔积液, 心脏, 左肺, 清晰}
    → "左侧"vs"右侧"不一致 → 扣分
    → 漏了"左肺清晰" → 扣分
    → 实体F1 = 0.6

  奖励2·NLI推理一致性：实体描述是否推理一致
    "心脏正常" vs 参考"心脏正常" → 蕴含 → 加分
    "左侧胸腔积液" vs 参考"右侧胸腔积液" → 矛盾 → 扣分

  奖励3·BERTScore：整体语义相似度

第三步：强化学习优化
  总奖励 = w1×实体F1 + w2×NLI一致率 + w3×BERTScore
  → 用PPO算法优化报告生成模型
  → 反复迭代：生成→打分→调整→再生成→再打分→...
  → 直到生成的事实正确
```

### 数字意味着什么

- 事实正确性+14.2%——生成的报告中正确的疾病描述多了14.2%
- 事实完整性+25.3%——生成的报告中遗漏的疾病少了25.3%
- F1提升+22.1（Delta +63.9%）——临床信息提取的F1从某基线提升了22.1个点

### 为什么这是"从源头减少不一致"

D1-D6都是**检测已有数据的不一致**——先有矛盾再发现。D7是**训练时就让模型学会不产生不一致**——让报告生成模型从训练阶段就学会写事实正确的报告。这比生成后再检测更彻底。

### 局限

- **需要RadGraph标注数据**——目前只有胸片报告有RadGraph标注，其他医学领域没有
- **RL训练不稳定**——强化学习训练比监督学习难调
- **只优化生成模型**——不适用于已有报告的检测
