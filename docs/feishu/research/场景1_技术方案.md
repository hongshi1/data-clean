# 场景1·SRS数据治理技术方案

> 将 >50TB GJB 438C-2021 军用 SRS 治理为高质量微调数据集，训北极星垂域大模型。
> v2.1 | 2026-07-08

---

## 数据线路总图

数据从原始 SRS 到微调数据集，经历 **6 次形态变化**，每步产出物是下一步输入：

```
┌────────────┐     ┌────────────┐     ┌────────────┐     ┌────────────┐     ┌────────────┐     ┌────────────┐
│  原始 SRS  │     │ 归一化 SRS │     │  条目库    │     │ 冲突标记库 │     │ 分级数据集 │     │ 微调数据集 │
│            │     │            │     │            │     │            │     │            │     │            │
│ Word/PDF   │     │ 章节树     │     │ 参数化条目 │     │ 条目+冲突  │     │ A/B/C 级   │     │ 3类样本    │
│ >50TB      │────→│ 结构化表   │────→│ 引用关系图 │────→│ 标记不删   │────→│ 质量打分   │────→│ +知识标签  │
│ 非结构化   │     │ 脱敏后     │     │ 条目ID     │     │ 冲突类型   │     │ 一票否决   │     │ 指令/诊断  │
│ 含表格     │     │ GJB七大块  │     │ 数值/单位  │     │ 严重度     │     │ 隐私层     │     │ /知识密集  │
│ 含涉密     │     │ 统一格式   │     │ 引用关系   │     │ 置信度     │     │            │     │            │
└────────────┘     └────────────┘     └────────────┘     └────────────┘     └────────────┘     └────────────┘
      │                  │                  │                  │                  │                  │
   ①标准化预处理      ②结构化转化        ③一致性校验        ④质量评估         ⑤知识融合          产出
```

**核心逻辑**：冲突样本不删除 → 反过来当微调数据 → 教模型"什么是不一致"。检出的矛盾越多，模型越能学会识别矛盾。

## ① 标准化预处理

**数据流**：`原始SRS(Word/PDF)` → 解析+表格+章节+脱敏 → `归一化SRS(章节树+结构化表, 脱敏后, GJB七大块)`

```
SRS.docx ──python-docx直抽──┐
                             ├──→ 统一IR ──GJB七大块映射──→ 脱敏 ──→ 归一化SRS
SRS.pdf  ──MinerU/PP-Structure┘
```

### 1.1 文档解析

| 方案 | 技术 | 中文 | 表格 | 许可 | 推荐 |
|---|---|---|---|---|---|
| **Word直抽** | python-docx读OOXML | ★★★★★ | ★★★★★无损 | MIT | .docx首选 |
| **MinerU** | DocLayout-YOLO+PaddleOCR+UniMERNet流水线 | ★★★★ | ★★★★ | Apache(核心) | PDF首选 |
| **PP-Structure** | 版面+表格+OCR一体化 | ★★★★★ | ★★★★ | Apache-2.0 | 国产替代 |
| LayoutLMv3 | 多模态Transformer版面分类 | ★★(需微调) | 仅分类 | MIT | 角色补充 |
| GOT-OCR2.0 | 580M统一端到端OCR-2.0 | ★★★★ | ★★★ | Apache | 轻量备选 |
| Nougat | 端到端图像→Markdown | ★(英文) | ★★ | Apache | 不适用 |

**技术详述**：

**Word直抽（python-docx）**：.docx 本质是 OOXML 压缩包，段落样式、编号体系、表格对象都是原生结构化数据。python-docx 直接读取这些对象，不走 OCR，精度是所有方案的上限——零 OCR 误差，合并单元格通过 `gridSpan`/`vMerge` 原生保留。对于 .doc 旧格式，先用 `libreoffice --headless --convert` 转 .docx。军用 SRS 大量有 Word 源文件，这是主路径，覆盖 80%+ 文档。

**MinerU**（arXiv:2409.18839, OpenDataLab）：目前最完善的开源 PDF 解析方案，是一条模块化流水线——`DocLayout-YOLO`（版面检测，arXiv:2410.12628，用合成数据增强泛化，是当前版面检测 SOTA，能区分标题/正文/表格/图/公式/列表等版面元素）→ `YOLOv8`（公式检测）→ `UniMERNet`（公式识别，arXiv:2404.15254）→ `PaddleOCR`（中文 OCR）→ `StructEqTable`（表格识别）→ 阅读序排序后处理。输出 Markdown + JSON，社区活跃（PDF-Extract-Kit 9.8k★），可私有化部署。缺点是依赖 AGPL 组件（PyMuPDF），军用需法务评估；对极复杂无框线表格结构仍会出错。

**PP-Structure**（PaddlePaddle）：如果 AGPL 不可接受，PP-Structure 是纯 Apache-2.0 国产替代。它是一体化流水线：版面检测（11 类版面元素）+ 表格识别（输出 HTML）+ 中文 OCR，中文原生支持是所有方案里最强的，部署成熟（含 C++/Serving）。缺点是对超复杂合并/嵌套表头不如专用大模型，推理链路较长。

**LayoutLMv3**（arXiv:2204.08387, ACM MM 2022）：微软的多模态 Transformer，文本+版面+图像统一掩码预训练，可做版面分类和 KIE（键值抽取）。优势是能理解文档的语义结构，但中文需 LayoutXLM（arXiv:2104.08836）或自行微调，本质是分类/标注模型需配套 OCR，对表头等复杂结构弱。适合作为版面元素"角色分类"的补充。

**GOT-OCR2.0**（arXiv:2409.01704）：580M 参数的统一端到端 OCR-2.0 模型，文本/公式/表格/图表一站式输出 markdown，中文良好，轻量可部署。缺点是超长表格、密集合并单元格易截断/错位，可控性弱于流水线。适合轻量端到端备选。

**推荐**：Word 走 python-docx 直抽（精度上限）；PDF 走 MinerU（DocLayout-YOLO + PaddleOCR）；AGPL 不可接受用 PP-Structure 全栈替代。

### 1.2 表格抽取

**分层策略（精度优先，由易到难）**：

| 层 | 方案 | 合并单元格 | 无框线 | 许可 | 效果 |
|---|---|---|---|---|---|
| 1 | **Word直抽** | ★★★★★无损 | — | MIT | 覆盖大多数 |
| 2 | **Camelot** | ★★ | ★★(stream弱) | MIT | 有框线近无损 |
| 3 | **PaddleOCR表格** | ★★★★ | ★★★★ | Apache | 中文工程首选 |
| 3 | **StructEqTable** | ★★★★ | ★★★★ | Apache | MinerU默认引擎 |
| 4 | **UniTable** | ★★★★SOTA | ★★★★ | MIT | 极复杂兜底 |
| 4 | Table Transformer | ★★★ | ★★★ | MIT | 行业基线 |

**技术详述**：

**Word原生直抽**：用 python-docx 遍历 `document.tables`，每个 cell 天然含合并信息。OOXML 的表格用 `gridSpan`（横向合并）和 `vMerge`（纵向合并）标记合并区域，可直接还原为二维矩阵并标注合并范围。这是无损方案——不经过任何 OCR 或模型推理，合并单元格精确、可区分嵌套表（cell 内嵌 table）。军用 SRS 的性能指标表/接口表/数据字典在 Word 中多为真实表格对象，直抽即得结构化数据，是最大性价比点。

**Camelot**：Python 库，提供 lattice（线框检测）和 stream（空白对齐）两种模式。lattice 模式基于 PDF 中的线条检测表格边界，对有明确框线的 PDF 表格精度极高、速度快、零模型依赖、中文无损（直接取文本层）。缺点是依赖线框——无框线表用 stream 模式靠空白对齐，易错乱；合并单元格还原弱；扫描版 PDF 无文本层则失效。适合作为 PDF 有框线表格的轻量首选。

**PaddleOCR表格识别**：PP-Structure 内置的端到端表格结构识别模块，能从图像中识别表格的行列结构、合并单元格，输出 HTML 格式（含 rowspan/colspan）。中文场景工程首选，对合并单元格和无框线表都有较好处理。缺点是对超复杂多级表头可能出错，需后处理校验。

**StructEqTable**：基于 InternVL2-1B 视觉大模型，把表格图像转为 LaTeX/HTML/Markdown 多格式输出。它是 MinerU 1.0 的默认表格引擎，中文较好，对复杂表格的理解能力强于传统 OCR 方法。缺点是模型较大（1B），推理速度不如规则法。

**UniTable**（arXiv:2403.04822, Georgia Tech）：自监督预训练的统一表格识别框架，把表格结构识别、内容识别、bbox 定位三个任务统一在一个模型里。在多个大规模表格数据集上达到 SOTA。MIT 许可，可迁移中文（需配 PaddleOCR 做文本填充）。适合作为极复杂嵌套表格的兜底方案。

**Table Transformer**（arXiv:2110.00061, 微软）：基于 DETR（arXiv:2005.12872）的表格检测+结构识别模型，用 PubTables-1M（100 万表）训练，解决了过分割问题。是行业标准基线，但英文科学文献训练为主，中文需配 OCR 做文本填充并微调。

**推荐**：Word直抽 > Camelot(有框线) > PaddleOCR/StructEqTable(无框线) > UniTable(兜底)。LlamaParse 等商用 API 因数据出域排除。

### 1.3 章节切分（对齐GJB七大块）

| GJB语义块 | 章节号 | 内含表格 |
|---|---|---|
| 功能需求 | 3.x | 功能/接口需求表 |
| 性能指标 | 3.x/4.x | **性能指标表** |
| 接口定义 | 5.x | **接口定义表** |
| 数据字典 | 6.x | **数据字典表** |
| 运行环境 | 7.x | 环境约束表 |
| 安全保密 | 8.x | 安全要求表 |
| 验收准则 | 9.x | 验收项表 |

| 方法 | 原理 | 准确率 | 可审计 | 推荐 |
|---|---|---|---|---|
| **规则法** | 编号正则+GJB锚点词典 | **95%+** | ✅完全可审计 | ★★★★★(主) |
| 版面模型 | LayoutLMv3角色分类 | 中高 | 需微调 | ★★★(兜底) |
| LLM | DocOwl/Qwen章节理解 | 高 | 弱/保密受限 | ★★(离线复核) |

**技术详述**：

**规则法（编号正则 + GJB七大块锚点词典）**：GJB 438C-2021 规定 SRS 含固定章节结构，编号体系稳定（如 `3.2.1` 三级条目）。用正则 `^\d+(\.\d+)*\s*[标题]` 匹配章节号，结合 Word heading 样式/字体特征，建立"章/节/条"三级树。再用预置的七大块标题词典（功能需求/性能指标/接口定义/数据字典/运行环境/安全保密/验收准则）做章节号→语义块映射。**规则法可达 95%+ 切分准确率**，且完全可审计——每条切分能给出依据（章节号/锚点匹配证据），满足军用文档治理审计要求。切分后做完整性校验（缺块告警），表格按"最近章节"归属挂载。

**版面模型法**：对无编号或编号异常的子标题（扫描件错字、跨文档模板漂移），用 LayoutLMv3 或 DocLayout-YOLO 做 title/section-header 角色分类二次判别。抗排版扰动、泛化好，但需标注微调、中文需调。仅处理规则失效的边角。

**LLM法**：用文档理解大模型（DocOwl/Qwen）直接给章节语义，鲁棒、可处理变体，但模型重、可解释性弱、保密受限。仅用于离线抽检/复核，不进入主链路。

**推荐**：规则法为主（95%+可审计）+ 版面模型兜底 + LLM仅离线复核。

### 1.4 涉密信息识别与脱敏

**三级级联识别**（SurrogateShield arXiv:2606.29567 验证 F1≈98.87%）：

| 级 | 方法 | 抓什么 | 优势 |
|---|---|---|---|
| 1 | 规则/正则 | 密级标识(机密★)、型号代号格式 | 零样本、可审计、召回稳 |
| 2 | 自定义军事NER | 装备型号、部队番号、战术指标 | 识别未登录实体、上下文感知 |
| 3 | LLM语义识别 | 作战场景描述、意图级敏感 | 捕获语义级敏感 |

**分层脱敏算子**：

| 敏感实体 | 算子 | 语义保留 | 对微调影响 | 效果实证 |
|---|---|---|---|---|
| 密级标识 | 删除(redact) | 低 | 大(无语义价值) | — |
| 装备型号代号 | 伪名化(EQUIP_01确定性映射) | 高(保共指一致) | 极小 | 对模型几乎无损 |
| 战术性能数值 | 泛化为区间(≥50km→[40,60)km) | 中高(保量级) | 小 | 保训练信号分布 |
| 作战场景描述 | 合成替换(生成等价虚构场景) | 高(保语义结构) | 小 | **BERTScore +13.26pp** |
| 接口参数/数据字典 | 保留(非敏感) | — | — | 微调必需 |

**技术详述**：

**三级级联识别**：单一方法不可靠，需三级级联。第一级用规则/正则抓密级标识（机密★/秘密★等固定格式）和型号代号模式（如 `XX-XX[0-9]{2,4}`），零样本、可审计、召回稳，作为保底层。第二级用自定义军事 NER（基于 BERT/RoBERTa 微调，自定义实体类型 EQUIP_MODEL/TACTICAL_INDICATOR/UNIT_NAME），能识别规则未覆盖的未登录实体，上下文感知。第三级用 LLM 做语义级识别，捕获"射程""精度"附近的数值、作战场景描述等规则和 NER 都遗漏的语义敏感内容。SurrogateShield（arXiv:2606.29567）验证此级联架构在 22 类 PII 上 F1≈98.87%，可迁移到军用实体类型。

**分层脱敏算子（不一刀切）**：关键设计是按敏感实体类型选择不同脱敏算子，而非统一删除。密级标识无语义价值，直接删除。装备型号代号用伪名化——同一型号确定性映射到固定假名（型号X→EQUIP_01），保持文档内引用一致性（共指一致性），对微调几乎无损。战术性能数值泛化为区间（≥50km→[40,60)km），保留量级分布，防精确值泄露。作战场景描述用合成替换——生成虚构但语义等价的场景，保留完整语义结构。

**关键实证**：SurrogateShield 证明合成替换 vs 占位符遮罩（redact），BERTScore 从 81.59% 提升至 94.85%（**+13.26pp**），且 100 条对抗查询中对手 LLM 无法恢复原始值。这直接解决了"脱敏后还能不能用于微调"的核心难题。

**反面警示**：纯 DP-SGD（差分隐私随机梯度下降）在 1B-3B 小模型上 F1 仅 0.19-0.28（arXiv:2606.28479），不足以支撑可用性。Kapelinski et al. 用 canary 审计发现 DP-SGD 的记忆化下降主要来自更新步数减少（占 66%-132%），而非 DP 本身的额外收益——提示**伪名化+控制训练步数**可能比单纯堆 DP 更高效。

**推荐**：Presidio V2（开源、可私有化部署、YAML no-code 配置、支持 spaCy/Stanza/Transformers/GLiNER 外接、全套算子 replace/redact/hash/mask/encrypt/custom/surrogate）。策略：伪名化/合成替换保语义 + DP-SGD 训练期兜底防记忆化 + canary 审计验证。

## ② 结构化转化

**数据流**：`归一化SRS(文本+表格)` → NER+参数化+映射+引用解析 → `参数化条目库(条目ID/类型/数值/单位/引用关系) + 引用关系图`

```
文本支路: 规则参数抽取 → NER微调 → UIE联合生成 → LLM校验 ─┐
                                                           ├─→ 条目融合 → 引用解析 → 条目库+关系图
表格支路: 表头模板匹配 → TableLlama列推断 → 术语归一化 ────┘
```

### 2.1 领域NER与参数抽取

**任务**："系统响应时间应≤50ms" → `{param:响应时间, op:≤, value:50, unit:ms, type:性能}`

| 方案 | 代表方法 | 准确率 | 标注成本 | 可审计 | 效果/论文 |
|---|---|---|---|---|---|
| **a)规则正则** | 自定义DSL、spaCy ruler | **>95%**(格式固定) | 低 | 极高 | GJB句式规整，高召回 |
| **b)模型微调NER** | RoBERTa-wwm+CRF | **F1 85-92%** | 中高 | 中 | 需GJB语料续训(MLM) |
| **c)生成式UIE** | UIE/DeepKE/GoLLIE | 中高 | 低(少样本) | 中 | UIE一次生成完整条目 |
| **d)LLM抽取** | Qwen2.5/DeepSeek few-shot→JSON | 中(zero)/高(few) | 极低 | 低(黑盒) | 过度自信(arXiv:2304.11633) |

**技术详述**：

**规则/正则+模板**：针对 GJB 文档高规范化的"参数+运算符+数值+单位"句式，编写正则模板库：`(?P<param>...)(?P<op>[≤≥<>≈])(?P<val>\d+\.?\d*)\s*(?P<unit>ms|Mbps|路|℃)`。GJB 文档句式规整（"响应时间应≤50ms""支持8路输入"），格式固定时**准确率 >95%**，零模型依赖，每条抽取可给出依据，满足军工可审计要求。缺点是仅覆盖已知模式，泛化弱——遇到"在满载工况下，端到端时延不超过200毫秒"这种复杂句式会漏抽。

**预训练模型微调NER**：用 RoBERTa-wwm-ext + CRF（条件随机场）做序列标注，标签集 `[PARAM][OP][VALUE][UNIT][PROTO]`，在 GJB 语料上做领域续训（MLM 预训练）。**F1 85-92%**，能处理术语边界模糊和多义词（如"端口"既可能是接口名也可能是参数名）。缺点是需数百-千条标注语料，军工领域标注稀缺。建议先用规则抽一批种子样本，再用主动学习挑选高价值样本送专家标注。

**生成式UIE/指令IE**：UIE（arXiv:2203.12277, ACL 2022）提出 Structured Extraction Language (SEL) + Structural Schema Instructor (SSI)，将 NER/RE/EE 统一为 text-to-structure 生成。可用 SSI 定义 `schema: [参数名, 运算符, 数值, 单位]`，**一次生成完整参数条目**，天然支持"参数+运算符+数值"联合抽取，不需要分别训练多个模型。DeepKE（arXiv:2201.03335, EMNLP 2022 Demo, zjunlp）是开源工具包，含中文预训练权重，开箱即用，支持低资源/文档级/多模态场景。GoLLIE（arXiv:2310.03668, ICLR 2024）用标注指南（Python 类形式的 schema）微调 LLM，**零样本迁移到未见 IE 任务**——消融实验证明详细 guideline 是关键，可把 GJB 438C 的参数书写规范写成 guideline，零样本抽出新类型指标。

**通用LLM抽取**：Qwen2.5/DeepSeek few-shot → JSON 输出，标注成本极低，适合冷启动和原型验证。**但 Li et al.（arXiv:2304.11633）证实 LLM 抽取过度自信、校准低**——解释质量高但准确率不稳定，在标准 IE 上差但在 OpenIE 上优秀。军工场景不可接受幻觉，必须人工复核。

**推荐**：三层 pipeline——规则兜底（>95%高召回+可审计）+ RoBERTa-wwm微调主力（边界模糊）+ LLM长尾+校验（GoLLIE guideline校验）。

### 2.2 表格结构化与字段映射

**任务**：三类表格(性能指标表/接口定义表/数据字典) → 统一schema + 术语归一化

| 方案 | 表头识别 | 跨表对齐 | 术语归一化 | 效果/论文 |
|---|---|---|---|---|
| **规则模板匹配** | 高(GJB固定表头) | 弱 | 弱 | 硬编码，表头稳定 |
| **TableLlama** | 高 | 高 | 高 | **7/8超SOTA，域外+5-44分** |
| TAPAS/TabBERT | 中高 | 中 | 中 | 英文为主 |
| 同义词典+向量 | — | — | 高 | "响应时间=反应时间=时延" |

**技术详述**：

**规则模板匹配**：GJB 表格表头相对固定——性能指标表典型列为「指标项|指标要求|验证方法|备注」，接口定义表为「接口编号|接口类型|信号名称|方向|协议|速率」，数据字典为「编号|参数名称|缩写|数据类型|取值范围|单位|说明」。按三类表各建表头模板，正则匹配列名。准确率高，但跨表 schema 对齐弱（硬编码，遇到非标准表头失效）。

**TableLlama**（arXiv:2311.09206, NAACL 2024）：首个开源表格通才模型，用 LongLoRA 微调 Llama2-7B 处理长表格。构建了 TableInstruct 数据集（含多种表格理解任务），在 8 个域内任务中 **7 个达到/超过 SOTA**，6 个域外数据集**提升 5-44 分**。开源可私有化部署，符合军工数据不出域要求。可用于 SRS 表格的字段映射、表头语义识别、列类型推断。

**Table Meets LLM**（arXiv:2305.13062, WSDM 2024, Microsoft）：系统评测了 LLM 对结构化表格的理解能力，设计了 7 类任务（单元格查找/行检索/尺寸检测等），发现**输入格式、内容顺序、分区标记显著影响性能**。关键结论：把表格序列化为 Markdown 格式 + 标注关键值，可显著提升 LLM 表格对齐准确率。这指导了如何把 SRS 表格喂给 LLM——推荐 Markdown 格式 + 关键值高亮标注。TAMA（arXiv:2501.14693, ACL 2025）进一步发现小学习率+少数据即能超越 GPT-3.5/4，提供低成本微调表格 LLM 的实践指南。

**术语归一化（核心难点）**：同一参数在不同位置写法不同——表格里写"响应时间"，正文写"反应时间"，数据字典写"时延"。需构建**军工参数同义词典**（响应时间=反应时间=时延=延迟），用实体链接+向量相似度做表-文术语对齐。词典+向量双保险：词典覆盖已知同义词，向量相似度（Sentence-BERT cosine）覆盖未登录同义变体。

**推荐**：规则模板匹配表头 + TableLlama列推断（开源可私有化）+ 同义词典+向量归一化。

### 2.3 交叉引用解析与关系建模

**任务**："见3.2节""如表4所示""参见GJB 438C第5.3条" → 引用关系图

| 方案 | 锚点识别 | 指向解析 | 可审计 | 效果 |
|---|---|---|---|---|
| **正则解析** | 高(编号固定) | 高(查索引表) | 极高 | **覆盖90%+显式引用** |
| HanLP依存句法 | 中高 | 中 | 高 | 关联锚点↔被修饰实体 |
| LLM引用抽取 | 高 | 中高 | 低 | 隐式引用 |
| **Neo4j存储** | — | — | 高 | 多跳溯源，**支撑RTM** |

**技术详述**：

**正则解析**：GJB 文档编号高度规范——章节号 `(\d+\.)+\d+`、表号 `表\s*\d+`、图号 `图\s*\d+`、外部标准条款 `GJB\s*\d+C.*第.*条`。正则可覆盖 **90%+ 显式引用**。建立"章节号→条目ID""表号→表条目ID"索引表后，即可精确解析引用指向。覆盖率最高、可审计，是军工场景首选。

**依存句法分析**：HanLP/LTP 提供中文依存解析，可识别"性能指标见3.2节"中动词"见"的宾语"3.2节"及其主语"性能指标"，建立主语→引用→目标的三元关系。处理引用嵌在句中的情况（"该指标依据3.2节规定执行"），正则只能抓锚点，依存句法能把锚点和被修饰实体关联起来。

**LLM引用抽取**：对隐式引用（"按前述规定执行""同上级要求""参见相关条款"）用 Qwen few-shot 抽取，输出 `{source_span, relation, target}` JSON。仅作正则结果的校验/补全——隐式引用占比小（<10%），但语义级关联需要 LLM 理解上下文。

**Neo4j关系图存储**：Neo4j 建模——节点（需求条目/参数/接口/表/外部标准），边（REFERS_TO/DEFINED_IN/VERIFIED_BY/DEPENDS_ON）。Cypher 支持多跳溯源查询："某性能指标依赖哪些接口与参数""哪些需求引用了 GJB 438C 第5.3条"。**天然支撑 GJB 5000B 的需求可追溯性矩阵(RTM)**——RTM 要求每条需求可追溯到上级需求、可向下追溯到设计和验证，图数据库的多跳查询正好满足。

**推荐**：正则为主（90%+覆盖）+ HanLP依存补强 + Qwen隐式引用 + Neo4j存储。

## ③ 一致性校验

**数据流**：`条目库` → 4检测点×(规则+LLM)两路 → `条目库+冲突标记(冲突类型/严重度/置信度)`

```
条目库 → ①抽取(NER只拆不判) → ②检测(规则L1/L2/L3 + LLM直判) → ③解释(定位) → ④置信度
                                                        ↓
                                              冲突标记挂stats(只标记不删)
```

### 3.1 三层治理体系

仓库已验证的三层递进式校验体系（`子课题3技术方案:10-101`）：

| 层 | 校验什么 | 业内技术 | 开源工具 | 场景1对应 |
|---|---|---|---|---|
| **L1语法一致性** | 字段格式/范围/类型 + 多字段联合约束 + 跨记录 | SHACL约束验证 | Great Expectations, Cleanlab, Pandera | 检测点1(数值)、3(术语) |
| **L2语义一致性** | 跨模态对齐 + KG事实核验 + 多粒度 | CLIP对齐, DEFAME核查 | CLIP, DEFAME, FAMDR | 检测点2(接口语义) |
| **L3逻辑一致性** | 专家知识形式化 + 约束求解 | 本体工程, Z3 Solver | Easy Dataset, Z3, PM4Py | 检测点4(跨条目参数) |

**技术详述**：

**L1语法一致性**：最底层，校验字段格式/范围/类型是否合规，以及多字段间的联合约束。用 W3C SHACL 约束验证（pySHACL 引擎）或 Great Expectations（300+ 内置规则）实现。例如：响应时间字段必须是数值、单位必须是 ms/s/ms 之一、值必须 >0——这是字段级校验。多字段联合约束如"口径×类型×重量"物理耦合关系——单字段合规但组合矛盾（如口径9mm但类型标狙击步枪），用 Cleanlab 或 Pandera 检测。仓库 `MedicalLabRangeFilter` 已验证此层：知识库驱动，单指标范围检测+严重度阶梯。

**L2语义一致性**：跨模态/跨位置的语义级比对。用 CLIP 做跨模态对齐（图文映射到统一语义空间），用 DEFAME 做知识图谱事实核验（检测"图片显示F-16但规格表写F-35"等事实矛盾），用 FAMDR（AAAI 2026）做多粒度一致性分析（特征层→事件层→语义层）。场景1没有图像，L2 主要用于接口类型/协议名称的语义比对（RS422 vs RS232 不是数值比，是语义矛盾）和术语语义对齐。

**L3逻辑一致性**：最高层，融合专家知识的跨条目逻辑约束。用 Easy Dataset 将工艺规范/设计准则转为可执行逻辑约束，用 Z3 Solver 做约束满足求解（检测"先运行后投料"等因果倒置），用 PM4Py 做流程挖掘（从事件日志重建工序流程，检测偏差）。场景1的检测点4（跨条目参数矛盾）属于此层——功能要求写"5路输入"、性能要求写"8路输入"，需要理解"输入路数"在两个条目里是同一参数，然后约束求解判定矛盾。

### 3.2 四检测点技术方案

| 检测点 | 对什么比 | 治理层 | 检测路线 | 仓库原型验证 |
|---|---|---|---|---|
| **1 性能正文↔指标表** | 正文阈值 vs 表数值(≤50ms vs ≤100ms) | L1b多字段约束 | **规则库**(数值直接比) | LabDiagnosisConflictFilter **1444条** |
| **2 接口正文↔接口表** | 正文协议 vs 表字段(RS422 vs RS232) | L2语义一致性 | **LLM直判**(语义级) | _llm_detect Qwen2:7b |
| **3 字典↔正文术语** | 正文参数名/单位 vs 字典定义(反应时间ms vs 响应时间s) | L1a字段+L2对齐 | **规则库**(归一化后比) | MedicalLabRangeFilter |
| **4 跨条目参数** | 同参数跨条目取值(功能5路 vs 性能8路) | L3约束求解 | **规则库+Z3**(跨条目比) | CrossLabConsistencyFilter |

**技术详述**：

**检测点1（性能正文↔指标表）**：从正文 NER 抽取 `{param:响应时间, op:≤, value:50, unit:ms, source:§3.2}`，从表格解析 `{param:响应时间, op:≤, value:100, unit:ms, source:性能指标表}`。术语归一化后比对：同参数、同单位、但值 50≠100 → 命中冲突。这是数值级直接比对，规则库确定性高、可解释。仓库 `LabDiagnosisConflictFilter` 在 MedTVT 10000 样本上检出 **1444 条冲突**，与知识库规则完全对齐，迁移到 SRS 只需换规则库。

**检测点2（接口正文↔接口表）**：正文写"接口采用RS422协议"，接口表写"RS232"。RS422 vs RS232 不是数值比，是语义矛盾——规则库难以穷举所有协议对（RS422/RS232/RS485/1553B/以太网/CAN...及其兼容性矩阵）。把正文接口描述和接口表字段喂给 LLM（Qwen2:7b 本地 Ollama），prompt 要求判断一致性并输出 JSON `{consistent, conflicts, explanation}`。LLM 能理解"RS422 是差分串行协议，RS232 是单端串行协议，二者不兼容"这种领域语义。仓库 `_llm_detect_medical` 已验证此路线可行。

**检测点3（字典↔正文术语）**：正文用"反应时间 ms"，数据字典定义"响应时间 s"。两步走：①术语归一化——用同义词典把"反应时间"映射到"响应时间"；②单位换算后比数值——ms→s 换算后比。如果归一化后参数名一致但单位换算后数值不符，则冲突。术语归一化用词典+向量相似度双保险，单位换算用标准换算因子。

**检测点4（跨条目参数）**：功能要求写"支持5路输入"，性能要求写"支持8路输入"。最复杂的检测点——需要理解"输入路数"这个参数在功能条目和性能条目里是同一个东西。用引用关系图（Neo4j）找到跨条目引用同一参数的关系，然后比对取值。L3 层用 Z3 Solver 约束求解器检测违反领域知识的参数组合矛盾。仓库 `CrossLabConsistencyFilter` 已验证 L3 路线——多指标组合同时满足条件时提示综合征，迁移到 SRS 即"多条目组合参数矛盾时提示冲突"。

### 3.3 两条检测路线（互补）

| 路线 | 实现 | 原理 | 覆盖 | 优势 | 仓库验证 |
|---|---|---|---|---|---|
| **规则库三层** | medical_operators.py风格 | 知识库驱动L1→L2→L3递进 | 检测点1,3,4 | 确定性高、可解释、可审计 | ✅1444条 |
| **LLM直判** | unified_operators.py风格 | 条目喂LLM判断→JSON | 检测点2+盲区 | 灵活、覆盖语义矛盾 | ✅Qwen2:7b |

**技术详述**：

**规则库三层**：参考仓库 `medical_operators.py` 已验证原型，知识库驱动，L1→L2→L3 逐层递进。L1 做单参数范围检测（参数名→正常范围+严重度阶梯），L2 做参数↔表格跨位置比对（同参数正文值 vs 表格值不一致→冲突），L3 做多要素协同约束（多条目组合参数矛盾）。每条规则带严重度（MEDIUM/HIGH/CRITICAL）和详情模板。优势是确定性高、可解释、可审计——每条冲突能给出违反了哪条规则、规则来自哪个 GJB 条文。缺点是规则覆盖面有限，遇到规则未定义的矛盾类型会漏检。

**LLM直判**：参考仓库 `unified_operators.py` 已验证原型，把抽出的条目喂给本地 LLM（Qwen2:7b via Ollama），prompt 描述判断规则，要求输出 JSON `{consistent: true/false, conflicts: [{type, detail, severity}], explanation}`。优势是灵活——能处理规则未覆盖的语义级矛盾（如接口协议兼容性、术语语义等价性）。缺点是黑盒、有幻觉风险、需置信度校准。两条路线互补：规则库覆盖已知冲突模式（确定性高），LLM 直判覆盖规则盲区（灵活）。

## ④ 质量评估

**数据流**：`条目库+冲突标记` → 7维打分+4层评估 → `分级数据集(A级直接微调 / B级人工复核 / C级退回)`

```
条目库+冲突标记
  ├─ L1规则层(GX):     完整性+一致性+合规性 → 自动评分
  ├─ L2标签层(Cleanlab): 标签置信度 → 噪声标记
  ├─ L3语义层(LLM抽样):  合规性/准确性 → 抽样报告
  ├─ L4隐私层(Presidio):  残留敏感 → 一票否决
  └─ 汇总 → 评分模型 → A/B/C分级
```

### 4.1 七维质量评估

| 维度 | SRS场景指标 | 评估方法 | 工具 |
|---|---|---|---|
| **完整性** | GJB七大块覆盖；字段缺失率 | 规则检查 | Great Expectations |
| **一致性** | 4类冲突检测通过率 | ③校验管道输出 | 自定义 |
| **合规性** | GJB 438C条目对标率 | 标准模板对标 | GE+SHACL |
| **准确性** | 术语库命中率；参数值合理性 | 置信学习 | **Cleanlab**(召回100%) |
| **可用性** | 脱敏后BERTScore语义保持度 | 效用-隐私权衡 | Sentence-BERT |
| **隐私性** | 残留敏感实体数；k-匿名 | 复检 | Presidio(**一票否决**) |
| **多样性** | 装备类型/场景分布均衡度 | 分布统计 | TADS(36%超全量) |

**技术详述**：

**完整性**：检查 GJB 438C-2021 规定的七大块（功能需求/性能指标/接口定义/数据字典/运行环境/安全保密/验收准则）是否齐全，各块内必需字段是否缺失。用 Great Expectations 声明式 Expectation 实现——每个七大块定义一组期望（如"性能指标表必须存在""性能指标表行数>0""每行必须有指标项和指标值"），自动校验并通过率打分。

**一致性**：直接取 ③一致性校验管道的输出——4 类冲突检测的通过率。0 冲突 = 满分，冲突数越多分越低。这是数据治理项目的核心质量指标。

**合规性**：GJB 438C-2021 条目对标率——每条需求条目是否能映射到 GJB 标准条文。用标准模板对标（GE+SHACL 规则集），检查条目格式、内容要素是否符合 GJB 要求。

**准确性**：术语在权威术语库的命中率、参数值合理性（范围/类型）。用 Cleanlab 置信学习检测标签错误——如果微调数据的指令-响应对有噪声（标注错误），Cleanlab 能自动识别。

**可用性**：脱敏后数据的语义保持度。用 Sentence-BERT 计算脱敏前后文本的 cosine 相似度，或用 BERTScore。这是"脱敏后还能不能用于微调"的量化指标。

**隐私性（一票否决）**：脱敏复检——用 Presidio 再扫一遍脱敏后数据，如果还有残留敏感实体，直接降 C 级，不进入加权评分。这是安全红线。

**多样性**：装备类型/场景分布的均衡度。用分布统计或聚类分析，检查数据集是否覆盖了各类装备和场景，避免模型在某些类别上过拟合。

| 工具 | 机制 | 适用维度 | 效果 | 仓库验证 |
|---|---|---|---|---|
| **Great Expectations** | 声明式Expectation(300+规则) | 完整性/一致性/合规性 | Data Docs可视化 | ✅ |
| **Cleanlab** | 置信学习(arXiv:1911.00068) | 准确性(标签噪声) | **召回100%** | ✅ |
| **TADS** | 任务感知(质量+相关+多样性) | 多样性 | **36%超全量+1.0%** | ❌ |
| **UniFilter** | 多模态质量分类器(半合成) | 多模态质量 | EMNLP 2025 | ❌ |

**技术详述**：

**Great Expectations**：Apache-2.0 开源，声明式 Expectation 框架——用 Python 声明"我期望这个字段非空""我期望这个值在 0-100 范围内""我期望这两列唯一"，自动校验并生成 Data Docs 可视化报告。300+ 内置规则，可集成 Airflow/Pandas/Spark/SQL。仓库已验证。适合完整性/一致性/合规性的自动化校验——GJB 七大块是否齐全、4 类冲突是否为 0、GJB 对标率，天然是规则检查。

**Cleanlab**：基于置信学习（Confident Learning，arXiv:1911.00068, JAIR 2021, Northcutt et al.）。核心原理：用模型预测概率估计噪声标签与真实标签的联合分布，自动找标签错误。**理论保证可证一致**（provably consistent），模型无关。在 MNIST 上都能找出"presumed error-free"数据集的标签错误。仓库在 GunsAndWeapons 数据上验证**召回率 100%**（但精确率低）。适合 SRS 微调数据的指令-响应标签质量审计——如果标注的"正确SRS章节"本身有错误，Cleanlab 能识别。

**TADS**（arXiv:2602.05251）：任务感知数据选择，用可学习价值函数综合评估内在质量+任务相关度+分布多样性三因子，配合反馈元学习。**仅用 36% 数据超越全量基线 +1.0%**。适合数据集筛选——不是所有条目都对微调 equally useful，TADS 能挑出对模型最有价值的子集。

**UniFilter**（arXiv:2510.15162, EMNLP 2025）：训练统一多模态质量分类器，用半合成四级质量标注训练（人工生成不同质量等级的数据），能同时过滤 caption 和交错文档。适合多模态数据质量打分，场景1纯文本/表格可简化使用。

**LLM抽样复核**：用 LLM 作为评判对数据质量打分/分级，灵活、可处理语义级质量（如"这条需求描述是否清晰""这个参数值是否合理"）。参考 DataGovBench（arXiv:2512.04416）的 Planner-Executor-Evaluator 架构。仅抽样进行，不作为全量主评估——成本高、需校准防偏。

### 4.3 分级标准

评分 = w1·完整性 + w2·一致性 + w3·合规性 + w4·准确性 + w5·可用性 + w6·隐私性。**隐私性一票否决**。

| 等级 | 分数 | 判定条件 | 处置 |
|---|---|---|---|
| **A** | ≥85 | 七大块齐全/4类冲突0/GJB对标≥95%/语义保持≥90%/无残留敏感 | **直接微调** |
| **B** | 70-84 | 个别缺失/冲突≤3/对标80-95%/语义保持75-90% | **人工复核后可用** |
| **C** | <70 | 大块缺失/冲突>3/对标<80%/语义损失大/残留敏感 | **退回重做** |

### 5.1 GJB标准条文→结构化规则库

**任务**：把 GJB 438C-2021 标准条文（PDF/Word）转成可执行规则，用于③校验规则基准 + ④合规评估。

| 方案 | 原理 | 效果 | 适用场景 | 工具 |
|---|---|---|---|---|
| **LLM+CoT规则抽取** | Chain-of-Thought提示LLM逐步推理出"前提-约束-值-例外"四元组 | 准确率70-85%，CoT比零样本+15-25% | 非结构化条文 | LangChain, LlamaIndex |
| **OLLM端到端本体学习** | 微调LLM建模整个本体子组件(非单条关系) | 语义准确度优于子任务组合 | 从零构建领域本体 | OLLM(arXiv:2410.23584) |
| **SHACL规则编码** | 标准条文→SHACL Shapes约束→pySHACL验证 | W3C标准，Trav-SHACL加速28x | 结构约束验证 | pySHACL, Apache Jena |
| **SWRL规则推理** | OWL本体上定义Horn逻辑规则 | 支持规则+本体联合推理 | 复杂条件约束 | Protégé SWRLTab, Pellet |
| **Datalog/Soufflé** | 递归规则演绎推理，编译为C++ | 可判定，极高效 | 传递性/层次约束 | Soufflé, VLog |
| **Great Expectations** | 本体约束→GE Expectation | 300+规则，DataFrame生态 | 表格约束校验 | ✅仓库已验证 |

**技术详述**：

**LLM+Chain-of-Thought规则抽取**：利用大语言模型（GPT-4o/Claude/Qwen）的 Chain-of-Thought 推理能力，将 GJB 438C-2021 条文分块输入，通过多轮提示引导 LLM 逐步识别条文的**前提条件、约束主体、约束值、例外情况**，输出结构化规则四元组。研究表明 CoT 提示相比零样本提升 15-25% 准确率，可结合 Few-Shot 示例和 Self-Consistency 投票进一步提升稳定性。例如条文"功能要求不应包含性能参数信息"→ `{前提:条目类型=功能需求, 约束:不含参数信息, 值:null, 例外:null}`。适合处理 GJB 标准中大量非结构化的自然语言条文。

**OLLM端到端本体学习**（arXiv:2410.23584）：不同于聚焦子任务（如实体间单条关系），OLLM 通过微调 LLM 并使用自定义正则化器（减少高频概念过拟合）来建模目标本体的**整个子组件**——即整个分类骨架。引入基于深度学习的图距离度量评估生成本体的语义和结构相似度，在 Wikipedia 数据集上显著优于子任务组合方法，且仅需少量训练样本即可高效迁移到新领域。适合从 GJB 文档自动构建军用软件需求领域本体的分类骨架，人工补充关键属性和关系。

**SHACL规则编码 + Trav-SHACL加速 + xpSHACL解释**：SHACL（Shapes Constraint Language，arXiv:2112.01441综述）是 W3C 推荐的 RDF 数据验证语言，将标准条文编码为**Shapes（形状约束）**——每个 Shape 定义一类需求条目必须满足的约束（属性存在性、基数、值域、闭合性等）。Trav-SHACL（arXiv:2101.07136）通过规划形状遍历顺序（先验证可能违规的形状）和重写查询，将验证时间**减少最多 28.93 倍**，支持 3400 万三元组规模。xpSHACL（arXiv:2507.08432, VLDB'25）结合 RAG 和 LLM 为约束违规生成**多语言人类可读解释**，并用 Violation KG 缓存解释提升效率——这对军用场景的可审计性至关重要，每条违规都有中文解释和修正建议。

**SWRL规则推理**：SWRL（Semantic Web Rule Language）在 OWL 本体上定义类 Datalog 的 Horn 逻辑规则，支持将 GJB 条文中复杂的**条件-结论**关系形式化。例如"若需求条目为安全性需求且危险等级为A级，则必须包含故障树分析"可编码为 SWRL 规则。由 Pellet 或 HermiT 推理机执行，可与 OWL 本体推理无缝集成，实现约束的自动传播。缺点是不支持非单调推理和否定。

**规则表示语言对比**：

| 语言 | 表达能力 | 可判定 | 效率 | 适用场景 |
|---|---|---|---|---|
| **Datalog** | 中(无算术/嵌套) | ✅ | ⭐⭐⭐⭐⭐ | 递归约束、传递闭包 |
| **SWRL** | 中高(Horn+OWL DL) | ✅(受限) | ⭐⭐⭐ | 本体+规则联合推理 |
| **SHACL** | 中(验证导向) | ✅ | ⭐⭐⭐⭐ | 数据验证、质量检查 |
| **SPARQL** | 高(图查询+CONSTRUCT) | ⚠️不可判定 | ⭐⭐⭐ | 查询驱动验证 |

**推荐**：LLM+CoT规则抽取 → SHACL结构约束编码 + SWRL条件推理 → Trav-SHACL高效验证 → xpSHACL可解释违规报告。

### 5.2 专家经验形式化

**任务**：把专家的设计准则、评审经验、常见错误转为可执行约束规则，挂载到条目上作为知识标签。

| 方案 | 原理 | 效果 | 适用场景 | 工具/论文 |
|---|---|---|---|---|
| **AMIE规则挖掘** | 枚举KG闭合路径，支持度/置信度评估 | 高精度可解释规则 | 从历史SRS挖掘设计准则 | AMIE3(WWW2013) |
| **AnyBURL规则学习** | 神经网络引导随机游走学Horn规则 | anytime策略，大规模KG | 大规模规则自动学习 | AnyBURL(ISWC2019) |
| **RNNLogic** | RNN生成规则+EM优化，规则作隐变量 | ICLR2021，可解释+高质量 | KG推理+规则发现 | arXiv:2010.04029 |
| **RL规则挖掘** | 生成-评估两阶段RL框架 | KBS2022 SOTA效率 | 动态KG持续挖掘 | arXiv:2202.10381 |
| **RotatE嵌入** | 复数空间旋转建模关系 | ICLR2019，建模对称/反对称/组合 | KG补全、缺失关系预测 | arXiv:1902.10197 |
| **LLM+KG协同** | LLM抽取知识，KG约束验证 | TKDE2024三大框架 | 专家口述→结构化知识 | arXiv:2306.08302 |
| **Drools规则引擎** | RETE算法前向链规则匹配 | 工业级成熟，支持CEP | 实时约束验证、规则触发 | Red Hat Drools |
| **Meta-Interpretive Learning** | 归纳逻辑编程，少量样例学递归谓词 | 样本效率高，符号可解释 | 从专家样例学设计模式 | Metagol(ILP2014) |

**技术详述**：

**AMIE规则挖掘**：AMIE（AMIE3, Galárraga et al., WWW 2013）在大规模知识图谱上**枚举闭合路径**（closed paths），生成形如 `h(X,Y) <= b1(X,Z) ∧ b2(Z,Y)` 的 Horn 规则。通过支持度（support）、置信度（confidence）和 PCA 置信度三个指标评估规则质量。AMIE3 引入语言偏置和并行化策略，在 DBpedia（数百万三元组）上可在合理时间内完成挖掘。适用于从历史 SRS 文档及其审核记录的知识图谱中自动发现**隐含设计准则**——如"若需求含'实时性'关键词，则必须关联响应时间指标"。

**AnyBURL规则学习**（Meilicke et al., ISWC 2019）：使用**神经网络引导的随机游走**在 KG 上学习 Horn 规则。采用"anytime"策略——可在任意时刻停止并获得当前最优规则集，支持大规模 KG 的近似规则学习。在 FB15k-237 等基准上，AnyBURL 生成的规则在链接预测任务上与 KGE 方法相当甚至更优，且**规则完全可解释**。适合从大规模 SRS 知识图谱中自动学习专家隐含的评审经验规则，比 AMIE 穷举搜索更高效。

**RNNLogic**（arXiv:2010.04029, ICLR 2021）：将逻辑规则视为**隐变量**，同时训练规则生成器（RNN）和推理预测器。采用 EM 算法优化：E 步从所有生成规则中通过后验推理选择高质量规则集，M 步用选中规则更新生成器。解决了 Neural LP（NeurIPS 2017）搜索空间大和 RL 方法奖励稀疏的问题。生成的规则既有可解释性又有预测力——适用于从 SRS 审核历史中学习"需求模式→评审建议"的映射规则。

**RotatE知识图谱嵌入**（arXiv:1902.10197, ICLR 2019）：将关系定义为**复数空间中的旋转**，能建模对称/反对称、逆反和组合等多种关系模式。每个关系是一个从源实体到目标实体的旋转操作，引入自对抗负采样提升训练效率。在多个基准 KG 上显著优于 TransE/DistMult/ComplEx。适用于 SRS 知识图谱中**缺失关系预测**——如预测需求条目间未显式标注的依赖关系、追溯关系。注意：Jøsang et al.（arXiv:2206.00983）研究表明 TransE 补全后会产生较多虚假规则，RotatE 更可靠。

**LLM+KG协同框架**（Pan et al., arXiv:2306.08302, IEEE TKDE 2024）：提出 LLM 与 KG 统一的**三大框架**——①KG 增强 LLM（预训练/推理阶段融入 KG 知识，增强事实准确性）；②LLM 增强 KG（LLM 做 KG 嵌入/补全/构建/图到文本生成）；③协同 LLM+KG（双向推理驱动）。LARK（arXiv:2305.01157）将 KG 复杂推理分解为上下文 KG 搜索 + LLM 逻辑推理，在标准基准上超越 SOTA。适用于将专家口述经验用 LLM 抽取为结构化知识，再用 KG 约束验证其一致性。

**Drools规则引擎**：Red Hat 开源的**前向链规则引擎**，基于 RETE 算法实现高效模式匹配。规则以 DRL（Drools Rule Language）格式定义，支持 WHEN-THEN 范式。支持复杂事件处理（CEP）、规则流组、决策表等高级特性，已在金融风控、电信计费等工业场景广泛部署。适合将 GJB 标准规则 + 专家经验规则 + 挖掘规则统一编码为 DRL 格式，对 SRS 需求条目执行**实时一致性约束验证**，特别是需要增量更新规则的场景。用规则优先级处理多规则冲突。

**知识类型映射**：

| 知识类型 | 来源 | 形式化方法 | 用途 |
|---|---|---|---|
| 设计准则 | 专家经验/评审记录 | LLM抽取→Drools DRL规则 | ③校验L3约束来源 |
| 隐含规则 | 历史SRS的KG | AMIE/AnyBURL自动挖掘 | ③校验规则补充 |
| 缺失关系 | KG中未标注的依赖 | RotatE嵌入预测补全 | ②引用关系图补全 |
| 常见错误 | 历史缺陷台账 | 错误模式→检测规则 | ③校验规则补充 |
| 参数约束 | 领域知识 | 参数范围→L1规则 | ③校验L1规则来源 |
| 设计模式 | 专家少量样例 | Meta-Interpretive Learning归纳 | 可复用递归设计规则 |

**推荐**：AnyBURL历史数据挖掘 + LLM+CoT经验抽取 + RotatE关系补全 + Drools统一规则执行。专家确认的新规则写回知识库（多轮迭代→可解释诊断→专家校验→规则增强→模型反馈闭环）。

### 5.3 知识图谱构建与五层约束验证

**KG真实角色**（`entity_research.md`关键结论）：标准ontology**没有显式"contradicts"边**。KG做**规范化+关系推理**，配合LLM判断矛盾。

**场景1的KG设计**：

```
节点: 需求条目 / 参数 / 接口 / 表格 / GJB条文 / 装备型号
边:   DEFINED_IN(参数→字典) / REFERS_TO(条目→条目/表/标准)
      VERIFIED_BY(需求→验收) / CONSTRAINED_BY(参数→GJB) / DEPENDS_ON(性能→接口)
```

**五层分层验证架构**：

```
SRS知识图谱(Neo4j)
    │
    ├─ 第1层·结构验证(SHACL)     Trav-SHACL验证Shapes约束(加速28x) → 结构完整性
    ├─ 第2层·逻辑推理(OWL)       HermiT/Pellet检测本体矛盾 → 分类/互斥/传递冲突
    ├─ 第3层·数值约束(Z3)        SMT求解器验证数值约束可满足性 → 参数矛盾+反例
    ├─ 第4层·语义核查(AMREx)     AMR语义包含验证需求↔标准一致性 → 语义偏离检测
    ├─ 第5层·质量监控(KG Curation) 多维质量度量持续监控 → 精度/完整度/一致性/时效
    │
    └─ xpSHACL: 所有层违规→RAG+LLM生成中文可读解释+修正建议
```

| 层 | 验证什么 | 首选工具 | 效果 | 论文 |
|---|---|---|---|---|
| **1.结构** | 字段格式/基数/值域/类型 | Trav-SHACL + pySHACL | **加速28.93x**，支持34M三元组 | arXiv:2101.07136 |
| **2.逻辑** | 类冲突/互斥/传递依赖环路 | HermiT/Pellet推理机 | Tableau算法，形式化保证 | arXiv:1602.04473 |
| **3.数值** | 性能参数数值约束可满足性 | Z3 SMT Solver | 自动求解+反例生成 | TACAS 2008 |
| **4.语义** | 需求声明↔GJB标准语义一致性 | AMREx(AMR+Smatch) | 可解释AMR映射 | arXiv:2411.01343 |
| **5.质量** | KG精度/完整度/一致性/时效 | KG Curation框架 | 多维质量度量 | arXiv:2208.08130 |
| **解释** | 违规→中文可读解释 | xpSHACL+RAG+LLM | Violation KG缓存 | arXiv:2507.08432 |
| **多模态** | 图文混合需求声明核查 | DEFAME六阶段管线 | ICML2025 SOTA，超GPT-4o | arXiv:2412.10510 |

**技术详述**：

**第1层·SHACL结构验证**：SHACL（arXiv:2112.01441综述）是 W3C 推荐的 RDF 数据验证语言，将约束建模为**形状网络（network of shapes）**，每个 Shape 包含目标节点选择器和约束条件（`sh:minCount`/`sh:maxCount`/`sh:nodeKind`/`sh:in`/`sh:closed`等）。Trav-SHACL（arXiv:2101.07136）通过规划形状遍历顺序（先验证可能违规的形状）和重写目标/约束查询，将验证时间**减少最多 28.93 倍**，支持 3400 万三元组规模的 KG。验证需求条目的结构完整性——必填属性是否存在、基数是否合规、值域是否在允许范围内、类型是否正确。

**第2层·OWL一致性推理**：OWL 描述逻辑推理机（Pellet, HermiT）通过 **Tableau 算法**检测本体不一致性——包括类层次冲突（如 `A ⊑ B ∧ A ⊑ ¬B`，安全性需求与非安全性需求不应有交集实例）、实例矛盾（个体同时属于互斥类）、基数违反等。HermiT 是第一个支持 OWL 2 Direct 语义的高性能推理机，采用 hypertableau calculus 减少非确定性。适合检测 SRS 需求分类体系中的逻辑矛盾——如"某条目同时被标为功能需求和性能需求，但本体定义二者互斥"。

**第3层·Z3数值约束求解**：Z3（de Moura & Bjørner, TACAS 2008）是微软研究院的高性能 **SMT（Satisfiability Modulo Theories）求解器**，支持线性/非线性算术、位向量、数组、量词等理论。将 SRS 需求间的数值约束（如"响应时间≤100ms 且 吞吐量≥1000req/s""安全性等级≥B的资源分配不超过总量50%"）建模为 SMT 公式，Z3 自动判断约束可满足性——不可满足时**输出反例**（哪几个参数组合导致矛盾）。适合③检测点4（跨条目参数矛盾）的精确求解。

**第4层·AMREx语义核查**：AMREx（arXiv:2411.01343, EMNLP FEVER 2024）基于**抽象意义表示（AMR）**进行事实验证——将需求声明和 GJB 标准条文解析为 AMR 图，用 Smatch 度量计算语义包含关系，判断需求声明是否被标准条文支持或否定。输出可解释的 AMR 节点映射作为验证依据，AMR 映射还可用于提示 LLM 生成自然语言解释，减少幻觉。适合检测"需求声称符合标准但实际语义偏离"的情况——如需求写"支持热插拔"但 GJB 条文要求的是"冷备份切换"，AMR 语义包含验证能识别这种语义偏离。

**第5层·KG质量监控**：Huaman & Fensel（arXiv:2208.08130, IJCKG'21）提出实用的 KG 策展框架，定义多维**质量度量**——①精度（Accuracy）：三元组正确率；②完整度（Completeness）：模式/实例覆盖度；③一致性（Consistency）：逻辑矛盾检测；④时效性（Timeliness）：知识更新程度。包含验证-验证（V&V）清洗任务、重复检测和知识融合策略。RDFUnit 提供基于 SPARQL 的 KG 测试驱动验证。适合对 SRS 知识图谱进行系统化质量评估和持续监控。

**DEFAME多模态事实核查**（arXiv:2412.10510, ICML 2025）：模块化的**零样本多模态 LLM 管线**，通过六阶段流程验证文本-图像声明——①声明分析 ②证据检索(文本+视觉) ③证据提取 ④证据评估 ⑤一致性聚合 ⑥报告生成。动态选择工具和搜索深度，在 VERITE/AVerITeC/MOCHEG 基准上超越所有先前方法，在知识截止后的 ClaimReview2024+ 基准上**大幅超越 GPT-4o**。适合 SRS 文档中图文混合需求声明的自动核查（场景1虽以文本+表格为主，但接口定义可能含信号波形图）。

**KGDMC**（ACM 2025, DOI:10.1145/3696410.3714813）：解耦 VAE 模块（DMR）将每个模态数据解耦为模态特定和模态不变特征空间，用准确的文本模态不变特征指导可疑视觉模态信息的跨模态重构；引入**多粒度三元组置信度（MTC）**，从局部三元组、全局邻居结构、全局路径传播三个层面评估事实自洽性。SNOMED CT + Neo4j（arXiv:2510.16899）将疾病/症状/药物建模为节点，"caused by"/"treats"为边，支持多跳推理——可迁移到 SRS 的"需求→参数→接口→标准"多跳溯源。

**约束验证流程**：①条目库实体链接到 KG（参数名→KG 节点，术语归一化）；②五层验证逐层执行（SHACL结构→OWL逻辑→Z3数值→AMREx语义→质量监控）；③约束传播推理检测违反领域知识的冲突（如口径9mm但类型标狙击步枪，本体规则"狙击步枪口径≥12.7mm"触发冲突）；④xpSHACL 生成中文可读违规解释+修正建议；⑤记录推理路径（证据溯源）。

**推荐**：五层分层验证——SHACL结构(Trav-SHACL加速28x) + OWL逻辑(HermiT/Pellet) + Z3数值(反例生成) + AMREx语义(AMR包含验证) + KG质量监控(Curation框架)，所有违规经 xpSHACL 生成中文可读解释。

## 产出：微调数据集

**数据流**：`知识增强数据集` → 3类样本封装 → `微调数据集` → 北极星模型 → 回灌9环节 → 闭环

| 样本类型 | 来自链路哪步 | 样本结构 | 教模型什么 |
|---|---|---|---|
| **指令微调样本** | ①②正常条目 | 输入:需求条目→输出:SRS章节 | "怎么按GJB写SRS" |
| **诊断样本** | ③冲突条目 | 输入:SRS片段→输出:冲突类型+位置+修复建议 | "什么是不一致、怎么改" |
| **知识密集型样本** | ⑤知识融合后 | 输入:设计场景→输出:专家准则+设计约束 | "设计准则和隐性经验" |

**闭环**（`典型场景:90`）：

```
多轮迭代 → 可解释诊断 → 专家校验 → 规则增强 → 模型反馈
    ↑                                                    │
    └────────────────────────────────────────────────────┘
```

- **多轮迭代**：同一批SRS反复跑①→⑤，每轮提升数据质量
- **可解释诊断**：每个冲突给出原因+位置+证据，不是黑盒
- **专家校验**：人工复核诊断结果，确认/修正
- **规则增强**：专家确认的新规则写回知识库
- **模型反馈**：模型上线后的误判/漏判，回流成新样本
