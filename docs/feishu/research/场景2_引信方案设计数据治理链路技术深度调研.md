## 0. 概述

### 0.1 场景定位

基于引信产品设计技术要求，开展 SysML 九视图建模与总体/详细方案设计，实现设计技术要求 → SysML 模型 → 详细方案的智能生成与映射。将历史引信方案设计数据治理为高质量微调数据集，训"北极星"垂域大模型。

### 0.2 五步治理链路全景

```
设计技术要求(Word/PDF) + SysML九视图(XMI) + 仿真模型(.slx/.mo/.wsv)
+ GJB引信标准条文 + 专家经验(隐性)
    │
  ①标准化预处理   要求文档解析→SysML解析→仿真解析→脱敏
    │              → 归一化资产(统一格式)
    ↓
  ②结构化转化     要求参数化→视图抽取→仿真抽取→映射构建
    │              → 结构化条目库 + 要求→实现映射图
    ↓
  ③一致性校验     3类检测点(规则+LLM+形式化)三路 → 标记冲突不删
    │              → 条目库+冲突标记
    ↓
  ④质量评估       覆盖性/一致性/可追溯性/准确性/合规性/完整性/可用性打分
    │              → 分级数据集(A/B/C级)
    ↓
  ⑤知识融合       GJB条文映射 + 专家经验显性化 + 知识图谱约束
    │              → 知识增强微调数据集
    ↓
  微调数据集 → 北极星垂域大模型 → 回灌方案设计全链路 → 闭环迭代
```

### 0.3 数据模态

文本（设计技术要求）+ 结构化模型（SysML 九视图）+ 时序仿真（Simulink/SystemVue/Mworks 动态行为）→ 对应课题"**表格 ↔ 时序**"模态组合。**三模态且含动态仿真**，是5个场景中模态最复杂的之一。

### 0.4 与场景1的差异

| 维度 | 场景1 (SRS) | 场景2 (引信方案) |
|---|---|---|
| 数据模态 | 文本+表格(2模态) | 文本+SysML+仿真(3模态) |
| 核心矛盾 | 文本↔表格数值矛盾 | **静态视图↔动态仿真行为冲突** |
| 检测点 | 4个(数值/语义/术语/跨条目) | 3个(覆盖性/静动一致性/传递链) |
| 新增技术 | — | SysML解析 + 仿真解析 + **形式化验证** |
| 可复用率 | — | ~70%(解析栈/脱敏/规则库/LLM直判/质量评估/KG架构) |

### 0.5 军用场景硬约束（贯穿5步，与场景1相同）

| 约束 | 含义 | 影响 |
|---|---|---|
| 数据不出域 | 全程本地推理，禁外发API | 优先开源可私有化模型 |
| 可审计 | 每步产出可追溯依据 | 规则层优先，模型层带置信度 |
| 可追溯 | 条目保留来源span+视图位置 | 满足GJB 3206配置管理 |
| 涉密脱敏 | 型号代号/战术指标需脱敏 | 脱敏后仍需可用于微调 |

## 1. ①标准化预处理

### 1.1 设计技术要求文档解析

**核心问题**：把设计技术要求 Word/PDF 解析成结构化文本，按 5 大部分切分。

**5 大部分结构**（GJB 2116 研制要求模板）：

| 部分 | 内容 | 典型参数 |
|---|---|---|
| 功能要求 | 引信必须做什么（保险/解保/引爆） | 解保方式、引爆方式 |
| 性能要求 | 量化阈值 | 引爆阈值、作用距离、时序精度 |
| 工作流程 | 操作序列/状态/模式 | 安全→解保→引爆状态转移 |
| 接口要求 | 机械/电气/信息接口 | 接口类型、信号定义 |
| 通用质量特性 | 六性指标(可靠性/维修性/测试性/安全性/保障性/环境适应性) | MTBF、MTTR、检测率 |

| 工具 | 原理 | 中文 | 表格 | 许可 | 推荐度 |
|---|---|---|---|---|---|
| **Word直抽(python-docx)** | 读取OOXML段落/样式/表格 | ★★★★★ | ★★★★★(合并无损) | MIT | ★★★★★(首选) |
| **MinerU** | DocLayout-YOLO+PaddleOCR+UniMERNet | ★★★★ | ★★★★ | Apache(核心) | ★★★★★(PDF首选) |
| **PP-Structure** | 版面+表格+OCR一体化 | ★★★★★ | ★★★★ | Apache-2.0 | ★★★★★(国产替代) |
| LLM辅助 | Qwen2.5 few-shot章节语义识别 | ★★★★ | — | 开源 | ★★★(离线复核) |

**推荐**：Word走 `python-docx` 直抽；PDF走 MinerU；LLM仅离线复核5大部分变体。**与场景1共用解析栈**。

### 1.2 SysML 九视图模型解析

**核心问题**：从 Cameo/Papyrus/MWorks.Sysbuilder 导出的 XMI/XML 文件中，提取九视图的结构化元素。

**九视图映射**（领域特化方法论，基于OMG SysML 9图适配引信设计）：

| # | 视图名称 | SysML图 | 核心元素 | 一致性检测角色 |
|---|---|---|---|---|
| 1 | 需求视图 | Requirement Diagram (req) | Requirement(id/text/type/priority) | DP1覆盖性检测源端 |
| 2 | 任务场景视图 | Use Case Diagram (uc) | UseCase/Actor/Include | DP1覆盖性检测 |
| 3 | 工作流程模型 | Activity Diagram (act) | Activity/Input/Output/ControlFlow | DP3传递链中间节点 |
| 4 | 时序交互视图 | Sequence Diagram (sd) | Lifeline/Message/Sequence | DP1接口覆盖检测 |
| 5 | 状态行为视图 | State Machine Diagram (stm) | State/Transition/Guard/Action | DP2静动比对源端 |
| 6 | 产品组成模型 | Block Definition Diagram (bdd) | Block/Attribute/Operation/Composition | DP3传递链结构节点 |
| 7 | 接口视图 | Internal Block Diagram (ibd) | Port/Connector/Interface | DP1接口覆盖检测 |
| 8 | 功能分配模型 | Activity Diagram(swimlanes) | Activity/Partition/Allocate | DP1功能覆盖检测 |
| 9 | 参数视图 | Parametric Diagram (par) | ConstraintBlock/ConstraintExpr/Parameter | DP2静动比对源端 |

**解析工具对比**：

| 工具 | 原理 | 语言 | 许可 | 优势 | 限制 |
|---|---|---|---|---|---|
| **pyEcore** | Eclipse EMF/Ecore的Python实现 | Python | BSD-3 | 纯Python、XMI原生支持、EMF兼容 | 需理解SysML元模型 |
| **PySysML2** | SysML 2.0文本语言解析器 | Python | MIT | 专为SysML 2.0设计 | 仅SysML 2.0文本格式 |
| **Eclipse Papyrus** | EMF-based Java API | Java | EPL 2.0 | 工业级、完整SysML 1.6支持 | 需Eclipse环境 |
| **Cameo API** | Java插件开发 | Java | 商业 | 工具内直接提取 | 需Cameo许可证 |
| **EA(Sparx) API** | COM API + XMI导出 | 多语言 | 商业 | XMI 2.1/Native XML导出 | 需EA许可证 |

**pyEcore 关键用法**：

```python
from pyecore.resources import ResourceSet, URI
rset = ResourceSet()
resource = rset.get_resource(URI('fuse_model.xmi'))
root = resource.contents[0]
# 遍历模型元素
for element in root.eAllContents():
    eclass = element.eClass.name  # 元素类型(如"Requirement","Block","Constraint")
    name = getattr(element, 'name', '')
    # 按SysML Profile标签分类
    if eclass == 'Requirement':
        # 提取需求条目
        req_id = getattr(element, 'id', '')
        req_text = getattr(element, 'text', '')
    elif eclass == 'Block':
        # 提取组件
        attrs = [a for a in element.eAllContents() if a.eClass.name == 'Property']
```

**关键挑战**：
- **XMI标准化不足**：不同工具导出的XMI存在工具特化扩展（Cameo的HUDS XML vs 标准XMI 2.1）
- **图表信息丢失**：XMI交换中diagram layout常丢失，仅模型元素和关系可靠传递
- **SysML 1.x vs 2.0**：SysML 2.0(2023发布)有全新文本语法和元模型，与1.x不兼容

**关键论文**：
- pyEcore: https://github.com/pyecore/pyecore (BSD-3, EMF Python实现)
- PySysML2: https://github.com/DAF-Digital-Transformation-Office/PySysML2 (SysML 2.0解析)
- Fu et al. (IEEE Access 2021, DOI:10.1109/access.2021.3115165): SysML模型图构建

### 1.3 仿真模型解析

**核心问题**：从 Simulink(.slx) / MWorks(.mo) / SystemVue 仿真文件中提取输入参数、输出轨迹、阈值约束、模块结构。

**Simulink .slx 解析**（.slx 是ZIP/OPC容器，内含XML文件，自R2012a起）：

| 方案 | 原理 | 需MATLAB | 提取内容 | 推荐度 |
|---|---|---|---|---|
| **SimulinkInterface** | zipfile+xml.etree解析.slx | ❌ | block_list/connection_list/参数/Mask | ★★★★★(无MATLAB时) |
| **MATLAB Engine API** | Python调用MATLAB引擎 | ✅ | 全功能(含sim()仿真执行) | ★★★★★(有MATLAB时) |
| **slxpy** | Embedded Coder生成Python绑定 | ✅+EC | 可执行仿真 | ★★★(需EC许可) |
| **SAGE** | C++17重写SimulinkInterface | ❌ | 同SimulinkInterface+模型diff | ★★★★(C++环境) |

**MWorks (苏州同元) 解析**：

MWorks是国产Modelica平台，亚洲唯一独立Modelica内核。Modelica模型是**文本格式**(.mo)，可直接解析。

| 方案 | 原理 | 优势 | 限制 |
|---|---|---|---|
| **MWorks.SDK** | 三层API(Kernel/Mo/Frame) | 官方支持、含仿真结果读写 | 需MWorks许可 |
| **Modelica文本解析** | .mo文件按Modelica语法解析(ANTLR) | 无需MWorks、纯文本 | 需自行实现语法解析 |
| **OpenModelica OMC** | 开源Modelica编译器API | 完全开源 | 与MWorks的Modelica方言可能有差异 |

**SystemVue (Keysight) 解析**：
- 无公开Python API
- 通过VBscript/Jscript脚本自动化
- COM接口外部控制
- 命令行批量执行+结果文件(.csv)解析

**FMI (Functional Mockup Interface) 跨工具统一标准**：

| 特性 | 说明 |
|---|---|
| **标准** | Modelica Association免费标准 v3.0.2 |
| **容器** | FMU = ZIP(XML元数据 + C代码 + 二进制) |
| **模式** | Model Exchange / Co-Simulation / Scheduled Execution |
| **支持** | 280+工具(Simulink/Dymola/OpenModelica/SystemVue/Mworks) |
| **顾问** | 波音/空客/Bosch/西门子/MathWorks/VW/Volvo |
| **分层标准** | FMI-LS-DAE(arXiv:2606.22544)/FMI-LS-BUS/FMI-LS-XCP等 |

```
Simulink .slx ──→ FMU导出 ──┐
MWorks .mo ────→ FMU导出 ──┤──→ 统一FMU容器 → fmpy库提取参数+执行仿真
SystemVue ─────→ FMU导出 ──┘
```

**FMI Python库(fmpy)用法**：
```python
from fmpy import read_model_description, simulate_fmu
md = read_model_description("fuse_model.fmu")
# md.modelVariables → 全部参数/输入/输出变量
# 按causality分类: parameter/input/output/local
for var in md.modelVariables:
    print(var.name, var.causality, var.type, var.unit)
# 执行仿真
result = simulate_fmu("fuse_model.fmu", stop_time=10.0)
# result → 字典{变量名: numpy数组}
```

- SimulinkInterface: https://github.com/Mukund-Iyer/SimulinkInterface
- FMI Standard: https://fmi-standard.org/ / fmpy: https://github.com/CATIA-Systems/fmpy
- FMI-LS-DAE: arXiv:2606.22544
- MWorks.SDK: https://www.tongyuan.cc/docs/sysplorer/

### 1.4 涉密信息识别与文本脱敏

**核心问题**：识别引信型号代号/战术性能指标/作战场景等敏感信息并脱敏。**复用场景1的三级级联+分层算子架构**，替换领域组件。

| 级 | 方法 | 抓什么 | 优势 |
|---|---|---|---|
| 1 | 规则/正则 | 引信型号代号格式、密级标识 | 零样本、可审计 |
| 2 | 自定义军事NER | 战术性能数值、装备参数 | 上下文感知 |
| 3 | LLM语义识别 | 作战场景描述、意图级敏感 | 捕获语义级敏感 |

| 敏感实体 | 脱敏算子 | 语义保留度 | 对微调影响 |
|---|---|---|---|
| 引信型号代号 | **伪名化**(FUSE_01确定性映射) | 高(保共指一致性) | 极小 |
| 战术性能数值 | **泛化为区间**(≥5V→[4,6)V) | 中高(保量级分布) | 小 |
| 作战场景描述 | **合成替换**(等价虚构场景) | 高(保语义结构) | 小 |
| 设计参数名/接口定义 | **保留**(非敏感) | — | —(微调必需) |

> **复用Presidio V2框架**，替换Recognizer为引信领域NER。SurrogateShield(arXiv:2606.29567)验证此架构F1≈98.87%。

## 2. ②结构化转化

### 2.1 设计技术要求参数化

**核心问题**：把5大部分的设计要求参数化为 `{param, op, value, unit, type, section}` 条目。

| 方案 | 代表方法 | 准确率 | 标注成本 | 可解释性 | 适用场景 |
|---|---|---|---|---|---|
| **a)规则/正则+模板** | 自定义DSL、spaCy ruler | 高(格式固定>95%) | 低 | 极高(可审计) | "≥5V""≤3s"等模式化表述 |
| **b)预训练模型微调NER** | RoBERTa-wwm+CRF | 中高(F1 85-92%) | 中高 | 中 | 术语边界模糊、多义词 |
| **c)生成式UIE/指令IE** | UIE、DeepKE、GoLLIE | 中高 | 低(少样本) | 中 | schema多变、低资源 |
| **d)通用LLM抽取** | Qwen2.5/DeepSeek few-shot→JSON | 中(zero)/高(few) | 极低 | 低(黑盒) | 冷启动、原型验证 |

**六性参数化映射**（场景2特有）：

| 六性 | GJB标准 | 典型参数化条目 |
|---|---|---|
| 可靠性 | GJB 450A | `{param:MTBF, op:≥, value:10000, unit:h, type:质量, section:通用质量特性}` |
| 维修性 | GJB 368A | `{param:MTTR, op:≤, value:0.5, unit:h}` |
| 测试性 | GJB 2547 | `{param:故障检测率, op:≥, value:95, unit:%}` |
| 安全性 | GJB 900 | `{param:安全距离, op:≥, value:50, unit:m}` |
| 保障性 | GJB 3872 | `{param:备件满足率, op:≥, value:90, unit:%}` |
| 环境适应性 | GJB 4239 | `{param:工作温度, range:[-40,70], unit:℃}` |

**推荐**：**规则兜底 + RoBERTa-wwm微调主力 + LLM处理长尾/校验** 的三层pipeline。**与场景1共用参数化栈**。

**关键论文**：UIE(arXiv:2203.12277) / GoLLIE(arXiv:2310.03668) / ChatGPT-IE评测(arXiv:2304.11633)

### 2.2 SysML 九视图结构化抽取

**核心问题**：从pyEcore解析出的原始模型元素，按九视图分类提取关键结构化数据。

**抽取结构**：

```
SysML九视图
├─ 需求视图(REQ)     → {id, text, type, priority, derived_from, satisfied_by[]}
├─ 任务场景视图(UC)  → {id, name, actors[], included_actions[]}
├─ 工作流程模型(ACT) → {id, name, inputs[], outputs[], control_flow[], object_flow[]}
├─ 时序交互视图(SD)  → {id, participants[], messages[], sequence_order[]}
├─ 状态行为视图(STM) → {id, state_name, entry_action, exit_action, transitions[{source, target, guard, trigger}]}
├─ 产品组成模型(BDD) → {id, name, type, attributes[], operations[], composition[{parent, child, multiplicity}]}
├─ 接口视图(IBD)     → {id, source_port, target_port, interface_type, direction, protocol}
├─ 功能分配模型(ACT+) → {function_id, allocated_to_block_id, allocation_type}
└─ 参数视图(PAR)     → {id, constraint_expr, parameters[{name, value, unit}], context_block}
```

**SysML元模型标签映射**：

| SysML标签 | 视图归属 | 提取字段 |
|---|---|---|
| `«Requirement»` | 需求视图 | Id, Text, Priority |
| `«Block»` | 产品组成模型 | Name, Attributes, Operations |
| `«ConstraintBlock»` | 参数视图 | Constraint Expression, Parameters |
| `Activity` | 工作流程/功能分配 | Name, InputPins, OutputPins, Partitions |
| `State` | 状态行为视图 | Name, Entry, Exit, Transitions |
| `«FlowPort»`/`«FlowSpecification»` | 接口视图 | Direction, Type |
| `«satisfy»` | 跨视图关系 | Source(需求), Target(Block/活动) |
| `«allocate»` | 跨视图关系 | Source(活动), Target(Block) |
| `«verify»` | 跨视图关系 | Source(需求), Target(测试用例) |

**关键论文**：Fu et al. (IEEE Access 2021, DOI:10.1109/access.2021.3115165) — SysML模型图构建，将模型文件转为跨产品图。

### 2.3 仿真参数与行为抽取

**核心问题**：从仿真模型提取输入参数、输出轨迹、阈值约束。

**抽取结构**：

```
仿真模型
├─ 输入参数: {param_name, value, unit, min, max, source_block, causality:parameter}
├─ 输出轨迹: {signal_name, time_series[], unit, sample_rate, causality:output}
├─ 阈值约束: {constraint_name, threshold, tolerance, actual_max, actual_min}
├─ 模块结构: {block_name, block_type, inputs[], outputs[], parameters{}}
└─ 仿真元数据: {solver, step_size, duration, tool, fmi_version}
```

**FMI统一提取**（推荐路径）：

| 数据类型 | FMI/FMU来源 | 提取方法 |
|---|---|---|
| 参数 | modelVariables[causality=parameter] | `read_model_description()` |
| 输入 | modelVariables[causality=input] | `read_model_description()` |
| 输出 | modelVariables[causality=output] | `read_model_description()` |
| 输出轨迹 | 仿真执行结果 | `simulate_fmu()` |
| 模块结构 | modelStructure | `md.modelStructure` |

### 2.4 要求→实现映射构建

**核心问题**：构建设计要求→SysML→仿真的全链路追溯关系，支撑RTM和覆盖性检测。

**映射关系结构**：

```
设计技术要求条目
    │
    ├─ «satisfy» → SysML需求视图条目
    │                ├─ «deriveReqt» → 派生需求
    │                ├─ «allocate» → 功能分配模型(子系统)
    │                │                ├─ 「实现于」 → 产品组成模型(部件)
    │                │                └─ 「验证于」 → 仿真模型(模块)
    │                └─ 「约束于」 → 参数视图(约束方程)
    └─ «verify» → 仿真输出(验证结果)
```

**方案对比**：

| 方案 | 原理 | 覆盖率 | 可解释性 | 工具依赖 |
|---|---|---|---|---|
| **SysML原生追溯** | 提取«satisfy»/«verify»/«allocate»关系 | 取决于建模规范性 | 极高 | pyEcore |
| **NLP追溯链恢复** | 语义相似度匹配 | 70-85%(工业实践) | 中 | T-SimCSE/BERT |
| **LLM语义对齐** | GPT跨模型语义匹配 | 中高 | 低 | Qwen2.5 |
| **Neo4j图存储** | 关系图查询 | — | 高(可视化) | Neo4j |

**关键论文**：
- T-SimCSE (arXiv:2603.11800, 2026): 对比预训练追溯链恢复，10个公开数据集
- Wheaton & Herber (arXiv:2410.21288, 2024): INCOSE SysML元模型，需求嵌入系统模型
- Li et al. (arXiv:2508.16181, 2025): LLM辅助SysML语义对齐
- Guo et al. (arXiv:2405.10845, 2024): 需求追溯NLP方法综述

**推荐**：SysML原生追溯为主 + NLP追溯链恢复补强 + LLM语义对齐处理长尾 + Neo4j存储映射图。

### 3.3 检测点1——设计技术要求 ↔ 总体方案覆盖性矛盾

**核心问题**：某条功能/性能要求在 SysML 九视图中无对应元素——要求→实现断裂。

**三层覆盖检测**：

| 层 | 检测什么 | 方法 | 示例 |
|---|---|---|---|
| **L1 功能覆盖** | 功能要求 → 功能分配模型(ACT+) | SysML«satisfy»关系 + NLP匹配 | 要求"电磁解保"但ACT+无对应活动 |
| **L2 性能覆盖** | 性能要求 → 参数视图(PAR) | 参数名匹配 + 约束方程存在性 | 要求"引爆阈值≥5V"但PAR无threshold约束 |
| **L3 接口覆盖** | 接口要求 → 接口视图(IBD) | 接口类型/方向匹配 | 要求"RS422"但IBD无RS422端口 |

**NLP追溯链恢复方法**：

| **LLM语义对齐** | GPT/Qwen做跨模型语义匹配 | few-shot示例 | 处理长尾/变体(arXiv:2508.16181) |
| **VSM/LSI/LDA** | 传统信息检索方法 | 无需标注 | 基线方法，召回较低 |

### 3.4 检测点2——静态视图参数 ↔ 动态仿真行为冲突

**核心问题**：SysML参数视图的阈值与仿真输出的实际行为超差。**这是场景2最核心的检测点**。

**三层检测**：

| 层 | 检测什么 | 方法 | 示例 |
|---|---|---|---|
| **L1 阈值比对** | 设计阈值 vs 仿真实际值 | 参数名归一化+数值直接比+容差检查 | 设计≥5V，仿真触爆4.2V → 冲突 |
| **L2 轨迹约束** | 设计约束范围 vs 仿真输出轨迹 | 轨迹极值/稳态值 vs 约束边界 | 设计温度≤70℃，仿真峰值82℃ → 冲突 |
| **L3 行为一致性** | SysML状态机 vs 仿真状态序列 | 状态转移序列匹配 + 形式化验证 | SysML"安全→解保→引爆"，仿真出现"安全→引爆"跳转 |

**形式化验证补强**（场景2新增，场景1没有）：

| 工具 | 原理 | 适用模型 | 能力 | 许可 |
|---|---|---|---|---|
| **Simulink Design Verifier** | SMT(可满足性模理论)求解器 | Simulink/Stateflow | 属性证明+反例生成+测试用例生成 | 商业(MathWorks) |
| **Modelica_Requirements** | 仿真中嵌入形式化需求约束块 | Modelica(MWorks/OpenModelica) | 仿真时自动评估需求满足度 | 开源(GitHub) |
| **PVS-Simulink** | PVS形式化规范+Simulink连续模型协同验证 | Simulink | CPS协同验证 | 开源 |
| **Eclipse OCL** | OMG OCL约束语言 | SysML/UML(EMF) | 模型良构性检查 | 开源(EPL 2.0) |

**Modelica_Requirements用法**（开源，推荐用于MWorks场景）：

```modelica
within FuseDesign.Requirements;
block ThresholdCheck
  parameter Real design_threshold = 5.0 "设计引爆阈值(V)";
  parameter Real tolerance = 0.5 "容差(V)";
  Real actual_voltage "仿真实际电压";
  Boolean satisfied;
equation
  satisfied = actual_voltage >= (design_threshold - tolerance);
  // 仿真时自动评估，不满足则标记
end ThresholdCheck;
```

**两路互补+形式化三路架构**（场景2新增形式化路线）：

| 路线 | 实现 | 原理 | 覆盖 | 优势 |
|---|---|---|---|---|
| **规则库数值比对** | 参数归一化+容差检查 | 设计值vs仿真值数值直接比 | L1,L2(数值级) | 确定性高、可解释、可审计 |
| **LLM语义判定** | Qwen2:7b本地直判 | 语义级理解参数对应关系 | L3(行为级)+补充 | 灵活、覆盖规则盲区 |
| **形式化验证** | SDV/Modelica_Requirements/OCL | SMT求解+约束满足+属性证明 | L3(属性级) | 数学证明、可穷举 |

### 3.5 检测点3——跨视图指标传递断裂

**核心问题**：参数从需求视图→结构视图→行为视图→参数视图的传递链中出现数值丢失/篡改。

**参数传递链**：

```
需求视图(REQ)          结构视图(BDD)         行为视图(STM/ACT)      参数视图(PAR)
┌──────────┐          ┌──────────┐         ┌──────────┐          ┌──────────┐
│ 引爆阈值  │─derive──→│ 解保电路  │─allocate→│ 解保状态  │─constrain→│ V≥5     │
│ ≥5V      │  Reqt    │ 阈值参数  │         │ 转移条件  │          │          │
│ REQ_001  │          │ BDD_003  │          │ STM_002  │          │ PAR_001  │
└──────────┘          └──────────┘         └──────────┘          └──────────┘
```

**检测流程**：
1. 从Neo4j映射图提取参数传递链（`deriveReqt → allocate → constrain`）
2. 提取链条上每个节点的参数值
3. 逐节点比对：参数值是否一致传递
4. 发现值丢失/篡改/不一致 → 传递断裂

**规则库设计（引信版fuse_kb.json，参考medical_kb.json结构）**：

```json
{
  "L1_param_ranges": {
    "引爆阈值": {"normal_op": ">=", "normal_val": 5, "unit": "V",
                 "severity_high": [{"threshold": 4, "level": "HIGH"}]},
    "安全距离": {"normal_op": ">=", "normal_val": 50, "unit": "m",
                 "severity_high": [{"threshold": 30, "level": "CRITICAL"}]},
    "解保延时": {"normal_op": "<=", "normal_val": 3, "unit": "s",
                 "severity_high": [{"threshold": 5, "level": "HIGH"}]}
  },
  "L2_param_transfer_rules": [
    {"param": "引爆阈值",
     "transfer_chain": ["需求视图", "结构视图", "行为视图", "参数视图"],
     "conflict_if": "链条上任一节点值≠源节点值",
     "tolerance": 0.1,
     "severity": "HIGH",
     "detail_template": "参数{param}在{view}视图中值为{val}{unit}，与需求视图{src_val}{unit}不一致"}
  ],
  "L3_cross_view_rules": [
    {"name": "解保延时一致",
     "conditions": [{"view":"需求视图.解保延时","op":"==","val":"参数视图.解保延时"}],
     "tolerance": 0.1,
     "severity": "CRITICAL"},
    {"name": "引爆阈值×安全距离耦合",
     "conditions": [{"param":"引爆阈值","op":"≥","val":5,"unit":"V"},
                    {"param":"安全距离","op":"≥","val":50,"unit":"m"}],
     "constraint": "threshold * safety_factor >= distance / sound_speed",
     "severity": "CRITICAL"}
  ]
}
```

**约束传播验证**：
用Z3 Solver做约束满足性检查。如果参数视图的约束系统不可满足（UNSAT），说明存在参数矛盾——Z3返回反例证明。

**关键论文**：
- Lu et al. (IEEE TSMC 2021, DOI:10.1109/tsmc.2020.3048821, 22引用): MBSE工具链自动化参数值选择和验证
- Zerwas et al. (Systems 2022, DOI:10.3390/systems10060199, 21引用): 模型签名集成仿真到SysML
- Torres et al. (SoSyM 2020, DOI:10.1007/s10270-020-00834-1, 56引用): 跨域模型一致性检查SLR

### 3.6 校验运作机制（四阶段管道，复用场景1架构）

```
结构化条目库 + 映射关系图
    ↓
①抽取：SysML/仿真参数提取（只拆不判）

```

| 常见错误模式 | 历史评审缺陷台账 | 错误模式库→冲突检测规则 | ③校验检测规则补充 |
| 仿真经验 | 仿真参数调优经验 | 参数范围规则→L1规则库 | ③校验L1层规则来源 |

**方法论**（复用场景1）：多轮迭代 → 可解释诊断 → 专家校验 → 规则增强 → 模型反馈闭环。

### 5.3 知识图谱构建与约束验证

**核心问题**：构建引信设计领域知识图谱，用本体约束传播验证跨视图一致性。

**KG设计**：

```
节点：设计要求条目 / SysML元素(Block/Requirement/Constraint/Activity/State) / 
      仿真模块 / 参数 / GJB条文 / 引信型号
边：  SATISFY(要求→SysML需求)
      ALLOCATE(SysML功能→子系统)
      VERIFY(要求→仿真验证结果)
      CONSTRAIN(参数→约束方程)
      IMPLEMENT(SysML部件→仿真模块)
      DERIVE_REQT(需求→派生需求)
      CONFORMS_TO(条目→GJB条文)
      TRANSFER(参数→参数,跨视图传递)
```

**SysML→KG转换**：
- Fu et al. (IEEE Access 2021, DOI:10.1109/access.2021.3115165): SysML模型图构建方法
- Wardhana et al. (IJACSA 2020, DOI:10.14569/IJACSA.2020.0110415): SysML需求图→OWL本体

**SHACL约束验证**：
- Westermann et al. (arXiv:2506.10678, 2025): LLM+SHACL自动验证工程约束——将非形式化约束文本转为SHACL形状
- Oudshoorn et al. (arXiv:2507.12286, 2025): SHACL+OWL组合验证(封闭世界约束检查)

**设计本体桥接协同仿真**：
- Lu et al. (IEEE Systems J. 2019, DOI:10.1109/jsyst.2019.2911418, 22引用): **最直接相关**——MBSE工具链中的协同仿真设计本体，桥接SysML设计模型和协同仿真
- Gregory & Salado (INCOSE 2024, DOI:10.1002/iis2.13210, 17引用): 系统工程本体栈，分层OWL本体
- Dunbar et al. (Systems Eng. 2023, DOI:10.1002/sys.21662, 43引用): 本体语义集成驱动数字工程

**约束验证流程**：
1. 条目库+映射图实体链接到KG
2. KG本体定义约束（如"引爆阈值×安全距离×解保延时"物理耦合关系）
3. 约束传播推理检测违反领域知识的冲突
4. 记录推理路径（证据溯源）
