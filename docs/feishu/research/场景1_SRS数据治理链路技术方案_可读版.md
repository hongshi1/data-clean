## ① 标准化预处理

**目标**：把 >50TB 杂乱的 Word/PDF 军用 SRS 文档，变成统一格式、脱敏后的归一化结构化文档。

### 细粒度点 1：文档解析与版面分析

**问题**：SRS 文档来源以 Word 为主、PDF 为辅，排版复杂，含标题/段落/列表/表格/公式/图。需要把非结构化文档解析成结构化内容，为后续步骤提供干净输入。

**技术方案**：

**方案A：Word 原生直抽（python-docx）**
Word 的 .docx 本质是 OOXML 压缩包，段落样式、编号体系、表格对象都是原生结构化数据。用 `python-docx` 直接读取，不走 OCR，精度是所有方案的上限——零 OCR 误差，合并单元格通过 `gridSpan`/`vMerge` 原生保留。对于 .doc 旧格式，先用 `libreoffice --headless --convert` 转成 .docx。这是军用 SRS 的**主路径**，因为大量文档有 Word 源文件。

**方案B：MinerU 流水线（PDF 主引擎）**
对于只有 PDF 的文档，MinerU（arXiv:2409.18839, OpenDataLab）是目前最完善的开源方案。它是一条模块化流水线：`DocLayout-YOLO`（版面检测，arXiv:2410.12628，用合成数据增强泛化，是当前版面检测 SOTA）→ `YOLOv8`（公式检测）→ `UniMERNet`（公式识别，arXiv:2404.15254）→ `PaddleOCR`（中文 OCR）→ `StructEqTable`（表格识别）→ 阅读序排序后处理。输出 Markdown + JSON，社区活跃（PDF-Extract-Kit 9.8k★），可私有化部署。缺点是依赖 AGPL 组件（PyMuPDF），军用需法务评估。

**方案C：PaddleOCR PP-Structure（纯国产替代）**
如果 AGPL 不可接受，PP-Structure 是纯 Apache-2.0 的国产替代。它是一体化流水线：版面检测（11 类版面元素）+ 表格识别（输出 HTML）+ 中文 OCR，中文原生支持是所有方案里最强的，部署成熟（含 C++/Serving）。缺点是对超复杂合并/嵌套表头不如专用大模型。

**方案D：LayoutLMv3 / Nougat / GOT-OCR2.0**
LayoutLMv3（arXiv:2204.08387, ACM MM 2022）是多模态 Transformer，文本+版面+图像统一预训练，可做版面分类和 KIE，但中文需 LayoutXLM 或微调。Nougat（arXiv:2308.13418, Meta）面向英文学术 PDF，中文弱，不适用。GOT-OCR2.0（arXiv:2409.01704）是 580M 统一端到端 OCR-2.0，文本/公式/表格/图表一站式输出 markdown，中文良好，可作为轻量备选。

**推荐**：Word 走 python-docx 直抽（精度上限）；PDF 走 MinerU（DocLayout-YOLO + PaddleOCR）；AGPL 不可接受时用 PP-Structure 全栈替代。

### 细粒度点 2：表格抽取与结构化

**问题**：SRS 含三类核心表格——性能指标表（参数名-指标值-约束，多级表头）、接口定义表（合并单元格多）、数据字典（多列表）。最大难点是合并单元格和无框线表格。

**技术方案**：

**分层策略（精度优先，由易到难）**：

**第1层：Word 原生直抽**——如果文档是 .docx，`python-docx` 遍历 `document.tables`，每个 cell 天然含合并信息，可还原为二维矩阵并标注合并区域。无损、零 OCR 误差、合并单元格精确、可区分嵌套表。这是性价比最高的路径，覆盖大多数 SRS。

**第2层：Camelot（PDF 有框线表）**——Camelot 的 lattice 模式基于线框检测，对有明确框线的 PDF 表格精度极高、速度快、零模型依赖、中文无损（直接取文本层）。缺点是依赖线框，无框线表（stream 模式靠空白对齐）易错乱，合并单元格还原弱。

**第3层：PaddleOCR 表格 / StructEqTable（扫描件/无框线）**——PaddleOCR 表格识别是端到端结构识别，输出 HTML，含合并单元格，中文场景工程首选。StructEqTable 基于 InternVL2-1B 视觉大模型，输出 LaTeX/HTML/Markdown，中文较好，是 MinerU 1.0 默认表格引擎。

**第4层：UniTable / Table Transformer（极复杂兜底）**——UniTable（arXiv:2403.04822, Georgia Tech）是自监督预训练统一框架，结构+内容+box 三任务统一，在多个大规模数据集上 SOTA。Table Transformer（arXiv:2110.00061, 微软）基于 DETR，用 PubTables-1M（100 万表）训练，解决了过分割问题，是行业标准基线。两者英文训练为主，中文需配 PaddleOCR 做文本填充并微调。

**效果参考**：Word 直抽是精度上限（无损）；Camelot 对有框线表近无损；PaddleOCR 表格在中文场景工程可用；UniTable 在多个 benchmark 上 SOTA 但需中文适配。

**推荐**：分层策略——Word 直抽 > Camelot(有框线) > PaddleOCR/StructEqTable(无框线) > UniTable(兜底)。LlamaParse 等商用 API 因数据出域在军用场景排除。

### 细粒度点 3：章节切分（对齐 GJB 7 大块）

**问题**：GJB 438C-2021 规定 SRS 含固定章节结构——功能需求/性能指标/接口定义/数据字典/运行环境/安全保密/验收准则七大块。需要自动切分章节，并把表格按"最近章节"归属挂载。

**技术方案**：

**方案A：规则法（编号正则 + GJB 锚点词典）**
GJB 模板高度规范，章节编号体系稳定（如 `3.2.1` 三级条目）。用正则 `^\d+(\.\d+)*\s*[标题]` 匹配章节号，结合 Word heading 样式/字体特征，建立"章/节/条"三级树。再用预置的七大块标题词典（功能需求/性能指标/...）做章节号→语义块映射。**规则法可达 95%+ 切分准确率**，且完全可审计——每条切分都能给出依据（章节号/锚点匹配证据），满足军用文档治理审计要求。

**方案B：版面模型法（LayoutLMv3 / DocLayout-YOLO 角色分类）**
对无编号或编号异常的子标题，用版面模型做 title/section-header 角色分类二次判别。抗排版扰动、泛化好，但需标注微调、中文需调。

**方案C：LLM 法（DocOwl / Qwen 章节理解）**
用文档理解大模型直接给章节语义，鲁棒、可处理变体，但重、可解释性弱、保密受限。仅用于离线抽检/复核。

**推荐**：规则法为主（95%+ 可审计）+ 版面模型兜底 + LLM 仅离线复核。

### 细粒度点 4：涉密信息识别与文本脱敏

**问题**：SRS 含密级标识（机密★/秘密★）、装备型号代号、战术性能指标、作战场景描述等敏感信息。需要脱敏后才能用于微调，但脱敏不能破坏语义——否则模型学不到东西。

**识别技术（三级级联）**：

| 级 | 方法 | 抓什么 | 效果 |
|---|---|---|---|
| 1 | 规则/正则 | 密级标识、型号代号格式 | 零样本、可审计、召回稳 |
| 2 | 自定义军事NER | 装备型号、部队番号、战术指标 | 识别未登录实体、上下文感知 |
| 3 | LLM语义识别 | 作战场景描述、意图级敏感 | 捕获规则/NER遗漏的语义敏感 |

> SurrogateShield（arXiv:2606.29567）验证此三级级联架构在 22 类 PII 上 **F1≈98.87%**。

**脱敏技术（分层算子，关键设计：不一刀切）**：

| 敏感实体 | 算子 | 语义保留 | 效果 |
|---|---|---|---|
| 密级标识 | 删除(redact) | 低 | 无语义价值，必须清除 |
| 装备型号代号 | 伪名化(EQUIP_01确定性映射) | 高(保共指一致性) | 对微调几乎无损 |
| 战术性能数值 | 泛化为区间(≥50km→[40,60)km) | 中高(保量级分布) | 保训练信号分布 |
| 作战场景描述 | 合成替换(生成等价虚构场景) | 高(保语义结构) | BERTScore +13.26pp |
| 接口参数名/数据字典 | 保留(非敏感) | — | 微调必需，不可脱敏 |

> **关键实证**：SurrogateShield 证明合成替换 vs 占位符遮罩，BERTScore 从 81.59% 提升至 94.85%（**+13.26pp**），且 100 条对抗查询中对手 LLM 无法恢复原始值。
> 
> **反面警示**：纯 DP-SGD 在 1B-3B 小模型上 F1 仅 0.19-0.28（arXiv:2606.28479），不足以支撑可用性，不应作为唯一手段。

**推荐工具**：Presidio V2（开源、可私有化部署、YAML no-code 配置、支持 spaCy/Stanza/Transformers/GLiNER 外接、replace/redact/hash/mask/encrypt/custom/surrogate 全套算子）。Google DLP 功能更全（含 k-匿名风险分析）但是云服务，仅作架构参考。

**推荐策略**：伪名化/合成替换保语义 + DP-SGD 训练期兜底防记忆化 + canary 审计验证。

## ② 结构化转化

**目标**：把归一化 SRS 的正文段落和表格，拆成参数化需求条目 `{参数名, 运算符, 数值, 单位, 条目类型, 引用关系}`，构建条目库和引用关系图。

### 细粒度点 1：领域 NER 与参数抽取

**问题**：SRS 正文有大量这样的表述——"系统响应时间应≤50ms"、"接口采用RS422协议"、"支持8路输入"。需要抽成 `{param:响应时间, op:≤, value:50, unit:ms, type:性能}`。本质是实体+关系+数值属性的联合抽取。

**技术方案**：

**方案A：规则/正则+模板（高召回+可审计）**
针对 GJB 文档高规范化的"参数+运算符+数值+单位"句式，编写正则模板库：`(?P<param>...)(?P<op>[≤≥<>≈])(?P<val>\d+\.?\d*)\s*(?P<unit>ms|Mbps|路|℃)`。格式固定时**准确率 >95%**，零模型依赖，每条抽取可给出依据，满足军工可审计要求。缺点是仅覆盖已知模式，泛化弱。

**方案B：预训练模型微调 NER（处理边界模糊）**
用 RoBERTa-wwm-ext + CRF 做序列标注，标签集 `[PARAM][OP][VALUE][UNIT][PROTO]`，在 GJB 语料上做领域续训（MLM）。**F1 85-92%**，能处理术语边界模糊和多义词。缺点是需数百-千条标注语料。

**方案C：生成式 UIE / 指令 IE（低资源场景）**
UIE（arXiv:2203.12277, ACL 2022）提出 Structured Extraction Language (SEL) + Structural Schema Instructor (SSI)，将 NER/RE/EE 统一为 text-to-structure 生成。可用 SSI 定义 `schema: [参数名, 运算符, 数值, 单位]`，**一次生成完整参数条目**，天然支持联合抽取。DeepKE（arXiv:2201.03335, EMNLP 2022 Demo, zjunlp）是开源工具包，含中文预训练权重，开箱即用。GoLLIE（arXiv:2310.03668, ICLR 2024）用标注指南（Python 类形式的 schema）微调 LLM，**零样本迁移到未见 IE 任务**，消融实验证明详细 guideline 是关键——可把 GJB 438C 的参数书写规范写成 guideline。

**方案D：通用 LLM 抽取（冷启动）**
Qwen2.5/DeepSeek few-shot → JSON 输出，标注成本极低，适合冷启动和原型验证。**但 Li et al.（arXiv:2304.11633）证实 LLM 抽取过度自信、校准低**，解释质量高但准确率不稳定，必须人工复核。

**推荐**：三层 pipeline——规则兜底（高召回+可审计）+ RoBERTa-wwm 微调主力（处理边界模糊）+ LLM 处理长尾/校验（GoLLIE 风格 guideline 校验）。

### 细粒度点 2：表格结构化与字段映射

**问题**：三类表格（性能指标表/接口定义表/数据字典）表头固定但术语写法不统一——表格里写"响应时间"，正文写"反应时间"，数据字典写"时延"。需要映射到统一 schema 并做术语归一化。

**技术方案**：

**方案A：规则模板匹配表头**
GJB 表格表头相对固定，按性能指标表/ICD表/数据字典表各建模板，正则匹配表头列名。准确率高，但跨表 schema 对齐弱（硬编码）。

**方案B：TableLlama 列类型推断**
TableLlama（arXiv:2311.09206, NAACL 2024）是首个开源表格通才模型，用 LongLoRA 微调 Llama2-7B 处理长表格。在 8 个域内任务中 **7 个达到/超过 SOTA**，6 个域外数据集**提升 5-44 分**。开源可私有化部署，符合军工数据不出域要求。

**方案C：LLM 表格理解（Table Meets LLM）**
Table Meets LLM（arXiv:2305.13062, WSDM 2024, Microsoft）系统评测了 LLM 对结构化表格的理解，发现**输入格式、内容顺序、分区标记显著影响性能**。关键结论：把表格序列化为 Markdown 格式 + 标注关键值，可显著提升 LLM 表格对齐准确率。TAMA（arXiv:2501.14693, ACL 2025）进一步发现小学习率+少数据即能超越 GPT-3.5/4。

**方案D：术语归一化（同义词典+向量）**
构建军工参数同义词典（响应时间=反应时间=时延=延迟），用实体链接+向量相似度做表-文术语对齐。这是核心难点——同一参数在不同位置写法不同。

**推荐**：规则模板匹配表头 + TableLlama 列类型推断 + 同义词典+向量归一化。

### 细粒度点 3：交叉引用解析与关系建模

**问题**：SRS 正文有大量交叉引用——"性能指标见3.2节"、"如表4所示"、"参见GJB 438C第5.3条"。需要解析引用指向，构建条目间引用关系图，支撑需求可追溯性矩阵(RTM)。

**技术方案**：

**方案A：正则解析（主路径）**
GJB 编号高度规范（`(\d+\.)+\d+` 章节号、`表\s*\d+`/`图\s*\d+` 表图号），正则可覆盖 **90%+ 显式引用**。建立"章节号→条目ID""表号→表条目ID"索引表后即可精确解析指向。覆盖率最高、可审计。

**方案B：依存句法分析（补强）**
HanLP/LTP 提供中文依存解析，可识别"性能指标见3.2节"中"见"的宾语"3.2节"及其主语"性能指标"，建立主语→引用→目标的三元关系。处理引用嵌在句中的情况。

**方案C：LLM 引用抽取（隐式引用）**
对隐式引用（"按前述规定执行""同上级要求"）用 Qwen few-shot 抽取，输出 `{source_span, relation, target}` JSON。仅作正则结果的校验/补全。

**方案D：Neo4j 关系图存储**
Neo4j 建模——节点（需求条目/参数/接口/表/外部标准），边（REFERS_TO/DEFINED_IN/VERIFIED_BY/DEPENDS_ON）。Cypher 支持多跳溯源查询："某性能指标依赖哪些接口与参数""哪些需求引用了 GJB 438C 第5.3条"。**天然支撑 GJB 5000B 的需求可追溯性矩阵(RTM)**。

**推荐**：正则解析为主（90%+覆盖）+ HanLP 依存补强 + Qwen 隐式引用 + Neo4j 存储。

## ③ 一致性校验

**目标**：在结构化条目库上检测 4 类矛盾，标记冲突不删数据——冲突样本本身是高价值微调数据。

### 细粒度点 1：检测点1——性能指标正文↔指标表数值矛盾

**问题**：正文叙述"响应时间≤50ms"，但性能指标表写"≤100ms"。同一参数在正文和表格中数值不一致。

**技术方案**：**规则库 L1b 多字段联合约束**
从正文 NER 抽取 `{param:响应时间, op:≤, value:50, unit:ms, source:§3.2}`，从表格解析 `{param:响应时间, op:≤, value:100, unit:ms, source:性能指标表}`。术语归一化后比对：同参数、同单位、但值 50≠100 → 命中冲突。这是数值级直接比对，规则库确定性高、可解释。

**效果参考**：仓库 `medical_operators.py` 的 `LabDiagnosisConflictFilter` 在 MedTVT 10000 样本上检出 **1444 条冲突**，与知识库规则完全对齐。

---

### 细粒度点 2：检测点2——接口定义正文↔接口表字段矛盾

**问题**：正文写"接口采用RS422协议"，接口定义表写"RS232"。协议类型/字段类型/字节序矛盾，不是数值比对，是语义级矛盾。

**技术方案**：**LLM 直判**
RS422 vs RS232 不是数值比，是语义矛盾——规则库难以穷举所有协议对。把正文接口描述和接口表字段喂给 LLM（Qwen2:7b 本地 Ollama），prompt 要求判断一致性并输出 JSON。LLM 能理解"RS422 是差分串行协议，RS232 是单端串行协议，二者不兼容"这种领域语义。

**效果参考**：仓库 `unified_operators.py` 的 `_llm_detect_medical` 已验证 LLM 直判路线可行，JSON 输出含 `{consistent, conflicts, explanation}`。

---

### 细粒度点 3：检测点3——数据字典↔正文术语不一致

**问题**：正文用"反应时间 ms"，数据字典定义"响应时间 s"。术语漂移 + 单位换算后数值不符。

**技术方案**：**规则库 L1a 字段校验 + L2 术语语义对齐**
两步走：①术语归一化——用同义词典把"反应时间"映射到"响应时间"；②单位换算后比数值——ms→s 换算后比。如果归一化后参数名一致但单位换算后数值不符，则冲突。术语归一化用词典+向量相似度双保险。

---

### 细粒度点 4：检测点4——跨条目参数矛盾

**问题**：功能要求写"支持5路输入"，性能要求写"支持8路输入"。同一参数在不同条目取值矛盾。

**技术方案**：**规则库 L3 多要素协同约束求解**
这是最复杂的检测点——需要理解"输入路数"这个参数在功能条目和性能条目里是同一个东西。用引用关系图(Neo4j)找到跨条目引用同一参数的关系，然后比对取值。L3 层用约束求解器(Z3 Solver)检测违反领域知识的参数组合矛盾。

**效果参考**：仓库 `medical_operators.py` 的 `CrossLabConsistencyFilter` 已验证 L3 多要素协同检测路线——多指标组合同时满足条件时提示综合征，迁移到 SRS 即"多条目组合参数矛盾时提示冲突"。

---

### 校验运作机制（四阶段管道）

```
结构化条目库
    ↓
①抽取：NER 只拆不判（unified_operators.py:6）
    ↓
②检测：规则库三层(L1→L2→L3) + LLM 直判，两路互补
    ↓
③解释：定位冲突到具体条目ID/章节位置
    ↓
④置信度：根据冲突严重度+检测方法+置信度，打 high/medium/low
```

**关键设计**：**只标记不删数据**（`process_single` 恒返回 True）。冲突挂到 `stats` 上出报告——冲突样本后续当微调数据，教模型"这种矛盾要报出来"。

## ④ 质量评估

**目标**：给治理后的数据集打分分级，决定哪些能直接微调、哪些需人工复核、哪些退回重做。

### 细粒度点 1：质量评估维度（7维，对齐 SRS/GJB）

| 维度 | 定义 | SRS 场景具体指标 |
|---|---|---|
| **完整性** | 必需内容是否齐全 | GJB 七大块覆盖；字段缺失率 |
| **一致性** | 内部无矛盾 | 4 类冲突检测通过率 |
| **合规性** | 符合标准 | GJB 438C-2021 条目对标率 |
| **准确性** | 参数值/术语正确 | 术语库命中率；参数值合理性 |
| **可用性** | 脱敏后能否微调 | 脱敏后 BERTScore 语义保持度 |
| **隐私性** | 脱敏彻底度 | 残留敏感实体数；k-匿名 |
| **多样性** | 覆盖分布均衡 | 装备类型/场景分布均衡度 |

---

### 细粒度点 2：评估工具选型

**Great Expectations（规则驱动底座）**
Apache-2.0 开源，声明式 Expectation（值域/非空/唯一性/分布），300+ 内置规则，Data Docs 可视化报告。适合完整性/一致性/合规性的自动化校验——GJB 七大块是否齐全、4 类冲突是否为 0、GJB 对标率，天然是规则检查。仓库已验证。

**Cleanlab（标签噪声检测）**
基于置信学习（Confident Learning，arXiv:1911.00068, JAIR 2021），估计噪声标签与真实标签的联合分布，自动找标签错误。**理论保证可证一致**，模型无关。在 MNIST 上都能找出"presumed error-free"数据集的标签错误。仓库在 GunsAndWeapons 数据上验证**召回率 100%**（但精确率低）。适合 SRS 微调数据的指令-响应标签质量审计。

**TADS（任务感知数据选择）**
arXiv:2602.05251，内在质量+任务相关度+分布多样性三因子可学习价值函数。**仅用 36% 数据超越全量基线 +1.0%**。适合数据集筛选和多样性评估。

**UniFilter（多模态质量分类器）**
arXiv:2510.15162, EMNLP 2025，半合成四级质量标注训练统一分类器。适合多模态数据质量打分。

**LLM 抽样复核**
用 LLM 作为评判对数据质量打分/分级，灵活、可处理语义级质量，但成本高、需校准防偏。参考 DataGovBench（arXiv:2512.04416）的 Planner-Executor-Evaluator 架构。仅抽样进行，不作为全量主评估。

---

### 细粒度点 3：质量分级标准

**评分模型**：加权综合分 = w1·完整性 + w2·一致性 + w3·合规性 + w4·准确性 + w5·可用性 + w6·隐私性。**隐私性为一票否决项**（残留敏感直接降 C）。

| 等级 | 分数 | 判定条件 | 用途 |
|---|---|---|---|
| **A级** | ≥85 | 七大块齐全、4类冲突0、GJB对标率≥95%、脱敏语义保持≥90%、无残留敏感 | 直接微调 |
| **B级** | 70-84 | 个别字段缺失/少量冲突(≤3)/对标率80-95%/语义保持75-90% | 人工复核后可用 |
| **C级** | <70 | 大块缺失/冲突>3/对标率<80%/语义损失大/残留敏感 | 退回重做 |

**分层评估架构**：

```
数据集
  ├─ L1规则层(GX)：完整性+一致性+合规性 → 自动评分
  ├─ L2标签层(Cleanlab)：标签置信度 → 噪声标记
  ├─ L3语义层(LLM抽样)：合规性/准确性复核 → 抽样报告
  ├─ L4隐私层(Presidio复检+k匿名)：残留敏感 → 一票否决
  └─ 汇总 → 评分模型 → A/B/C分级 → 路由处置
```

## ⑤ 知识融合

**目标**：把 GJB 标准条文和专家经验挂载到条目上，让微调数据集带知识标签——教模型不只"怎么写SRS"，还教"为什么这么写"。

### 细粒度点 1：GJB 标准条文结构化

**问题**：GJB 438C-2021 标准条文是 PDF/Word，需要转成可执行规则，用于合规比对和冲突判定。

**技术方案**：

**Easy Dataset（文档→结构化规则）**
Easy Dataset（arXiv:2507.04009）是开源工具，流程：上传标准文档 → 解析分块 → LLM 提取规则 → 输出结构化规则库。仓库已克隆验证。用法：上传 GJB 438C-2021 → Easy Dataset 解析分块 → LLM 提取"功能要求不含参数信息""各条目之间参数不能存在矛盾"等准则 → 输出结构化规则库。

**SHACL 约束验证**
将武器装备本体属性约束转为 W3C SHACL 形状（Shape）定义，用 pySHACL 引擎自动校验字段格式/范围/类型。SHACL 是 W3C 标准，可审计。

**Great Expectations 规则集**
将本体约束转为 GE 的 Expectation 规则集，300+ 内置规则可复用。仓库已验证。

**技术路线**：
```
GJB标准文档 → Easy Dataset+LLM提取 → 结构化规则库
    → 转化为 SHACL形状 + GE规则集
    → 用于 ③校验规则基准 + ④合规性评估
```

---

### 细粒度点 2：专家经验显性化

**问题**：设计准则、评审经验、常见错误模式散落在专家脑中，是隐性知识。需要结构化采集，转为可执行规则和知识标签。

**技术方案**：

| 知识类型 | 来源 | 形式式化方法 | 用途 |
|---|---|---|---|
| 设计准则 | 专家经验/评审记录 | 规则模板→L3约束规则 | ③校验L3层规则来源 |
| 常见错误模式 | 历史缺陷台账 | 错误模式库→冲突检测规则 | ③校验检测规则补充 |
| 参数约束 | 领域知识("军用响应时间≤50ms") | 参数范围规则→L1规则库 | ③校验L1层规则来源 |
| 合规要求 | GJB条文+所内规范 | 条文→条目映射→合规标签 | ④合规性评估基准 |

**方法论**（`典型场景:90`）：多轮迭代 → 可解释诊断 → 专家校验 → 规则增强 → 模型反馈闭环。专家确认的新规则写回知识库，持续扩充规则覆盖。

---

### 细粒度点 3：知识图谱构建与约束验证

**问题**：构建 SRS 领域知识图谱，用本体约束传播验证条目间一致性。

**KG 在冲突检测中的真实角色**（`entity_research.md:80-110` 关键结论）：

> 标准 ontology（如 SNOMED CT）**没有显式"contradicts"矛盾边**。KG 的真实用法是：**规范化 + 关系推理**，配合 LLM 或嵌入做矛盾判断，不是直接查"矛盾边"。

**场景1的 KG 设计**：

```
节点：需求条目 / 参数 / 接口 / 表格 / GJB条文 / 装备型号
边：  DEFINED_IN(参数→数据字典)
      REFERS_TO(条目→条目/表/标准条文)
      VERIFIED_BY(需求→验收准则)
      CONSTRAINED_BY(参数→GJB条文)
      DEPENDS_ON(性能指标→接口定义)
```

**约束验证流程**：
1. 条目库实体链接到 KG（参数名→KG 节点，术语归一化）
2. KG 本体定义约束（如"口径×类型×重量"物理耦合关系）
3. 约束传播推理检测违反领域知识的冲突
4. 记录推理路径（证据溯源）

**关键论文**：
- KGDMC（ACM 2025, DOI:10.1145/3696410.3714813）：解耦 VAE 将每模态解耦为特定+不变特征空间，多粒度三元组置信度(MTC)从局部/全局邻居/全局路径三层评估事实自洽性。
- SNOMED CT + Neo4j（arXiv:2510.16899）：疾病/症状/药物建模为节点，"caused by"/"treats"为边，支持多跳推理。
- DEFAME：多模态事实核查引擎，记录推理路径。
