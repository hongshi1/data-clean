# R9: 可立项方向细化

> 基于 R1（7篇A类论文）+ R2（3大工具对比）+ R3（9类5层冲突分类体系），定义"面向多模态数据集治理的跨模态冲突检测框架"的具体研究方案。

---

## 一、研究方向定义

**题目**：面向多模态数据集治理的跨模态冲突检测框架——以医疗图文数据为验证场景

**一句话定位**：现有数据治理工具（Data-Juicer/CleanLab/Great Expectations）做多模态数据处理但不做跨模态冲突检测；现有冲突检测论文（FOIL-COCO/HalDec-Bench/DeFT）检测部分类型但不以数据治理为框架。本方向将两者结合，定义完整的冲突类型分类体系，设计检测算子库，构建benchmark，并集成到Data-Juicer。

**与现有工作的差异**：

| 维度 | 现有工作 | 本方向 |
|------|---------|--------|
| 框架 | 各论文各自定义部分冲突类型 | 统一9类5层分类体系 |
| 工具 | Data-Juicer只做CLIP score过滤 | 新增Conflict Detector算子，输出冲突报告而非keep/drop |
| 覆盖 | HalDec-Bench覆盖4类(仅幻觉)，DeFT覆盖1类(标签噪声) | 覆盖全部9类 |
| 目标 | "扔掉坏数据"(过滤) | "诊断数据问题"(检测+定位+解释) |
| Benchmark | FOIL-COCO/NewsCLIPpings各测一种 | 统一benchmark覆盖9类冲突 |

## 二、检测算子库设计

基于R3的9类冲突，设计9个检测算子。每个算子遵循统一接口：输入(图文对) → 输出(冲突报告)。

### 算子接口设计

```python
class ConflictDetector(Filter):
    """冲突检测算子基类——突破Data-Juicer的keep/drop范式"""
    
    def compute_stats_single(self, sample):
        """输出结构化冲突报告，而非标量分数"""
        conflicts = self.detect(sample)
        stats = sample.get(Fields.stats, {})
        stats["conflicts"] = conflicts  # 冲突列表
        stats["conflict_count"] = len(conflicts)
        stats["has_conflict"] = len(conflicts) > 0
        sample[Fields.stats] = stats
        return sample
    
    def process_single(self, sample):
        """恒返回True——标记不丢弃，产出检测报告"""
        return True
    
    def detect(self, sample) -> list[dict]:
        """子类实现：返回冲突列表
        每个冲突: {
            "type": "C1完全错配",
            "severity": "HIGH",
            "evidence": "CLIP score=0.12, 阈值0.2",
            "location": {"image_region": None, "text_span": None},
            "explanation": "图像与文本完全无关"
        }
        """
        raise NotImplementedError
```

### 9个具体算子

| 算子 | 冲突类型 | 检测原理 | 输入 | 输出 | 依赖模型 | 预期精度 |
|------|---------|---------|------|------|---------|---------|
| **PairingConflictDetector** | C1完全错配 | CLIP cosine相似度<θ₁(如0.2) | 图+文 | {type, score, severity} | CLIP/CheXzero | 高(粗筛) |
| **EntityMismatchDetector** | C2配对混淆 | 实体提取(NER)+交叉验证 | 图+文 | {type, entities, mismatch_list} | scispaCy+图像目标检测 | 中 |
| **LabelNoiseDetector** | C3标签噪声 | CLIP零样本分类概率 vs 给定标签 | 图+标签 | {type, predicted_label, confidence} | CLIP/DeFT | P/R≈85% (DeFT) |
| **EntityMissingDetector** | C4实体缺失 | 文本短语提取+图像目标检测(phrase grounding) | 图+文 | {type, missing_phrases, image_regions} | Owl-ViT/OwlV2 | 中(召回率) |
| **EntitySurplusDetector** | C5实体多余 | 图像AI推理结果 vs 文本NER结果交叉比对 | 图+文 | {type, unmentioned_diseases, ai_prob} | TorchXRayVision+CheXpert Labeler | 依赖AUC |
| **AttributeConflictDetector** | C6属性矛盾 | VLM细粒度推理：逐一验证文本属性描述 | 图+文 | {type, attribute, text_value, image_value} | GPT-4V/CheXagent | AUROC≈80% (HalDec) |
| **RelationConflictDetector** | C7关系矛盾 | 场景图生成+关系抽取+比对 | 图+文 | {type, relation, text_relation, image_relation} | 场景图模型 | 研究阶段 |
| **NegationConflictDetector** | C8否定矛盾 | 三态NER(肯定/否定/不确定)+冲突矩阵 | 图+文 | {type, disease, text_state, image_state, severity} | CheXpert Labeler+TorchXRayVision | 依赖κ和AUC |
| **InternalConflictDetector** | C9内部矛盾 | 文本内一致性检查(正文vs结论) | 文 | {type, positive_findings, conclusion_normal} | 规则/LLM | 高(规则可解释) |

### 算子优先级（按实现难度和价值排序）

**第一优先级（已有验证，可直接实现）**：
- C1 PairingConflictDetector → Data-Juicer已有CLIP filter，改为输出报告
- C8 NegationConflictDetector → 我们已验证（62冲突/20样本）
- C9 InternalConflictDetector → 我们已验证（4条报告内部矛盾）
- C5 EntitySurplusDetector → 我们已验证（42条图片↔报告结论冲突）

**第二优先级（技术积木存在，需组装）**：
- C3 LabelNoiseDetector → DeFT/CLIPCleaner已有方法
- C4 EntityMissingDetector → Data-Juicer已有phrase_grounding，改为输出冲突短语
- C6 AttributeConflictDetector → HalDec-Bench已评测VLM能力(AUROC 79.8)

**第三优先级（需新研究）**：
- C2 EntityMismatchDetector → 需NER+知识图谱
- C7 RelationConflictDetector → 需场景图+关系抽取

## 三、Benchmark构建方案

### 设计原则
- 覆盖全部9类冲突
- 混合合成冲突+真实冲突
- 支持单类型评测和整体评测
- 医疗领域为主，通用领域为辅

### 数据来源

| 冲突类型 | 合成冲突来源 | 真实冲突来源 | 规模目标 |
|---------|------------|------------|---------|
| C1完全错配 | NLMCXR报告+随机配对其他图 | — | 500对 |
| C2配对混淆 | 同患者不同次检查的图+报告交叉配对 | — | 200对 |
| C3标签噪声 | 随机翻转CheXpert标签 | Rafferty et al.发现的标签错误 | 1000样本 |
| C4实体缺失 | 从报告中删除某疾病mention | — | 500对 |
| C5实体多余 | TorchXRayVision阳性但报告未提及 | NLMCXR实测42条 | 500对 |
| C6属性矛盾 | 替换报告中的属性词(如"left"→"right") | — | 500对 |
| C7关系矛盾 | 替换关系描述(如"A导致B"→"B导致A") | — | 200对 |
| C8否定矛盾 | 将肯定句改为否定句 | NLMCXR实测12条 | 500对 |
| C9内部矛盾 | 在称正常的结论前加阳性描述 | NLMCXR实测4条 | 200对 |

### 评测指标

| 指标 | 说明 |
|------|------|
| Per-type Precision/Recall/F1 | 每类冲突的检测精度 |
| Overall F1 | 全部9类的综合F1 |
| False Positive Rate | 误报率（关键：冲突检测不能太多误报） |
| Localization Accuracy | 冲突定位精度（图像区域/文本短语的IoU） |
| Explanation Quality | 冲突解释质量（人工评估） |

### 与现有benchmark的对比

| Benchmark | 覆盖冲突类型 | 数据治理框架 | 规模 |
|-----------|------------|------------|------|
| FOIL-COCO | C6(foil, 1类) | 否(模型评估) | ~数千 |
| NewsCLIPpings | C1+C2(2类) | 否(虚假信息) | 大规模 |
| HalDec-Bench | C4+C6(4类幻觉) | 部分(curating) | 104.3K句 |
| **本benchmark** | **C1-C9(9类)** | **是(数据治理)** | ~4000对 |

## 四、Data-Juicer集成路径

### 现状（R2发现）

Data-Juicer 2.0的Filter算子遵循`compute_stats() → 阈值 → keep/drop`范式：
- `image_text_similarity_filter`：CLIP cosine → 标量 → 过滤
- `phrase_grounding_recall_filter`：Owl-ViT召回率 → 标量 → 过滤
- **不输出冲突类型、冲突位置、冲突原因**

### 改造方案

**Step 1: 新增ConflictDetector算子基类**
- 继承Filter但`process_single()`恒返回True（标记不丢弃）
- `compute_stats_single()`输出结构化冲突报告（非标量）
- 报告格式：`{conflict_type, severity, evidence, location, explanation}`

**Step 2: 实现9个具体算子**（按优先级分3批）
- 第1批：C1/C5/C8/C9（已有验证，改Data-Juicer现有算子+我们的算子）
- 第2批：C3/C4/C6（集成DeFT/CLIPCleaner/HalDec-Bench方法）
- 第3批：C2/C7（新研究）

**Step 3: 新增ConflictReportExporter**
- 汇总所有算子的冲突报告
- 输出JSON/HTML格式的数据集质量报告
- 支持按冲突类型/严重度/样本ID过滤查看

**Step 4: 新增冲突标注但不过滤的模式**
- Data-Juicer现有模式：检测到问题→丢弃样本
- 新增模式：检测到冲突→标记+报告+保留样本（供人工审核）

### 集成后的Data-Juicer配置示例

```yaml
# config_conflict_detection.yaml
process:
  # 传统过滤（保留）
  - image_text_similarity_filter:
      min_score: 0.1  # 只过滤完全无关的
  
  # 新增：冲突检测算子（标记不丢弃）
  - pairing_conflict_detector:      # C1
      threshold: 0.2
  - entity_surplus_detector:        # C5
      image_model: torchxrayvision
      text_ner: chexpert_labeler
  - negation_conflict_detector:     # C8
      image_model: torchxrayvision
      text_ner: chexpert_labeler
      boundary_band: 0.05
  - internal_conflict_detector:     # C9
      normal_phrases: ["clear", "no acute", "normal"]
  
  # 新增：冲突报告导出
  - conflict_report_exporter:
      output_path: conflict_report.json
      export_html: true
```

## 六、与军工五场景的关联

9类冲突分类体系可直接映射到军工场景：

| 冲突类型 | 军工场景映射 |
|---------|------------|
| C1完全错配 | 监控视频与标注标签完全无关 |
| C3标签噪声 | 安全规则标签与视频内容不匹配 |
| C5实体多余 | AI检出违规行为但工单未记录 |
| C8否定矛盾 | 传感器时序异常但工单记"正常" |
| C9内部矛盾 | 工单正文描述故障但结论称"无异常" |

医疗验证的C5/C8/C9三类冲突（我们已验证）恰好对应军工场景4（航发维护）和场景5（现场监管）的核心需求。
