# 三大数据治理工具多模态支持与跨模态冲突检测能力对比

> 调研日期：2026-07-08
> 数据来源：Data-Juicer 2.0 论文 (arXiv:2501.14755)、CleanLab GitHub 仓库与官方文档、Great Expectations 官网与文档

---

## 一、核心结论（先读这段）

三大工具**均不支持跨模态冲突检测**，但缺失的原因各不相同：

| 工具 | 多模态数据处理 | 跨模态冲突检测 | 缺失根因 |
|------|:---:|:---:|------|
| Data-Juicer 2.0 | ✅ 强（text/image/video/audio，150+ 算子） | ❌ 无 | 架构是"打分+阈值过滤"，只做 keep/drop 二值决策，不做冲突定位与诊断 |
| CleanLab | ⚠️ 弱（各模态独立处理，无原生跨模态） | ❌ 无 | 核心是 confident learning 检测"标签噪声"，检测对象是 label↔prediction，不是 image↔text |
| Great Expectations | ❌ 无（纯表格/结构化数据） | ❌ 无 | 纯规则断言框架，无语义理解、无 ML 模型、无多模态抽象 |

**关键洞察**：Data-Juicer 2.0 是三者中最接近的——它有 `image_text_similarity_filter`（CLIP cosine）和 `phrase_grounding_recall_filter`（Owl-ViT 检测召回），但这些算子的输出是**一个标量分数 + 阈值过滤**，而非**冲突类型分类 + 冲突区域定位 + 冲突原因解释**。这就是"对齐过滤"和"冲突检测"的本质区别。

## 二、逐工具详细分析

### Data-Juicer 2.0

- **定位**: 面向基础模型（LLM/VLM）的多模态数据处理系统，提供 150+ 算子覆盖 text/image/video/audio 的清洗、过滤、合成、标注，支持 PB 级数据云端处理。

- **核心机制**:
  - **算子（Operator）体系**：10 类算子——Formatter（加载）、Mapper（编辑）、Filter（过滤）、Deduplicator（去重）、Selector（采样）、Grouper（分组）、Aggregator（聚合）、FusedOP（融合算子）、ScriptOP（自定义脚本）、HumanOP（人工标注）。
  - 其中 ~90% 的算子是 Mapper 和 Filter，体现了"逐样本操作 + 大规模并行"的设计哲学。
  - Filter 算子的统一范式：`compute_stats()` 计算统计量 → 与阈值比较 → keep/drop。所有过滤算子都遵循这个模板。
  - 运行时层支持 Ray/MaxCompute 分布式执行，自适应算子重排、GPU 资源分配、批处理。

- **多模态支持**:
  - **支持模态**：text、image、video、audio，四模态全覆盖。
  - **多模态算子清单**（约 20 个跨模态算子，以下为关键的 Image-Text 和 Video-Text 类）：

    | 算子名 | 功能 | 底层模型 | 类型 |
    |--------|------|---------|------|
    | `image_text_similarity_filter` | 计算 image-text 特征余弦相似度，保留在指定范围内的样本 | **CLIP** | Cleaning |
    | `image_text_matching_filter` | 计算 image-text 分类匹配分数，保留在指定范围内的样本 | **BLIP** | Cleaning |
    | `phrase_grounding_recall_filter` | 从文本提取名词短语，用开放词汇目标检测模型在图中定位，计算召回率 | **Owl-ViT** | Cleaning |
    | `image_pair_similarity_filter` | 图像对余弦相似度过滤 | CLIP | Cleaning |
    | `text_pair_similarity_filter` | 文本对余弦相似度过滤 | CLIP | Cleaning |
    | `video_frames_text_similarity_filter` | 视频采样帧与文本相似度过滤 | 模型 | Cleaning |
    | `image_captioning_mapper` | 图生文 | BLIP-2 等 | Synthesis |
    | `image_diffusion_mapper` | 文生图 | SDXL | Synthesis |
    | `image_captioning_from_gpt4v_mapper` | GPT-4V 生成图像描述 | GPT-4V | Synthesis |
    | `video_captioning_from_summarizer_mapper` | 多维度视频字幕生成 | 多模型 | Synthesis |
    | `mllm_mapper` | 多模态大模型视觉问答 | MLLM | Wrapper |

  - 还有大量单模态算子：image 美学过滤、NSFW 过滤、人脸模糊、宽高比过滤；video 运动评分、场景分割、ASR、语音情感识别；audio 信噪比过滤等。

- **跨模态冲突检测**: **不支持**。
  - 系统中**没有任何算子**命名为"conflict detection"或功能等价于"检测并报告 image 与 text 之间的语义冲突"。
  - **CLIP score 算子的具体功能**：`image_text_similarity_filter` 使用 CLIP 模型分别编码图像和文本，计算两个特征向量的**余弦相似度**（一个标量），然后判断该标量是否在用户指定的 `[min, max]` 范围内，超出范围则丢弃样本。
  - **为什么只做过滤不做冲突检测**？根因在架构设计：
    1. **Filter 范式限制**：所有 Filter 算子遵循 `compute_stats() → 阈值判断 → keep/drop` 的统一模板。输出是一个 boolean（保留/丢弃），不是结构化的冲突报告。
    2. **无冲突分类机制**：CLIP cosine 相似度低可能是因为"图文完全无关"、"图文部分相关但细节矛盾"、"图文相关但风格不一致"等完全不同的原因——但系统不区分，统一当作"低分→丢弃"。
    3. **无冲突定位能力**：系统不会告诉你"图片中哪个区域与文本描述矛盾"或"文本中哪个短语与图片内容不符"。`phrase_grounding_recall_filter` 虽然做了短语级的 grounding，但输出仍是召回率标量 + 阈值过滤，不报告具体哪些短语未匹配。
    4. **无冲突解释能力**：系统不生成"为什么这条数据是冲突的"的自然语言解释。
    5. **设计目标导向**：Data-Juicer 的定位是**数据处理 pipeline**（清洗→过滤→增强→训练），目标是高效地"扔掉坏数据"，而非"诊断数据问题"。论文中明确说 Filters 的作用是 "compute data stats and remove samples accordingly"。

- **最接近的功能**:
  - **`image_text_similarity_filter`（CLIP cosine 过滤）**：最接近"图文对齐检测"。计算图文 CLIP 余弦相似度，低分样本被丢弃。这是 LAION-400M 等大规模数据集的标准清洗方法。
  - **`image_text_matching_filter`（BLIP 匹配过滤）**：用 BLIP 计算 image-text 分类匹配分数，比 CLIP cosine 更语义化，但仍是标量+阈值。
  - **`phrase_grounding_recall_filter`（短语定位召回）**：最接近"细粒度冲突定位"。它将文本中的名词短语提取出来，用 Owl-ViT 在图像中检测对应实体，计算召回率。高召回=图文一致，低召回=图文不一致。但输出仍是召回率标量 + keep/drop，**不报告具体哪些短语未在图中找到**（即不输出"冲突短语列表"）。
  - **OP Insight Mining**：Data-Juicer 2.0 有一个"算子洞察挖掘"功能，跟踪每个算子执行后的数据集统计变化（如 perplexity、图像类别分布），生成报告。例如"应用 BLIP-2 image-text matching Filter 后文本长度突然下降，可能说明 caption 有噪声"。但这是**数据集级别的统计洞察**，不是**样本级别的冲突诊断**。

- **差距分析**（要支持跨模态冲突检测需要加什么）:
  1. **新增 Conflict Detector 算子类型**：突破 Filter 的 keep/drop 二值范式，输出结构化冲突报告 `{conflict_type, conflict_region, conflict_explanation, confidence}`。
  2. **细粒度冲突定位**：`phrase_grounding_recall_filter` 已经做到了短语级 grounding，需要扩展为输出"未匹配短语列表 + 对应图像区域 + 冲突类型（缺失/多余/矛盾）"。
  3. **冲突类型分类体系**：定义跨模态冲突的类型学——如"实体缺失"（文本提到但图中没有）、"属性矛盾"（文本说红色但图中是蓝色）、"关系矛盾"（文本说A在B左边但图中相反）、"数量矛盾"（文本说3个但图中有5个）、"完全无关"等。
  4. **冲突解释生成**：集成 VLM（如 GPT-4V/Qwen-VL）对检测到的冲突生成自然语言解释。
  5. **多粒度冲突评分**：不仅有整体相似度分数，还要有分维度分数（实体级、属性级、关系级、数量级对齐分数）。

### CleanLab

- **定位**: 数据中心 AI（data-centric AI）开源库，通过 confident learning 算法自动检测 ML 数据集中的标签错误、异常值、重复数据等问题，并用清洗后的数据训练更鲁棒的模型。

- **核心机制**:
  - **Confident Learning（置信学习）**：核心算法。原理是利用模型的**预测概率分布**（pred_probs）与**给定标签**（given labels）之间的统计差异，估计标签噪声的联合分布（confident joint matrix），从而识别可能被错误标注的样本。
    - 关键假设：需要一个已训练的 ML 模型提供 out-of-sample 预测概率。
    - 有理论保证：即使模型不完美，也能精确估计标签噪声（发表于 JAIR 2021）。
  - **Datalab 统一接口**：`Datalab(data, label).find_issues(features, pred_probs).report()` 一行代码检测多种问题。
  - **模型无关**：与 PyTorch/TensorFlow/OpenAI/XGBoost 等任何模型兼容，只要能提供 pred_probs 或 features。

- **多模态支持**:
  - **支持的数据类型**：text、image、audio、tabular——但**处理方式是模态无关的**。
  - **关键设计**：CleanLab 不直接处理原始多模态数据，而是要求用户提供**特征向量（features/embeddings）**或**预测概率（pred_probs）**。无论数据是文本、图像还是音频，用户先用某个模型将其编码为向量 embedding，然后 CleanLab 在 embedding 空间中做 KNN 分析、异常检测等。
  - **各模态独立处理**：text tutorial 用文本 embedding、image tutorial 用图像 embedding、audio tutorial 用音频 embedding——**每个模态单独处理，没有跨模态联合分析**。
  - **Image 专属功能**（通过 CleanVision 集成）：检测暗/亮/模糊/异常尺寸/异常宽高比/灰度/低信息量等图像质量问题，以及图像属性与标签之间的**伪相关**（spurious correlations）。

- **跨模态冲突检测**: **不支持**。
  - CleanLab 检测的是**"标签噪声"（label noise）**，不是**"图文语义冲突"（image-text semantic conflict）**。
  - **检测对象不匹配**：Confident Learning 的检测对象是 `label ↔ prediction` 的不一致（即"这张图片的类别标签标错了"），而非 `image ↔ text` 的语义不一致（即"这张图片和这段文字描述的内容不匹配"）。
  - **无跨模态联合分析**：CleanLab 的所有 issue 类型都基于单一 feature 空间或单一 pred_probs。没有机制同时接收图像 embedding 和文本 embedding，然后分析它们之间的对齐关系。
  - **Spurious Correlations 是数据集级的**：虽然能检测"图像暗度与标签的伪相关"，但这是统计层面的数据集级问题（"这个类别的图片普遍更暗"），不是样本级的图文冲突（"这张图的描述与内容矛盾"）。
  - **Issue 类型清单中无跨模态项**：官方文档列出的 issue 类型包括 label、outlier、near_duplicate、non_iid、class_imbalance、underperforming_group、null、data_valuation——没有一个是跨模态的。

- **最接近的功能**:
  - **Label Issue（标签问题检测）**：最接近但本质不同。检测"给定标签是否可能错误"，基于模型预测概率与标签的偏离。如果是 image-text 数据，用户可以把 text 当作"标签"来检测——但这需要 text 是离散类别标签，而非自由文本描述。
  - **Outlier Detection（异常检测）**：基于 KNN 在 embedding 空间中找离群点。如果用 CLIP image embedding，可以找到"与其他图片风格不同的图片"，但不涉及文本对齐。
  - **Spurious Correlations（伪相关检测）**：检测图像属性（如暗度）与标签之间的统计相关性。这是最接近"跨模态关系分析"的功能，但粒度粗（数据集级统计），且只针对图像低级属性与离散标签的关系。

- **差距分析**（要支持跨模态冲突检测需要加什么）:
  1. **新增跨模态 Issue Manager**：Datalab 支持自定义 issue manager（`Creating Your Own Issues Manager`），理论上可以扩展。需要实现一个 `CrossModalConflictIssueManager`，同时接收 image embedding 和 text embedding。
  2. **跨模态对齐评分**：集成 CLIP/BLIP 等模型计算图文对齐分数，作为 issue 检测的输入特征。
  3. **冲突类型分类**：将单一的"label 对不对"判断扩展为多类型的"image-text 冲突类型"分类（实体矛盾、属性矛盾、关系矛盾等）。
  4. **从"需要标签"到"无需标签"**：Confident Learning 依赖标签列。但 image-text 冲突检测通常没有"正确标签"——需要无监督/弱监督的冲突检测方法。
  5. **细粒度定位**：CleanLab 目前只输出样本级的 boolean flag + score，需要扩展为输出冲突的具体位置和原因。

### Great Expectations (GX Core)

- **定位**: 世界上最流行的开源数据质量框架，通过定义"期望"（Expectations，即对数据的断言规则）来验证结构化数据是否符合预期，支持自动化数据质量监控。

- **核心机制**:
  - **Expectation（期望）**：核心抽象。用户定义对数据的断言规则，如"passenger_count 列的值必须在 1 到 6 之间"（`ExpectColumnValuesToBeBetween`），然后系统验证数据是否符合。
  - **工作流**：连接数据源 → 创建 Batch → 定义 Expectation Suite → 创建 Validation Definition → 运行 Checkpoint → 查看 Validation Results。
  - **规则驱动**：所有验证都是基于预定义的规则/断言，不涉及 ML 模型或语义理解。
  - **Data Docs**：自动将验证结果渲染为可视化 HTML 报告，便于与业务方沟通。
  - **集成**：支持 Pandas DataFrame、PostgreSQL、Snowflake、Spark、S3、Azure Blob、Databricks、Airflow 等。

- **多模态支持**: **不支持**。
  - **纯表格/结构化数据工具**。所有 Expectation 都是列（column）级别的断言，如：
    - `ExpectColumnValuesToBeBetween`（值在范围内）
    - `ExpectColumnValuesToBeUnique`（值唯一）
    - `ExpectColumnValuesToNotBeNull`（值非空）
    - `ExpectColumnValuesToMatchRegex`（值匹配正则）
    - `ExpectTableRowCountToBeBetween`（行数在范围内）
  - **不支持图像、音频、视频、文本（NLP）**等非结构化数据。
  - 没有 embedding、没有 ML 模型集成、没有语义理解能力。
  - 示例数据是 NYC出租车行程记录（CSV/Postgres 表），完全是结构化数值/类别数据。

- **跨模态冲突检测**: **不支持**。
  - 既没有多模态支持，也没有语义理解能力，完全无法处理"图文是否匹配"这类问题。
  - Expectation 框架本质上是"规则引擎"，只能检查预定义的规则（如"值在范围内"、"格式正确"），无法判断语义层面的冲突。

- **最接近的功能**:
  - **`ExpectColumnValuesToMatchRegex` / `ExpectColumnValuesToMatchStrftimeFormat`**：可以验证文本列的格式是否符合正则/时间格式——但这只是语法层面的格式检查，不是语义层面的内容匹配。
  - **`ExpectColumnPairValuesAToBeGreaterThanB`**：可以检查两列之间的关系（如 A 列值 > B 列值）——这是最接近"跨字段关系检查"的功能，但只能做数值比较，无法做语义匹配。
  - 如果非要用 GX 检查"图文对齐"，只能先外部计算 CLIP score 存为一列，然后用 `ExpectColumnValuesToBeBetween` 检查 score 是否在阈值内——但这只是把外部计算结果做阈值断言，GX 本身不提供任何多模态能力。

- **差距分析**（要支持跨模态冲突检测需要加什么）:
  1. **多模态数据源支持**：目前只支持表格数据源（DataFrame/SQL），需要增加图像/音频/视频/文本文件的数据源抽象。
  2. **语义 Expectation 类型**：需要全新的 Expectation 类，如 `ExpectImageTextAlignmentScoreToBeAbove(min_score, model="clip")`，内部调用 ML 模型计算对齐分数。
  3. **ML 模型集成层**：GX 目前完全无 ML 依赖，需要引入模型推理层（CLIP/BLIP/VLM）来计算语义特征。
  4. **非结构化数据处理管线**：需要从"列值断言"扩展到"非结构化内容断言"，这是架构层面的根本性改变。
  5. 本质上，GX 的设计哲学（规则断言）与跨模态冲突检测（语义理解）是**不同范式**，差距是三者中最大的。

## 三、横向对比表格

### 维度一：多模态数据处理能力

| 能力维度 | Data-Juicer 2.0 | CleanLab | Great Expectations |
|---------|:---:|:---:|:---:|
| 支持模态数 | 4（text/image/video/audio） | 4（text/image/audio/tabular，但各模态独立） | 1（tabular/结构化） |
| 原生多模态算子 | ✅ ~20 个跨模态算子 | ❌ 无跨模态算子 | ❌ 无 |
| 图像处理 | ✅ 丰富（美学/NSFW/人脸/宽高比/水印/去重） | ⚠️ 仅图像质量（暗/亮/模糊/尺寸，via CleanVision） | ❌ 无 |
| 视频处理 | ✅ 丰富（运动评分/场景分割/ASR/人脸追踪/字幕生成） | ❌ 无 | ❌ 无 |
| 音频处理 | ✅ 基础（时长/信噪比/FFmpeg） | ⚠️ 通过 embedding 间接支持 | ❌ 无 |
| 文本处理 | ✅ 丰富（50+ 文本算子，含后训练） | ⚠️ 通过 embedding 间接支持 | ⚠️ 仅格式/正则检查 |
| 跨模态合成 | ✅ any-to-any 生成（GPT-4V/SDXL/BLIP-2） | ❌ 无 | ❌ 无 |
| 底层模型集成 | ✅ CLIP/BLIP/BLIP-2/SDXL/GPT-4V/Owl-ViT/Qwen | ⚠️ 用户提供（模型无关） | ❌ 无 |
| 大规模处理 | ✅ PB 级，10k+ CPU 核心 | ⚠️ 中等（依赖用户基础设施） | ⚠️ 依赖数据源（SQL/Spark） |

### 维度二：跨模态冲突检测能力

| 能力维度 | Data-Juicer 2.0 | CleanLab | Great Expectations |
|---------|:---:|:---:|:---:|
| 是否支持跨模态冲突检测 | ❌ 不支持 | ❌ 不支持 | ❌ 不支持 |
| 图文对齐评分 | ✅ CLIP cosine + BLIP matching score | ❌ 无 | ❌ 无 |
| 细粒度对齐检测 | ⚠️ phrase_grounding_recall（短语级，但仅输出召回率标量） | ❌ 无 | ❌ 无 |
| 冲突类型分类 | ❌ 无（统一按分数阈值过滤） | ❌ 无（只有 label 对/错） | ❌ 无 |
| 冲突区域定位 | ❌ 无（不定位图像/文本中的冲突位置） | ❌ 无 | ❌ 无 |
| 冲突原因解释 | ❌ 无（不生成解释） | ❌ 无（不生成解释） | ❌ 无 |
| 样本级冲突报告 | ❌ 无（只输出 keep/drop） | ⚠️ 输出 is_issue + score，但无冲突维度 | ❌ 无 |
| 数据集级洞察 | ✅ OP Insight Mining（算子级统计变化） | ⚠️ issue_summary（数据集级 issue 汇总） | ✅ Validation Results 报告 |
| 检测范式 | 打分 + 阈值过滤（Filter） | 统计估计（Confident Learning） | 规则断言（Expectation） |
| 是否需要标签 | ❌ 不需要 | ✅ 需要标签列 | ❌ 不需要（但需要预定义规则） |
| 是否需要 ML 模型 | ✅ 内置模型 | ✅ 用户提供模型 | ❌ 不使用模型 |
| 可扩展性 | ⚠️ 可自定义算子，但 Filter 范式限制 | ✅ 支持自定义 Issue Manager | ✅ 支持自定义 Expectation |

## 四、核心差距总结：为什么三大工具都不支持跨模态冲突检测？

### 1. 范式鸿沟：现有工具的检测范式与冲突检测不匹配

| 工具 | 现有范式 | 冲突检测需要的范式 |
|------|---------|---------------|
| Data-Juicer | 标量打分 + 阈值过滤（keep/drop） | 结构化诊断（冲突类型 + 位置 + 原因） |
| CleanLab | 统计估计（label↔prediction 噪声） | 语义对齐（image↔text 一致性） |
| Great Expectations | 规则断言（值在范围内/格式正确） | 语义理解（内容是否匹配） |

### 2. 粒度鸿沟：现有工具的输出粒度太粗

- Data-Juicer 的 Filter 输出：`boolean (keep/drop)` + `score (scalar)`
- CleanLab 的 issue 输出：`is_issue (boolean)` + `score (scalar)` + `predicted_label`
- 冲突检测需要的输出：`{conflict_type, conflict_location_in_image, conflict_location_in_text, conflict_explanation, confidence}`

### 3. 语义鸿沟：现有工具缺乏细粒度语义理解

- CLIP cosine 相似度只能告诉你"图文整体相关度是 0.3"，但不能告诉你"文本说'红色汽车'但图中是蓝色汽车"。
- `phrase_grounding_recall_filter` 已经做到了短语级 grounding（最接近的），但丢弃了定位细节，只保留召回率标量。
- 真正的冲突检测需要：实体级对齐 → 属性级对齐 → 关系级对齐 → 数量级对齐，每个维度独立评分和诊断。

### 4. 可行路径：谁最容易被扩展？

**Data-Juicer 2.0 是最容易扩展的**，原因：
1. 已有最丰富的多模态算子生态和模型集成（CLIP/BLIP/Owl-ViT）。
2. `phrase_grounding_recall_filter` 已经具备了短语级 grounding 的基础能力，只需扩展输出格式。
3. 算子系统是可扩展的（ScriptOP/FusedOP 支持自定义），可以新增 Conflict Detector 算子类型。
4. 已有 OP Insight Mining 框架，可以扩展为冲突诊断报告。

**CleanLab 次之**，原因：
1. Datalab 支持自定义 Issue Manager，架构上是可扩展的。
2. 但需要从"需要标签"范式转变为"无需标签的跨模态对齐"范式。
3. 需要集成多模态模型（目前完全依赖用户提供的 features/pred_probs）。

**Great Expectations 最难扩展**，原因：
1. 从"规则断言"到"语义理解"是范式级的根本改变。
2. 需要从零构建多模态数据源抽象和 ML 模型集成层。
3. 与工具的核心设计哲学不兼容。
